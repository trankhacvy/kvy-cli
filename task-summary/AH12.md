# AH12 — password-signin-pending-pair

## What

`docs/auth-ux-hardening-plan.md` item 12: `completePasswordSignIn` and
`completePasswordSignUp` (`packages/web/src/lib/complete-password-sign-in.ts`) now resolve
`nextUrl` from `consumePendingPair()` instead of hardcoding `"/"`, mirroring
`completeOAuthSignIn`. The addendum's third sibling, `rotateKeyEpoch`'s own hardcoded
`nextUrl: "/"`, gets the identical one-line fix. `password/page.tsx`'s post-login
`PostLoginStep` variants (`needs-unlock`, `unlocking`) now carry the resolved `nextUrl`
through `afterLogin`/`handleUnlockSubmit` so the final `router.replace(...)` actually uses
it instead of unconditionally replacing to `"/"`.

Test coverage added in `complete-password-sign-in.test.ts`: a
"resolves nextUrl from a pending /pair stash, same as completeOAuthSignIn" case for each of
`completePasswordSignUp`, `completePasswordSignIn`, `rotateKeyEpoch`, and (pre-existing sibling)
`rotateKeyEpochOAuth`, plus the `window.sessionStorage` stand-in (`createMemoryStorage`) needed
because this package's vitest config runs under `environment: "node"`.

## Why

`/pair` → `/signin/` → `/password/` is item 1's fallback for a genuinely signed-out browser
(no refresh token recoverable). Before this fix, finishing that detour via email+password
always dumped the user on Home, silently abandoning the CLI pairing request they came from —
the OAuth sibling already handled this correctly, so this was strictly a password-path gap.
`rotateKeyEpoch` (the "forgot PIN → rotate" flow) had the identical gap.

## Live verification (real stack, real browser, no mocks)

Followed CLAUDE.md's runbook, on non-default ports to avoid the other worktree's stack already
running on :3000/:3005 (verified each PID's cwd before touching anything):

- Postgres: already running locally (shared dev DB, disposable).
- `@falcon/server` dev on **:3006** (`CORS_ALLOWED_ORIGINS=http://localhost:3001
  FALCON_DEV_AUTH=1`, migrated on boot).
- `@falcon/web` dev on **:3001** (`NEXT_PUBLIC_API_URL=http://localhost:3006`).
- Browser: `playwright-cli` (Chrome MCP extension was not connected in this environment —
  reported below — so I used this real, non-mocked browser automation tool instead of faking
  it).

Drove three real flows against the live server (a real `passwordRegister`/`passwordLogin`
network call to `/v1/auth/password/*`, real crypto-worker `init`/`unlock` in the actual page,
real PIN-wrapped key material in IndexedDB):

1. **Sign-up resumes pending pair** — stashed `falcon:pendingPair` in `sessionStorage`
   (simulating item 1's stash step, which is out of this unit's scope and already covered by its
   own tests), went to `/password/`, signed up a fresh throwaway account + PIN. Landed on
   `http://localhost:3001/pair/#<ephPub>` rendering the real "Device pairing… Approve/Cancel"
   screen — **not** Home.
2. **Sign-in + PIN-unlock resumes pending pair** — reloaded (locks the crypto worker), re-stashed
   the pending pair, switched to "Sign in", submitted the same account's email+password → hit the
   real "Unlock this device" PIN prompt (confirming `nextUrl` survived being carried in
   `PostLoginStep`'s `needs-unlock`/`unlocking` variants) → entered the PIN → landed on
   `/pair/#<ephPub>` at the Approve screen again. This is the specific caller-threading path the
   plan's "Caller check" callout warned to verify.
3. **Control — no pending pair still lands on Home** — fresh navigation (no `sessionStorage`
   stash), signed in with the same account, unlocked with the PIN → landed on `http://localhost:3001/`
   (Home), confirming the fix is additive and doesn't change the default no-pairing path.
4. **`rotateKeyEpoch`'s error branches, live** — triggered "Forgot your PIN?" → step-up password
   → new PIN → real `POST /v1/auth/keys/bind` call got a genuine `409` ("other devices online" —
   the earlier sign-up's session was still active, a real system property, not a bug) and
   separately a scenario elsewhere in the same file's test suite covers the `401` path. This
   confirms the untouched error branches still work against the real server.

**Not live-verified**: `rotateKeyEpoch`'s own one-line `nextUrl` fix (the "ok" success branch) —
forcing that live requires first revoking the account's other active session (a "log out other
devices" step this environment's account only just created via the sign-up above), which I did
not chase down given time budget. That branch is verified instead by: (a) the passing unit test
`rotateKeyEpoch … resolves nextUrl from a pending /pair stash, same as completeOAuthSignIn`
(mocks `keys/bind` to succeed, asserts `{ kind: "ok", nextUrl: "/pair/#..." }`), and (b) the fix
is textually identical in shape to the two branches (sign-up, sign-in) that *were* fully
live-verified end-to-end above.

**Chrome MCP**: reported as its own item per the runbook's instructions — the Chrome extension
was not connected in this subagent's environment (`tabs_context_mcp` returned "Browser extension
is not connected"). I used `playwright-cli` (a real, non-mocked browser automation tool already
available) as the live-verification vehicle instead of skipping verification.
