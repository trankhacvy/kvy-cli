# P1-1.3-cli-auth-login — `falcon auth login/logout/status`

**Section:** Phase 1 — §1.3 CLI skeleton + local mode (falcon-plan.md §2.2 "`falcon auth login`
— pairing client"; plan.md §5/§6.1; falcon-system-design.md §5.2 "CLI pairing")

## What was done

Implemented the full CLI account-auth command surface on top of the already-merged
crypto primitives (`@falcon/crypto`) and server routes (`POST /v1/auth/pair*`,
`packages/server/src/app/api/pair.ts`). `packages/cli/src/index.ts`'s `case "auth"`
was previously a `not implemented yet` stub; it now dispatches to real logic in a new
`packages/cli/src/auth/` module:

- **`config.ts`** — resolves `FALCON_BACKEND_URL`/`FALCON_FRONTEND_URL` (documented
  env vars already listed in `falcon --help`), defaulting to the production
  `api.falcon.dev`/`app.falcon.dev` hosts named throughout falcon-plan.md.
- **`credentials.ts`** — `~/.falcon/access.key` read/write/clear. Shape is exactly
  falcon-plan.md §2.1's `{token, masterSecretOrContentBundle}` base64 JSON, chmod
  `0600` (explicitly re-chmod'd on every write, not just at creation, so a stale
  looser-permissioned file never survives a re-login). Zod-validated on read;
  malformed/missing file is just "not logged in", never a thrown error.
- **`pair.ts`** — the actual pairing client, a port of Happy's `doAuth`
  (`happy-cli/src/ui/auth.ts`) onto Falcon's real merged routes rather than Happy's
  `/v1/auth/request`: generates an ephemeral X25519 keypair (`tweetnacl.box.keyPair()`,
  never persisted), `POST /v1/auth/pair {ephPub}`, polls `GET /v1/auth/pair/status`
  every 2s (falcon-plan.md §2.2's specified interval) until `authorized`/`expired`,
  then one more `POST /v1/auth/pair` to fetch the token + sealed box (`/status`
  deliberately never returns secret material — see the server route's own comment),
  and opens it with `libsodiumDecryptWithSecretKey` (inverse of the approver's
  `libsodiumEncryptForPublicKey`) to recover the raw 32-byte masterSecret. Every
  network call is wrapped so this never throws; a 15-minute deadline (mirroring the
  server's own `PAIR_REQUEST_TTL_MS`) bounds the poll loop even if the network never
  surfaces an explicit `expired`. Cancellable via an `AbortSignal`.
- **`browser.ts`** / **`qrcode.ts`** — best-effort automatic browser launch (`open`,
  headless/CI/TTY-detection ported from Happy's `utils/browser.ts`) and a terminal QR
  code (`qrcode-terminal`, per falcon-plan.md §2.2). `falcon auth login` always prints
  the URL and QR code (works headless) and *additionally* tries to open a browser —
  that combination is what the task description's "opens the OAuth browser flow and
  falls back to the QR/URL device-pairing flow" maps onto: there is one pairing
  mechanism (falcon-plan.md §2.2 only documents pairing, no separate CLI-side OAuth
  route exists among the merged Phase-0.4 routes), and the printed URL *is* the "OAuth
  browser flow" — it points at the web app, which is what actually talks to
  Google/GitHub and already holds the account's keys once signed in there.
- **`jwt.ts`** — unverified JWT payload decode (`sub`/`exp` only), used solely for
  `auth status` display. Clearly never used for authorization — the CLI has no way to
  verify the server's HS256 signature and rightly doesn't try.
- **`login.ts` / `logout.ts` / `status.ts` / `index.ts`** — the three command handlers
  (a light, non-interactive adaptation of Happy's `commands/auth.ts`; daemon-lifecycle
  and confirmation-prompt steps from Happy's version are out of scope here) plus the
  `runAuthCommand(action, logger)` dispatcher wired into `index.ts`.

### `index.ts` / `index.test.ts` changes

`main()`/`run()` had to become `async` — `auth login` genuinely needs to await network
I/O, unlike every other still-stubbed command. Updated the bottom `process.exit(...)`
guard and `index.test.ts` (`await main([...])` instead of the previous synchronous
`main([...])`) to match. The "never writes CLI-level output through the logger's
channel" test now also asserts `auth login` resolves (not throws) with exit code 1
against an intentionally-unreachable `FALCON_BACKEND_URL` — safe in CI/sandboxes since
`process.stdout.isTTY` is false there, so `openBrowser()` never actually tries to
launch anything.

### New dependencies (`packages/cli/package.json`)

`@falcon/crypto` (workspace), `tweetnacl`, `open`, `qrcode-terminal` (+
`@types/qrcode-terminal`) — versions matched to what `happy-cli` already pins.
Used native `fetch` (Node 20+, this repo's `engines.node` floor) instead of adding
`axios`, since no other package needed axios's extra surface for two JSON endpoints.

## Assumptions / notes for whoever lands this alongside other pairing work

- **Sealed-box plaintext = raw 32-byte masterSecret**, no type-tag prefix. Confirmed
  by reading the (unmerged, not authoritative, but informative) `P1-1.6-auth-pages`
  worktree's `sealForPeer`/pairing-approve implementation, which seals exactly the
  masterSecret and documents as much in its own tests. If a future landed web pairing
  page seals something else (e.g. a tagged/versioned bundle), this CLI's
  `libsodiumDecryptWithSecretKey` call in `pair.ts` will need a matching update.
- **URL fragment encoding mismatch with that same unmerged worktree**: this CLI
  follows falcon-plan.md §2.2 literally and encodes the ephPub in the printed pairing
  URL fragment as **base64url** (`.../pair#<base64url ephPub>`). The unmerged
  `P1-1.6-auth-pages` pair page currently decodes `window.location.hash` as **plain
  base64** instead. One side will need to change when both pieces land together —
  flagging it here rather than silently picking a side, since I have no way to
  coordinate with an unmerged, out-of-scope branch. The server's own `/v1/auth/pair*`
  JSON bodies (what this CLI actually talks to) are unambiguous and unaffected: plain
  base64 there, confirmed directly from `packages/server/src/app/api/pair.ts` and its
  tests.
- `falcon auth login` unconditionally starts a fresh pairing attempt (no "already
  logged in, use --force" guard like Happy's). Re-running it while already logged in
  simply re-authenticates and overwrites `~/.falcon/access.key` — a deliberate
  simplification since Falcon's CLI has no daemon/machine-id coupling yet for this to
  interact with (that's separate 1.5/1.6 work).
- `auth status` does not call the server — it only reports what's stored locally,
  decoding the JWT's `sub`/`exp` claims for display without verifying the signature
  (clearly labeled "(unverified)" in the output). A network round trip to confirm the
  token is still accepted server-side was judged out of scope for this bullet.

this branch was cut, all touching `packages/cli/src/index.ts`). No task logic was
reimplemented; this pass only integrates the existing auth work onto the current tip:
