# P1-1.5-daemon-cli-commands — Wire `falcon daemon start/start-sync/stop/status`

Implements the actual behavior behind `falcon daemon start|start-sync|stop|status`
(plan.md §7.2, design §8), replacing the `"falcon daemon ${action}: not implemented
yet"` stub in `packages/cli/src/index.ts`. Wires together the three pieces that
were already merged on `main`: the singleton lock (`daemon/lock.ts`), the
`daemon.state.json` read/write helpers (`daemon/state.ts`), and the Fastify
control server (`daemon/controlServer.ts`).

## What was built

- **`packages/cli/src/args.ts`** — added `start-sync` as a fourth `daemon`
  action alongside the existing `start`/`stop`/`status` (which already had a
  `--no-wait` flag on `start`, presumably scaffolded ahead of this task).
  `start-sync` is the daemon's own long-running process body — normally
  spawned detached by `start`, but also directly invocable for foreground
  debugging. This is exactly the argv `daemon/markers.ts` (already merged,
  from the `kill` task) documents and classifies as the `"daemon"` process
  kind for `falcon kill`, so no changes were needed there.
- **`packages/cli/src/daemon/state.ts`** — added `clearDaemonState(homeDir)`
  (unlinks `daemon.state.json`, ENOENT-tolerant — "safe to call twice", same
  convention as `lock.ts`'s `release()`). Needed by both `stop` and
  `start-sync`'s own cleanup path.
- **`packages/cli/src/daemon/commands.ts`** (new) — the actual wiring:
  - `runDaemonStart(deps, {noWait})`: reads `daemon.state.json`; if it names a
    live pid, reports "already running" without spawning anything (idempotent).
    Otherwise spawns `falcon daemon start-sync` detached (re-invokes
    `process.argv[1]` — works under `tsx`, `node dist/index.mjs`, and the
    `bin/falcon.mjs` shim alike) and, unless `--no-wait`, polls
    `daemon.state.json` (bounded by `readyTimeoutMs`, default 5000ms) until the
    spawned daemon reports ready, printing its pid/port. Reports a timeout
    (exit 1) if it never becomes ready.
  - `runDaemonStartSync(deps)`: the daemon's actual foreground body. Starts
    the control server first (to learn its OS-assigned port), then calls
    `acquireDaemonLock` with a `{pid, port, version, startedAt}` payload; on
    `"held-by-running-process"` or `"contended"`, stops the control server and
    exits 1 without touching `daemon.state.json`. On success, writes
    `daemon.state.json`, registers shutdown signal handlers, and blocks until
    shutdown is requested — either an OS signal or the control server's own
    `/stop` endpoint (both resolve the same internal promise) — then stops the
    control server, releases the lock, and clears the state file.
  - `runDaemonStop(deps)`: reads state; if absent, reports "not running". If
    the pid is already dead, clears the stale state file and reports that. If
    alive, first tries a graceful `POST /stop` to the control server and waits
    (`stopWaitTimeoutMs`) for the pid to exit; if that doesn't work (control
    server unreachable, or didn't die in time), falls back to
    SIGTERM-then-wait-then-SIGKILL via the pid `daemon.state.json` advertises.
    Always clears `daemon.state.json` afterward. Deliberately does **not**
    also unlink the lock file — `acquireDaemonLock`'s existing stale-PID
    reclaim (already merged in `lock.ts`) handles that automatically on the
    next `start`, once the pid is confirmed dead, so `stop` doesn't need to
    duplicate that logic.
  - `runDaemonStatus(deps)`: reads state; reports "not running" if absent or
    if the pid is dead (clearing the stale file in the latter case). If the
    pid is alive, additionally probes the control server (`POST /list`) before
    reporting "running" — a bare pid-alive check isn't enough on its own since
    PIDs get reused by the OS across reboots (same caveat Happy's
    `checkIfDaemonRunningAndCleanupStaleState` documents).
  - Everything is behind an injectable `DaemonCommandDeps` (homeDir, version,
    logger, `now`/`sleep`, `spawnStartSync`, `killPid`, `isProcessAlive`,
    `fetchImpl`, `registerShutdownSignals`, `readyTimeoutMs`,
    `stopWaitTimeoutMs`), with `createDaemonCommandDeps()` wiring the real
    OS-backed implementation — same DI shape as `kill.ts`'s `KillDeps`, so
    tests never spawn real child processes, touch real signals, or wait out
    real multi-second timeouts.
  - Session tracking/spawning (`getSessions`/`stopSession`/`spawnSession` on
    the control server) is out of scope for this task — that's the daemon's
    session-registry/spawner work (§7.3/§8, separate plan bullets) — so
    `start-sync` wires the control server with honest stand-ins: no sessions
    tracked yet, `spawnSession` always returns a `type: "error"` result
    explaining it isn't implemented yet.
- **`packages/cli/src/index.ts`** — replaced the `daemon` stub with a
  `runDaemon()` dispatcher (same async shape as the existing `runKill()`) that
  calls the above and writes the resulting message to stdout. Passes this
  process's own `readVersion()` into `createDaemonCommandDeps({version})`
  explicitly — see "bug found & fixed" below. Updated the help text line for
  `start-sync`.

## Bug found and fixed during manual verification

`daemon/commands.ts`'s own default `version` (via a `readCliVersion()` helper
inside that file, mirroring `index.ts`'s `readVersion()`) located `package.json`
relative to its own source file's `import.meta.url` — correct in dev (`tsx`,
where `commands.ts` is a real file two directories under `packages/cli`), but
wrong once `pkgroll` bundles every module into a single `dist/index.mjs`: at
that point `commands.ts`'s code shares `index.ts`'s `import.meta.url` (one
level under `packages/cli`, not two), so the two-`../..`-relative lookup
resolved outside the package and silently fell through to fallback `"0.0.0"`.
Caught this via an end-to-end smoke test (`node dist/index.mjs daemon status`
after a real build reported `version 0.0.0` instead of the real `0.1.0`).
Fixed by having `index.ts` pass its own already-bundle-path-correct
`readVersion()` result into `createDaemonCommandDeps({version})` explicitly,
rather than relying on `commands.ts`'s independent (and, for the bundled case,
wrong) computation. Re-verified after the fix: real build reports the correct
version.

## Assumptions / design notes

- **`start`/`start-sync` split, not a single blocking command.** The task
  brief and `args.ts` (already merged, pinned by existing tests) model this as
  one `start` action with a `noWait` flag plus a separate `start-sync` action,
  rather than two independently-flagged verbs — this matches Happy's actual
  architecture (`daemon start` spawns detached `daemon start-sync`, which is
  the real long-running process body) and is exactly what `markers.ts`
  already documents/expects for `falcon kill`'s classification.
- **`stop` never touches the lock file directly** — relies entirely on
  `acquireDaemonLock`'s existing stale-PID reclaim to clean up a lock left
  behind by a hard-killed daemon, on the next `start`. Avoids duplicating
  ownership-verification logic that already exists and is already tested in
  `lock.ts`.
- **No WS machine client, no heartbeat, no self-update, no session
  spawner/registry.** Per the task brief, those are separate, still-unclaimed
  plan bullets (`ensureDaemonRunning()`, the machine-scoped WS client,
  `notifyDaemonSessionStarted`, actual tmux/detached session spawning). This
  task only wires the lock + control server + state file into the four CLI
  verbs; the control server's `getSessions`/`stopSession`/`spawnSession` deps
  are honest stand-ins (empty registry, spawn always errors) until that work
  lands.
- **`readyTimeoutMs` (default 5000ms) / `stopWaitTimeoutMs` (default 3000ms)**
  are injectable dependencies specifically so tests don't have to wait out
  multi-second real timeouts — production defaults are otherwise unexercised
  by any test.
