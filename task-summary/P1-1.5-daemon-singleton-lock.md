# P1-1.5-daemon-singleton-lock — Daemon singleton lock file with stale-PID detection

**Section:** 1.5 Daemon v1 (plan.md §7.1, line 690–691) · design doc §7.2, §8

## What was implemented

`packages/cli/src/daemon/`:

- **`lock.ts`** — `acquireDaemonLock(homeDir, payload)` implements the singleton
  guard as an atomic hard-link lock file (`~/.falcon/daemon.lock`), porting
  Happy's daemon singleton pattern **(V)**. No Happy source tree was present
  in this repo/checkout to copy from directly, so this is a faithful
  reimplementation of the documented pattern (design §8: "atomic lock file
  (hard-link with pid payload; stale detection via `kill(pid, 0)`"), using
  the classic mkstemp+link technique:
  1. Write the PID/port/version/startedAt payload to a private per-attempt
     temp file (`.daemon.lock.<pid>.<random>.tmp`).
  2. `link(tmpPath, daemon.lock)` — this filesystem call is atomic: if the
     destination name already exists, exactly one of any concurrent callers
     succeeds and the rest get `EEXIST`. This is what makes the "one winner"
     guarantee real even for genuinely concurrent OS processes, not just
     something enforced by an in-process mutex.
  3. On `EEXIST`, read the existing lock's payload and probe its `pid` with
     `process.kill(pid, 0)` (signal 0 = existence check only).
     - Alive (or `EPERM`, i.e. exists but owned by another user — never
       steal a lock we can't prove is dead) → return
       `{ ok: false, reason: "held-by-running-process", existing }`.
     - Dead (`ESRCH`) or the lock file is corrupt/unparseable → stale;
       unlink it and retry the link (bounded to 5 attempts to avoid
       spinning forever under adversarial contention).
  4. `release()` on the returned handle unlinks the lock file; idempotent.

  Also exports `isProcessAlive(pid)` and `lockFilePath(homeDir)` as small
  reusable primitives.

- **`state.ts`** — `daemon.state.json` read/write helpers, singleton portion
  only per the task's scope note (plan.md line 691 field list: `pid`, `port`,
  `version`, `startedAt`). `readDaemonState` returns `null` (not a throw) for
  a missing file, an unparseable file, or a well-formed-JSON-but-wrong-shape
  file — callers treat "no state" and "corrupt state" identically, since
  either way there's nothing to trust. `writeDaemonState` creates `homeDir`
  if needed and writes pretty-printed JSON.

  `DaemonLockPayload` in `lock.ts` is a type alias for `DaemonState` — the
  lock file and the state file carry the same shape, per plan.md ("atomic
  hard-link lock file ... storing PID + metadata").

- Explicitly **out of scope** (separate later plan.md bullets, left
  untouched): `falcon daemon start/stop/status` CLI commands, the control
  server, `ensureDaemonRunning()`, and any wiring of these modules into
  `index.ts`'s command dispatcher (which still prints "not implemented yet"
  for `daemon` — unchanged).

## Tests

`packages/cli/src/daemon/lock.test.ts` (10 tests) and `state.test.ts` (5 tests):

- **acquire**: succeeds when no lock exists; a second acquire while the
  first holder is alive is refused with `held-by-running-process` and the
  existing payload.
- **stale-detect**: spawns a real child process, waits for it to exit
  (Node reaps it via the `exit` event, so the pid is genuinely dead
  afterward), writes a lock file naming that dead pid, and confirms
  `acquireDaemonLock` reclaims it. A separate test covers reclaiming a
  corrupt/unparseable lock file the same way.
- **release**: releasing frees the lock for a subsequent acquire; calling
  `release()` twice doesn't throw.
- **concurrent-acquire-race**: fires 12 concurrent `acquireDaemonLock` calls
  at the same `homeDir` via `Promise.all` (all naming `process.pid`, which
  is alive throughout — the current test process). Exactly one resolves
  `ok: true`; the other 11 resolve `held-by-running-process`. This exercises
  the real async race across concurrent Node fs operations, not just
  sequential calls.
- `isProcessAlive`: true for the current process, false for pid 0 /
  negative / non-integer pids, false for an exited child's pid.
- `state.ts`: round-trip write/read, missing file → `null`, corrupt JSON →
  `null`, wrong-shape JSON → `null`, creates `homeDir` if missing.

## Assumptions / notes

- No Happy source directory was present in this checkout (`biome.json`
  excludes `!happy`/`!superset` paths that don't currently exist locally),
  so the hard-link singleton pattern was reconstructed from the design
  doc's description (§8) and the well-known mkstemp+link lock-file
  technique it describes, rather than copied line-for-line from a Happy
  source file. If a real Happy `daemon.ts`/lock module surfaces later, it's
  worth a follow-up diff against this to confirm no behavioral drift.
- `daemon.state.json`'s field set here matches the task description's
  explicit list (`pid, port, version, startedAt`) rather than the system
  design doc's `{pid, controlPort, version, startedAt, logPath}` — the task
  instructions call out plan.md line 691 as authoritative for this bullet
  and mark the CLI/control-server wiring (where `controlPort`/`logPath`
  would presumably get plumbed in) as out of scope here.
- `EPERM` from `kill(pid, 0)` (process exists, owned by another user) is
  treated as "alive" — conservative by design: never reclaim a lock unless
  we can positively confirm the owning process is gone.
