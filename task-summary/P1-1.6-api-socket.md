# P1-1.6-api-socket — apiSocket: user-scoped WS client with infinite reconnect + app-state reporting

**Section:** 1.6 Web app v1 read-only (plan.md §8.1, line 704) — **(P)** port with changes,
from Happy's `happy-app/sources/sync/apiSocket.ts`.

## What was built

`packages/web/src/sync/`:

- **`apiSocket.ts`** — the core, pure client: `createApiSocket(socketFactory, visibility)`.
  Singleton connection state machine:
  - `connect(token)` — idempotent no-op if already connected with the same token; tears
    down and replaces the socket if the token changes (re-auth).
  - `disconnect()` — full teardown (logout); safe to call when already disconnected.
  - A generic typed `on(event, handler)` / `off(event, handler)` emitter over
    `'update' | 'ephemeral' | 'reconnect' | 'connect' | 'disconnect'`, matching plan.md
    §8.1's literal usage sample (`apiSocket.on('update', ...)`,
    `apiSocket.on('reconnect', () => queryClient.invalidateQueries())`).
  - `'reconnect'` fires only from the *second* `'connect'` onward (per-instance
    `hasConnectedBefore` flag) — the signal the (not-yet-built) sync engine invalidates
    every TanStack Query on, per design §9.1.
  - Incoming `update`/`ephemeral` payloads are validated with `@falcon/wire`'s
    `UpdateSchema` / `EphemeralSchema` (`.safeParse`) before being handed to listeners —
    a malformed payload is logged (`console.error`) and dropped, never thrown or silently
    swallowed.
  - `appState()` reports the current `"active" | "background"` (design §9.1/§6.4 push
    suppression input); on every visibility change it re-emits `app-state` to the *live*
    socket and updates the closure so the *next* connect/reconnect attempt's auth
    handshake carries the fresh value too.
  - `SocketLike` is a minimal structural interface (`connected`/`connect`/`disconnect`/
    `on`/`off`/`emit`) — a real `socket.io-client` `Socket` satisfies it with no wrapping
    (mirrors `crypto/client.ts`'s `WorkerLike` split), so `apiSocket.ts` itself never
    imports `socket.io-client` and is fully unit-testable without a network connection.
- **`socket-factory.ts`** — `createSocketFactory(serverUrl?)`: the real Socket.IO
  connection. `path: "/v1/stream"`, `autoConnect: false` (apiSocket calls `.connect()`
  itself), `reconnection: true, reconnectionAttempts: Infinity` (infinite reconnect,
  exponential backoff via `reconnectionDelay`/`reconnectionDelayMax`/
  `randomizationFactor` — Socket.IO's own well-tested backoff engine, not a hand-rolled
  timer), and `auth: (cb) => cb(getAuth())` — the callback form, so Socket.IO
  re-evaluates the handshake payload (token + `clientType: 'user-scoped'` + current
  `appState`) before *every* (re)connection attempt, not just the first. `serverUrl`
  defaults to `NEXT_PUBLIC_FALCON_API_URL` (falls back to `http://localhost:3005` for
  local dev).
- **`visibility.ts`** — `createBrowserVisibilitySource()`: `document.visibilitychange` →
  `"active" | "background"`. Falls back to `"active"` + a no-op subscription when
  `document` doesn't exist (Next statically prerenders in Node — design §9: static
  export, no SSR of user content).
- **`index.ts`** — public barrel; exports the real singleton `apiSocket` (wired to the
  real socket factory + browser visibility source) plus all types/factories for tests
  and for the (later) sync-engine task to compose against.

`packages/web/package.json` — added `"@falcon/wire": "workspace:*"` (first consumer of
the wire package in `@falcon/web`) and `"socket.io-client": "^4.8.1"` (same major/minor
already used server-side in the unmerged `P1-1.1-server-realtime` worktree, confirmed by
reading its `packages/server/src/app/socket.ts` for the exact handshake contract this
client needs to match: `path: "/v1/stream"`, `handshake.auth = {token, clientType,
sessionId?, machineId?, appState}`, server emits `"update"`/`"ephemeral"`, client emits
`"app-state"`).

## Tests (`packages/web/src/sync/__tests__/`)

- **`fakes.ts`** — `createFakeSocketFactory()` (in-memory `SocketLike` double with
  `serverEmit()` to simulate inbound server events and `emitted`/`authSnapshots` to
  inspect what the client sent) and `createFakeVisibilitySource()` (manually
  `trigger()`-able instead of real `document` events) — mirrors
  `crypto/__tests__/loopback.ts`'s approach of testing the pure client against an
  in-process double.
- **`apiSocket.test.ts`** (12 tests): idempotent connect on the same token; token change
  tears down the old socket and opens a new one; `disconnect()` teardown +
  double-disconnect safety; `'reconnect'` fires on the 2nd+ `connect` event but not the
  1st; a fresh `connect()` with a *new* token is not treated as a reconnect; well-formed
  `update`/`ephemeral` payloads are delivered and malformed ones are dropped without
  throwing (console.error is asserted, not just swallowed); visibility changes emit
  `app-state` to the live socket and are picked up by the next connection's auth
  snapshot; app-state is not emitted to a torn-down socket; `'disconnect'` listeners
  fire; `on()`'s returned unsubscribe and `off()` both work. Plus a module-wiring smoke
  test that imports the real `index.ts` singleton under Node (no `document`, `autoConnect:
  false`) and asserts it constructs without throwing and reports sane defaults
  (`appState() === "active"`, `isConnected() === false`).

All 12 new tests pass; full `packages/web` suite is 48/48 (36 pre-existing + 12 new).

## Assumptions / scope decisions

- **End-to-end wiring against a live server is out of scope**, as the task description
  says: `/v1/stream` doesn't exist on `main` yet (Phase 1's server-realtime work is
  sitting unmerged in `P1-1.1-server-realtime`). This task builds and unit-tests the
  client module and its reconnect/backoff state machine against the `@falcon/wire`
  contract in isolation, per the task description. I *did* read
  `P1-1.1-server-realtime/packages/server/src/app/socket.ts` and `events/eventRouter.ts`
  (read-only, to extract the exact wire contract this client must match — path, auth
  handshake shape, event names) but made no changes there and did not depend on that
  worktree's code.
- **Reconnection uses Socket.IO's built-in engine (`reconnectionAttempts: Infinity`)
  rather than a hand-rolled backoff timer.** It already implements exponential backoff +
  jitter correctly and is what the server side (`P1-1.1-server-realtime`) was built
  against; reinventing that state machine on top of it would be duplicated, less-tested
  logic. What *is* custom, and what the unit tests exercise, is: idempotent
  connect/reconnect-on-token-change, the `'reconnect'`-vs-`'connect'` distinction (fires
  only from the 2nd connect onward — this is *not* something Socket.IO exposes itself,
  Socket.IO's own `'reconnect'` event only fires after a `reconnect_attempt` sequence,
  not on a fresh manual `.connect()`, so it can't be used directly for the "invalidate
  everything" signal plan.md's sample code wants), schema-validated event forwarding,
  and app-state propagation into both the live connection and the next handshake.
- **Event API is a generic `on`/`off` emitter (`'update' | 'ephemeral' | 'reconnect' |
  'connect' | 'disconnect'`)** rather than separate `onUpdate`/`onEphemeral`/... methods,
  to match plan.md §8.1's literal code sample (`apiSocket.on('update', ...)`,
  `apiSocket.on('reconnect', ...)`) exactly, since the not-yet-built sync-engine task
  will consume this surface directly.
- **No RPC/`rpc-call`/`rpc-register` support here.** Per design §9.1, the web app's
  apiSocket is explicitly read-only (`update`/`ephemeral` in, `app-state` out) — RPC
  calls (e.g. `perm.answer`) are a separate concern layered on top in the permission
  pipeline task (plan.md §9/2.3), out of this task's scope.
- **`NEXT_PUBLIC_FALCON_API_URL` is a new env var convention** (no prior precedent in
  the repo for a client-side API base URL) — mirrors the server's `PORT`/`HOST` naming
  style, prefixed `NEXT_PUBLIC_` per Next.js convention for client-exposed env vars.
- Nothing in `packages/web/src/app/` calls `apiSocket.connect()` yet — that's downstream
  of the auth pages (plan.md 1.6, "still not started") and the sync-engine task, both out
  of scope here.
