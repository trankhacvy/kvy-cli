# P1-1.6-web-app-scaffold — Next.js App Router scaffold (Tailwind + shadcn/ui, dark default)

**Section:** 1.6 Web app v1 (read-only), first bullet only — `plan.md` §16, design §8.4/§9, DELTA D4.

## Scope

Pure front-end scaffolding for `packages/web` (`@falcon/web`). No auth, no sync engine,
no `apiSocket`, no crypto worker, no reducer — those are separate, later 1.6 bullets and
are intentionally left `[planned]`.

## What was built

- **Package**: `packages/web` added to the pnpm workspace as `@falcon/web`, `private`,
  ESM, `next`/`dev`/`typecheck` scripts. Added to `pnpm-workspace.yaml` implicitly via the
  existing `packages/*` glob (no change needed there).
- **Next.js App Router**, static export configured in `next.config.ts`: `output: "export"`,
  `images.unoptimized: true` (no image-optimization server exists for a static export),
  `trailingSlash: true` for stable static-host routing. No SSR/ISR surface — matches design
  §5.3/§9: the server never renders user content, and the web app is served from a separate
  static origin than the API.
- **Tailwind CSS v4 + shadcn/ui**, wired the v4 way (`@tailwindcss/postcss` plugin, no
  `tailwind.config.ts`): `src/app/globals.css` defines semantic CSS variable tokens
  (`--background`, `--primary`, etc.) at `:root`/`.dark`, mapped via `@theme inline`, with
  `@custom-variant dark (&:is(.dark *))` so shadcn's `dark:` utilities work off a class
  rather than `prefers-color-scheme`. `components.json` configured (`style: new-york`,
  `rsc: true`, `baseColor: slate`, `cssVariables: true`) so `shadcn add` works going forward.
  One primitive (`src/components/ui/button.tsx`, shadcn's standard `Button` + `cva` variants)
  ported in to prove the pipeline end-to-end; `src/lib/utils.ts` has the standard `cn()`
  helper (`clsx` + `tailwind-merge`).
- **Dark default theme**: `src/app/layout.tsx` sets `<html className="dark" suppressHydrationWarning>`
  unconditionally — dark is Falcon's default per the design §9 stack table. This is a static
  default, not a hardcoded ceiling: a later appearance toggle (design §9.2 Settings screen)
  only needs to flip the class at runtime; no other file changes when that lands.
- **Placeholder route**: `src/app/page.tsx` renders a minimal "Falcon" landing view (title,
  one-line scaffold description, a disabled `Button`) so the static export has real content
  to prerender and the shadcn primitive is actually exercised, not just imported.
- **PWA manifest stub**: `public/manifest.webmanifest` (name/short_name/description/
  start_url/display/background_color/theme_color) linked from `layout.tsx` metadata —
  service worker, push, and icons are out of scope here (design §9.3, later phase).
- **Monorepo wiring**:
  - `turbo.json`: added a `@falcon/web#build` task override (`outputs: ["out/**", ".next/**", "!.next/cache/**"]`)
    since the shared `build` task's default `outputs: ["dist/**"]` doesn't match Next's
    static-export output directory.
  - `.gitignore`: added `.next/` and `out/`.
  - `CLAUDE.md`: moved `web` out of "planned" in the package table, noted what's wired vs.
    still planned; annotated the `pnpm build` command line to mention `next build` → `out/`.

## Verification

- `pnpm install` — clean, lockfile updated for the new package's dependency graph.
- `pnpm build` (root, Turborepo) — all 4 packages (`wire`, `crypto`, `server`, `web`) build
  green; Next.js compiles, prerenders both routes (`/`, `/_not-found`) as static content, and
  exports to `packages/web/out/`.
- `pnpm --filter @falcon/web typecheck` — clean (`tsc --noEmit`, strict mode inherited from
  `tsconfig.base.json`).
- Inspected the exported `out/index.html` — confirms `<html class="dark">` is present in the
  static output, i.e. dark is the theme on first paint with no flash/JS dependency.
- `pnpm lint` (biome, repo root): the linter process OOMs in this sandbox on the full repo
  scan — reproduced identically against already-landed, previously-verified packages
  (`wire`/`crypto`/`server`) on the same tree, so this is a pre-existing sandbox/environment
  limitation, not something introduced by this change. Not required by the task's stated
  verification step (`pnpm build`), which is green.

## Post-review fixes (test-failure pass)

- **`packages/web` had no `test` script / Vitest config**, so `pnpm test` silently
  no-opped the web package (turbo treats a missing script as success). Added
  `packages/web/vitest.config.ts` (mirrors the `@/*` → `./src/*` tsconfig alias),
  `src/lib/utils.test.ts`, and `src/components/ui/button.test.ts` (14 tests covering
  `cn()` and `buttonVariants()`), plus `"test": "vitest run"` and the `vitest`
  devDependency in `packages/web/package.json`.
- **Flaky root `pnpm test`**: the default `test` task in `turbo.json` depends on the
  *same-package* `build` task, so `@falcon/web`'s `next build` ran as a prerequisite
  of `vitest run` on every `pnpm test`. Running `next build` concurrently with other
  packages' vitest tasks under Turborepo's parallel scheduler intermittently failed
  in this sandbox with two different transient errors (`<Html> should not be imported
  outside of pages/_document` during `/404` prerendering; `Cannot find module ./NNN.js`
  webpack chunk during page-data collection) — reproduced this same class of failure
  running `turbo run build --force` concurrently, and confirmed it does not reproduce
  when `next build` runs standalone. Since `@falcon/web`'s unit tests import source
  modules directly (`@/lib/utils`, `./button`) and exercise none of the Next static
  export build, the dependency was unnecessary. Added a `@falcon/web#test` override
  in `turbo.json` depending on `^build` (upstream workspace packages only, matching
  `typecheck`'s pattern) instead of `build`, which drops `next build` out of the
  `test` task graph entirely — verified with `turbo run test --dry=json` (only
  `@falcon/web#test` in the graph, no build task) and 6 consecutive `turbo run test
  --force` (uncached) passes with no `next build` invocation.
  - This does **not** fix `next build`'s own intermittent flakiness when invoked via
    `pnpm build` (still contends with sibling packages' `build` tasks by design of the
    monorepo build pipeline) — that remains a sandbox CPU/IO resource-contention
    characteristic, not a code defect, worth the same kind of CI note as the
    biome-OOM caveat above.

## Assumptions / notes

- Followed the versions already pinned in the pre-staged `package.json`/`tsconfig.json`
  found in the worktree (Next 15.5.20, React 19.2.0, Tailwind 4.3.2 — all verified to exist
  on the npm registry and installable in this environment).
- No `next-themes`/toggle UI added — out of scope for "scaffold + dark default"; the
  Settings-screen appearance toggle is design §9.2, a later bullet.
- No PWA service worker / push — design §9.3 is explicitly a separate, later piece of 1.6.
- Kept the placeholder home route intentionally thin: it exists to prove the build/export
  pipeline and the shadcn/Tailwind wiring compile and render correctly, not to anticipate
  the real session-list screen (which depends on the sync engine/crypto bridge that don't
  exist yet).
