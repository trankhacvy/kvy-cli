# P17-2.0-wire-envelope-verification

**Task:** Verify wire schema needs no new envelope types for ACP mapping
(plan.md §17 "Phase 2.0 — foundation", last bullet: "Wire schema: no new
envelope types needed (verified mapping, proposal §3 A4) — assert via golden
fixtures rather than schema change").

## What this task is

A verification/documentation task, not a code-change task. Design authority
already asserts the mapping is sound:

- `falcon-system-design.md` §7.3 ("v0.3" note): ACP `session/update` kinds map
  1:1 onto existing `SessionEvent` variants —
  `agent_message_chunk`→`text`, `agent_thought_chunk`→`text{thinking}`,
  `tool_call`/`tool_call_update`→`tool-start`/`tool-end`,
  `session/request_permission`→`perm-request`/`perm-resolve`,
  `session/prompt` call/return→`turn-start`/`turn-end`, tool-call
  `_meta.claudeCode.parentToolUseId`→`subagent` scope.
- `docs/acp-delta-proposal.md` §3, row A4: "`SessionEnvelope` schema
  (`@falcon/wire`) — **Unchanged**... nothing in ACP's event model needs a new
  envelope type."

The job here was to turn that design-doc assertion into an executable,
regression-proof claim, per the task description's explicit instruction:
"Assert this via golden fixtures added to the existing golden-trace test
corpus (rather than any schema change)."

## What I did

No changes to `packages/wire` — confirming §5.2's design principle ("the wire
schema is closed and stays provider-agnostic") holds: zero new variants, zero
new fields, zero schema edits anywhere in this change.

Added three new fixtures to the existing golden-trace corpus at
`packages/web/src/sync/reducer/__testdata__/` (the only golden-trace test
corpus in the repo — discovered and run by
`packages/web/src/sync/reducer/golden.test.ts`, which globs `trace_*.json`,
parses each fixture's `envelopes` through `SessionEnvelopeSchema.parse`, feeds
them through the real `reduceEnvelopes` reducer, and diffs the result against
the fixture's recorded `expected` output — an unparseable/mismatched fixture
fails the suite, same guarantee every other trace fixture in that directory
already relies on):

1. **`trace_acp_turn_lifecycle.json`** — a full ACP-driven turn built entirely
   from existing envelope variants: `session/prompt` call/return brackets the
   turn (`turn-start`/`turn-end`), `agent_thought_chunk` → `text{thinking:
   true}`, `agent_message_chunk` → plain `text`, `tool_call`/
   `tool_call_update` → `tool-start`/`tool-end`.
2. **`trace_acp_request_permission.json`** — ACP's server→client
   `session/request_permission` → the existing `perm-request` envelope; the
   mapped ACP option response → the existing `perm-resolve` envelope, reusing
   the `PermDecision` discriminated union (`allow`/`deny`/`mode`) already
   defined in `@falcon/wire` — no new decision kind needed either.
3. **`trace_acp_parent_tool_use_subagent.json`** — a tool-call update carrying
   ACP's `_meta.claudeCode.parentToolUseId` maps onto the existing `subagent`
   envelope field, same Task-call-id-as-subagent-id convention local mode
   already uses (mirrors the pre-existing `trace_subagent_task.json`, framed
   explicitly as the ACP-sourced case).

Each fixture's `description` field cites the design §7.3 mapping table /
proposal §3 A4 row it's demonstrating, so a reader can trace fixture → design
claim directly.

Also expanded `golden.test.ts`'s file-level docstring to explain what the new
`trace_acp_*.json` fixtures are for (the mapping-verification purpose, not
just "another golden trace") so the intent survives independent of this
summary file.

## Why fixtures, not a new test file or a wire-package change

The task explicitly asked for verification "via golden fixtures added to the
existing golden-trace test corpus (rather than any schema change)" — the
`trace_*.json` + `golden.test.ts` pair in `packages/web/src/sync/reducer/` is
that corpus (confirmed by grepping the whole repo for "golden": only that
directory and two unrelated CLI envelope-mapper test files matched, and the
CLI ones aren't a "fixture corpus", they're inline-authored unit tests). Using
the same mechanism as every other reducer regression test means: (a) the
proof is exercised on every `pnpm test` run, not a one-off script; (b) a
future accidental wire-schema change that actually breaks ACP-shaped envelopes
would fail this suite the same way it'd fail any other golden trace; (c) no
new test infrastructure was invented for a task whose whole point is "don't
add anything new to the schema."

## Assumptions / scope notes

- The actual `acp/acpToEnvelope.ts` mapper (Phase 2.1) doesn't exist yet, so
  these fixtures model the *envelopes the mapper will emit* for each ACP
  update kind (post-mapping shape), not raw ACP JSON-RPC payloads — that's
  consistent with the task's own framing ("demonstrating each ACP update kind
  maps onto an existing envelope variant") and with how every other fixture
  in this corpus is authored (hand-built representative envelope streams, not
  captured raw provider output — see the file's own docstring: "recorded (or
  hand-built, representative)").
- No `@falcon/wire` files were touched. `pnpm build` confirms the wire
  package's `dist/` is unchanged in shape (still builds clean, no new
  exports).
- Left the six pre-existing `trace_*.json` fixtures untouched.
