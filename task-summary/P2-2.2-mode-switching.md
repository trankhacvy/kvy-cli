# P2-2.2-mode-switching — Port `loop.ts` orchestration + local/remote launchers for mode switching

Section: Phase 2 — Control: steer from the web (M2) — §2.2 Mode switching (plan.md §6.7)

## What was built

Three new files under `packages/cli/src/claude/`:

- **`loop.ts`** — the mode state machine (**V/P**, ported from Happy's `loop.ts` per
  plan.md §6.2, whose five-line shape is quoted verbatim in the file header and
  preserved). Also owns, since Falcon's launchers deliberately don't own their own
  transport (see below):
  - The long-lived subscriptions to the three external triggers — `onMessage` (the
    `message` RPC), `onTakeControl` (`takeControl` RPC / Ctrl-T / double-space), and
    `onExitRequested` (double-Ctrl-C) — routed via a mutable `activeLocal`/`activeRemote`
    indirection into whichever launcher handle is *currently* running.
  - `providerSessionId` and switch-time queued messages (`pendingMessages`), carried
    across the local↔remote boundary between launcher invocations.
  - `ModeSwitchDedupe` — the cross-mode dedupe ring buffer (plan.md: "5-min, text+id
    keyed"), exported from this file since it's the one piece of state shared by both
    launchers across every switch.
- **`claudeLocalLauncher.ts`** — `startClaudeLocalLauncher()`. Orchestrates one local-mode
  run: spawns the already-landed `claudeLocal()` child, tails its transcript via the
  already-landed `createSessionScanner()` + `mapClaudeToEnvelopes()` (filtered through the
  shared dedupe), and reports back `{type:'exit', code}` or `{type:'switch',
  providerSessionId, queuedMessages}`. Returns a handle (`{done, requestSwitch}`, matching
  `startClaudeRemote`'s own handle-based shape) so `loop.ts` can call `requestSwitch()`
  on the currently-running launcher the instant a `message`/`takeControl` event arrives,
  without waiting on the async run itself. `requestSwitch()` aborts the child (local→remote
  trigger per plan.md) and emits a `mode-switch` envelope once the abort resolves.
- **`claudeRemoteLauncher.ts`** — `startClaudeRemoteLauncher()`. Orchestrates one
  remote-mode run: starts the already-landed `startClaudeRemote()` SDK query, delivers
  `initialMessages` (queued during a prior local→remote switch) immediately, and exposes
  `deliverMessage()`/`requestSwitchToLocal()`/`requestExit()` for `loop.ts` to push events
  into. On `requestSwitchToLocal()`, calls `handle.stop()` to capture the SDK's own
  `providerSessionId` (remote→local trigger per plan.md — "SDK stop → capture new
  providerSessionId → `claude --resume <id>`") and emits a `mode-switch` envelope;
  `requestExit()` stops without emitting one.

Plus one test file per module (`loop.test.ts`, `claudeLocalLauncher.test.ts`,
`claudeRemoteLauncher.test.ts`), 22 tests total, including the loss-lessness "switch storm"
test.

## Design decisions / assumptions

1. **Handle-based launchers, not bare promises.** Both `startClaudeLocalLauncher` and
   `startClaudeRemoteLauncher` return `{ done: Promise<Result>, ...imperative methods }`
   rather than a single awaited call — this mirrors `startClaudeRemote`'s own existing
   shape and is what lets `loop.ts` push external events (`requestSwitch`/`deliverMessage`/
   etc.) into whichever launcher is *currently* running without restructuring around the
   async body.

2. **Launchers don't own their transport.** Neither launcher registers real session RPCs,
   sockets, or Ink keypress handling — each accepts plain callback-registration functions
   (`onMessage`, `onTakeControl`, `onExitRequested` on `LoopOptions`) that a future
   "session runner" task (not yet built — see `CLAUDE.md`'s "RPC handler registration...
   still [planned]") wires to the real `registerSessionRpcHandlers`/`RemoteModeDisplay`.
   This mirrors how `claudeLocal.ts` treats its launcher-script path as "a given" and how
   `claudeRemote.ts`'s own file header explicitly deferred this exact orchestration task.
   Similarly, `onEnvelopes` is a plain callback the caller wires to the HTTP `Outbox` —
   these files don't construct an `Outbox`, `bootstrapSession`, or `sessionClient`
   themselves.

3. **The dedupe key is `(role, text)`, not `(id, text)`.** The task description says
   "keyed by text+id"; I initially considered preserving an envelope's own `id` across
   the switch, but that's not achievable without modifying `claudeRemote.ts` (out of
   scope): `send(prompt: string)` always mints its own fresh envelope id internally, and
   a `message` RPC's client-minted envelope id is necessarily discarded once reduced to
   the plain-text `send()` call. `@falcon/wire`'s own design principle — provider/producer
   ids never cross a boundary, only content does — applies here too: the only key that's
   actually stable across the local tailer and the remote SDK's own emission is the
   rendered text (per happy-research.md §8: "deduped ... via a 5-minute text ring
   buffer" — literally text-only). I used `${role} ${text.trim()}` as the composite key
   (role folded in so identical text from `user` vs `agent` never collides), documented
   at length in `loop.ts`'s file header. Only `t: 'text'` events are deduped; tool
   calls/turn markers already carry their own `call`/`turn` identity.

4. **Dedupe filtering happens once, inside each launcher — not again in `loop.ts`.** Both
   launchers filter through the *same* shared `ModeSwitchDedupe` instance before calling
   `onEnvelopes`. I initially also wrapped `onEnvelopes` a second time in `loop.ts` itself,
   which was a real bug caught by the loss-lessness test: since `isDuplicate()` is
   stateful (records-on-first-call), re-checking the same envelope a moment later against
   the same instance always reads back "already seen" and silently drops every single
   envelope. Fixed by having `loop.ts` pass `opts.onEnvelopes` straight through.

5. **`onMessage`/`onTakeControl`/`onExitRequested` are the loop's only external inputs.**
   `loop.ts` decides how to route a `message` event based on current mode (deliver
   directly if remote, queue-and-switch if local) rather than the launchers each
   registering their own subscriptions — this keeps exactly one live subscription per
   trigger for the whole `loop()` call, so there's never a window (no `await` between
   clearing the old active handle and setting the new one) where an incoming event has
   nothing to route to.

6. **Hook-mode session-id discovery is out of scope.** `claudeLocalLauncher` supports
   offline-mode session-id discovery (the synchronous `onSessionFound` callback
   `claudeLocal()` already calls directly) fully. Wiring the SessionStart-hook-server path
   (`hookServer.ts`, already landed as a separate module) into this launcher is a
   follow-up — same scope boundary `claudeLocal.ts`'s own header already draws.

## Loss-lessness test

`loop.test.ts`'s `"loss-lessness: a storm of rapid switches with messages queued
mid-flight..."` test drives the *real* `loop()` + both *real* launchers (only the deepest
layer — `claudeLocal`, `createSessionScanner`, `startClaudeRemote` — is faked) through 5
rapid local→remote→local round trips, each carrying one queued message, plus one message
delivered directly while remote is already active. After each switch back to local, it
simulates the actual race this task is about: the freshly-restarted local tailer observing
the *same* text still sitting in the (simulated) on-disk transcript, as if the SDK's
subprocess had just written it moments after the scanner seeded its own dedup set. Asserts
every one of the 7 distinct message texts appears in the forwarded envelope stream exactly
once (no drops, no dupes).
