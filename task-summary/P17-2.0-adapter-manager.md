# P17-2.0-adapter-manager — Adapter manager (pinned ACP adapter installs)

**Section:** §17 v2 ACP migration — Phase 2.0 foundation (plan.md: "Adapter manager
(`cli/src/adapters/`, design §7.9): pinned-version manifest (package id + exact version +
integrity hash), install into `~/.falcon/adapters/` own npm prefix, verify-before-spawn,
`falcon adapters install|upgrade` command, `falcon doctor` adapter checks. No npx at
session start"). Design authority: `falcon-system-design.md` §7.9.
**Port type:** (N) new code — mobvibe's `src/registry/` (dynamic CDN registry + npx/uvx/
binary resolution) was read as a reference but is *not* the porting source: Falcon's design
explicitly rejects that model in favor of pinned, Falcon-shipped exact versions with no
runtime resolution. This task is bespoke to the design doc.

## What was done

New standalone module, `packages/cli/src/adapters/`:

- **`manifest.ts`** — `ADAPTER_MANIFEST`: exact `{packageName, version, integrity, binEntry}`
  for both official ACP adapters, verified live against the real npm registry while writing
  this manifest (`npm view <pkg>@<version> dist.integrity`):
  - `claude-code` → `@agentclientprotocol/claude-agent-acp@0.59.0`
  - `codex` → `@agentclientprotocol/codex-acp@1.1.4`

  **Naming note:** the design doc's prose shorthand (`claude-agent-acp` / `codex-acp`,
  unscoped) does not match what's actually published — those unscoped names don't exist on
  npm. Both adapters are scoped under `@agentclientprotocol/*` (the Claude adapter's
  predecessor, `@zed-industries/claude-code-acp`, is now deprecated and redirects to this
  one). Documented directly in `manifest.ts`'s header comment so this doesn't read as a typo
  later.
- **`paths.ts`** — `adaptersDir()`/`adapterEntryPath()`/etc., all homeDir-parameterized (no
  hidden `home.ts` dependency, matching `workspace/registry.ts`'s `RegistryOptions` seam).
- **`install.ts`** — `installAdapter`/`installAllAdapters`: runs a real
  `npm install <pkg>@<exact version> --save-exact --omit=dev --no-audit --no-fund` into
  `~/.falcon/adapters/` (its own npm prefix — a root `package.json` Falcon writes and never
  hand-edits), then re-verifies the result against the manifest before reporting success.
  `runNpm` is injectable (`NpmExec`, same `execFile`-wrapper shape as `daemon/gitExec.ts`'s
  `runGit`) so tests never touch the network. Idempotent by default (skips npm entirely when
  already satisfied); `force: true` always reinstalls. Per-adapter failure isolation:
  `installAllAdapters` never throws on the first failure, so one adapter's registry hiccup
  doesn't block the other's install.
- **`verify.ts`** — `verifyAdapterInstall`: the actual integrity check. Reads npm's own
  `node_modules/.package-lock.json` (the hidden, auto-maintained lockfile npm writes after
  every install describing exactly what's on disk — verified empirically by running a real
  `npm install` in a scratch dir and inspecting the output) and compares `version`/`integrity`
  against `ADAPTER_MANIFEST`. Never throws; returns a discriminated
  `not-installed | version-mismatch | integrity-mismatch | entry-missing | ok` result.
- **`health.ts`** — `checkAllAdaptersHealth`, the `falcon doctor` / `falcon adapters` facing
  wrapper around `verify.ts`, independently testable with no `daemon/` dependency.
- **`spawn.ts`** — `resolveAdapterSpawn`: the verify-before-spawn seam Phase 2.1's
  `acpConnection.ts` will call instead of touching `paths.ts` directly — refuses (rather than
  guessing) on any verification failure, returns `{command: execPath, args: [entryPath]}` on
  success.
- **`index.ts`** — barrel re-exporting the above.

CLI wiring (matching the existing `falcon workspace ...`/`falcon doctor` precedent, no
framework — hand-rolled `args.ts` parsing):

- **`commands/adapters.ts`** — `runAdaptersInstallCommand`/`runAdaptersUpgradeCommand`, thin
  terminal-output wrappers around `installAllAdapters`. `install` is idempotent; `upgrade`
  always force-reinstalls (design §7.9: "upgrades are never implicit"). No daemon
  interaction — this is a local npm-prefix operation, same rationale as `workspace
  register`/`workspace config` skipping `ensureDaemon()`.
- **`args.ts`** — new `{type: "adapters", action: "install" | "upgrade"}` command +
  `parseAdapters`.
- **`index.ts`** — `runAdapters` dispatcher, wired into the top-level `run()` switch and the
  `--help` text (`falcon adapters install|upgrade`).

`falcon doctor` integration (design §7.9: "reports adapter presence/version/integrity and
the underlying provider CLI detection"):

- **`daemon/doctor.ts`** — `DoctorReport` gained `adapters: AdapterHealth[]` and
  `providers: {claude, codex}`. `DoctorDeps` gained three *optional*, injectable fields
  (`checkAdapters`, `detectClaudeProvider`, `detectCodexProvider`) defaulting to
  `checkAllAdaptersHealth` / the already-existing `detectClaudeCode`
  (`provider/claudeProviderAdapter.ts`) / `detectCodex` (`codex/codexProviderAdapter.ts`) —
  reusing those two `ProviderAdapter.detect()` implementations rather than duplicating CLI
  detection logic. `describeDoctorReport` renders two new sections ("ACP adapters:",
  "provider CLIs:"). Existing `doctor.test.ts` calls were updated to inject fakes for the
  three new deps so tests never touch a real `~/.falcon/adapters` install or shell out to a
  real `claude`/`codex` on this machine.

## Design decision: no hand-authored full lockfile

The manifest pins only the *target* package's own version + integrity, not a full
hand-authored `package-lock.json` for its entire transitive dependency tree. This was
evaluated and rejected: verified empirically (`npm ci` against a hand-written lockfile
missing transitive/optional entries) that it requires the lockfile to exactly describe every
transitive dependency or `npm ci` refuses to run — which would go stale the moment any
transitive dependency published a patch release, independent of Falcon's own release cycle.
Installing normally (`npm install <pkg>@<exact version>`) and then comparing the resulting
`node_modules/.package-lock.json` entry for the top-level package against the pinned
manifest value is simpler, survives transitive churn, and still catches what actually
matters: the registry serving different bytes than what Falcon's release was tested against
under the same `package@version`. Verified this catches tampering: a deliberately-wrong
integrity value in a real `npm ci` run produces `npm error code EINTEGRITY` and a nonzero
exit — confirmed live against the registry while building this.

## Assumptions / scope notes

- Standalone module as required by the task brief: no import from the claim store or any
  `@falcon/wire` schema change — `adapters/` has zero dependency on either.
- `falcon adapters install|upgrade` does **not** call `ensureDaemon()` — a local npm-prefix
  filesystem operation, not a daemon-mediated one, matching `workspace register`'s existing
  precedent for the same reasoning.
- Automatic first-run install ("also run automatically once at `falcon auth login`/first
  `falcon <provider>` when missing", design §7.9) is explicitly **not** wired in this task —
  that hook belongs with Phase 2.1's `acpConnection.ts`/provider spawn wiring, which is what
  actually needs the adapter to exist before it can spawn it. This task lands the manager
  itself (install/upgrade/verify/health/spawn-resolution) as the prerequisite; the caller
  that triggers an implicit first install doesn't exist yet, matching the same "adapter
  modules land ahead of the orchestration that spawns them" precedent already set by the
  Claude/Codex provider-adapter tasks (see `CLAUDE.md`'s `cli/` package-layout notes).
