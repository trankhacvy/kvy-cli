# P1-1.5-control-server — Daemon control server (local Fastify HTTP API)

**Phase 1 — 1.5 Daemon v1, §7.1 (plan.md).** Ported Happy's
`happy-cli/src/daemon/controlServer.ts` (MIT) into
`packages/cli/src/daemon/controlServer.ts`.

## What was implemented

- `packages/cli/src/daemon/types.ts` — daemon-local (non-wire) types adapted
  from Happy's `daemon/types.ts`: `SessionEncryptionData`, `TrackedSession`,
  `SpawnSessionOptions`, `SpawnSessionResult`. These never cross a network
  boundary; they describe the daemon's own in-memory bookkeeping.
- `packages/cli/src/daemon/controlServer.ts` — `startControlServer(deps)`:
  a Fastify server bound to `127.0.0.1:0` (ephemeral port, resolved from
  `app.listen`'s callback — never a fixed port) exposing:
  - `POST /session-started` — webhook a spawned session posts its Falcon
    `sessionId` + optional encryption material (`encryptionKey`, `seq`,
    `metadataVersion`, `agentStateVersion`) back to. Kept verbatim per
    plan.md §7.1: this is the only path by which a spawned session's
    encryption material reaches the daemon, and daemon durability (§7.4,
    separate task) persists exactly this shape so resume survives a daemon
    restart.
  - `POST /list` — lists tracked sessions that have self-reported
    (`startedBy`, `sessionId`, `pid`); sessions not yet self-reported are
    filtered out, matching Happy's behavior.
  - `POST /stop-session` — forwards `sessionId` to an injected `stopSession`
    callback, echoes `{ success }`.
  - `POST /spawn-session` — forwards validated options to an injected
    `spawnSession` callback and maps its discriminated-union result to
    Happy's exact status codes: `200` success, `409` + `CREATE_DIRECTORY`
    when directory-creation approval is needed, `500` + error message.
  - `POST /stop` — responds `{ status: 'stopping' }` immediately, then
    calls the injected `requestShutdown` after a 50ms delay (same as Happy,
    so the HTTP response reaches the caller before the process exits).
  - Zod validation via `fastify-type-provider-zod`, `logger: false` (the
    caller's own file-only `Logger` is optionally injected and used for
    debug lines instead).
- `packages/cli/src/daemon/controlServer.test.ts` — 12 unit tests using real
  `fetch()` against the ephemeral port (no mocking of Fastify itself),
  covering: ephemeral port binding, `/session-started` with and without
  encryption material, 400 on a missing required field, `/list` filtering
  un-self-reported sessions, `/stop-session` and `/spawn-session` (all three
  result branches + invalid-enum 400), `/stop`'s delayed shutdown callback,
  and that `stop()` actually closes the listener.

## Design notes / deltas from Happy

- **Standalone module, own schemas.** Per the task brief, this does not
  depend on the (separately-implemented, currently unmerged)
  `packages/cli/src/daemon/lock.ts` singleton lock — `startControlServer`
  only takes injected callbacks (`getSessions`, `stopSession`,
  `spawnSession`, `requestShutdown`, `onSessionStarted`), so it composes
  with whatever owns the daemon process lifecycle (§7.2/§7.4) without a
  file-level dependency today.
- **Reuse of `@falcon/wire`:** `StopSessionParamsSchema` (machine RPC
  contract) is reused verbatim for `/stop-session`'s request body since the
  shapes overlap exactly (`sessionId` [+ optional `force`, unused by this
  HTTP layer]). `PermissionModeSchema` is reused for `/spawn-session`'s
  `permissionMode` field instead of a bare `z.string()`. `/list` and
  `/session-started` keep bespoke schemas — `@falcon/wire`'s
  `LocalSessionInfoSchema`/`ListSessionsResultSchema` require fields
  (`workspaceId`, `provider`, `controlMode`, `status`, `startedAt`) that
  `TrackedSession` doesn't populate until fuller daemon state tracking lands
  (§7.2/§7.4), so forcing that reuse now would mean fabricating placeholder
  values — deferred rather than over-fit.
- **Renamed fields vs. Happy:** `happySessionId` → `sessionId` (Falcon's own
  session id, cuid2, matching wire's naming throughout `rpc.ts`); Happy's
  `agent` field → `provider` (matching wire's `"claude-code" | "codex"`
  enum). Happy's `encryptionVariant: 'legacy' | 'dataKey'` enum (a
  migration artifact from Happy's own protocol evolution) was dropped —
  Falcon has no legacy encryption format to migrate from, so it would be
  dead code from day one.
- **No tmux/spawn/lock logic implemented here** (explicitly out of scope
  per the task brief) — `spawnSession` is an injected async callback; the
  real tmux-preferring spawner (§7.3) and the singleton lock (§7.1 sibling
  bullet, `.worktrees/P1-1.5-daemon-singleton-lock`) are separate,
  independently-landing pieces.

## Assumptions

- The `/session-started` payload's `sessionId` is Falcon's own session
  identifier (minted by `POST /v1/sessions`, per
  falcon-system-design.md §10.1 — "CLI ── POST /v1/sessions … CLI ── WS
  connect … daemon loopback /session-started"), not the provider's own
  conversation id (`providerSessionId`, e.g. Claude's `--resume` target).
  The provider session id is established later via a `SessionStart` hook →
  metadata CAS update (§10.1), not through this webhook — plan.md §7.1's
  own wording ("reports its sessionId + encryption keys back for resume")
  and Happy's actual verbatim payload (`{ sessionId, metadata, encryption
  }`) both confirm this.
- `metadata` in the `/session-started` body is left as `z.unknown()` —
  there's no Falcon-side `Metadata` wire schema yet (Happy's own is a loose
  `Metadata` type, not strictly validated at this layer either); typing it
  precisely is deferred to whichever task defines that schema.
