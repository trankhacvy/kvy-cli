# U4.6 — session-registration (W4.4 + W4.5 — bootstrap/start)

No prior commits existed on this branch for U4.6 (`git log v2-pty-injection..HEAD`
was empty in the worktree at task start) — this is a from-scratch implementation,
not a continuation.

## What changed

### W4.4 — same-directory duplicate session lock

New `packages/cli/src/session/sessionLock.ts`: an exclusive,
per-`(machineId, workspacePath)` lock at
`~/.falcon/locks/session-<sha256(machineId|path)>.lock`. Ported/generalized the
existing `daemon/lock.ts` hard-link + stale-pid-reclaim pattern (same
"why a hard link" rationale, same corrupt/stale reclaim re-check races) instead
of writing a new locking primitive from scratch — reuses `daemon/lock.ts`'s
`isProcessAlive` directly rather than duplicating it.

One deliberate divergence from a literal port: the daemon singleton lock knows
its full payload (`pid`, `port`, `version`, `startedAt`) at acquire time, but a
session lock must be taken *before* `bootstrapSession()` mints/reuses a
`sessionId` (that's the whole point — lock the directory before the network
round trip, so two concurrent `falcon claude` invocations in the same directory
can't both proceed to bootstrap). So the payload's `sessionId` starts `null` and
`SessionLockHandle` gained a second method, `updateSessionId()`, that rewrites
the lock file (tmp-write + rename, ownership-checked the same way `release()`
is) once bootstrap resolves — so a later contender prints a real session id
instead of "unknown". This is noted as an intentional adaptation, not a plan
snippet deviation (the plan gave prose for W4.4/W4.5, no code snippet to diverge
from).

Wired into `commands/start.ts`'s `runStartClaudeCommand`:
- `--force-new-session` is parsed out of `deps.claudeArgs` at the very top of
  the function (Falcon's own flag — never Claude Code's — so it must never
  reach the real `claude` CLI; same "intercept our own flag before passthrough"
  precedent as `claudeLocal.ts`'s `--resume`/`--continue` interception, just for
  a flag Claude Code doesn't know about at all). The filtered array is used
  everywhere `deps.claudeArgs` previously was (PTY session, remote loop,
  `detectStartingMode`).
- If not force-bypassed, the lock is acquired right after `machineId` is known
  and right before `bootstrapSession()`'s nonce mint. `held-by-running-process`
  prints the existing session id (or "unknown session id" if the holder hasn't
  called `updateSessionId()` yet) + pid + "attach from the web, or run in
  another directory" + the `--force-new-session` escape hatch, then exits 1.
  `contended` (lock-acquisition race exhausted its retry budget) is a distinct
  honest error, also exit 1.
- The lock is released in every exit path after acquisition: the
  `bootstrapSession()` failure catch, and the outer `finally` alongside the
  existing `sessionClient.stop()`/`outbox.dispose()`.
- Scope decision: applied uniformly to both the terminal PTY flow and the
  daemon-spawned `--starting-mode remote` flow (the check runs before
  `detectStartingMode()`'s fork), since the directory-level guard is meaningful
  for both — this also naturally covers the daemon's own resume path
  (`FALCON_RECONNECT_SESSION_ID`) without special-casing: a resumed session's
  prior holder is normally dead by then, so the existing stale-pid reclaim
  handles it transparently. Not wired into `startCodex.ts` — out of this
  bundle's stated scope (W4.4/W4.5 name `bootstrap.ts`/`start.ts` specifically;
  Codex has no local/terminal mode to duplicate-guard against yet).

### W4.5 — register PTY sessions with the daemon

`daemon/notify.ts`'s `notifyDaemonSessionStarted` (already built + fully
unit-tested, zero callers per the plan) is now called from
`runStartClaudeCommand` right after `bootstrapSession()` resolves (both flows,
since it's above the `runLocalPty`/`runRemoteLoop` fork) — best-effort per its
own contract (never throws; a debug log records the typed result either way,
so "daemon absent" is visible in `~/.falcon/logs/` without being an error).

The wrapped-DEK for the `encryption.encryptionKey` field is computed locally
(`wrapDek(bootstrap.dek, contentKeyPair.publicKey)`, `encodeBase64`'d) since
`BootstrapSessionResult` only returns the unwrapped `dek`. `seq` /
`metadataVersion` / `agentStateVersion` are sent as `0` — this matches the
server schema's own defaults for a freshly created (or freshly reattached) row;
reconciling those counters as the session progresses is a separate concern this
startup self-report doesn't attempt (noted honestly in the code comment, not
silently assumed correct). `metadata` reuses the same `{title, path}` object
already built for `bootstrapSession`'s own metadata param (factored into a
shared `sessionMetadata` const).

## Tests

- `packages/cli/src/session/sessionLock.test.ts` (new): key/path determinism +
  NUL-boundary collision guard; fresh acquire; refused-while-live with the
  existing payload surfaced; stale (dead-pid, via a real spawned-and-reaped
  child) reclaim; corrupt-file reclaim; `release()` idempotency and its
  ownership guard (a stale "owner" releasing after a real reclaim must not
  delete the new owner's lock); `updateSessionId()` visible to a later
  contender, and its own no-op-after-release guard.
- `packages/cli/src/commands/start.test.ts` (new describe block): held-by-live
  process → exit 1 with session id + pid in the message; "unknown session id"
  when the existing payload's `sessionId` is still `null`; `contended` → exit 1;
  `--force-new-session` skips the lock entirely and is stripped before reaching
  the PTY session's `claudeArgs`; successful bootstrap → `updateSessionId()` +
  `notifyDaemonSessionStarted()` called with the right `sessionId`/wrapped-DEK,
  lock released after; lock released even when `bootstrapSession()` throws;
  daemon self-report being `unreachable` never blocks a successful start (exit
  0 either way).
- `baseDeps()` in `start.test.ts` gained safe default fakes for both new
  injectable deps (`acquireSessionLock`, `notifyDaemonSessionStarted`) so every
  pre-existing test in that file keeps working without real fs/network access
  (the real `acquireSessionLockDefault` was crashing pre-existing tests that
  use a fictional `/fake/home` — fixed by defaulting to a fake, not by changing
  those tests' `homeDir`).

## Gaps / follow-ups (not silently skipped, explicitly out of scope here)

- `startCodex.ts` doesn't take the directory lock — Codex has no local mode to
  duplicate-guard against today; if/when it gains one, wiring should mirror
  `start.ts`'s.
- `seq`/`metadataVersion`/`agentStateVersion` sent to the daemon are placeholder
  `0`s at startup, not live-tracked counters — matches the plan's stated scope
  ("with pid/sessionId/wrapped-DEK") and the server's own defaults; a future
  task that needs the daemon to see live counters would need to thread them
  through separately.
