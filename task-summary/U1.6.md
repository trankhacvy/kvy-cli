## W1.9 — auth-gate the session routes

`packages/web/src/features/auth/require-auth.tsx` (new) extracts the "checked" gate
`app/page.tsx` / `settings/recovery/page.tsx` / `settings/notifications/page.tsx`
each already hand-roll (`isSignedIn()` check inside a `useEffect`, `router.replace`
to sign-in, `checked` state gating the render so `children` never flashes even for
one frame on a client-side navigation). Exposes `RequireAuth`, plus
`shouldRedirectToSignin` (the pure boolean the effect calls) and `SIGNIN_PATH` (the
redirect target constant) for testability, re-exported via
`packages/web/src/features/auth/index.ts`.

**Drift from plan-v2.md's snippet:** the snippet imports `isSignedIn` from
`@/features/auth` — that module doesn't exist. The real implementation lives at
`@/lib/session` (confirmed via `grep -rn isSignedIn`, used by `app/page.tsx` and both
settings pages). `RequireAuth` imports it from there instead. The plan's version also
computes `signedIn` directly at render time rather than via an effect-gated
`checked` state; I matched the codebase's actual established idiom (see
`app/page.tsx`, `settings/recovery/page.tsx`) instead, since that's what the other
three call sites already do and what avoids the render-time flash the plan's own
problem statement is about.

Wrapped the three target page components in `RequireAuth`:
- `packages/web/src/app/session/[id]/page.tsx`
- `packages/web/src/app/session/[id]/git/page.tsx`
- `packages/web/src/app/session/new/page.tsx`

All three stay otherwise unchanged (`/session/[id]` and `/session/[id]/git` remain
async Server Components with `generateStaticParams`; `RequireAuth`, a Client
Component, composes fine as their child per Next's normal server/client
composition).

## W1.10 — error boundaries + decrypt-failure surface

- `packages/web/src/app/error.tsx` (new): App-Router error boundary
  (`{error, reset}` props, "Try again" button wired to `reset()`).
- `packages/web/src/app/not-found.tsx` (new): App-Router 404 page, link back to `/`.
- `packages/web/src/features/session-control/use-live-render-items.ts`: now returns
  `{ items, error }` instead of a bare `RenderItem[]`. A total decrypt-pipeline
  failure (the existing `console.error`-only catch block) now also calls the new
  `setError(formatDecryptError(err))`; both `items`/`error` reset together on a
  session switch (existing biome-ignore'd reset effect, extended).
- `packages/web/src/features/session-control/decrypt-error.ts` (new):
  `formatDecryptError(err: unknown): string` — pulled out of the hook's catch block
  so the message-shaping logic is unit-testable without mounting the hook (this
  package has no DOM test environment; see "Tests" below).
- `packages/web/src/components/timeline/SessionTimelineScreen.tsx`: destructures
  `{ items, error: decryptError }` from the hook, threads `decryptError` +
  a `retryDecrypt` callback (`queryClient.invalidateQueries({ queryKey:
  messagesQueryKey(sessionId) })`, exactly the plan's snippet) down to
  `SessionTimelineBody`, which renders an inline destructive banner + "Retry"
  button right below the header when `decryptError` is set.

Both new export surfaces (`formatDecryptError`) are re-exported through
`features/session-control/index.ts` alongside the rest of that barrel.

## Tests

- `packages/web/src/features/auth/__tests__/require-auth.test.ts`: redirect logic
  (`shouldRedirectToSignin(true/false)`) + locks `SIGNIN_PATH` to `"/signin/"`.
- `packages/web/src/app/__tests__/error.test.ts` /
  `packages/web/src/app/__tests__/not-found.test.ts`: boundary components, rendered
  via `react-dom/server`'s `renderToStaticMarkup` (same technique
  `lib/markdown.test.ts` already uses to avoid needing jsdom) — asserts the error
  message/fallback text and the "Try again"/"Back to sessions" controls render.
- `packages/web/src/features/session-control/__tests__/decrypt-error.test.ts`:
  `formatDecryptError` — real `Error` message, empty-message `Error`, non-`Error`
  throw, `undefined`/`null`, all falling back to the generic message where
  appropriate.

**Test-infra change required:** `packages/web/vitest.config.ts` gained
`esbuild: { jsx: "automatic" }`. `tsconfig.json` sets `"jsx": "preserve"` (Next's own
SWC compiler does the real transform; `tsc` never touches it) and there's no
`@vitejs/plugin-react` registered in the vitest config, so without this, Vite's
esbuild pretransform left `.tsx` JSX as classic `React.createElement(...)` calls
with no matching `React` import (the app uses the automatic runtime everywhere,
same as Next) — `error.test.ts`/`not-found.test.ts` are this package's first tests
to actually render a project `.tsx` component's JSX rather than only import plain
functions from one, so this gap existed but was never hit before. Fixed at the
config level rather than adding an explicit `import React from "react"` to just
these two files, which would have been inconsistent with every other component in
the app.

  edited files against `biome.json` (double quotes, semicolons, trailing commas,

  `settings/notifications/page.tsx`) — all consistent.
