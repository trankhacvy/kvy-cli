# P1-1.3-cli-package-scaffold — CLI skeleton: arg parsing, flag passthrough, file-only logger

Scaffolds `packages/cli` (bin name `falcon`): the first, unchecked bullet of
plan.md §16 **"1.3 CLI skeleton + local mode"** — `packages/cli` scaffold with
hand-rolled arg parsing, `falcon` / `falcon claude [args]` / `falcon codex
[args]` with full flag passthrough, and a file-only logger that never writes
stdout/stderr. Pure scaffolding per scope: no daemon, no provider spawning,
no network calls (those are later 1.3/1.5 bullets in the same section).

## What was added

```
packages/cli/
├─ package.json        # bin: falcon → ./bin/falcon.mjs; no runtime deps
├─ tsconfig.json         # extends ../../tsconfig.base.json (strict, @/* alias)
├─ vitest.config.ts
├─ bin/
│  └─ falcon.mjs         # bin shim: re-exec node --no-warnings dist/index.mjs (Happy's bin/happy.mjs pattern)
└─ src/
   ├─ args.ts            # hand-rolled parseArgs(argv) — the core deliverable
   ├─ args.test.ts        # 41 tests
   ├─ home.ts             # resolveHomeDir(): ~/.falcon or FALCON_HOME_DIR
   ├─ home.test.ts         # 4 tests
   ├─ logger.ts            # file-only logger (~/.falcon/logs/, never stdout/stderr)
   ├─ logger.test.ts        # 6 tests, incl. a spy asserting stdout/stderr are never touched
   ├─ index.ts             # entrypoint: parseArgs → stub dispatch; exported main() for testing
   └─ index.test.ts         # 5 tests
```

56 tests total, all passing. `pnpm --filter falcon build` (tsc --noEmit +
pkgroll → `dist/index.mjs`) and `pnpm --filter falcon typecheck` both pass.
Manually ran the built bin (`node packages/cli/bin/falcon.mjs …`) to confirm
`--help`, `--version`, `claude --resume abc123 --model opus` (passthrough),
and a malformed `resume` (usage error, exit 1) all behave as expected, and
that only `~/.falcon/logs/*.log` receives internal diagnostics — never
stdout/stderr.

## Implementation notes

- **Hand-rolled arg parsing (`src/args.ts`), no framework** — per
  falcon-plan.md §6.1 / plan.md §16: "hand-rolled arg parse (Happy does
  this, no framework)". A framework (commander/yargs) wants to own and
  validate every flag, which is exactly wrong for `falcon claude [args...]`
  where *every* flag must reach the provider CLI untouched. `parseArgs`
  returns a discriminated union `FalconCommand`; malformed **Falcon-level**
  commands (e.g. `falcon resume` with no id) throw a typed `ArgParseError`
  carrying a `usage` string — never a silent failure. Provider passthrough
  (`claude`/`codex`) never throws on unrecognized flags — it doesn't
  interpret them at all.
- **Passthrough semantics, precisely.** Two entry points reach `{ type:
  "start" }`:
  - `falcon claude [args...]` / `falcon codex [args...]`: once the literal
    provider name is consumed, every remaining token — including flags that
    happen to look like Falcon's own (`-b`, `--help`) — is forwarded
    verbatim as `providerArgs`. Verified by a test that `falcon claude -b
    feature/x` does **not** extract `-b`, unlike the bare-`falcon` form.
  - `falcon [args...]` (no recognized subcommand as the first token):
    defaults to provider `claude`, and extracts only Falcon's own `-b
    <branch>`/`--branch <name>` flag (PRD §5.3 row 3: "start the session on
    a new git worktree/branch") before forwarding the rest verbatim. This
    is what makes both `falcon --resume <id>` and `falcon -b feature/x`
    work without naming a provider.
  - Top-level `--help`/`-h`/`--version`/`-v`/`-V` are checked before the
    provider check, so `falcon --help` shows Falcon's help but `falcon
    claude --help` correctly forwards `--help` to Claude Code.
- **Other subcommands are parsed but stubbed.** The full command surface
  from PRD §5.3 (`auth login|logout|status`, `daemon start [--no-wait]|
  stop|status`, `kill daemon|sessions|all|all-force`, `sessions list`,
  `resume <id>`, `workspace config [--base-ref|--remote|--directory]|sync`,
  `notify -p <msg>`) is recognized and validated by `parseArgs` (so the
  parser's shape matches the full CLI surface up front), but `src/index.ts`
  dispatches each to a `"not implemented yet"` stub — no daemon control, no
  auth, no network, per this task's explicit scope. `workspace sync`
  prints "cloud sync coming soon" per PRD §5.3's own stub wording (it's a
  `[P2]` MVP non-goal).
- **File-only logger (`src/logger.ts`)** — writes newline-delimited JSON to
  `~/.falcon/logs/falcon-YYYY-MM-DD.log` (or under `FALCON_HOME_DIR`), and
  is architecturally incapable of writing to stdout/stderr (no
  `console.*`/`process.std{out,err}` call anywhere in the module).
  `logger.test.ts` spies on `process.stdout.write`/`process.stderr.write`
  and asserts they're never called across debug/info/warn/error. This
  matters now, and is load-bearing later: once local-mode session spawning
  lands (plan.md §6.3), Falcon inherits its stdio into the real provider
  child (`stdio: ['inherit','inherit','inherit','pipe']`) — any stray
  logger write on those descriptors would corrupt the Claude Code TUI.
  Level gating: `debug` only when `FALCON_DEBUG=1` (or `{debug:true}`
  passed to `createLogger` for tests) — everything else defaults to `info`+.
  Writes are synchronous (`appendFileSync`) — CLI invocations are
  short-lived and low-volume, so a blocking write is simpler and safer than
  a buffered stream that could lose lines on an abrupt `SIGTERM` mid
  local↔remote handoff.
- **This is *not* the same rule as "no stdout at all."** `src/index.ts`
  writes help text, `--version`, command stubs, and usage errors directly
  to stdout/stderr — that's ordinary, necessary CLI UX, not logging, and is
  unaffected by the logger's rule. The distinction is documented inline in
  both modules so a future contributor doesn't "fix" index.ts's stdout
  writes into logger calls (which would silence normal CLI output) or vice
  versa.
- **`~/.falcon` home resolution (`src/home.ts`)** — `resolveHomeDir()`
  defaults to `~/.falcon`, overridden by `FALCON_HOME_DIR` (trimmed,
  blank-safe, resolved to an absolute path). Kept as its own tiny module
  (rather than inlined in the logger) because later 1.3 bullets
  (`settings.json`, `access.key`) need the same resolution and this task
  is scaffolding for those, not implementing them.
- **Bin shim (`bin/falcon.mjs`)** — re-execs `node --no-warnings
  dist/index.mjs`, mirroring Happy's `bin/happy.mjs` (falcon-plan.md §6.1:
  "bin shim that re-execs node with `--no-warnings`... keeps stdout
  clean"). `--no-warnings` suppresses Node's experimental-feature banners
  on stdout/stderr — the same channel-hygiene concern as the logger, for a
  different source. `spawnSync(..., { stdio: 'inherit' })` + propagate the
  child's exit code (or 1 if `spawnSync` itself failed to launch node).
- **`main(argv)` is exported and testable** without a real process. A
  top-level guard (`process.argv[1] === fileURLToPath(import.meta.url)`)
  only calls `process.exit(main())` when the module is run directly, not
  when imported by vitest — so `index.test.ts` can assert on return codes
  and spy on stdout/stderr without an actual `process.exit()` killing the
  test runner.
- **`package.json`** — bin entry `"falcon": "./bin/falcon.mjs"`; `main`
  points at `dist/index.mjs` for consistency with the other packages (not
  actually consumed as a library import anywhere yet). No runtime
  dependencies at all — hand-rolled parsing needs none, and file logging
  only needs `node:fs`/`node:path`. Dev deps (`pkgroll`, `shx`, `tsx`,
  `typescript`, `vitest`, `@types/node`) mirror `@falcon/server`'s exact
  versions for consistency.
- **Build/tsconfig** — identical `shx rm -rf dist && tsc --noEmit &&
  pkgroll` pattern and `tsconfig.json` (extends
  `../../tsconfig.base.json`, `@/*` → `./src/*`) as `@falcon/wire` /
  `@falcon/crypto` / `@falcon/server`. `pkgroll` warns
  `Ignoring file outside of dist directories` for the `bin` field — expected
  and harmless, since `bin/falcon.mjs` is a hand-written static shim, not
  something pkgroll bundles.
- **Workspace/turbo/CI wiring** — none needed. `pnpm-workspace.yaml`
  already globs `packages/*`; `turbo.json`'s task pipeline is generic
  (`build`/`typecheck`/`test`/`lint`); CI's explicit steps only special-case
  `@falcon/wire` (built first as a shared dependency) and otherwise run the
  generic `pnpm typecheck`/`pnpm test`, which now include `falcon`
  automatically. `pnpm install` updated `pnpm-lock.yaml`.
- Updated root `CLAUDE.md`'s package-layout table: `cli/` moves out of
  `[planned]` to describe what actually exists (arg parsing, passthrough,
  file logger), noting auth/daemon/provider spawning are still planned —
  per that file's own instruction to update it as each phase lands.

## Assumptions

- **Command name is `falcon`, package name is also `falcon`** (not
  `@falcon/cli`) — matches the design's own bin-name convention (`falcon`,
  not scoped) and how npm resolves an unscoped global bin; `private: true`
  since it's not published as a library.
- **Default provider is `claude`** when no provider is named (PRD §5.3 row
  1: "default provider: last used, else Claude Code"). "Last used" tracking
  requires `settings.json` persistence, which is out of scope for this
  task — deferred to a later 1.3 bullet; `claude` is the correct fallback
  either way.
- **`-b`/`--branch` is a Falcon-level flag only in the default-start form**,
  not after an explicit `claude`/`codex` name — this follows directly from
  "ALL unknown flags pass through verbatim" for the explicit-provider case,
  and is covered by a dedicated test (`does not intercept -b when it
  appears after an explicit provider name`).
- **Full command-surface stubs, not just `claude`/`codex`.** The task
  description's core ask is arg-parsing + passthrough + logger; I chose to
  give `parseArgs` full coverage of PRD §5.3's command table (rather than
  only `claude`/`codex`/`-b`) so the "hand-rolled arg parse... subcommand
  table" design intent is visible now, while keeping every non-passthrough
  handler an honest `"not implemented yet"` stub with zero daemon/network
  logic — consistent with "pure scaffolding" scope.
- **Logger format is structured JSON lines** (`{time, level, message,
  meta?}`), not a framework like pino. The design doc doesn't mandate a
  format, only "file-only... never stdout"; JSON lines are simple to grep
  and parse, need zero dependencies, and match the hand-rolled spirit of
  this package (as opposed to pulling in pino, already used by
  `@falcon/server` for a different reason — Fastify's logger *is* pino
  there).
- **No `NOTICE`/Happy attribution added.** Nothing here is a verbatim port
  of Happy source (no Happy source tree is present in this repo to port
  from); the bin shim and arg-parsing approach are described in prose in
  falcon-plan.md/plan.md and reimplemented from that description, not
  copied from a `happy/` checkout. Verbatim-port packages (`@falcon/wire`,
  `@falcon/crypto`) already carry their own attribution.
