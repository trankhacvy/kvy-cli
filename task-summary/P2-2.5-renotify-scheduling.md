# P2-2.5-renotify-scheduling

Phase 2 — Control: steer from the web (M2), §2.5 Notifications (plan.md §10 / design §6.4).

## What this closes

`P2-2.5-notifications-dispatch` (merge `5310de0`, already on `main`) implemented lifecycle
dispatch + presence suppression + Web Push, but left one clause of the design's "Server
dispatch" bullet unimplemented: **re-notify an unanswered permission-request push at +5 min
and +10 min, capped at 3 total notifications** (design §6.4: "Re-notify unanswered
`perm-request` at +5 min, +10 min (max 3)"). This task adds that piece.

## Implementation

- **`packages/server/src/app/push/renotify.ts` (new)** — `createRenotifyScheduler()`, a small
  per-session timer tracker:
  - `onDispatch({ sessionId, kind, retry })` first cancels any timers already pending for that
    `sessionId` (a later lifecycle event for the same session always supersedes a stale
    schedule), then — only if `kind` is `"perm"` or `"question"` — arms two `setTimeout`s (+5
    min, +10 min) that call `retry()`. Both timers are `.unref()`'d so a pending re-notify never
    keeps the process alive on its own.
  - `question` is included alongside `perm` because design §6.4 itself defines an "agent
    question" as "a perm-request with `name: 'AskUserQuestion'`" — both are lifecycle kinds
    that await a human answer; `done`/`failed` are terminal and never scheduled.
  - `cancelAll()` clears every pending timer (useful for shutdown/tests).
  - `retry()` rejections are caught and logged (`console.error`), never thrown — matches
    `dispatch.ts`'s existing "never rejects" contract.

- **`packages/server/src/app/push/dispatch.ts` (modified)** — `buildPushDispatcher` now:
  1. Creates one `RenotifyScheduler` per dispatcher instance.
  2. Extracted the existing presence-check + subscription-fanout body into an internal
     `attempt()` function (unchanged behavior — same presence fail-open, same per-channel
     catch/prune-on-410 logic).
  3. `dispatch()` runs `attempt()` once immediately (the existing behavior, now the "1st of up
     to 3" notification), then calls `scheduler.onDispatch(...)` with a `retry` closure that
     re-runs `attempt()` with the same params. Each follow-up attempt re-checks presence fresh
     at fire time — a follow-up is suppressed **exactly the same way** the initial dispatch is
     (per the task's instruction), there is no separate "answered" tracking mechanism.

- No other files were touched. `buildPushDispatcher(db, presence)`'s signature is unchanged, so
  `server.ts` and the two call sites (`sessionStatus.ts`, `sessionNotify.ts`) needed no changes.

## Design decisions / assumptions

- **No explicit "answered" signal.** The server never sees plaintext permission state —
  `agentState` is an E2E-encrypted CAS blob (design §5.3) and the actual perm-answer RPC
  (`perm.answer`, plan.md §9) is a daemon/CLI-side handler, not an HTTP call into this server.
  The task's own wording — "suppressed the same way as the initial dispatch (presence/
  app-state)" — confirms presence suppression *is* the intended re-notify suppression
  mechanism, not a new answered-tracking channel. This keeps the change fully self-contained
  to `packages/server/src/app/push/**`.
- **Supersession instead of explicit cancel-on-answer.** Any subsequent `dispatch()` call for
  the same `sessionId` (any kind — a new `perm`, or a terminal `done`/`failed`) cancels a
  still-pending schedule before deciding whether to arm a new one. In practice a session has
  one outstanding perm-request at a time, so this is the natural signal that the old schedule
  is stale, without needing a dedicated "answered" event.
- **`question` treated as re-notifiable alongside `perm`** per design §6.4's framing of agent
  questions as a perm-request variant; `done`/`failed` are terminal and never scheduled.
- **Max 3 total** = the immediate dispatch + 2 scheduled follow-ups (`RENOTIFY_DELAYS_MS =
  [5min, 10min]`). No 4th attempt is ever scheduled.

## Testing

- `packages/server/src/app/push/renotify.test.ts` (new): scheduler unit tests using
  `vi.useFakeTimers()` — fires at +5/+10min, stops after 2 follow-ups, only schedules for
  `perm`/`question`, supersession cancels a stale schedule (including mid-flight restart for a
  new perm-request), independent per-session schedules, `cancelAll()`, and swallowed retry
  rejections.
- `packages/server/src/app/push/dispatch.test.ts` (extended): a new `describe("re-notify
  scheduling")` block verifies the wiring end-to-end through the real dispatcher (PGlite-backed
  db + fake presence/channel spies) — 3 total sends for an unanswered `perm`, no follow-ups for
  `done`, a follow-up suppressed by presence, and a same-session `done` cancelling a pending
  `perm` schedule.
