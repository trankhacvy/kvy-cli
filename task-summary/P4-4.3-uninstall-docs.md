# P4-4.3-uninstall-docs — Uninstall docs + cleanup guide

**Section:** Phase 4 — Ship / 4.3 Distribution & self-host
**Refs:** falcon-prd.md FR-1.6 ("Clean uninstall documented: `falcon daemon stop && falcon
kill all-force && rm -rf ~/.falcon` + platform service cleanup (launchd / systemd-user /
schtasks)"), FR-9.6 (shell shim), FR-4.1 (login-service install); plan.md §16 "4.3
Distribution & self-host" (last unchecked bullet in that section).

## What was built

`docs/uninstall.md` — a user-facing uninstall/cleanup walkthrough, in the same style as
`deploy/README.md`. Docs-only; no source files touched, no shared modules changed, so this
ran fully independent of the other two 4.3 tasks it depends on for content
(`P4-4.3-daemon-service-install`, `P4-4.2-shell-shim` — both already landed on `main` per
`plan.md`).

Sections:

1. **Quick uninstall** — the FR-1.6 one-liner up front (`falcon daemon stop && falcon kill
   all-force && rm -rf ~/.falcon`), plus the two extra opt-in steps (`falcon shim uninstall`,
   `falcon daemon service uninstall`) for anyone who installed those, plus removing the
   `falcon` binary itself (npm vs. `curl | sh` standalone).
2. **`falcon shim uninstall`** — what it does (removes `~/.falcon/bin/{claude,codex}`,
   strips the marked PATH block from *every* rc-file candidate, not just the current shell's),
   why uninstall scans more rc files than install writes, and the "restart your shell"
   caveat.
3. **`falcon daemon service uninstall`** — per-platform behavior (launchd `bootout` + plist
   delete vs. systemd `disable --now` + unit delete + `daemon-reload`), and why these paths
   are *outside* `~/.falcon` (OS service-manager locations: `~/Library/LaunchAgents/`,
   `~/.config/systemd/user/`) — so `rm -rf ~/.falcon` alone doesn't undo this step, which is
   why it's ordered before it. Also notes `loginctl enable-linger` isn't auto-disabled.
4. **Stop everything still running** — `falcon daemon stop` (graceful) vs. `falcon kill
   all-force` (process-scan-based escape hatch, no daemon/state-file dependency) and why the
   force variant is what you want right before deleting `~/.falcon`.
5. **`rm -rf ~/.falcon` — what's actually in there** — a table of every file/dir Falcon
   writes under its home directory (`settings.json`, `access.key`, `daemon.lock`,
   `daemon.state.json`, `sessions.json`, `workspaces.json`, `bin/`, `logs/`, `outbox/`),
   sourced by reading `home.ts`/`persistence.ts`/`daemon/{lock,state,sessionsStore}.ts`/
   `workspace/registry.ts`/`logger.ts`/`api/queue.ts` directly rather than guessing. Notably
   corrects the task brief's "sockets" framing: Falcon's control server is a loopback TCP
   listener on an OS-assigned port (`controlServer.ts`, `127.0.0.1:0`), not a Unix domain
   socket — there's no socket *file* to clean up, just `daemon.lock` (singleton guard) and
   `daemon.state.json` (published pid/port), both already covered by the directory delete.
6. **What uninstalling does *not* do** — Claude Code's/Codex's own config is untouched (Falcon
   never stores provider credentials of its own, FR-2.6); the server-side machine/account
   record has no deregister endpoint yet (verified: `packages/server/src/app/routes/
   machines.ts` only exposes `POST`, no `DELETE`) — a stopped daemon just goes stale/offline,
   documented honestly as a gap rather than glossed over; git worktrees/branches Falcon
   created are the user's own repo state, not `~/.falcon`.
7. **Troubleshooting** — three practical gotchas (per-user service scope, stale shell PATH
   cache, running-process file handles during `rm -rf`).

Also updated `CLAUDE.md`'s "Docs" list (the existing index of `docs/*.md` pointers) to add a
one-line entry for `docs/uninstall.md`, matching the existing `docs/protocol.md`/
`docs/encryption.md`/`deploy/README.md` entries' style.

## Design notes / assumptions

- **No root-level `README.md` exists in this repo** (only `deploy/README.md`, which is
  self-host-specific). Rather than inventing a new top-level README as part of a docs-only
  task, this follows the existing precedent of small `docs/*.md` pages (`protocol.md`,
  `encryption.md`) indexed from `CLAUDE.md`'s "Docs" section — same place a future root
  README would point readers anyway.
- **Every path and command in the doc was verified against the actual source**, not assumed
  from the task brief or PRD prose alone: `~/.falcon`'s file list came from grepping every
  `path.join(homeDir, ...)` call in `packages/cli/src`; the shim/service uninstall behavior
  descriptions came from reading `shim/uninstall.ts`, `shim/paths.ts`, `shim/rcBlock.ts`,
  `daemon/serviceInstall.ts`, and `daemon/serviceInstallPaths.ts` directly; `falcon kill
  all-force`'s process-scan-based (not state-file-based) discovery came from `daemon/kill.ts`'s
  doc comment.
- **"Sockets" in the task brief** doesn't map to a literal Unix domain socket file in this
  codebase — the daemon's control server is TCP-on-loopback (`controlServer.ts`). The doc
  says so explicitly rather than silently inventing a socket-file cleanup step that doesn't
  exist, or silently dropping the word from the brief without explanation.
- **Scope boundary:** this task only documents the three already-implemented pieces (shim
  uninstall, daemon service uninstall, `rm -rf ~/.falcon`) — it does not add a server-side
  "deregister machine" endpoint or a `falcon account delete` command; both are called out
  honestly in the "what uninstalling does not do" section as documented gaps, not implemented
  here (out of scope for a docs task).
