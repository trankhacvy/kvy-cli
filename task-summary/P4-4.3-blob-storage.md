# P4-4.3-blob-storage — Blob storage: presigned upload/download routes + S3/local-disk drivers

**Section:** Phase 4 — §4.3 Distribution & self-host
**Status:** implemented, `pnpm build`/`pnpm typecheck` green across all 5 packages; `pnpm test` green except one pre-existing, unrelated flaky integration test (see "Known issues" below).

## What was built

This was the largest fully-unchecked, self-contained block of work in `plan.md`, with no prior branch. It touches five packages: `@falcon/crypto`, `@falcon/wire`, `@falcon/server`, `falcon` (CLI/daemon), `@falcon/web`.

### 1. `@falcon/crypto` — blob key derivation

- `packages/crypto/src/keys.ts`: new `deriveBlobKey(dek)` — `HKDF(DEK, "falcon-blobs")` per falcon-system-design.md §5.1, reusing the existing `deriveDomainSeed` HMAC-SHA512 construction but rooted in a DEK instead of the master secret. Exported from both `index.ts` (node) and `index.web.ts` (browser) — the derivation itself is platform-agnostic. `encryptBlob`/`decryptBlob` already existed (an earlier task's verbatim Happy port) and needed no changes.
- Tests: `packages/crypto/src/__tests__/keys.test.ts` — determinism, correct length, round-trips through `encryptBlob`/`decryptBlob`, isolation from other key-tree domains.

### 2. `@falcon/wire` — REST contract

- `packages/wire/src/blobs.ts` (new): `BlobRequestUploadBodySchema`/`Result`, `BlobRequestDownloadBodySchema`/`Result` — the `POST /v1/blobs/request-upload` / `POST /v1/blobs/request-download` contract from falcon-system-design.md §6.2. Registered in the wire-shapes additive-only-compat fixture (`schemaRegistry.ts` + regenerated `wire-shapes.json`).

### 3. `@falcon/server` — the storage subsystem itself

- `packages/server/src/blobStorage/types.ts`: `BlobStorageDriver` interface — `createUploadTarget`/`createDownloadTarget`, two methods, driver-agnostic.
- `packages/server/src/blobStorage/s3Driver.ts`: S3-compatible driver using `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` (presigned PUT/GET). Works unmodified against AWS S3, Cloudflare R2, and MinIO (self-host) — `forcePathStyle` is the one MinIO-specific knob.
- `packages/server/src/blobStorage/localToken.ts`: short-lived HMAC tokens (hand-rolled, not JWT — narrow claim set, single consumer) authorizing one PUT/GET against the local-disk sink; embedded in the URL query string, the local-disk equivalent of an S3 presigned URL's SigV4 signature.
- `packages/server/src/blobStorage/localDriver.ts`: local-disk driver — mints URLs pointing back at this server's own `/v1/blobs/local/:id` sink; `writeLocalBlob`/`readLocalBlob`/`deleteLocalBlob` do the actual tmp-write-then-rename I/O, with path-traversal defense-in-depth on the blob key.
- `packages/server/src/blobStorage/index.ts`: `buildBlobStorage(env)` — driver selection (`S3_BUCKET` set ⇒ S3, unset ⇒ local-disk, per design §6.5 "blobs fall back to local disk when unset"). `resolveLocalDriverConfig(env)` shared between the factory and the routes.
- `packages/server/src/app/routes/blobs.ts`: three routes —
  - `POST /v1/blobs/request-upload` (authenticated): validates size against `BLOB_MAX_SIZE_BYTES`, validates an optional `sessionId`'s ownership, inserts a `blobs` accounting row (already existed in schema from an earlier task), asks the driver for an upload target.
  - `POST /v1/blobs/request-download` (authenticated): looks up an owned `blobs` row, asks the driver for a download target. 404s (not 403) for both "doesn't exist" and "not yours" — same non-leaking convention as every other route in this codebase.
  - `PUT`/`GET /v1/blobs/local/:id` — the local driver's own sink, only mounted when that driver is active. Token-authorized (query string), not `app.authenticate` — same trust model as a real presigned URL. The PUT handler cross-checks the uploaded byte length against the size declared at `request-upload` time.
- `packages/server/src/config.ts`: new env vars — `S3_BUCKET`/`S3_REGION`/`S3_ENDPOINT`/`S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY`/`S3_FORCE_PATH_STYLE`, `BLOB_LOCAL_DIR` (default `~/.falcon/server/blobs`), `BLOB_LOCAL_TOKEN_SECRET` (falls back to `FALCON_MASTER_SECRET`), `BLOB_URL_EXPIRY_SECONDS` (300), `BLOB_MAX_SIZE_BYTES` (64 MiB), `PUBLIC_API_ORIGIN` (optional, for building local-driver URLs behind a proxy). A `.refine` fails fast at boot if `S3_BUCKET` is set without both credentials (half-configured S3 is a config error, not a "fall back to local" signal).
- `packages/server/src/app/server.ts`: wires `buildBlobsRoutes` in, with `blobStorage`/`blobLocalConfig` as injectable `buildServer()` deps (tests never touch real S3 or `~/.falcon`).
- Tests: `blobStorage/{localToken,localDriver,index}.test.ts`, `app/routes/blobs.test.ts` (S3-backed via a fake driver + full local-disk end-to-end round trip through real HTTP `app.inject()` calls, including a token-tampering/wrong-op/size-mismatch coverage). `config.test.ts` extended for the new env vars.

### 4. `falcon` (CLI/daemon) — landing the reserved `blobRef` fields

- `packages/cli/src/daemon/blobClient.ts` (new): daemon-side HTTP client — `uploadBlob`/`downloadBlob`, encrypt/decrypt with `encryptBlob`/`decryptBlob` + a caller-supplied blob key, talk to the server's REST routes. **Best-effort by design**: every failure mode resolves `null` rather than throwing (mirrors `unmanagedSessionClient.ts`'s established "background side channel, log and return a falsy sentinel" contract) — a failed blob upload must never break the RPC handler that was about to serve a truncated/chunked fallback anyway.
- `packages/cli/src/daemon/gitDiff.ts`: `GitDiffDeps.uploadBlob` — when a diff is truncated, the *full* diff is also uploaded (best-effort) and `blobRef` set alongside the still-served truncated `inline` preview. Untruncated diffs never touch the blob path.
- `packages/cli/src/daemon/transcriptMirror.ts`: `TranscriptMirrorDeps.uploadBlob` — on the *first* page of a mirror that doesn't fit in one chunk, the whole transcript is uploaded once (not re-uploaded on subsequent cursor pages) and `blobRef` set alongside that first chunk. The chunked path is unconditional and correct on its own regardless — this is purely an efficiency addition, matching the precedent both handlers' prior doc comments already established.
- `packages/cli/src/daemon/machineIntegration.ts`: wires `uploadBlob` into both handlers — derives this machine's blob key via `deriveBlobKey(dek)` (the same machine DEK every other machine RPC's params/results are already sealed under) and binds `blobClient.ts`'s `uploadBlob` to this machine's server credentials. `git.diff` is now passed explicitly into `registerMachineRpcHandlers` (previously relied on its dependency-free default).
- Tests extended: `gitDiff.test.ts` (+3), `transcriptMirror.test.ts` (+5), new `blobClient.test.ts` (9 tests). Full CLI suite (101 files / 993 tests) green.

### 5. `@falcon/web` — encrypted attachment path in the composer

- Crypto worker: `sealBlob`/`openBlob` request types added end-to-end — `protocol.ts` → `worker-handler.ts` (derives `deriveBlobKey(activeDek)`, calls `encryptBlob`/`decryptBlob`) → `client.ts`'s `CryptoBridgeClient`. Same never-throws-keys-out-of-the-worker trust boundary as `seal`/`open`.
- `packages/web/src/lib/api.ts`: `requestBlobUpload`/`requestBlobDownload` REST calls.
- `packages/web/src/lib/blobs.ts` (new): `uploadAttachment`/`downloadAttachment` — orchestrates encrypt-via-worker → request a target → raw `fetch` PUT/GET → (on download) decrypt-via-worker.
- `packages/web/src/features/session-control/optimistic-composer.ts`: `PendingMessage` is now a `{kind: "text"} | {kind: "file"}` discriminated union; new `buildFileEnvelope`.
- `packages/web/src/features/session-control/use-composer-state.ts`: new `sendAttachment(file)` — encrypts+uploads via the same per-session crypto bridge (`useSessionCrypto`) `useLiveSessionControl` already unwraps, then sends a `file` `SessionEnvelope` through the existing `sendMessage` RPC path (no wire/RPC changes needed — `file` events were already a first-class `SessionEventSchema` variant from earlier work).
- `packages/web/src/components/timeline/Composer.tsx`: paperclip button + hidden `<input type="file">`.
- `packages/web/src/components/timeline/FileAttachment.tsx`: closes the loop — click-to-download, decrypts via the same session blob key, saves via a `Blob`/object-URL anchor click.
- Tests extended: `optimistic-composer.test.ts` (+file-kind coverage), `crypto/__tests__/{worker-handler,client}.test.ts` (+sealBlob/openBlob coverage), new `lib/__tests__/blobs.test.ts` (5 tests). Full web suite (44 files / 370 tests) green.

## Design notes / deltas from plan.md's literal wording

- The `blobs` DB table and its `bytea` custom type already existed (an earlier task, per `plan.md`'s already-checked "Drizzle schema... blobs" bullet) — this task only added the routes/drivers on top of it.
- `git.diff`/`adopt.mirror` keep their existing truncated-inline/chunked behavior unconditionally; the blob path is additive (a `blobRef` alongside, not instead of). This matches both handlers' own prior doc comments ("efficiency improvement for later, not a correctness gap today") and avoids any behavior change for callers that don't consume `blobRef` yet.
- The local-disk driver's "presigned URL" is a self-referential URL back at this same Fastify process, HMAC-token-authorized via the query string — there's no third-party object store to presign against in self-host-without-MinIO mode, so the server plays that role itself, same posture the design doc's own self-host section describes ("blobs fall back to local disk when unset").

## Assumptions

- Blob size cap defaults to 64 MiB (`BLOB_MAX_SIZE_BYTES`), configurable — plan.md/design docs didn't specify a number; chosen to comfortably cover large diffs/transcripts/attachments while giving self-hosters an explicit dial.
- `contentHash` (SHA-256 of the *encrypted* bytes) is recorded for accounting/integrity purposes only; the server never verifies it against re-hashed content beyond what's already implicit in the local driver's size check.
- Docker Compose wiring (a separate, still-unchecked plan.md bullet) was intentionally left untouched — this task added the env vars a compose file would set, but didn't write `deploy/docker-compose.yml` itself.

## Known issues

- `packages/cli/src/daemon/commands.machineWiring.integration.test.ts` intermittently fails its `beforeAll` with a 10s hook timeout **only** when the full monorepo `pnpm test` runs all packages' vitest suites in parallel (heavy CPU contention from multiple concurrent PGlite instances) — it passes reliably (~1.2s) when run standalone (`pnpm --filter falcon exec vitest run src/daemon/commands.machineWiring.integration.test.ts`). This is pre-existing environmental flakiness (the same class of issue `packages/server/vitest.config.ts` already documents and mitigates with a bumped `hookTimeout` for its own route tests) — the file is untouched by this task and the failure is a resource-timing artifact of `beforeAll`, not a logic regression.
- `pnpm lint` (biome) fails with "Linter process terminated abnormally (possibly out of memory)" in this environment even when scoped to a single trivial file with `--no-daemon` — appears to be a sandbox memory constraint unrelated to this change; could not be verified in this session.
