# U3.1 — tool-cards

Bundle unit implementing plan-v2.md's **W3.1 (C18) "Tool-card registry parity"**:
dedicated `ToolCard`s for `WebFetch`, `WebSearch`, `NotebookEdit`, and `LS`, following
the existing `BashCard`/`ReadCard`/`GrepGlobCard` pattern, wired into
`registry.tsx`, with parsing/dispatch tests.

No prior commits existed for this unit (`git log v2-pty-injection..HEAD --oneline`
was empty at start) — built from scratch, not a continuation.

## What was built

**`packages/web/src/lib/tool-args.ts`** — four new defensive parsers, following
the file's existing "degrade to `undefined`/raw-JSON fallback, never throw" style:

- `parseWebFetchArgs` — `url`/`prompt`.
- `parseWebSearchArgs` — `query`/`allowed_domains`/`blocked_domains`.
- `parseWebSearchResults` — extracts the embedded `Links: [{"title":...,"url":...}]`
  JSON array out of Claude Code's `WebSearch` tool-result, which is a **plain text
  blob**, not structured JSON at the top level. Verified against a real transcript
  already vendored in the repo (`packages/cli/src/claude/__fixtures__/task_non_sdk.jsonl`,
  `toolu_01NeNNHZD5QYiBQCRYTUwhME`'s `WebSearch` call) rather than guessing the shape —
  this is a drift from what the plan bullet implies ("WebSearch (query + result
  list)" reads as if the output were already structured); the fixture proved
  otherwise, so the parser reads it out of the text via a regex + `JSON.parse`, and
  falls back to `undefined` (→ raw `JsonBlock`) for any other shape.
- `parseNotebookEditArgs` — `notebook_path`/`cell_id`/`new_source`/`cell_type`/`edit_mode`.
- `parseLsArgs` — `path`/`ignore`. `LS`'s own tool-result shape (also verified
  against a real fixture, `packages/cli/src/claude/__fixtures__/1-continue-run-ls-tool.jsonl`)
  is a plain indented `- entry` text tree, not an array — so the card just renders it
  verbatim (same "show it raw" precedent as `BashCard`/`ReadCard`) rather than
  re-parsing individual entries out of it.
- `readStringArray` — new general helper (parallel to the existing `readRecordArray`),
  used by the `ignore`/domain-filter fields above.

**`packages/web/src/components/timeline/tool-cards/`** — four new cards, each
following the `ToolCardShell` wrapper convention:

- `WebFetchCard.tsx` — url + prompt + the fetched result via `JsonBlock` (its
  existing "Show all"/"Show less" toggle already satisfies the plan's "collapsible
  result" ask — no bespoke `Collapsible` needed).
- `WebSearchCard.tsx` — query + a parsed result-link list (each entry as a link
  when a `url` is present), falling back to `JsonBlock` when `parseWebSearchResults`
  can't find the embedded array.
- `NotebookEditCard.tsx` — path/cell metadata + `newSource` rendered via the
  existing `DiffView` component as a pure addition (same precedent as `EditCard`'s
  handling of `Write`, which also has no "old" side).
- `LsCard.tsx` — path + the raw directory-listing text, `JsonBlock` fallback if
  output isn't a string.

**`registry.tsx`** — registered all four (`WebFetch`, `WebSearch`, `NotebookEdit`,
`LS`) in the `REGISTRY` map alongside the existing entries.

## Tests

- `packages/web/src/lib/tool-args.test.ts` — added coverage for all four new
  parsers plus `readStringArray`, including a `parseWebSearchResults` test built
  directly from the real fixture's tool-result text (not synthetic JSON), and its
  degrade-to-`undefined` cases (no `Links:` array, non-array `Links:` value,
  non-string output).
- `packages/web/src/components/timeline/tool-cards/registry.test.ts` — dispatch
  tests confirming `WebFetch`→`WebFetchCard`, `WebSearch`→`WebSearchCard`,
  `NotebookEdit`→`NotebookEditCard`, `LS`→`LsCard`.
- Followed the existing convention in this directory: only the registry dispatch
  and the one card with real interactive-body complexity
  (`AskUserQuestionToolCard.test.ts`) get direct component tests; the other simple
  display cards (`BashCard`, `ReadCard`, `GrepGlobCard`, `EditCard`, `TaskCard`,
  `TodoCard`, `McpGenericCard`) have none — the four new cards match that
  precedent and rely on the parser-level tests + registry dispatch tests instead.

## Drift from the plan snippet

The plan's W3.1 bullet describes the four cards only by their fields
("`WebFetch` (url + prompt + collapsible result)", "`WebSearch` (query + result
list)", etc.) with no code snippet to follow verbatim — unlike some other wave
sections, this one has no grounded code to diff against. All four cards and their
parsers were designed fresh, directly against this repo's existing
`BashCard`/`ReadCard`/`GrepGlobCard`/`EditCard` conventions and against real
Claude-Code transcript shapes already vendored as test fixtures
(`packages/cli/src/claude/__fixtures__/`), rather than assumed/synthetic ones —
called out above per-parser where the real shape differed from what the plan
bullet's wording might suggest (`WebSearch`'s text-blob result, `LS`'s
plain-text tree).
