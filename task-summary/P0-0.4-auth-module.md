# P0-0.4-auth-module — Server auth module: JWT mint/verify + token cache

**Section:** falcon-plan.md §16 (canonical `plan.md`) "0.4 Server foundation" —
`- [ ] Auth module: token mint/verify (JWT, RS256 or HMAC — decide), token cache`

## What was built

`packages/server/src/auth/`:

- `tokens.ts` — `mintToken(accountId, opts?)` / `verifyToken(token, opts?)`. Algorithm
  decision documented in-file: **HS256 (HMAC), not RS256**, per `jose`. Falcon MVP is a
  single server process that both mints and verifies its own tokens, so there is no
  party that needs to verify without holding the signing secret — the scenario RS256's
  asymmetric split is for. This also matches the explicit call in `plan.md` §16/§4.4:
  *"Token: short-lived JWT (jose, HS256 from FALCON_MASTER_SECRET at MVP)"*.
  - `ACCESS_TOKEN_TTL_SECONDS = 3600` (1 h), per `falcon-system-design.md` §5.2 ("JWT
    (1 h, auto-refresh)").
  - `verifyToken` never throws — invalid/expired/tampered/wrong-secret all collapse to
    `null`, mirroring the crypto package's "unwrap never throws" rule
    (`falcon-system-design.md` §5.1) and the task's null-safe/no-silent-failure
    guidance for new code.
  - Token payload is minimal: JWT `sub` = accountId, `exp`/`iat` only. No other claims —
    keeps the module genuinely DB-agnostic (no session/device/role data baked into the
    token).
- `token-cache.ts` — `TokenCache`: in-memory `Map`-backed cache from raw token string →
  verified payload, so the `authenticate` preHandler can skip re-running `jwtVerify` on
  every request from the same bearer token. Lazy expiry (checked against the token's own
  `exp` on `get`), FIFO eviction past a configurable `maxSize` (default 10k) as a simple
  memory-growth safeguard, injectable clock for tests.
- `plugin.ts` — `authPlugin`, a `fastify-plugin`-wrapped Fastify plugin that decorates
  `app.authenticate` (a preHandler) and `request.accountId`. Reads
  `Authorization: Bearer <token>`, checks the per-app-instance `TokenCache` first, falls
  back to `verifyToken`, caches the result, or replies `401` on any failure (missing
  header, malformed scheme, invalid/expired/tampered token).
- `index.ts` — barrel export (`authPlugin`, `TokenCache`, `mintToken`, `verifyToken`,
  `ACCESS_TOKEN_TTL_SECONDS`, types) for the route files that will consume this once the
  DB layer merges.

**Wiring:** `packages/server/src/app/server.ts` now does
`await app.register(authPlugin)` right after building the app and before
`healthRoutes`, so `app.authenticate` is available to any route registered afterwards
(and to routes registered by future plugins, since `fastify-plugin` breaks the usual
decorator encapsulation).

**Config:** `packages/server/src/config.ts` gained `FALCON_MASTER_SECRET` (zod, min 32
chars) with a dev-only default (`"dev-only-insecure-master-secret-change-me!!"`).
`config.test.ts` was extended to cover the new field (default value, full round-trip,
and a "too short → throws" case) — this is a real schema addition, not incidental, so
its test needed updating to keep the existing "applies defaults" / "accepts a
fully-specified valid env" tests accurate.

## Assumptions / decisions

- **Algorithm: HS256, not RS256.** Explicit per task instructions ("decide and
  document") — see rationale in `tokens.ts` and above. Revisit if a separate verifier
  (e.g. a CDN edge check) ever needs to verify tokens without holding the mint secret.
- **Secret source:** `env.FALCON_MASTER_SECRET`, read at call time (not captured at
  module load), with an explicit `opts.secret` override for test isolation — avoids the
  `vi.resetModules()` + env-mutation dance the existing `config.test.ts` pattern uses,
  which would have been awkward to require for every auth test.
- **`request.accountId` naming:** the task description says `mintToken(accountId)`;
  `plan.md`'s illustrative route snippets sometimes say `req.userId` even while the
  Drizzle table is `accounts`/`accountId` — I used `accountId` throughout (token claim,
  cache payload, decorated request field) to match the DB column name that routes will
  actually join against once `P0-0.4-drizzle-schema` merges.
- **No DB/account existence check.** Per task scope, this module is intentionally
  DB-agnostic: `mintToken`/`verifyToken`/`authenticate` never touch a database and don't
  know whether an `accountId` is real — that's the caller's job (e.g. the future
  `POST /v1/auth` challenge/response route upserts the account, then calls
  `mintToken(account.id)`).
- **Cache is per-`buildServer()` instance**, not a module-level singleton — each call to
  `buildServer()` gets its own `TokenCache`, so tests building multiple app instances
  don't leak cached tokens between them (verified in `plugin.test.ts`).
- **Added `jose` and `fastify-plugin` as new `@falcon/server` dependencies** (via
  `pnpm add … --filter @falcon/server`); `pnpm-lock.yaml` updated accordingly.
  `fastify-plugin` is needed because Fastify's default plugin encapsulation would
  otherwise hide `app.authenticate`/`request.accountId` from sibling route plugins.

## Not in scope (left for other tasks)

- `POST /v1/auth` Ed25519 challenge/response + account upsert (separate unchecked
  bullet in the same `0.4 Server foundation` section) — will call `mintToken()` from
  this module once written.
- The Drizzle `accounts` table — complete-but-unmerged in
  `.worktrees/P0-0.4-drizzle-schema`, deliberately not duplicated here.
- Refresh-token endpoint / auto-refresh client behavior (`falcon-system-design.md` §5.2
  mentions "auto-refresh" as a client-side re-mint-before-expiry concern).
