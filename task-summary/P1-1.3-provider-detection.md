## `claudeAuth.ts` — new code

Happy has no equivalent (it just launches `claude` and lets the child
handle its own login prompt). Falcon checks proactively so `detect()` can
report auth state without spawning a process, matching how the real
Claude Code CLI resolves credentials, checked in order:
1. `ANTHROPIC_API_KEY` env var (direct API-key auth).
2. `CLAUDE_CODE_OAUTH_TOKEN` env var (`claude setup-token`, headless/CI).
3. `~/.claude/.credentials.json` (the OAuth file the CLI writes on Linux,
   and elsewhere whenever the OS keychain is unavailable).
4. macOS Keychain (`security find-generic-password -s "Claude Code-credentials"`).

Every check is best-effort and swallows its own errors (unreadable file,
locked keychain, missing `security` binary) — degrades to "not
authenticated" rather than throwing.

`checkMacKeychain` is an injectable option (defaults to the real `security`
CLI check) specifically so tests are hermetic regardless of whether the
machine running them has Claude Code signed in — this repo's own dev
machine does, which the test suite exercises directly by injecting
`checkMacKeychain: () => false` and, separately, `() => true`.

## `claudeProviderAdapter.ts` — new code, PRD FR-2.7

`detectClaudeCode()` implements the `detect()` member of design §7.3's
`ProviderAdapter` interface for `claude-code`: locates the CLI, resolves
its version, checks auth, and returns
`{ installed, authenticated, version?, error? }`. `error` is set with
actionable, exact-command copy whenever `installed` or `authenticated` is
false — never a silent hang, per PRD FR-2.7:
- not installed → `CLAUDE_NOT_INSTALLED_MESSAGE` (npm/brew/curl install
  commands).
- installed but not authenticated → `CLAUDE_NOT_AUTHENTICATED_MESSAGE`
  ("run `claude` and complete the /login flow, or set ANTHROPIC_API_KEY").

`claudeCodeProvider` exports `{ id: 'claude-code', detect: detectClaudeCode }`
— deliberately **not** a class declared `implements ProviderAdapter`. The
rest of that interface (`startLocal`, `startRemote`, `listRecentSessions`,
`importTranscript`) is separate, not-yet-built plan.md work (the launcher,
`claudeLocal.ts` port, and transcript pipeline). Stubbing those methods
just to satisfy the type would be exactly the "half-finished code" this
task was told to avoid, so this file only exposes what it actually
implements.

`detect()` accepts injectable `locate`/`resolveVersion`/`checkMacKeychain`
options (defaulting to the real implementations) for the same hermeticity
reason as above — the dev machine used to build this has a real Claude
Code install, so tests that assert "not installed" or "not authenticated"
need to be able to say so regardless of host state.

## Assumptions

- Claude Code's real credential-check order (API key → OAuth token env var
  → credentials file → OS keychain) is inferred from public documentation
  of the CLI's auth mechanisms, not from Happy source (Happy doesn't check
  provider auth state at all). No live Claude Code login flow was exercised
  in tests; `claudeAuth.test.ts` verifies the layering logic and I/O
  handling, not against a real Anthropic-issued token.
- `ProviderDetectionResult` and `DetectClaudeCodeOptions` are defined
  locally in `claudeProviderAdapter.ts` rather than in `@falcon/wire`,
  since the full `ProviderAdapter` interface (which would be the natural
  home for a shared type) doesn't exist as code anywhere yet — it's
  currently only a TypeScript snippet in `falcon-system-design.md` §7.3.
