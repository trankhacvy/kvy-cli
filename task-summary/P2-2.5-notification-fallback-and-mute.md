# P2-2.5-notification-fallback-and-mute

Phase 2 — Control (M2), §2.5 Notifications (plan.md §10 / design §6.4). The two remaining
unchecked items from the section: **(1)** Telegram/ntfy fallback channels (real senders +
Telegram `/start` pairing), **(2)** per-account quiet controls (mute-all + per-session mute).

## What this closes

- Server dispatch, Web Push, and re-notify scheduling were already merged
  (`P2-2.5-notifications-dispatch`, `P2-2.5-renotify-scheduling`). `telegram.ts`/`ntfy.ts` were
  documented log-and-drop stubs, and there was no settings UI (or server route) for mute-all/
  per-session mute.
- This task: (1) makes `telegramChannel`/`ntfyChannel` real senders, adds the Telegram bot
  `/start` deep-link pairing flow (link-mint route + webhook), and (2) adds per-account
  "mute all" + per-session "mute" — plaintext DB columns the dispatcher checks directly, two
  small server routes, and a settings-page addition (mute toggles + fallback-channel controls).

## Implementation

### Fallback channels (packages/server/src/app/push/)

- **`channels/messageText.ts` (new)** — `notificationLabel(kind)` (the same fixed, kind-keyed
  labels as `public/sw.js`'s `KIND_LABELS`, kept in lockstep by convention since the two can't
  share code) and `notificationDeepLink(sessionId)` (a `/session/<id>/` link built from the new
  `PUBLIC_WEB_ORIGIN` env var, or `null` if unset — webpush doesn't need this since its service
  worker already knows its own origin, but Telegram/ntfy compose their message text
  server-side).
- **`channels/telegram.ts` (rewritten)** — `sendTelegramMessage(chatId, text)` (raw Bot API
  `sendMessage` call, shared with the webhook's pairing-confirmation message) and
  `telegramChannel.send`: logs-and-skips if `TELEGRAM_BOT_TOKEN` is unset (same "missing config
  = skipped capability" stance as `webpush.ts`'s VAPID check), otherwise posts the kind-keyed
  label (+ deep link). Maps Telegram's 400/403 ("chat not found"/"bot blocked") onto
  `statusCode: 410` so `dispatch.ts`'s existing gone-subscription pruning picks it up for free.
- **`channels/ntfy.ts` (rewritten)** — POSTs the label as the ntfy message body to
  `${NTFY_BASE_URL}/${topic}` (default `https://ntfy.sh`, so no bot registration needed — a
  topic is just a name the user picks), with the deep link (if configured) riding in ntfy's
  `Click` header. No subscription needed beyond the existing `POST /v1/push/subscribe
  {channel:"ntfy"}` — no pairing flow required, unlike Telegram.
- **`routes/telegramLink.ts` (new)** — `POST /v1/push/telegram/link` (authenticated): mints a
  random `code` (`telegram_link_requests` table, 10-min TTL, same bounded-window rationale as
  `pairRequests`) and returns `https://t.me/<bot>?start=<code>`; 400s with a clear error if
  `TELEGRAM_BOT_TOKEN`/`TELEGRAM_BOT_USERNAME` aren't configured, rather than minting a
  code that can never be completed. `POST /v1/push/telegram/webhook` (unauthenticated —
  called by Telegram's servers; gated by `TELEGRAM_WEBHOOK_SECRET`'s
  `X-Telegram-Bot-Api-Secret-Token` header when configured): parses `/start <code>` +
  `chat.id`, resolves the code (single-use — deleted before acting on it), reassigns the
  `push_subscriptions` row for that chat id to the requesting account (last `/start` wins —
  a Telegram chat belongs to one person, unlike webpush's endpoint-collision 409), and sends a
  best-effort confirmation message. Always 200s past the secret check (Telegram retries
  aggressively on non-2xx; nothing a retry could fix for an unknown/expired code).

### Quiet controls (mute-all + per-session mute)

- **`db/schema.ts`** — `accounts.notificationsMutedAll` and `sessions.notificationsMuted`,
  both plaintext booleans (not inside the encrypted `settings`/`metadata` blobs) — the push
  dispatcher has to check them without decrypting anything, since the server holds no keys
  (design §5.3). Migration generated via `drizzle-kit generate`
  (`drizzle/0001_clear_starjammers.sql`).
- **`app/push/dispatch.ts`** — `attempt()` now checks `accounts.notificationsMutedAll` and
  `sessions.notificationsMuted` (in parallel, one query each) right alongside the existing
  presence check, before any channel fan-out. Fails **open** on a broken lookup (same stance as
  the presence check's own fail-open) — a mute-check bug must never silently swallow a real
  notification. A muted-then-unmuted session picks the very next lifecycle event back up
  automatically; nothing is cached.
- **`routes/notificationSettings.ts` (new)** — `GET`/`PUT /v1/account/notifications-mute`
  (`{mutedAll}`) and `PUT /v1/sessions/:id/notifications-mute` (`{muted}`, 404 if the session
  isn't the caller's, idempotent no-op — no headerSeq bump/fan-out — if already at the
  requested value). The session route bumps `headerSeq` and emits a `session-update` so other
  connected clients see the mute state live.
- **`@falcon/wire`** — `SessionRowSchema` gained `notificationsMuted: boolean` (additive; every
  literal `SessionRow` fixture across `packages/{wire,web,cli}` needed the new field added —
  confirmed via the additive-only compat test, which passed unmodified) and
  `UpdateBodySchema`'s `session-update` variant gained an optional `notificationsMuted` field.

### Web settings page (`packages/web/src/app/settings/notifications/page.tsx`)

Extended the existing Web Push toggle page with two new sections:
- **Fallback channels** — "Link Telegram" button (calls `linkTelegram`, opens the deep link in
  a new tab) and an ntfy topic input + Subscribe button (calls the existing `subscribePush`
  with `channel: "ntfy"`).
- **Quiet controls** — a mute-all checkbox and a per-session mute checklist, sourced from
  `GET /v1/sessions` (already existed; used here only to populate the picker — no new list
  endpoint was added) and `GET /v1/account/notifications-mute`. Toggles are optimistic with
  rollback-on-error.
- `lib/api.ts` gained `GET`/`PUT` support in its shared `request()` helper (previously
  POST/DELETE only) plus `linkTelegram`, `listSessions`, `getMutedAll`, `setMutedAll`,
  `setSessionMuted`.
- Fixed a latent bug while touching the page's `useEffect`: a second `let cancelled = false`
  I'd added (for the new mute/session fetches) shadowed the original one used by the push-status
  check, so the cleanup function only cancelled the second — collapsed to one shared
  `cancelled` flag guarding every async load the effect kicks off.

## Design decisions / assumptions

- **No "list my push subscriptions" endpoint added.** The ntfy/Telegram sections don't reflect
  prior-session subscription state on page reload (e.g. "already subscribed to topic X") —
  there's no existing GET for `push_subscriptions`, and adding one felt like scope creep beyond
  "a small settings addition." Re-subscribing/re-linking is idempotent either way.
- **Telegram re-pairing reassigns ownership (delete-then-insert on the chat id), not a 409.**
  Unlike webpush endpoints (one device, one account, collision = error), a Telegram chat id is
  inherently one person doing `/start` — "most recent pairing wins" is the correct semantics,
  not a conflict.
- **`PUBLIC_WEB_ORIGIN` is optional.** Deep links in Telegram/ntfy messages are a nice-to-have,
  not required for the fallback channels to work — unset just omits the link, matching this
  file's existing "missing config = skipped capability, not a crash" convention (VAPID keys).
- **Per-session mute lives in the notifications settings page**, not the session timeline
  (§2.4's territory) — per the task's own framing ("exposed via a small settings addition").
