# P1-1.5-ensure-daemon-running

Implements `ensureDaemonRunning()` auto-start wiring in the CLI (plan.md §16
"1.5 Daemon v1", design §7.2/§8, PRD FR-1.2: "First run of `falcon` triggers
... daemon auto-start — no separate setup steps").

## What was implemented

**`packages/cli/src/daemon/ensureDaemonRunning.ts` (new)**

- `ensureDaemonRunning(deps)`: reads `daemon.state.json` via the already-merged
  `state.ts`, verifies the named pid is actually alive via the same
  `kill(pid, 0)` liveness probe `lock.ts` uses for its own stale-lock
  detection (`isProcessAlive`, threaded through `DaemonCommandDeps` exactly
  as `commands.ts` already does — so a dead pid in the state file is treated
  identically to no state file at all). If no live daemon is found, it
  delegates straight to the already-merged `runDaemonStart` (from
  `daemon/commands.ts`), which spawns `daemon start-sync` detached and polls
  `daemon.state.json` until ready or `readyTimeoutMs` elapses. No spawn/poll
  logic is duplicated — this is a thin wrapper reusing existing pieces, per
  the task description.
- Respects `FALCON_NO_SERVICE=1` (already documented in `index.ts`'s help
  text/PRD's env var list, previously unread by any code): when set, returns
  `{ ok: false, reason: "disabled" }` without touching the filesystem or
  spawning anything, before any of the above.
- `EnsureDaemonRunningDeps` extends `DaemonCommandDeps` with an `env` field;
  `createEnsureDaemonRunningDeps()` builds one via `createDaemonCommandDeps()`
  defaulting `env` to `process.env`.
- Return type: `{ ok: true; state }` | `{ ok: false; reason: "disabled" }` |
  `{ ok: false; reason: "start-failed"; message }` — callers get both a
  simple pass/fail and, on failure, the exact human-readable message
  `runDaemonStart` already produces (e.g. "timed out waiting for the daemon
  to become ready").

**`packages/cli/src/index.ts`**

- New `ensureDaemon()` helper wraps `ensureDaemonRunning()` + `
  createEnsureDaemonRunningDeps({ version: readVersion() })`, treating both
  `ok: true` and `reason: "disabled"` as success (the "disabled" case means
  the user explicitly opted out via `FALCON_NO_SERVICE=1`, not a failure).
- Wired into every agent-invoking subcommand that previously short-circuited
  with a stub message: `start` (`falcon` / `falcon claude` / `falcon codex`),
  `auth`, `sessions`, and `resume`. Each now calls `ensureDaemon()` first; on
  failure it writes the failure message to stderr and exits 1 *without*
  printing its stub message; on success it proceeds to print the existing
  stub output unchanged. This covers the "at minimum `start`... and ideally
  `auth`, `sessions`, and `resume`" scope from the task description in full.
- `run()`'s switch now dispatches `start`/`auth`/`sessions`/`resume` to new
  `async` handlers (`runStart`/`runAuth`/`runSessions`/`runResume`), each
  returning `Promise<number>` — the same shape `kill`/`daemon` already used,
  so `main()`'s existing `number | Promise<number>` handling needed no
  changes.

**`CLAUDE.md`**

- Updated the `packages/cli` layout bullet: `ensureDaemonRunning()` moved out
  of the "planned" list into the implemented-features list.

## Tests

**`packages/cli/src/daemon/ensureDaemonRunning.test.ts` (new, 5 tests)** —
dependency-injected fakes mirroring `daemon/commands.test.ts`'s style
(`buildDeps` helper, real tmpdir-backed `homeDir`, fake `spawnStartSync`/
`isProcessAlive`/`sleep`):

- no daemon running → spawns one (fake `spawnStartSync` asynchronously
  writes `daemon.state.json`; `ensureDaemonRunning` returns `{ok: true,
  state}`).
- stale state file naming a dead pid → treated as not-running and
  respawned (pre-existing state names a pid `isProcessAlive` reports dead;
  `spawnStartSync` is still invoked and its fresh state is what's returned).
- already-running healthy daemon → no-op, returns immediately
  (`spawnStartSync` never called).
- spawned daemon never becomes ready within `readyTimeoutMs` → `{ok: false,
  reason: "start-failed"}` with a "timed out" message.
- `FALCON_NO_SERVICE=1` → `{ok: false, reason: "disabled"}`, no filesystem
  access or spawn at all.

**`packages/cli/src/index.test.ts` (updated)**

- `beforeEach`/`afterEach` now also set/clear `FALCON_NO_SERVICE=1` — since
  `start`/`auth`/`sessions`/`resume` now call `ensureDaemonRunning()` for
  real, leaving it unset would spawn a genuine detached daemon subprocess on
  every test run. This keeps the existing tests (which aren't about daemon
  wiring) side-effect-free, matching the documented env-var opt-out.
- The pre-existing "describes a claude passthrough start" test now `await`s
  `main(...)` (it returns a `Promise<number>` now).
- The "never writes CLI-level output" test now awaits/`resolves` the
  `auth`/`daemon`/`sessions` calls instead of only asserting a synchronous
  `not.toThrow()` (calling an async function never throws synchronously
  regardless of what happens inside it, so the old assertion was a weaker
  check now that these are async).
- New `describe("daemon auto-start wiring (ensureDaemonRunning)")` block (3
  tests), mocking `./daemon/ensureDaemonRunning.js` the same way the
  existing `kill` tests mock `./daemon/kill.js`:
  - `ensureDaemonRunning` is called before `start` prints its description,
    and success lets the stub start message through.
  - a `start-failed` result exits 1, writes the failure message to stderr,
    and never reaches the stub start message.
  - a `disabled` result is treated as success for `auth`/`sessions`/`resume`
    (each still returns 0 and calls `ensureDaemonRunning` once).

## Assumptions

- `FALCON_NO_SERVICE=1`'s semantics were not fully specified anywhere in the
  plan/design/PRD beyond being listed as an env var alongside
  `FALCON_NO_UPDATE`; no code previously read it. This task interprets it as
  "the user has opted out of Falcon managing the daemon lifecycle" —
  `ensureDaemonRunning()` returns a distinct `"disabled"` reason (not an
  error) and every calling site treats it identically to success, letting
  the (still-stubbed) command proceed without a daemon.
- Actual provider/session spawning, `falcon auth`, `falcon sessions`, and
  `falcon resume` remain honest stubs (unrelated to this task's scope) — the
  only behavioral change to those commands is that they now genuinely
  ensure a daemon is running (or that the user opted out) before printing
  their existing "not implemented yet" message.
