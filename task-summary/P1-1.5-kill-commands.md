# P1-1.5-kill-commands — `falcon kill` commands (process-scan based)

Implements `falcon kill daemon|sessions|all|all-force` per plan.md §7.2/§7.4 and
falcon-system-design.md §11 ("Wedged provider process ... SIGKILL fallback;
`falcon kill sessions` escape hatch").

## What was built

- `packages/cli/src/daemon/processScan.ts` — generic `ps`-based process-list
  primitive. `parsePsOutput()` parses `ps -axo pid=,ppid=,command=`-style text
  (pure function, fixture-testable); `listProcesses()` shells out to real `ps`
  and is best-effort (returns `[]` on any failure — `ps` missing/erroring is
  never allowed to crash the kill command). macOS/Linux only; Windows is PRD
  FR-1.1 P2 and out of scope at this phase, matching the rest of the CLI.
- `packages/cli/src/daemon/markers.ts` — the Falcon process marker convention
  and classifier. Argv-based (not env-var-based — reading another process's
  environment isn't portable, whereas `ps` gives every process's command line
  for free), documented in the file header for coordination with whichever
  task lands the daemon spawner:
  - `daemon`: command line is `falcon daemon start-sync` (the daemon's real
    long-running process; per Happy's `spawnHappyCLI(['daemon','start-sync'],
    {detached:true})` pattern in `daemon/CLAUDE.md`) or a still-running bare
    `daemon start`.
  - `session`: every other bare `falcon` / `falcon <provider>` invocation,
    including daemon-spawned remote sessions (`falcon <provider>
    --starting-mode remote --started-by daemon`, plan.md §7.3) — flagged with
    `spawnedByDaemon: true` for informational purposes only, not a different
    kill bucket.
  - `other`: Falcon's own short-lived administrative subcommands (`daemon
    stop/status`, `kill`, `auth`, `sessions`, `resume`, `workspace`, `notify`,
    `--help`/`--version`) — never a kill target.
  - `classifyProcesses()` also excludes the invoking `falcon kill` process's
    own pid, so a kill command can never target itself.
- `packages/cli/src/daemon/kill.ts` — orchestration:
  - `killDaemon` / `killSessions` / `killAll`: SIGTERM every matched target,
    then poll (fake-clock-testable via injected `now`/`sleep`) for up to
    `gracefulTimeoutMs` (default 5000ms), SIGKILL anything still alive.
  - `killAllForce`: SIGKILL every matched target immediately, no grace period.
  - Fully dependency-injected (`KillDeps`: `listProcesses`, `killPid`,
    `isAlive`, `sleep`, `now`, `currentPid`, optional `logger`) so unit tests
    never touch real OS processes or real timers — `createKillDeps()` wires
    the real OS-backed implementation for production use.
  - Per-pid failures (e.g. `EPERM`) are captured as `KillOutcome.error` and
    surfaced in the summary rather than throwing and aborting the whole
    command — one un-killable process must not stop the rest.
  - `describeKillSummary()` renders a `KillSummary` as the CLI-facing text.
- `packages/cli/src/index.ts` — wired the `kill` case (previously a "not
  implemented yet" stub) to actually call the above and print the result.
  This is the first subcommand whose handler is genuinely async (`ps` +
  graceful-timeout wait), so `run()`/`main()` were widened from `number` to
  `number | Promise<number>` and the bottom-of-file guard now awaits when
  `main()` returns a promise before calling `process.exit`. Every other
  subcommand is untouched and stays synchronous — existing `index.test.ts`
  assertions (`main()` returning a plain number) are unaffected since none of
  them exercise the `kill` path.

## Tests

All against mocked/injected fixtures, no real OS process interaction:

- `processScan.test.ts` — `parsePsOutput` against fixture `ps` transcripts
  (multi-process, blank lines, garbage lines, empty output);
  `listProcesses` against a mocked `node:child_process.execFile` (success and
  failure paths).
- `markers.test.ts` — every classification branch (daemon prod/dev/bare
  entrypoints, `daemon stop`/`status` as `other`, daemon-spawned vs. ordinary
  sessions, every administrative subcommand, non-Falcon processes, and the
  "contains 'falcon' as a substring but isn't the entrypoint" false-positive
  guard) plus `classifyProcesses`' pid-exclusion behavior.
- `kill.test.ts` — `killDaemon`/`killSessions`/`killAll`/`killAllForce`
  against a fixed process fixture with fully injected deps: correct
  targeting per command, SIGTERM→wait→SIGKILL escalation via a fake clock
  (`sleep` advances a fake `now()`, no real timers), immediate SIGKILL for
  `all-force` even against processes still reporting alive, per-pid error
  capture without aborting the batch, and `describeKillSummary` output
  formatting.

`pnpm --filter falcon test`: 91/91 tests green (9 files, including the 3 new
ones above). `pnpm --filter falcon typecheck`: clean. `pnpm build` (full
monorepo via turbo): all 5 packages build.

`pnpm lint` (biome): failed both attempts with "Linter process terminated
abnormally (possibly out of memory)" — but this failure reproduces identically
against `packages/cli/src/args.ts` (a pre-existing, completely untouched
file), confirming it's the transient resource-contention issue already
documented in the repo's `CLAUDE.md` (many concurrent worktree agents
building/testing at once), not something introduced by this change.

## Assumptions / coordination notes

- **No dependency on `controlServer.ts` or `daemon.state.json`.** Per the
  task brief, this module discovers targets purely via `ps` — neither of
  those (both separately in-flight/unclaimed at the time of writing) exists
  anywhere in this worktree's `packages/cli/src/daemon/`, and this code
  never references them.
- **Marker convention is a documented proposal, not yet cross-validated
  against the actual spawner.** `packages/cli/src/daemon/` had no existing
  files before this change (the daemon singleton lock and control-server
  tasks are unmerged in sibling worktrees). The convention here — daemon
  process launched as `falcon daemon start-sync`; daemon-spawned sessions
  carrying `--started-by daemon` — was derived directly from plan.md §7.3/§7.4
  and Happy's `daemon/CLAUDE.md` control-flow doc, so it should already match
  whatever the spawner task implements, but the merge landing both should
  double check argv literals line up exactly.
- **`falcon kill sessions`/`all` do not distinguish daemon-spawned vs.
  local-mode sessions** — both are "sessions" for kill purposes (the design
  doc doesn't ask for finer-grained targeting here); `spawnedByDaemon` is
  carried through to `ClassifiedProcess`/`KillOutcome` for observability
  (e.g. a future `falcon doctor`) but isn't used to split behavior.
- **Graceful timeout default is 5000ms**, matching the SIGTERM-then-SIGKILL
  grace period used elsewhere in the design (`adopt.take`'s takeover,
  falcon-system-design.md §7.8). Exposed as an optional parameter on
  `killDaemon`/`killSessions`/`killAll` for callers (and tests) that need a
  different value.
- Real OS interaction (`ps`, `process.kill`) is confined to
  `processScan.ts`'s `listProcesses()` and `kill.ts`'s `createKillDeps()`
  defaults — both are thin, and everything else takes injected dependencies,
  which is what let the tests above run fully offline/deterministically.
