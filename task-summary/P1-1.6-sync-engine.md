# P1-1.6-sync-engine — Web sync engine: headerSeq/msgSeq fast-path with gap-invalidation

Phase 1 / §1.6 Web app v1 (read-only), plan.md line 705, delta **D2** (two-level
seq). Implements `packages/web/src/sync/` per `falcon-system-design.md` §8.1/§9.1
and `plan.md` §16 (1.6): port of Happy's `sync.ts` model (`apiSocket` +
invalidate-on-gap), split for **DELTA D1/D2** — reads over WS, writes over HTTP
(out of this task's scope), two independent seq counters (account `headerSeq`
for structural changes, per-session `msgSeq` for messages).

## What was built

- `packages/web/src/sync/queryKeys.ts` — shared TanStack Query key builders:
  `syncQueryKey` (`['sync']`) and `messagesQueryKey(sessionId)`
  (`['messages', sessionId]`), plus the guards the engine uses to recognize
  its own queries in a `QueryCache` subscription (`isSyncQueryKey`,
  `messagesSessionIdFromKey`). Centralized so any future hook that owns the
  actual `useQuery`/`useInfiniteQuery` fetches agrees on the key shape with
  the engine's `setQueryData`/`invalidateQueries` calls.
- `packages/web/src/sync/types.ts` — `SyncSnapshot` (mirrors the server's
  `GET /v1/sync` `SyncResponseSchema`: `headerSeq` + `sessions`/`machines`/
  `unmanagedSessions` from `@falcon/wire`'s row types), `MessageItem`/
  `MessagesPage`/`MessagesQueryData` (mirrors `GET /v1/sessions/:id/messages`'s
  `MessageItemSchema` — not exported from `@falcon/wire` since it's an HTTP
  response shape, not a wire envelope; spelled out locally field-for-field).
- `packages/web/src/sync/engine.ts` — `createSyncEngine(queryClient, socket)`:
  - **Structural (header) fast-path**: on a WS `update` whose body isn't
    `message-new`, applies directly to the `['sync']` Query cache via
    `setQueryData` when `update.seq === lastHeaderSeq + 1` (upsert-by-id for
    session-new/machine-*/unmanaged-*, field-level patch for session-update,
    filter-out for session-delete); any gap, a missing `seq`, or no baseline
    yet ⇒ `invalidateQueries(['sync'])`.
  - **Per-session message fast-path**: on `message-new`, applies directly
    (prepends to the newest cached page) when `msgSeq === lastMsgSeq[sessionId]
    + 1`, *only* for sessions that already have a cached message page (i.e.
    currently open — the tracker is never seeded for sessions nobody has
    opened, so it doesn't grow unbounded); a gap ⇒
    `invalidateQueries(['messages', sessionId])`; a duplicate/stale delivery
    (`msgSeq <= known`) is ignored, not reapplied.
  - **Reconnect**: `invalidateQueries()` with no key — every query, not just
    `['sync']` — per design §9.1 ("reconnect ⇒ invalidate all queries"),
    matching plan.md §8.1's own pseudocode.
  - **Ownership split**: the engine never fetches anything itself (no
    `fetchQuery` call anywhere) — it only reads/writes the Query cache. Both
    seq trackers are reconciled with whatever's actually in the cache via a
    `QueryCache.subscribe` (for changes after construction) plus an
    initial-state read at construction time (for anything already cached
    before the engine was created — a fetch that resolved earlier, or a
    dev/test setup that pre-seeds the cache).
  - `dispose()` detaches every listener (socket + cache subscription); safe
    to call more than once.
- `packages/web/src/sync/index.ts` — barrel export + usage doc comment.
- `packages/web/src/sync/engine.test.ts` + `__tests__/fakes.ts` — 13 unit
  tests (`createFakeSyncSocket`, an in-memory `SyncSocketSource` double, same
  pattern as `apiSocket`'s own `fakes.ts` one level down the stack) covering:
  contiguous structural apply (no invalidation), header gap invalidation, no
  baseline yet, missing `seq`, session-update field patching, machine
  upsert, contiguous message apply + tracker advance, message gap
  invalidation (scoped to that session only), duplicate/stale message
  ignored, message for an unopened session ignored, tracker re-seeding after
  a gap-triggered refetch lands, reconnect invalidates everything, and
  `dispose()` idempotency/teardown.

## Key design decision: decoupled `SyncSocketSource`

`apiSocket` (the real WS client `.on('update'|'reconnect', ...)` source) was
built in a sibling, still-unmerged worktree (`P1-1.6-api-socket`) and does not
exist on `main` — this worktree branched from `main`, so it has no
`apiSocket.ts` to import. Rather than depending on that unmerged branch (which
would make this task un-buildable in isolation), `engine.ts` declares a
narrow local interface, `SyncSocketSource`, capturing exactly the two events
the engine needs (`on('update', handler)`, `on('reconnect', handler)`). This
mirrors the codebase's existing injectable-dependency pattern (`SocketFactory`/
`VisibilitySource` in `apiSocket.ts` itself, `WorkerLike` in
`crypto/client.ts`) and matches plan.md 1.6's own note that "the sync
engine... can be built and verified in isolation now against the wire
contract." The real `ApiSocket` type (once `P1-1.6-api-socket` lands) is
structurally compatible — no adapter needed at the eventual call site,
`createSyncEngine(queryClient, apiSocket)`.

## Assumptions / scope notes

- **New dependency**: added `@tanstack/react-query` (`^5.101.2`) to
  `packages/web/package.json` — not previously a dependency anywhere in the
  monorepo. Also added `@falcon/wire` as an explicit `packages/web`
  dependency (it was transitively resolvable but not declared — the crypto
  worker code didn't need it, this module does).
- **Message page cache holds ciphertext**: `MessageItem.content` stays an
  untouched `EncryptedBox` — decryption is a separate boundary (crypto-bridge
  worker, design §5.3) that some future hook applies when reading the cache,
  not this engine's job.
- **`account-update` is a documented no-op**: `UpdateBody`'s `account-update`
  variant carries `settings: EncryptedBox`, but the server's actual
  `SyncResponseSchema` (`packages/server/src/app/routes/sync.ts`) doesn't
  include a `settings` field at all — there's nothing in the cached
  `SyncSnapshot` shape to patch. Handled explicitly (not silently dropped)
  with a comment; revisit if/when a settings query is added.
- **`createdAt` approximation on fast-path-applied messages**: the WS
  `message-new` update doesn't carry the row's real `createdAt` (only the
  outer `Update.ts` envelope timestamp), so the fast-path uses `update.ts` as
  an approximation — negligibly different from the server's real insert time
  in practice, and only affects display until a gap-triggered refetch
  replaces it with the authoritative row.
- **Per-open-session tracking only**: `lastMsgSeq` is never populated for a
  session that hasn't had its message page fetched into the Query cache —
  matches design §10.5 ("per-open-session: GET messages?before/after msgSeq
  cursors").
- Did not touch `apiSocket.ts`, auth pages, the reducer, or any UI screens —
  all explicitly out of this bullet's scope (separate, already-tracked plan.md
  bullets).
