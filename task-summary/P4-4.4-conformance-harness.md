# P4-4.4-conformance-harness — 20-step conformance script (`exercise-flow`)

**Section:** Phase 4 — Ship / 4.4 Hardening & release gate
**Plan reference:** plan.md line 802 / falcon-system-design.md §13 item 3
**Fidelity:** (N) new code — greenfield, no Happy equivalent (this is a Falcon-specific
release-gate concept; the underlying mechanisms it exercises — permission pipeline, mode
switching, adoption's `adopt.take`, reconnect/resync — are all already merged on `main`).

## What was built

A new `e2e/` workspace package (`@falcon/e2e`), added as system-design §3's repo tree
predicted (`e2e/ # conformance harness (scripted agent exercise, chaos tests)`), containing
a scripted 20-step conformance harness that runs against a **real local stack**:

- A real `@falcon/server` (real Fastify app, real Socket.IO, real in-memory Postgres via
  `@electric-sql/pglite` — same "real server, not a mock" posture as the existing
  `bootstrap.integration.test.ts` / `commands.machineWiring.integration.test.ts`).
- A real `falcon` daemon boot (`runDaemonStartSync` — real singleton lock, real control
  server, real session registry, real machine-scoped RPC handler wiring via
  `machineIntegration.ts`).
- A real "controller" `socket.io-client` connection standing in for the web/mobile app.
- A `FakeSessionProcess` (`e2e/src/fakeSessionProcess.ts`) standing in for the one thing no
  sandbox here can run for real — an actual Claude Code subprocess. It is **not** a mock of
  the wire protocol: it drives the real `registerSessionRpcHandlers` (session RPC
  registration/decrypt/validate/dispatch), the real `PermissionHandler` (auto-rules,
  allow-lists, first-wins resolution), and the real `Outbox` (coalescing HTTP POST of sealed
  `SessionEnvelope[]` batches) — exactly the building blocks `claudeRemote.ts`/`loop.ts`
  wire together for a genuine remote-mode session. Only the *decision* to call a tool is
  scripted by the harness instead of decided by a real model (matching the design doc's own
  division of labor — real LLM-transcript fidelity is item 1's separate "Provider contract
  tests" task; this harness's job is the surrounding machinery item 3 names).
- A `spawn`/`adopt.take` fake process launcher (`testStack.ts`'s `buildFakeLaunchProcess`)
  that performs the exact two steps a real spawned `falcon claude --starting-mode remote`
  process performs on startup — real `bootstrapSession` against the real server (real
  session row, real minted DEK) and starting a `FakeSessionProcess` — then self-reports via
  the real `notify.ts` client hitting the daemon's own real control server
  `/session-started` webhook, mirroring `commands.machineWiring.integration.test.ts`'s own
  established pattern for this exact problem.

### The 20 steps (`e2e/src/steps.ts`)

1. Spawn a remote session via the machine `spawn` RPC
2. Verify the spawned session process answers session RPCs
3. Controller sends the initial user message (`message` RPC)
4. Verify the initial message landed in the transcript
5. Permission **ALLOW** (once) — `Write` tool
6. Permission **DENY** — `Edit` tool
7. Permission **ALLOW-SESSION** — `Bash` tool
8. Verify allow-session was persisted (same `Bash` literal auto-approves, no new `perm-request`)
9. **Question** (`AskUserQuestion`) answered allow
10. **Interrupt** mid-permission-request (pending request rejected + `turn-end{cancelled}`)
11. **Mode switch #1**: local → remote via `takeControl` RPC
12. Verify remote-mode message flow
13. **Mode switch #2**: remote → local via a simulated terminal takeback (design §7.5: this
    direction has no RPC, only a local terminal action — `FakeSessionProcess` exposes
    `simulateTerminalTakeback()` standing in for that)
14. Verify mode-switch envelope ordering (`remote` then `local`)
15. **Reconnect** — session process socket disconnect/reconnect
16. Verify session RPC still reachable after the session process reconnects
17. **Reconnect** — controller socket disconnect/reconnect
18. Verify a fresh permission round trip works after the controller reconnects
19. **Adoption takeover** — `adopt.take` machine RPC (`mode: 'takeover'`) mints a real
    continuation session
20. Final transcript integrity check (turn lifecycle, exactly 6 `perm-request` / 5
    `perm-resolve` envelopes with the one interrupted request correctly unresolved, both
    mode-switches, the adopted session tracked)

Every step calls real RPCs over real encrypted sockets and reads back the real,
server-persisted, decrypted transcript to assert on outcomes — no in-memory shortcuts.

### Entry points

- `pnpm --filter @falcon/e2e exercise-flow` (`e2e/src/cli.ts`, wraps `exerciseFlow.ts`) —
  the human/CI-facing release-gate script plan.md asks for: prints a PASS/FAIL/timing line
  per step and exits non-zero on any failure.
- `pnpm --filter @falcon/e2e test` (`e2e/src/exerciseFlow.test.ts`) — the same harness
  wired into the ordinary `pnpm test` / CI pipeline, so a regression fails CI immediately
  rather than only being caught by someone remembering to run the release-gate script by
  hand.
- A step failure stops the run (later steps depend on earlier state — e.g. step 2 needs
  step 1's `sessionId`); every step after the first failure is reported `skipped`, not
  silently omitted, so a partial run is still fully legible.

## Assumptions / scope decisions

- **No real Claude Code subprocess.** This harness proves the wire/RPC/permission/mode-
  switch/reconnect/adoption *machinery* end-to-end against a real server + real daemon; it
  does not (and per the design doc's own split, should not) also re-verify real
  Claude-Code transcript fidelity — that is item 1 in the same plan.md section ("Provider
  contract tests in CI (daily cron): latest Claude Code against fixture prompts"), a
  separate, still-`[ ]` task.
- **Adoption takeover goes through the real `adopt.take` machine RPC** with `mode:
  'takeover'` against a real (but never-actually-running) synthetic provider session — the
  daemon's real `findOwningClaudeProcess` OS-level liveness scan runs for real and correctly
  finds no live process (there is none), so the takeover proceeds straight to spawning a
  continuation with no `warning`. The SIGTERM→SIGKILL escalation sub-branch (when a live
  owning process *is* found) already has full, deterministic unit coverage in
  `packages/cli/src/daemon/adoptTake.test.ts` with injected liveness/kill fakes; re-testing
  that same branch here would need to either fake OS process-liveness (not currently an
  injectable seam on `createDaemonCommandDeps`'s `resolveProviderSession`/adopt wiring) or
  spawn a real subprocess literally named `claude` — both out of scope for a portable,
  deterministic pre-release script. Going through the real RPC with the "nothing to
  interrupt" outcome is still a genuine, non-trivial exercise of the `mode==='takeover'`
  code path (real `getProjectPath`, real `findOwningClaudeProcess`, real OS `ps` scan) that
  the existing unit tests never exercise (they inject `liveness` directly and never touch
  the real daemon-wiring seam).
- **`setMode` (permission-mode: default/acceptEdits/plan/bypassPermissions) is not a
  separate step.** The task's own named primitive list (plan.md line 802 / design §13 item
  3) is "perm allow/deny/allow-session, question, interrupt, mode switch ×2, adoption
  takeover, reconnect" — `setMode` isn't named, and its mechanism
  (`PermissionHandler.setMode`) already has direct unit coverage in
  `permissionHandler.test.ts`. Left out to keep the 20 steps mapped 1:1 onto the task's
  explicit list rather than padding the count.
- **`FakeSessionProcess` starts in `local` control mode** (regardless of the `spawn` RPC's
  own `--starting-mode remote` argv, which nothing here actually execs) so the harness can
  demonstrate both legs of the local→remote→local mode-switch cleanly. This is a harness-side
  simplification, not a claim about what a real spawned process's initial mode is.
- **Interrupted permission requests never get a `perm-resolve` envelope** — traced from the
  real `permissionHandler.ts`: `interrupt()`'s abort path deletes the pending entry and
  rejects the promise directly, without calling `completeRequest`/emitting `perm-resolve`
  (that only happens via `resolve()` or `reset()`). Step 20's final integrity check asserts
  this precisely (exactly one unresolved `perm-request`, matching the interrupted `Bash`
  call) rather than assuming a spurious 1:1 request/resolve count — this was verified by
  reading the real source, not assumed.
- **No `bun`/real-Postgres dependency.** Like every other integration test in this repo,
  the harness uses `@electric-sql/pglite` (in-memory Postgres) rather than a real Postgres
  instance or Docker — keeps the release-gate script runnable anywhere `pnpm test` already
  runs, with no extra infra.
