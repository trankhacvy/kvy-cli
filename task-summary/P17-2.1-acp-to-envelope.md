# P17-2.1-acp-to-envelope

`cli/src/acp/acpToEnvelope.ts` — ACP `session/update` -> `SessionEnvelope` mapper
(plan.md §16 "Phase 2.1 — ACP core"; design §7.3).

## What landed

- `packages/cli/src/acp/acpToEnvelope.ts` — the single, provider-agnostic mapper.
  Exports:
  - `createAcpEnvelopeMapperState()` / `AcpEnvelopeMapperState` — mutable per-session state
    (current turn id, one shared provider-id -> cuid2 map, subagent tracking sets).
  - `mapAcpUpdateToEnvelopes(update, state, logger?)` — the main per-notification mapper.
    Handles `agent_message_chunk` -> `text`, `agent_thought_chunk` -> `text{thinking:true}`,
    `tool_call` -> `tool-start`, `tool_call_update` -> `tool-end` (only on terminal
    `completed`/`failed` status). `user_message_chunk` is dropped silently (the caller
    already emits the human prompt synchronously around `session/prompt`, mirroring
    `remote/sdkToEnvelope.ts`'s identical rule). Every other kind (`plan*`,
    `current_mode_update`, `available_commands_update`, `session_info_update`,
    `usage_update`, `config_option_update`, and any future/unrecognized kind) is logged
    (`logger.warn("acp_session_update_unknown_kind_dropped", ...)`) and dropped — never
    thrown.
  - `startAcpTurn(state)` / `endAcpTurn(state, stopReason)` / `closeAcpTurnWithStatus(state, status)`
    — turn-start/turn-end are synthesized around the `session/prompt` call/return boundary
    (not a `session/update` kind), per the task description. `mapAcpStopReasonToTurnStatus`
    is exported separately and unit-tested in isolation.
  - `AcpSessionUpdate` — a narrow structural input type (only the fields actually read),
    decoupled from `@agentclientprotocol/sdk` entirely, matching the same pattern
    `remote/sdkToEnvelope.ts` already uses for `@anthropic-ai/claude-agent-sdk`. This keeps
    the module buildable and testable today, without adding the ACP SDK as a dependency
    ahead of the sibling `acpConnection.ts` task that will actually spawn/drive an adapter
    child process.
- `packages/cli/src/acp/acpToEnvelope.test.ts` — 22 unit tests: turn lifecycle (open/close,
  every `stopReason` -> status mapping, force-close, no-active-turn drop), text chunk mapping
  (message/thought, non-text content dropped, `user_message_chunk` dropped silently),
  unknown-kind logging, tool_call/tool_call_update start/end lifecycle (id minting stability,
  intermediate-status drop, missing-id drop, `_meta.claudeCode.toolName` name fidelity),
  subagent scoping via `_meta.claudeCode.parentToolUseId` (sub-start/sub-stop bracketing,
  scope remembered across an update that omits `_meta`, mid-turn force-close flushing open
  subagent scopes), and state reset across turn boundaries.

## Design decisions / assumptions (flagged for the Phase 2.1 golden-trace-fixture task to confirm)

The public ACP spec doesn't pin every field this task's mapping table needs, so two
judgment calls were made and are called out in the file's header comment as well:

1. **`_meta` is readable on every `session/update` variant**, not only
   `tool_call`/`tool_call_update` — needed so a subagent's own thinking/text chunks (not
   just its tool calls) resolve to the right `subagent` scope, matching the
   `trace_acp_parent_tool_use_subagent.json` fixture's `e3` (a thinking chunk carrying
   `subagent: "acp-task-1"`) from the Phase 2.0 wire-envelope-verification task.
2. **Tool `name` fidelity**: `_meta.claudeCode.toolName` is preferred when present (best
   fidelity for the Claude adapter, same `_meta.claudeCode` namespace design §7.3 already
   established for `parentToolUseId`), falling back to ACP's own standardized `kind`
   taxonomy (`read`/`edit`/`execute`/...) for any other ACP-conformant agent, and finally the
   literal string `"tool"`.

Also: `stopReason` -> `turn-end.status` maps `end_turn`->`completed`, `cancelled`->`cancelled`,
and everything else (`max_tokens`, `max_turn_requests`, `refusal`, unrecognized) -> `failed`
(the turn stopped without reaching a natural or user-requested end).

The subagent-scope algorithm mints exactly one cuid2 per raw ACP id from a single shared
map (`providerIds`), used for both tool-call ids and parent-tool-use ids — this is what
makes a spawning call's own minted `call` id and the cuid2 a child's
`_meta.claudeCode.parentToolUseId` resolves to byte-for-byte identical, matching the
wire-envelope-verification fixture's stated rule: "the subagent id equals the spawning
Task-like call's id." Unlike Claude's local-mode mapper (`claude/envelopeMapper.ts`), the
spawning call's own `tool-start`/`tool-end` are **not** hidden — ACP's `tool_call` for a
Task-like call is a normal, visible tool call; only its *children* get subagent scope.
State (id maps, subagent tracking) resets fully on every turn close, matching
`claude/envelopeMapper.ts`'s `clearSubagentTracking` precedent.

`session/request_permission` -> `perm-request`/`perm-resolve` mapping (also listed in
design §7.3's table) is intentionally **not** implemented here — it belongs to the "Unified
ACP permission handler" bullet (a separate Phase 2.1 task), which emits those envelopes
directly as part of the permission pipeline, the same way `claude/permissionHandler.ts` and
`codex/permissionHandler.ts` already do for their providers (see `codex/envelopeMapper.ts`'s
own file-header note making the identical scoping call).
