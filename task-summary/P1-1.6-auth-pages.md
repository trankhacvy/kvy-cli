# P1-1.6-auth-pages — Web auth pages: OAuth sign-in, key generation, recovery-code export, pairing-approve

**Section:** Phase 1 §1.6 Web app v1 (falcon-system-design.md §9 "Web App Design", §5.2 "Auth flows")

## What was built

### 1. Crypto-bridge worker extensions (`packages/web/src/crypto/`)

The already-landed crypto-bridge worker (`P1-land-1.6-crypto-worker-final`) only exposed
`init`/`setSessionKey`/`seal`/`open`/`clear` — enough for the sync engine, but nothing an
auth page could use to check "does this device already have an identity?", sign a
challenge, export a recovery code, or seal to a pairing peer, all while keeping the "keys
never leave the worker" invariant intact. Added four new RPCs (`protocol.ts`,
`worker-handler.ts`, `client.ts`, all with new tests in `worker-handler.test.ts` /
`client.test.ts`):

- `getIdentity()` → `{ signPubKey, contentPubKey } | null` — public keys only.
- `signInChallenge()` → `{ signPubKey, contentPubKey, challenge, signature }` — everything
  `POST /v1/auth` needs, in one call.
- `exportRecoveryCode()` → grouped-Base32 string — the one deliberate exception to
  "never leaves the worker": that's the whole point of a recovery code.
- `sealForPeer(ephPub)` → base64 sealed box of `[0x00|masterSecret]` — the payload
  `POST /v1/auth/pair/approve` relays.

### 2. `@falcon/crypto` addition (`packages/crypto/src/keys.ts`)

Added `signDetached`/`verifyDetached` (thin tweetnacl wrappers over `KeyTree.signing`,
colocated with `deriveKeyTree` since both operate on the same tweetnacl-native keypair
format already proven in `keys.test.ts`). Needed so the worker can turn a locally-generated
challenge into `POST /v1/auth`'s `signature` field without a new dependency.

### 3. GitHub OAuth code-exchange proxy (`packages/server/src/auth/oauth.ts`, `app/routes/oauth.ts`)

Google's flow (OIDC implicit — ID token straight from a browser redirect) needs no server
help. GitHub's authorization-code flow does: exchanging `code` for an access token requires
the app's client secret, and GitHub's token endpoint has no browser-CORS allowance — so a
static-export SPA cannot complete it alone. Added `exchangeGithubCode` +
`POST /v1/auth/oauth/github/exchange` (mirrors the existing `OAuthVerifier`
injectable-dependency pattern exactly: `GithubCodeExchanger` interface, `defaultGithubCodeExchanger`,
injected through `buildOAuthRoutes`/`buildServer`). New env vars `GITHUB_OAUTH_CLIENT_ID` /
`GITHUB_OAUTH_CLIENT_SECRET` (optional — fails closed like `GOOGLE_OAUTH_CLIENT_ID`). New
tests in both `auth/oauth.test.ts` (unit, injected fetch) and `app/routes/oauth.test.ts`
(route, injected exchanger).

### 4. Web app pages (`packages/web/src/app/`, `src/components/auth/`, `src/lib/`)

- **`/signin`** — sign-in/sign-up landing. If this browser already holds a provisioned
  identity, signs in silently via `signInChallenge` + `POST /v1/auth` (no OAuth round trip
  for returning devices). Otherwise shows "Continue with Google" / "Continue with GitHub"
  (each hidden if its client id isn't configured).
- **`/auth/callback/google`**, **`/auth/callback/github`** — OAuth redirect targets. Share
  one component (`OAuthCallbackPage`) parametrized by how each provider's proof is
  obtained. On success: generates a new masterSecret client-side (or reuses this device's
  existing identity, if any — an idempotent rebind, since `/v1/auth/register` upserts by
  `signPubKey`), calls `POST /v1/auth/register`, stores the JWT, and — only for a
  genuinely new identity — shows the recovery code once with an explicit "I've saved it"
  gate before continuing.
- **`/settings/recovery`** — on-demand recovery-code export (design §9.2 Settings). Nothing
  shown until the user clicks "Reveal" — the whole point of a secret-export screen.
- **`/pair`** — reads `#<ephPub>` from the URL, validates it, and (once the browser is
  signed in — stashing the pending pairing request across a `/signin` detour if not) shows
  an Approve/Cancel confirmation. Approve seals the master secret to `ephPub`
  (`sealForPeer`) and calls `POST /v1/auth/pair/approve`.
- Shared plumbing: `lib/config.ts` (`NEXT_PUBLIC_*` build-time config), `lib/session.ts`
  (JWT in `localStorage` — not key material, safe there), `lib/api.ts` (typed fetch
  wrappers + `ApiError`), `lib/oauth.ts` (redirect URL builders + state/nonce handling),
  `lib/pending-pair.ts`, `lib/use-crypto-bridge.ts` (per-page worker lifecycle),
  `lib/complete-oauth-sign-in.ts` / `lib/complete-challenge-sign-in.ts` (the two sign-in
  completion flows, shared between pages).

### 5. Build fix (`packages/web/next.config.ts`)

`next build`'s webpack resolver doesn't understand the NodeNext-style `.js`-suffixed
relative imports the crypto-bridge source already used throughout (`tsconfig.base.json`'s
`moduleResolution: "bundler"` and Vitest both already handled it fine, so this was dormant
— no page had imported `src/crypto/*` before this task). Added `resolve.extensionAlias`
so webpack treats `./foo.js` imports the same way tsc/Vitest already do.

## Assumptions / scope boundaries

- **No recovery-code *import*/restore page.** The task scoped recovery codes as an
  *export* ("back up your key material") and pairing as *approving a new device*, not
  "restore this browser's access from a code typed in." That's a materially different flow
  (masterSecret decode → re-derive keys → sign in as an *existing* account with no fresh
  OAuth proof) and wasn't in the four listed deliverables — left for a follow-up task.
- **Google OIDC implicit flow, not the GIS `<script>` widget.** Chosen deliberately over
  loading `accounts.google.com`'s JS SDK, which would conflict with the design doc's "no
  third-party scripts" CSP goal (§12). A full-page redirect returning the ID token in the
  URL fragment needs no external script at all.
- **GitHub needs one small, injectable server proxy endpoint** for the code→token
  exchange — unavoidable for a static-export SPA (GitHub's token endpoint requires a client
  secret and has no CORS allowance). Scoped tightly: one new route, one new interface,
  same DI pattern as the existing `OAuthVerifier`, doesn't touch `/v1/auth/register` itself.
- **No shadcn `Card`/`Input`/`Dialog` additions** — pages are built with the existing
  `Button` primitive plus plain Tailwind, matching the scaffold's current minimalism rather
  than pulling in new shadcn components for a first pass.
- **No React Testing Library / jsdom** — the web package's Vitest config runs under
  `environment: "node"` with no DOM testing set up yet; added logic-level tests (crypto
  worker RPCs, `@falcon/crypto` signing) instead of introducing new test infra for
  page-level rendering. `pnpm build`'s static export succeeding for all 7 routes is the
  end-to-end compile/render check for the pages themselves.
- **Per-page crypto-bridge worker instance** (`useCryptoBridge` hook: create on mount,
  terminate on unmount) rather than a cross-page singleton — simpler lifecycle; every op
  these pages need lazily re-derives from the IndexedDB-persisted master secret on a fresh
  worker, so there's no cross-page state to lose.

## Verification

- `pnpm build` — all 5 packages build clean, including `@falcon/web`'s static export
  (7 routes: `/`, `/signin`, `/auth/callback/google`, `/auth/callback/github`,
  `/settings/recovery`, `/pair`, plus `/_not-found`).
- `pnpm typecheck` — clean across all packages.
- `pnpm test` — 96 server tests, 53 web tests, 67 crypto tests, 66 CLI tests, 61 wire
  tests, all passing (new tests added for every new crypto-worker RPC, `signDetached`,
  `exchangeGithubCode`, and the new GitHub-exchange route).
- `pnpm lint` — **could not get a clean run in this session**: `biome check` (and even
  `biome --version`) repeatedly reported "Linter process terminated abnormally (possibly
  out of memory)" against this shared machine while several other worktree agents were
  running concurrently (confirmed via `vm_stat`: free pages fell from run to run with no
  code-related change). This matches CLAUDE.md's documented transient-OOM caveat, just
  outlasting the built-in single retry. A scoped `biome check packages/crypto/src` run
  earlier in the session (before memory pressure worsened) succeeded and showed only
  pre-existing warnings (`noExplicitAny`, `noNonNullAssertion`) in code this task didn't
  touch — nothing from the new files. A manual grep for `any`/`as any` across every new
  file found none. Re-running `pnpm lint` once the shared machine's load clears is
  recommended before merge.
