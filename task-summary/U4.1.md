# U4.1 — wave4-trivia (W4.1)

Inline unit covering plan-v2.md's Wave 4 W4.1 (E27, "Streaming text"). Both
sub-tasks land the *non-streaming* half of that item — the design explicitly
decides against real token streaming for the local (non-ACP) path and
prescribes two cheaper wins instead: lower outbox coalescing latency, and
document the decision so it isn't re-litigated. (W1.8's activity row and
W1.6's auto-follow, the other two prongs of the same W4.1 design note, are
separate, already-landed units.)

## What

1. **Outbox flush 300ms → 150ms.** `packages/cli/src/api/outbox.ts`:
   `DEFAULT_FLUSH_MS` lowered from `300` to `150`, with the module docstring,
   the constant's own comment, and `OutboxOptions.flushMs`'s comment all
   updated to match and to cite W4.1. `packages/cli/src/api/outbox.test.ts`'s
   "uses the documented defaults" test updated to assert `150` (this was the
   only place a test asserted the literal old default — the other
   `flushMs`-exercising tests already pass an explicit override and are
   unaffected). Nothing else references the 300ms outbox constant: grepped
   `packages/cli/src` and `packages/web/src` for stray `300` occurrences near
   outbox/flush and confirmed every other hit (`fileWatcher.test.ts`,
   `scanner.test.ts`, `transcriptIndexer.test.ts` sleeps, various `timeout:
   3000`/`readyTimeoutMs` constants) is unrelated. Both session-process
   entrypoints that construct a real `Outbox` (`commands/start.ts`,
   `commands/startCodex.ts`) never override `flushMs`, so they pick up the
   new default automatically — no wiring changes needed.

2. **Protocol-doc note on the no-streaming decision.** `docs/protocol.md` §2
   ("Session event envelope") gained a new paragraph explaining: the local
   tailer only ever sees whole JSONL lines so there's no partial text to
   stream; perceived latency is instead reduced via the activity row/
   following (W1.8/W1.6) and the now-150ms outbox flush; ACP remote mode does
   receive real per-token `session/update` chunks from the adapter, but
   `acpToEnvelope.ts` coalesces them into the same whole-envelope shape
   before they reach the wire, so `SessionEnvelope` carries no
   streaming/partial variant today; revisit only if ACP remote becomes
   dominant and that coalescing is deliberately relaxed. This mirrors
   plan-v2.md's W4.1 note nearly verbatim, per the doc's own stated rule
   ("this file is updated in the same PR as any protocol change").

## Why

Straight from plan-v2.md's W4.1 section: whole-message pop-in is
CLI-shaped (only complete JSONL lines are ever observed), so real streaming
would require inventing partial-envelope semantics with no present payoff.
The cheaper, already-designed alternative is to shrink the batching window
and make the decision legible in the protocol doc so a future contributor
doesn't reopen the streaming question without first checking whether ACP
remote has become the dominant transport.

## Assumptions

- "protocol-doc" in the task brief refers to `docs/protocol.md` (the doc
  whose own header states it's the definitive place for protocol-adjacent
  decisions and must track changes in the same PR) rather than
  `falcon-system-design.md` §4, which is out of scope for a small doc note
  like this.
- plan-v2.md's own checkboxes are left unchecked, matching the existing
  pattern in this file: every other landed-but-still-`[ ]` item (W3.9, W3.10,
  etc., confirmed via `git log`) is tracked by a separate progress-tracker
  process, not by the implementing task itself — Wave 0's live-gate probes
  are the only checkboxes flipped inline, and W4.1 isn't one of those.
- No wire-schema change was needed or made — this unit is pure
  constant-value + doc-comment work, consistent with `@falcon/wire`'s
  additive-only policy having nothing to add here.
