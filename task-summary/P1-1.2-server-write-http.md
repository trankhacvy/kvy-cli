# P1-1.2-server-write-http — HTTP write endpoints: sessions, messages, metadata/state CAS, sync snapshot

Implements `plan.md` §16 "1.2 Server write path (HTTP)" / §4.3 (⚠ DELTA D1: writes
move off WS onto idempotent HTTP, unlike Happy) on top of the already-landed Drizzle
`sessions`/`sessionMessages` schema and `db/seq.ts` allocator. No schema changes.

This worktree branched from `main` (which had `packages/server` through the Drizzle
schema/seq-allocator/auth-module layer, but no HTTP routes and no Socket.IO/eventRouter
yet — task 1.1 "Server realtime (read path)" is still unimplemented as of this branch's
base). Since the write routes need somewhere to fan out to, this task adds a small
`EventRouter` seam (`src/app/eventRouter.ts`) rather than waiting on 1.1 or building
Socket.IO itself (out of scope here) — see "eventRouter seam" below.

## Routes implemented (all behind `app.authenticate`)

- **`POST /v1/sessions`** — create-or-get by `(accountId, tag)`. Uses
  `onConflictDoNothing({ target: [accountId, tag] })` + re-select so a lost race under
  concurrency gets the same 200-replay a sequential retry would; only the actual
  creator bumps `headerSeq` and fans out `session-new` (201). A pure replay returns 200
  with no fan-out.
- **`POST /v1/sessions/:id/messages`** — body `{localId, content}`. Looks up
  `(sessionId, localId)` first (fast path); on a genuine miss, calls the existing
  `allocMsgSeq(tx, id)` and inserts. If two requests for the *same* localId race past
  that lookup concurrently, the unique index on `(session_id, local_id)` rejects the
  loser's insert — caught (`isUniqueViolation`) and turned into the same replay a
  sequential retry gets, so blind retries are safe under real concurrency, not just in
  sequence. Fan-out (`message-new`) is registered via `reply.raw.once("finish", ...)`
  — **never inside the tx** — and only on the request that actually inserted the row;
  a replay returns the same `seq` with zero additional fan-out.
- **`PUT /v1/sessions/:id/metadata`** and **`PUT /v1/sessions/:id/state`** — CAS on
  `metadataVersion`/`agentStateVersion`. Reads current version, 409s with
  `{current: {value, version}}` on mismatch (`value` is `null` for a never-set
  `agentState`), otherwise does a conditionally-scoped `UPDATE ... WHERE version =
  expected` (defense against a race between the read and the write — if that loses
  too, re-reads and 409s with the fresh value rather than the stale one) and bumps
  `headerSeq`. Both routes share one `casUpdateSessionField` core, parameterized by
  `field: "metadata" | "agentState"`.
- **`GET /v1/sync?since=<headerSeq>`** — full account snapshot (`headerSeq`, all
  `sessions`/`machines`/`unmanagedSessions` for the account). There's no persisted
  change log, so this is a snapshot, not an incremental delta from `since` — matches
  the design doc's own description ("account snapshot headers"); `since` is validated
  per the wire contract but doesn't currently narrow the query (documented as a future
  optimization, not a correctness gap).
- **`GET /v1/sessions`** — keyset-paginated (`cursor`/`limit`, default 50, max 200) by
  `(updatedAt desc, id desc)`; opaque base64url cursor, not offset-based, so a page
  stays stable under concurrent writes.
- **`GET /v1/sessions/:id/messages?before&limit`** — `msgSeq` cursor pagination,
  newest-first, `before` = the oldest `seq` from the previous page.
- **`POST /v1/machines`** — register (no `machineId`, requires `dek`) or update
  (`machineId` present, CAS'd independently on `metadata` and, if included in the
  body, `daemonState`). 400 if registering without a `dek`; 404 if `machineId` doesn't
  belong to the caller; 409 with both current versioned fields on a mismatch.

## The `eventRouter` seam

Task 1.1 (Socket.IO read path / room-based fan-out) isn't landed on this branch's
base, so there's no real transport to fan out to yet. Rather than block this task on
1.1 or build Socket.IO myself (out of scope for "HTTP write endpoints"), I added a
small `EventRouter` interface (`emitUpdate`/`emitEphemeral`, typed against `@falcon/
wire`'s `Update`/`Ephemeral`) with an in-process `EventEmitter`-backed default
implementation. Every write route calls `eventRouter.emitUpdate(...)` post-commit
instead of touching Socket.IO rooms directly — when 1.1 lands, `app/socket.ts` just
subscribes via `eventRouter.onUpdate(...)` and calls `io.to(room).emit(...)`; no route
code changes. `InMemoryEventRouter` is exported as a value (not just its type) so
tests can instantiate an isolated router per test file and assert "exactly one
fan-out event" without cross-test interference.

`db`/`eventRouter` are both injected into `buildServer(opts, deps)` (mirroring the
already-established `buildAuthRoutes(db)` pattern from the not-yet-merged
`P0-0.4-auth-challenge-route` worktree) and into each route factory
(`buildSessionsRoutes(db, eventRouter)`, etc.), defaulting to the module singletons —
tests bind an in-memory Postgres (`@electric-sql/pglite`) and a fresh
`InMemoryEventRouter` instead of touching `DATABASE_URL` or a shared event stream.

## Database type (`db/types.ts`)

`Database = PgDatabase<any, typeof schema>`: the query-result HKT (first type param)
is erased to `any` (the one thing that genuinely differs between production's
`PostgresJsDatabase` and tests' `PgliteDatabase`), but the schema type param is
pinned to the real schema so `db.query.sessions`/`.sessionMessages`/etc. stay fully
typed across every route file — this is what let `allocMsgSeq`/`allocHeaderSeq`
(typed against the concrete `db/client.ts` `Database`) and the route-level `db.query.*`
calls both type-check against either driver without any casts.

## EncryptedBox <-> bytea codec (`db/box.ts`)

Every `bytea` column stores the **whole** `EncryptedBox` envelope (`{t, v, c}`), not
just the inner ciphertext `c` — so routing/version metadata (`t`/`v`) round-trips
byte-for-byte. `encodeBox`/`decodeBox` are a thin JSON stringify/parse over UTF-8
bytes; the server never touches `c` itself (design §5.3 — no keys held server-side).

## Rate limits & request-size caps

`@fastify/rate-limit` registered globally in `server.ts` (300/min, keyed by
`accountId` when authenticated, else IP) so every route — including the not-yet-landed
auth routes, once they land — gets a floor. Write routes narrow it further via
`config.rateLimit`: session/machine creation 60/min, message ingest 120/min, metadata/
state CAS 240/min (structural PUTs are cheap and legitimately more frequent than
session/machine creation). Default Fastify `bodyLimit` set explicitly to 1 MiB;
message ingest overrides to 16 MiB to fit one coalesced CLI-outbox flush (the outbox's
own disk-backed queue caps at 10 MB, base64 inflates ~33%) — every other route is
small structural JSON, for which 1 MiB is already generous.

## Required integration test

`messages.test.ts`'s first test is exactly the task's ask: POSTs the same `localId`
twice, asserts both responses are `200 {seq: 1}`, queries the DB directly to confirm
**exactly one** `session_messages` row, and asserts the injected `InMemoryEventRouter`
observed **exactly one** `message-new` update. Also covers: increasing `seq` across
distinct `localId`s, 404 on a session that isn't the caller's / doesn't exist, and
`before`/`limit` pagination ordering.

### A real (if narrow) finding surfaced while writing that test

`reply.raw.on("finish", ...)` fired **twice** per single `app.inject()` call (verified
with a throwaway repro script; a real `app.listen()` + `fetch()` request fires
`finish` exactly once, so this is specific to Fastify's `light-my-request` inject
mock, not production behavior). Switched every post-commit fan-out registration from
`.on("finish", ...)` to `.once("finish", ...)` across all four write routes — this is
strictly more correct regardless of the inject quirk: the fan-out contract is "exactly
once, post-commit," and `.once` enforces that defensively rather than relying on the
underlying stream never double-emitting.

## Assumptions

- **Task 1.1 (Socket.IO/eventRouter) not landed on this branch's base** — addressed via
  the `EventRouter` seam described above rather than blocking or building Socket.IO
  myself; 1.1 remains a separate, smaller task (wire the seam to real rooms).
- **Auth routes (`P0-0.4-auth-challenge-route`/`oauth-signin-routes`/
  `pairing-endpoints`) also not landed on this branch's base** — these routes exist
  behind `app.authenticate` regardless of which auth flow issued the token, so nothing
  here depends on them; the global rate-limit registration in `server.ts` will also
  cover those routes' own `config.rateLimit` once they land, satisfying the "rate
  limits on auth ... routes" part of this task's ask without editing files outside
  this task's scope.
- **`GET /v1/sync` returns a full snapshot, not an incremental delta** — there's no
  changelog table for structural entities (only two seq counters, both counts not
  logs), and the design doc itself calls the endpoint "account snapshot headers." A
  future changelog-backed incremental sync is an optimization, not something this task
  regresses.
- **Machine `dek` rotation is out of scope for `POST /v1/machines`'s update path** — a
  `dek` is only accepted/required when registering (no `machineId`); updating an
  existing machine only ever touches `metadata`/`daemonState`.
- **`executionTarget` on session creation accepts any non-empty string** (not
  restricted to `'local'`, matching the schema's own `text` column with no CHECK
  constraint) — `'sandbox'` is explicitly noted as deferred in the schema comments, so
  over-validating here would just have to be loosened later.
- **404, not 403, for cross-account access** (wrong `sessionId`/`machineId` for the
  caller's account) — consistent with the existing schema/design's general posture of
  not distinguishing "doesn't exist" from "not yours" to avoid resource-existence
  enumeration.
