# P4-4.4-prometheus-metrics — Prometheus metrics endpoint + docs quickstart

**Section:** Phase 4 — Ship (M4) / §16 "4.4 Hardening & release gate": "Prometheus
metrics + `/metrics`; docs site quickstart; onboarding time measured <5min".

## What was done

### `GET /metrics` (`packages/server/src/app/routes/metrics.ts`, new)

A Fastify plugin exposing `prom-client`'s shared default `register` in
Prometheus text-exposition format. Defines and exports:

- `httpRequestsTotal` (counter, labels `method`/`route`/`status_code`) —
  request rate; error rate is derived from the `status_code` label at query
  time (`rate(http_requests_total{status_code=~"5.."}[5m])`), not a separate
  metric.
- `httpRequestDurationSeconds` (histogram, same labels) — HTTP latency.
- `wsConnectionsActive` (gauge, label `scope`) / `wsConnectionsTotal`
  (counter, label `scope`) — Socket.IO connection counts by client scope
  (`session-scoped` / `machine-scoped` / `user-scoped`, matching
  `app/socket.ts`'s `ClientType`).
- `collectDefaultMetrics({ register })` — standard Node.js/process metrics
  (event loop lag, heap, GC, fds), guarded by a module-level flag so
  re-importing the module in the same process doesn't double-register
  (`prom-client` throws on that).

RPC latency (the other metric plan.md §16 names explicitly) was **already**
landed — `app/socket/rpcHandler.ts` registers `rpc_calls_total` /
`rpc_call_duration_seconds` / `rpc_lookup_retries` /
`rpc_fetchsockets_timeouts_total` against the same shared `register` from an
earlier task. `/metrics` exposes those too, for free — one scrape endpoint
covers everything registered anywhere in the process, not just what
`routes/metrics.ts` itself defines.

`route` labels always use `request.routeOptions.url` (the *registered
pattern*, e.g. `/v1/sessions/:id/messages`), never the literal request path
— same unbounded-cardinality concern `rpcHandler.ts`'s `method`-not-target-id
labels already guard against. Unmatched routes (404s) label as `"unmatched"`.

### Wiring (existing files, minimal/additive touches)

- `packages/server/src/app/server.ts`: registers `metricsRoutes` alongside
  `healthRoutes`, and adds one `onResponse` hook (fires for every route,
  present and future, without each one instrumenting itself — same pattern
  `rpcHandler.ts` uses for its own `finish()` closure) calling
  `recordHttpRequest(method, route, statusCode, reply.elapsedTime / 1000)`.
- `packages/server/src/app/socket.ts`: calls `recordWsConnectionOpened`
  in the `connection` handler and `recordWsConnectionClosed` in the
  `disconnect` handler, both keyed by `connection.connectionType`.

These two touches were unavoidable — "request rates" and "WS connections"
can't be measured without hooking into where HTTP requests and Socket.IO
connections actually happen. Both are small, additive (no existing logic
changed, only new calls inserted) and outside the CLI-focused surface the
task description asked to stay disjoint from.

### Docs (`docs/quickstart.md`, `docs/observability.md`, new)

- `docs/quickstart.md` — the "docs site quickstart page" plan.md §16 calls
  for: install → sign in → first session → watch/control from web → optional
  shim install, each step time-boxed (~1 min) to sum to the <5min target
  from falcon-prd.md §5.1/§7 ("M4 — Ship" exit criterion). Ends with a
  "Reporting onboarding time" section describing how to actually measure and
  record a run (stopwatch + fresh tester, same as Happy/Omnara's own
  validation approach) — no automated onboarding-time tooling exists yet,
  so this documents the manual process rather than fabricating a number.
- `docs/observability.md` — what `/metrics` exposes (the table above), why
  RPC metrics live in `rpcHandler.ts` but appear at this endpoint anyway,
  and the "keep this off the public ingress" operational note driven by
  falcon-system-design.md §6.2's `GET /metrics (bind-local)` — Fastify has
  no per-route listener binding, so that's a reverse-proxy/network-policy
  concern for operators (documented, not enforced in-process).

Both docs follow the existing `docs/protocol.md`/`docs/encryption.md`
"lightweight stub, expand later" convention (status banner, TODO section,
cross-links).

### Tests (`packages/server/src/app/routes/metrics.test.ts`, new)

6 tests via `buildServer({ logger: false }).inject(...)`: 200 + `text/plain`
content type; the shared `rpc_calls_total` metric shows up (proving the
shared-registry wiring works); default Node.js process metrics present;
an HTTP request made before the scrape is counted; an unknown route labels
as `"unmatched"` rather than leaking the literal 404 path; `POST /metrics`
404s/405s since only `GET` is registered.

## Assumptions

- Kept the new metric definitions inside `routes/metrics.ts` rather than a
  separate `app/metrics.ts` module, since the task explicitly named
  `packages/server/src/app/routes/metrics.ts` as the deliverable file and
  the metric set is small enough not to warrant splitting registration from
  the route that exposes it.
- `/metrics` is unauthenticated, matching `/health`'s existing precedent —
  a Prometheus scrape target can't hold a bearer token any more meaningfully
  than a liveness probe can. Restricting exposure is documented as a
  network-layer (reverse proxy / firewall) concern in `docs/observability.md`,
  per the design doc's own `(bind-local)` annotation — not something the
  route can enforce in-process.
- `docs/quickstart.md` is Markdown, not a real "docs site" (no static-site
  generator exists in this repo yet) — same honest-stub approach
  `docs/protocol.md`/`docs/encryption.md` already took for their areas, with
  an explicit TODO noting the gap. "Onboarding time measured <5min" is
  addressed as a documented manual measurement process (stopwatch + fresh
  tester), not automated telemetry — no existing instrumentation point for
  "time from install to first successful remote session" exists anywhere in
  the CLI, and building one was out of scope for this metrics/docs task.
- Did not add a separate `error_rate` metric — Prometheus convention is to
  derive error rate from `status_code`/`result` labels on the existing
  counters via a query (`rate(...{status_code=~"5.."}[5m])`), which is what
  both `http_requests_total` and the pre-existing `rpc_calls_total` already
  support; a redundant pre-aggregated counter would just be another way the
  two could drift.
