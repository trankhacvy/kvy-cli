# P0-0.4-server-skeleton — Server foundation

Scaffolds `packages/server` (`@falcon/server`): a Fastify 5 app skeleton using
the zod type-provider for typed routes, a `GET /health` liveness endpoint, and
pino structured logging wired through Fastify's built-in logger. This is the
foundation the rest of Phase 0.4 (Drizzle schema, `seq.ts`, auth routes) will
build on — no DB or auth in this task, per scope.

## What was added

```
packages/server/
├─ package.json          # @falcon/server — private app package
├─ tsconfig.json          # extends ../../tsconfig.base.json (strict, @/* alias)
├─ vitest.config.ts
└─ src/
   ├─ main.ts             # process entry: build → listen → graceful shutdown
   ├─ config.ts            # zod-validated env (NODE_ENV, PORT, HOST, LOG_LEVEL)
   ├─ logger.ts             # pino LoggerOptions (pretty outside prod, JSON in prod, redacts auth headers)
   └─ app/
      ├─ server.ts          # buildServer() factory: Fastify + zod type-provider wiring
      ├─ server.test.ts     # vitest + app.inject() — /health 200, unknown route 404
      └─ api/
         └─ health.ts       # GET /health (zod response schema)
```

File layout follows falcon-system-design.md §3/§6's
`src/{main,app/{api,...}}` shape. `app/api/`, `app/auth/`, `app/events/`,
`app/rpc/`, `app/push/`, `app/presence/`, `app/blobs/`, and `db/` are left for
the tasks that actually need them (Drizzle schema, auth routes, event router,
etc.) rather than stubbed out empty now.

## Implementation notes

- **Zod type-provider**: `fastify-type-provider-zod` v7 (matches the version
  Happy's server already runs against Fastify 5 + zod v4). `buildServer()`
  calls `.withTypeProvider<ZodTypeProvider>()` and installs
  `validatorCompiler`/`serializerCompiler` before any routes are registered,
  so every route below can declare `schema: { response: { 200: ZodSchema } }`
  with full type inference — exactly what `POST /sessions/:id/messages`,
  `PUT .../metadata` etc. will need in the next tasks.
- **Pino logging**: rather than hand-rolling a separate pino instance (Happy's
  approach — needed there because happy-server ships as a `bun build --compile`
  single-file binary where pino's worker-thread transport can't resolve
  `pino-pretty` from a virtual filesystem), `src/logger.ts` returns
  `pino.LoggerOptions` passed straight into `Fastify({ logger })`. Fastify's
  logger *is* pino, so this is the minimal, idiomatic way to wire it in — no
  bun-compile constraint applies to `@falcon/server` (it runs as a normal
  Node process / docker image per design §6.5), so the simpler path was
  taken deliberately. Structured JSON in production, `pino-pretty` outside
  production (dev only — not a production dependency path). Redacts
  `authorization`/`cookie` headers as a baseline (no user content ever
  reaches Fastify's request logger regardless, since all content is
  E2E-encrypted before the server sees it — design principle #2).
- **`buildServer(opts)` app-factory pattern**: separates app construction
  from `listen()` so tests use `app.inject()` with `{ logger: false }` and
  never open a real port — matches the Fastify testing guidance and keeps
  the health-route test fast/deterministic.
- **`GET /health`**: returns `{ status: "ok", uptimeSeconds, timestamp }`
  with a zod response schema (demonstrates the type-provider end-to-end).
  Deliberately has no DB/dependency check yet — that's out of scope here and
  will likely become a real readiness probe once Postgres lands.
- **Config**: `src/config.ts` validates `process.env` once at import time
  with zod (`NODE_ENV`, `PORT` default 3005, `HOST` default `0.0.0.0`,
  `LOG_LEVEL` default `info`) — "config via env only" per design §6.5's
  self-host docker-compose shape. Fails fast on a bad env instead of a
  runtime crash mid-request.
- **Build**: mirrors `@falcon/wire`/`@falcon/crypto`'s existing
  `shx rm -rf dist && tsc --noEmit && pkgroll` pattern rather than
  introducing a new bundler. `pkgroll` bundles `src/main.ts` into a single
  `dist/main.js` (resolving all relative imports, so Node's native ESM
  loader — which requires explicit extensions — never has to resolve
  bare/extensionless specifiers at runtime). `pnpm --filter @falcon/server
  start` runs `node dist/main.js`; `pnpm --filter @falcon/server dev` runs
  `tsx watch src/main.ts` for local iteration.
- **Workspace/turbo wiring**: no changes needed to `pnpm-workspace.yaml`
  (already globs `packages/*`) or `turbo.json` (task pipeline is generic —
  any package exposing `build`/`typecheck`/`test`/`lint` scripts picks it up
  automatically). `pnpm-lock.yaml` updated by `pnpm install`.

## Assumptions

- `PORT` default `3005`, `HOST` default `0.0.0.0` — no default was specified
  in the design doc beyond "config via env only"; chose 3005 to match
  Happy's server default (least-surprise for anyone porting further Happy
  routes) and `0.0.0.0` since the design's deployment shapes (Docker, Fly,
  K8s, compose) all expect the container to bind all interfaces.
  `GET /metrics (bind-local)` from §6.2 is explicitly out of scope for this
  task.
- No `@fastify/cors` or other ecosystem plugins added — not requested by
  this task and would expand scope beyond "app skeleton + zod type-provider
  + /health + pino logging."
- Health payload shape (`status`/`uptimeSeconds`/`timestamp`) is not
  specified anywhere in the design doc; kept intentionally minimal since the
  doc only says `GET /health` exists.

## Verification

- `pnpm --filter @falcon/server build` — passes (tsc --noEmit, then pkgroll
  → `dist/main.js`).
- `pnpm --filter @falcon/server typecheck` — passes.
- `pnpm --filter @falcon/server test` — 2/2 tests pass (`server.test.ts`).
- `pnpm build && pnpm typecheck && pnpm test` at the repo root — all green
  across `@falcon/wire` (61 tests), `@falcon/crypto` (65 tests), and
  `@falcon/server` (2 tests).
- Manually booted `node dist/main.js` (`NODE_ENV=production`) and
  `pnpm dev` (tsx watch): both bind, log structured pino output, and
  `curl http://127.0.0.1:<port>/health` returns
  `200 {"status":"ok","uptimeSeconds":...,"timestamp":"..."}`. `SIGTERM`
  triggers a clean `app.close()` shutdown in both modes.
- `pnpm lint` / `biome check` currently fails with
  `[warn] Linter process terminated abnormally (possibly out of memory)` in
  this sandbox — confirmed **pre-existing and unrelated to this change**:
  the same OOM reproduces running `npx biome check packages/wire` (an
  already-merged, passing package) in this environment, and even on a
  single new file in isolation. Not something introduced or fixable within
  this task's scope.
