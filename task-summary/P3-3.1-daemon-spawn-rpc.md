# P3-3.1-daemon-spawn-rpc — Daemon `spawn` RPC

Phase 3 §3.1 "Remote spawn" (plan.md line 751-754), design §7.3/§4.4/§12.

## What was built

All new/changed files live under `packages/cli/src/daemon/` (plus one shared
utility touch-up). No wire schema changes were needed — `@falcon/wire`'s
`SpawnParamsSchema`/`SpawnResultSchema` (`packages/wire/src/rpc.ts`) already
matched the design doc's `SpawnParams` shape verbatim, including
`idempotencyKey`.

**New modules:**

- `envExpand.ts` — `expandEnvVars(template, baseEnv)`: expands `${VAR}`
  placeholders in an env-var template against a base environment, **failing
  fast** (returns `{ok:false, unresolved:[...]}`, collecting every unresolved
  name across all entries) rather than the Bash/Node convention of silently
  substituting `''`.
- `workspacePath.ts` — `validateSpawnWorkspace({workspaceId, directory}, lookupRoot)`:
  rejects non-absolute directories, unknown workspaces, nonexistent paths,
  non-directories, and directories that resolve (via `realpath`, so symlink
  escapes are caught) outside the registered workspace root. `lookupRoot` is
  injected — this module owns the validation *policy* (design §12: "spawn
  params validated against registered workspace paths (no arbitrary-directory
  execution from remote)"), not wherever "registered workspaces" end up
  persisted (that registry doesn't exist in `packages/cli` yet — see
  Assumptions below).
- `processLauncher.ts` — `launchProviderProcess(opts, deps)`: tmux-preferred
  spawner (`tmux new-session -d -s falcon-<sessionLabel>`), detached
  (`unref`'d) fallback when tmux isn't installed (ENOENT). For the tmux path,
  it queries `tmux list-panes -t <name> -F "#{pane_pid}"` to recover the
  *actual* spawned process's pid (not tmux's own server pid) — required for
  the pid↔webhook matching below. Uses the same `cross-spawn` convention as
  `claude/claudeLocal.ts` (Windows `.cmd` shim correctness), injectable
  `spawnImpl` for tests.
- `spawnAwaiter.ts` — `createSpawnAwaiter({timeoutMs = 15_000})`: a
  pid-keyed `Map` of pending waiters. `waitFor(pid)` blocks until `resolve({
  sessionId, pid, ... })` is called with a matching pid, or rejects after the
  15s timeout. This is the "spawn↔webhook matching by PID" mechanism —
  the daemon knows the pid it just launched immediately but not the
  `sessionId` until the spawned session self-reports.
- `spawnEngine.ts` — `spawnSession(params, deps)`: the orchestrator. Validates
  the workspace path → expands the env template → builds
  `falcon <provider> --starting-mode remote --started-by daemon [--permission-mode
  <mode>] [--model <model>] [--continue-from <id>]` by re-invoking this same
  falcon entrypoint (same `process.execPath`/`execArgv`/`argv[1]` pattern as
  `daemon/commands.ts`'s `defaultSpawnStartSync`) → launches it → awaits the
  matching webhook by pid. Throws a `SpawnError` (one exception type) for
  every failure stage so callers have one thing to catch.
- `machineRpc.ts` — `registerMachineRpcHandlers(deps)`: the wire-level RPC
  handler. Mirrors `rpc/sessionRpc.ts`'s registration/decrypt/validate/seal
  shape exactly, adapted to the machine-scoped `m:<machineId>:spawn` target.
  Owns the **idempotency-key replay map** (`Map<idempotencyKey, SpawnResult>`)
  exactly as sketched in plan.md's `machineRpc.ts` snippet — a retried call
  with the same key replays the prior *successful* result; a failed attempt
  is deliberately **not** cached, since the actual non-idempotent side effect
  is the process spawn itself, so a validation/timeout failure is safe (and
  correct) to retry from scratch.

**Modified:**

- `controlServer.ts` — added optional `pid` to `SessionStartedBodySchema` and
  threaded it through to `onSessionStarted(sessionId, metadata, encryption,
  pid)`. This is the one piece of shared, already-existing surface both spawn
  paths (wire RPC and the pre-existing HTTP loopback `/spawn-session`) go
  through, and it's the only way `spawnAwaiter.ts` can correlate a webhook
  back to a launched pid.
- `notify.ts` — `notifyDaemonSessionStarted`'s POST body now includes `pid`
  (defaults to `process.pid`, overridable). This is the client-side half of
  the same webhook; sending it unconditionally is harmless (a
  terminal-started session has no pending awaiter, so `resolve()` is a no-op
  for it on the daemon side).
- `controlServer.test.ts` / `notify.test.ts` / `notify.integration.test.ts` —
  updated the affected exact-call/body assertions for the new `pid` field.

## Idempotency, workspace validation, tmux spawn, env expansion, PID awaiter — all five task bullets

1. **Idempotency-key replay** — `machineRpc.ts`'s `spawnResults` map.
2. **Workspace-path validation** — `workspacePath.ts`, invoked from
   `spawnEngine.ts` before any process is launched.
3. **tmux-preferred spawner + detached fallback** — `processLauncher.ts`.
4. **Env `${VAR}` expansion, fail-fast** — `envExpand.ts`, invoked from
   `spawnEngine.ts` (via the injectable `envTemplate`/`baseEnv` seam) before
   launch.
5. **Spawn↔webhook matching by PID, 15s awaiter** — `spawnAwaiter.ts`,
   invoked from `spawnEngine.ts` right after launch.

## Assumptions / scope boundaries

- **`registerMachineRpcHandlers` is not yet wired into a live daemon boot
  sequence**, by design, matching an existing boundary already documented in
  this codebase: `machineClient.ts`'s own header comment says "RPC handler
  registration ... is a separate, later plan bullet." `startMachineClient`
  (the module that owns the daemon's actual socket to the server) is itself
  not called anywhere in `commands.ts`/`runDaemonStartSync` yet — wiring it
  in would require synthesizing daemon-side auth-token/DEK acquisition that
  doesn't exist yet in `packages/cli`, which is a different, not-yet-started
  piece of work, not this task's scope. `machineRpc.ts` is complete, fully
  unit-tested (mirroring the exact pattern `rpc/sessionRpc.ts` used before
  `claudeRemote.ts` wired *that* one in), and ready to be handed a real
  `Socket` + machine DEK once that boot-sequence task lands.
- **Workspace-root resolution is injected, not persisted.** There is no
  on-disk "registered workspaces" store in `packages/cli` yet (`falcon
  workspace config` is still a stub in `index.ts`). `workspacePath.ts` takes
  a `WorkspaceRootLookup` callback rather than inventing that registry itself
  — building it is a different, unscoped piece of work, and guessing at its
  storage shape here risked conflicting with whatever task actually builds
  it.
- **The pre-existing HTTP loopback `/spawn-session` path (`controlServer.ts`
  + `commands.ts`'s `spawnSession` stub) was deliberately left untouched**,
  beyond the shared `pid` field addition. Its body schema has no
  `workspaceId`/`idempotencyKey` and a `sessionId` field whose semantics
  belong to the resume RPC (§3.2, a separate plan bullet with its own
  `FALCON_RECONNECT_*` env-var contract) — wiring it to this task's spawn
  engine would have required guessing at that different feature's design.
  `commands.ts`'s `spawnSession` callback still honestly reports "not
  implemented yet" for that path.
- Env-var expansion's `envTemplate` has no default non-empty content (an
  empty template is a no-op) — this task builds and wires the *mechanism*
  the design calls for; any specific "which vars get propagated" policy is a
  product decision for whoever does the boot-sequence wiring above.
- `--permission-mode`/`--model`/`--continue-from`/`--starting-mode`/
  `--started-by` are argv flags the spawned `falcon <provider>` process is
  expected to parse — that parsing itself lives in `args.ts`/the `claude`
  package (a disjoint, parallel Phase-2 task's file scope) and isn't touched
  here; `daemon/markers.ts` already documents `--starting-mode
  remote --started-by daemon` as the process-marker convention this spawner
  must produce.
- Branch/worktree (`-b`, `git worktree add`) is explicitly the next, separate
  plan.md §3.1 bullet — not implemented here.

## Bug found and fixed during testing

`processLauncher.ts`'s detached-fallback path called `child.unref()`
unconditionally; changed to `child.unref?.()` — defensive, since not every
object shaped like a `ChildProcess` (e.g. a test double, or conceivably some
future non-Node runtime) is guaranteed to have it, and there's no reason for
a successful spawn to hard-crash over a missing convenience method.
