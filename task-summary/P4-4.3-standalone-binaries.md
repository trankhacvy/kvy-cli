## What was built

Fidelity: **(N)** new code. There is no Happy source available in this environment to port from (`/private/tmp/happy-src` referenced in `happy-research.md` is an empty directory) — `research.md`/`happy-research.md` only describe Happy/Superset's release engineering at a narrative level (rolling `cli-latest` GitHub release tag, atomic self-update, unified semver across CLI/desktop). This task follows falcon-system-design.md §3's explicit choice ("npm package + `bun build --compile` standalone binaries (mac arm64/x64, linux x64)") and plan.md §16's "4.3 Distribution & self-host" bullet, built from scratch as ordinary release-engineering scripts + a GitHub Actions workflow.

### 1. `scripts/build-binaries.sh` (new)

Compiles `packages/cli/dist/index.mjs` (the existing `tsc`+`pkgroll` bundle `pnpm --filter falcon build` already produces and tests) into three standalone executables via `bun build --compile`:

- `falcon-darwin-arm64`, `falcon-darwin-x64`, `falcon-linux-x64` — via `--target=bun-darwin-arm64` / `bun-darwin-x64` / `bun-linux-x64`. Bun cross-compiles all three from a single host (no macOS runner needed), so the release workflow builds everything on one `ubuntu-latest` job.
- Bakes the real package version into the binary via `--define:__FALCON_CLI_VERSION__="\"$VERSION\""` (see the `index.ts` change below — without this, a compiled binary has no on-disk `package.json` sibling to read and would silently report `--version` as `0.0.0`).
- Emits a `.sha256` checksum file alongside each binary (`sha256sum`/`shasum -a 256`, whichever is available), which `scripts/install.sh` verifies before installing.
- Fails loudly (non-zero exit, clear stderr message) if `bun` isn't on `PATH` or if `dist/index.mjs` hasn't been built yet — no silent fallback.
- Output directory defaults to `dist-binaries/` at the repo root (gitignored — new `.gitignore` entry).

### 2. `scripts/install.sh` (new) — the `curl | sh` path

POSIX `sh` (not bash) for maximum portability on a fresh machine that only has `curl`/`sh`:

- Detects OS (`Darwin`/`Linux`) and arch (`arm64`/`aarch64` → `arm64`, `x86_64`/`amd64` → `x64`) via `uname`. Any other combination (Windows, linux-arm64 — no binary published for it yet, Windows itself unsupported by this path) exits with a clear message pointing at `npm install -g falcon` as the fallback, rather than failing opaquely.
- Downloads from `https://github.com/$FALCON_REPO/releases/latest/download/falcon-$platform-$arch` (or a pinned `$FALCON_VERSION` tag), verifies the `.sha256` sidecar, and only then installs.
- Installs to `$FALCON_HOME_DIR/bin/falcon` (default `~/.falcon/bin/falcon`) — deliberately the *same* directory the existing shell-shim feature (`packages/cli/src/shim/paths.ts`'s `shimBinDir()`) already uses for `claude`/`codex` wrapper shims, so there's one `~/.falcon/bin` PATH entry regardless of which Falcon-provided binaries a machine ends up with.
- If that directory isn't already on `$PATH`, appends a PATH export to the user's shell rc file (zsh/bash/fish/`.profile`, detected via `$SHELL`), using **the exact same marker comments** (`# >>> falcon shell shim >>>` / `# <<< falcon shell shim <<<`) that `packages/cli/src/shim/rcBlock.ts`'s `BLOCK_START`/`BLOCK_END` already define. This is intentional: `falcon shim install/uninstall`'s `hasRcBlock()`/`removeRcBlock()` string-match on those exact markers, so a machine that ran `curl | sh` first and later runs `falcon shim install` sees the PATH block as already present instead of writing a duplicate one. The two files carry a comment cross-reference to keep them in sync if the marker text ever changes.
- Idempotent: re-running skips the rc-file write if the block (or the directory generally) is already on `PATH`.

### 3. `packages/cli/src/index.ts` — version embedding for compiled binaries (small, targeted change)

`readVersion()` previously always read `package.json` next to the running module via `import.meta.url`. That works for `npm install -g falcon` and local dev, but a `bun build --compile` binary has no such sibling file on disk — it would silently fall through to the existing `catch { return "0.0.0" }` and misreport its own version forever. Added one early-exit branch:

```ts
declare const __FALCON_CLI_VERSION__: string | undefined;

function readVersion(): string {
  if (typeof __FALCON_CLI_VERSION__ !== "undefined") return __FALCON_CLI_VERSION__;
  // ...unchanged package.json read...
}
```

`typeof` on an undeclared identifier never throws, so this is a no-op for every existing execution path (dev via `tsx`, `npm`-installed, current test suite) — `__FALCON_CLI_VERSION__` is only ever defined when `scripts/build-binaries.sh` passes `--define:__FALCON_CLI_VERSION__` to `bun build`. Verified with `node dist/index.mjs --version` → `falcon 0.1.0` (unchanged behavior).

### 4. `packages/cli/package.json` — publish config

- Removed `"private": true` (it was the only thing that would have made `npm publish`/`pnpm publish` refuse to run — every *other* workspace package correctly keeps `"private": true`; `falcon` is the one package meant to actually ship).
- Added `files: ["bin", "dist"]` so the published tarball doesn't include `src/`, tests, or config files.
- Added `publishConfig.access: "public"` (required for an unscoped/scoped-but-public npm publish under an npm org).
- Added `repository`/`homepage`/`bugs`/`keywords` metadata (placeholder `falcon-dev/falcon` GitHub slug — see "Known limitations"/assumptions below).
- Added `engines.node: ">=20"` (matches the root package.json's existing constraint; npm warns instead of silently misbehaving on older Node).
- Added `prepublishOnly: "pnpm run build"` as a last-line-of-defense so a manual `npm publish` from a stale `dist/` can't happen (CI's publish job also builds explicitly first).

`npm install -g falcon` needs no compiled binary or platform-specific packaging (no `optionalDependencies`-per-platform / wrapper-package pattern was needed) — the package already ships a plain Node CLI (`bin/falcon.mjs` → `dist/index.mjs`), which runs identically on any platform with Node ≥20. The standalone-binaries path exists specifically for machines *without* Node; the two distribution paths are complementary, not redundant.

### 5. `.github/workflows/release.yml` (new)

Triggers on `vX.Y.Z` tag push or manual `workflow_dispatch`. Three jobs:

1. **`build-binaries`** (`ubuntu-latest`): `pnpm install --frozen-lockfile` → `pnpm --filter falcon... build` (builds `@falcon/wire`/`@falcon/crypto` first, then `falcon`, respecting the workspace dependency graph) → `oven-sh/setup-bun` → `scripts/build-binaries.sh` → uploads `dist-binaries/*` as a build artifact.
2. **`github-release`** (needs `build-binaries`): downloads the artifact, publishes a GitHub Release with the three binaries + their `.sha256` files attached via `softprops/action-gh-release`, `fail_on_unmatched_files: true` so a missing binary fails the release instead of publishing an incomplete one.
3. **`publish-npm`** (needs `build-binaries`, runs independently of `github-release`): rebuilds (same `pnpm --filter falcon... build`) and runs `pnpm --filter falcon publish --access public --no-git-checks` against `NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}`.

### 6. Misc

- `.gitignore`: added `dist-binaries/`.
- Root `package.json`: added a `build:binaries` convenience script (`bash scripts/build-binaries.sh`) alongside the existing `build`/`test`/`typecheck`/`lint` scripts.

## Known limitations / assumptions

- **No `bun` in this sandbox.** `scripts/build-binaries.sh` was verified for shell syntax (`bash -n`) and its pure-logic pieces (platform/arch detection, PATH-already-present check) were smoke-tested by extracting them into a standalone script and running under `sh`/`bash` — but the actual `bun build --compile` invocation itself could not be exercised end-to-end here, since `bun` isn't installed. The GitHub Actions workflow installs it via `oven-sh/setup-bun@v2`, which is the intended real execution environment.
- **Placeholder GitHub repo slug.** `git remote -v` on this worktree is empty (no real origin configured yet), so `packages/cli/package.json`'s `repository`/`homepage`/`bugs` fields and `scripts/install.sh`'s default `FALCON_REPO="falcon-dev/falcon"` are placeholders. Both are trivially overridable (`FALCON_REPO=<org>/<repo> curl ... | sh`) and should be updated to the real slug once the project has an actual GitHub repo.
- **`NPM_TOKEN` secret assumed.** `publish-npm` reads `secrets.NPM_TOKEN` — this needs to be configured in the repo's GitHub Actions secrets before the workflow can actually publish; until then the job fails at the `npm publish` auth step rather than silently no-opping.
- **`pnpm lint`/`biome check` could not be run to completion in this environment** — it consistently hit the pre-existing `[warn] Linter process terminated abnormally (possibly out of memory)` flake documented in this repo's `CLAUDE.md` (multiple concurrent worktree sandboxes competing for memory), including on retry and when scoped to just the ~6 changed/new files. `pnpm build`, `pnpm typecheck`, and `pnpm test` (the three checks this task's instructions require) all ran to completion and are green; the new shell/YAML/JSON files were hand-reviewed for Biome's formatting conventions (double quotes, trailing commas per existing `packages/cli/package.json` style, etc.) as a substitute.
- **Out of scope, deliberately not touched** (belongs to other unchecked plan.md bullets, not this task): CLI self-update (`cli-latest` rolling tag, atomic replace, `FALCON_NO_UPDATE`), daemon service install (launchd/systemd), and `deploy/docker-compose.yml` — those are the two sibling P4-4.3 worktree tasks (`P4-4.3-daemon-service-install`, `P4-4.3-docker-compose-selfhost`) running in parallel; this task touched only the files listed above, no overlap.
