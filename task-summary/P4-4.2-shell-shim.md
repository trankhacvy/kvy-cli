# P4-4.2-shell-shim — Shell shim

**Section:** plan.md §16 "4.2 Adoption Tier 3 + polish" — "Shell shim: `falcon shim
install/uninstall/status`, `~/.falcon/bin` PATH block, onboarding opt-in prompt — §11".
Backed by falcon-prd.md FR-9.6 and falcon-system-design.md §7.2 (`bin/` — optional
shims (Tier 3 adoption): `claude`, `codex` → `falcon`).

Classified as **(N) new code** — no direct Happy precedent for this feature.

## What was built

A new `packages/cli/src/shim/` module plus CLI wiring:

- **`shim/paths.ts`** — path resolution. Two independently-overridable home
  directories are in play (both test seams, never set in production):
  `homeDir` (Falcon's own `~/.falcon`/`FALCON_HOME_DIR`, where the shim binaries
  live) and `userHomeDir` (`os.homedir()`, where shell rc files live) — kept
  strictly separate so `FALCON_HOME_DIR`-isolated tests never touch a real
  `.zshrc`/`.bashrc`/`.profile`. `preferredRcFile()` picks a single target rc
  file from `$SHELL` (zsh → `.zshrc`, bash → `.bashrc`, fish →
  `.config/fish/config.fish`, else → `.profile`, the POSIX-universal login
  fallback). `rcFileCandidates()` lists all four — used by `status`/`uninstall`
  so they self-heal even if `$SHELL` changed since install.
- **`shim/rcBlock.ts`** — pure string functions for the single clearly-marked
  PATH block (`# >>> falcon shell shim >>> ... # <<< falcon shell shim <<<`),
  syntax-aware (POSIX `export PATH=...` vs. fish `set -gx PATH ...`).
  `insertRcBlock`/`removeRcBlock` are both idempotent and round-trip exactly
  (install→uninstall restores the original file byte-for-byte). No filesystem
  I/O in this file — fully unit-testable without touching disk.
- **`shim/install.ts`** — writes `~/.falcon/bin/{claude,codex}` as 0755 POSIX
  shell scripts (`exec falcon <name> "$@"`) via tmp-file + rename (atomic,
  matches the codebase's existing `persistence.ts`/`workspace/registry.ts`
  pattern), then appends the PATH block to the preferred rc file (also
  tmp+rename) — a no-op if the block is already present.
- **`shim/uninstall.ts`** — removes both shim binaries (if present) and strips
  the PATH block from *every* rc-file candidate that has one, not just the
  preferred one.
- **`shim/status.ts`** — read-only report: which binaries exist, which rc
  files carry the block, and whether `~/.falcon/bin` is on the *current*
  process's `$PATH` (informational — a fresh install can't retroactively
  change the running shell's environment).
- **`shim/onboardingPrompt.ts`** — the FR-9.6 "opt-in at onboarding" prompt.
  Gated on `persistence.ts`'s existing (previously-unused) `Settings.
  onboardingCompleted` field — this task is its first real consumer. Runs at
  most once: asks a y/n question (only when interactive — `process.stdin.
  isTTY`), installs the shim on "yes", and marks `onboardingCompleted: true`
  regardless of the answer or of interactivity (a non-interactive/CI run
  never re-prompts on a later interactive run). A failed install (e.g. a
  permission error) is reported but never thrown — the surrounding `auth
  login` command still succeeds.
- **`commands/shim.ts`** — thin CLI-output wiring over the three functions
  above, following the same injectable-`write`/options-object pattern as
  `commands/workspaceConfig.ts`.

## Wiring

- **`args.ts`** — new `{ type: "shim"; action: "install" | "uninstall" |
  "status" }` command; `falcon shim <action>` parses/validates like every
  other Falcon subcommand.
- **`index.ts`** — new `runShim()` dispatcher (no `ensureDaemon()` call — pure
  local filesystem work, same rationale as `workspace config`/`workspace
  register`). `runAuth()` now calls `maybePromptShimOptIn()` after a
  successful `auth login` (and only then — not on `logout`/`status`, and not
  on a failed login). Help text gained a `falcon shim install|uninstall|status`
  line.

## Testing

37 new tests across `shim/paths.test.ts`, `shim/rcBlock.test.ts`,
`shim/install.test.ts`, `shim/uninstall.test.ts`, `shim/status.test.ts`,
`shim/onboardingPrompt.test.ts`, `commands/shim.test.ts`, plus additions to
`args.test.ts` (shim parsing) and `index.test.ts` (shim command wiring +
auth-login → onboarding-prompt wiring, using the file's existing
`vi.doMock`/`importMain()` pattern). All filesystem-touching tests use
`mkdtempSync` for both `homeDir` and `userHomeDir` — nothing here ever reads
or writes a real `~/.falcon` or a real shell rc file.

`pnpm build` / `pnpm typecheck` / `pnpm test` all green workspace-wide
(9/9 tasks; 963/963 `falcon` cli tests, up from 926).

## Assumptions / scope notes

- Only zsh, bash, fish, and the POSIX `.profile` fallback are supported rc
  targets — covers the realistic macOS/Linux dev-machine set called out in
  falcon-prd.md FR-1.1 (macOS arm64/x64, Linux x64 at MVP; Windows is P2, and
  a `cmd`/`powershell` shim would need a wholly different mechanism anyway).
- The onboarding prompt is wired at the single natural trigger point the
  existing codebase actually has — a successful `falcon auth login` — since
  `falcon`'s own "first run" flow (FR-1.2: sign-in + machine registration +
  daemon auto-start) isn't fully composed yet (`describeStart()` in
  `index.ts` is still an honest stub). No other first-run hook exists to wire
  it into today.
- `falcon shim install` always targets a single rc file (the `$SHELL`-derived
  preferred one); `status`/`uninstall` scan all four candidates so a later
  shell switch never leaves an orphaned PATH block invisible to either
  command.
- No new `settings.json` fields beyond reusing the existing
  `onboardingCompleted` boolean — shim installation state is derived
  entirely from the filesystem (binary presence + rc-block presence), not
  tracked redundantly, so `status` can never drift from reality.
