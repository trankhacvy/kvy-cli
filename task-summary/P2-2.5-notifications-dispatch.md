# P2-2.5-notifications-dispatch — Server lifecycle notification dispatch + Web Push subscription

Phase 2 §2.5 Notifications (plan.md §10, falcon-system-design.md §6.4, falcon-prd.md
§5.7/§5.8 FR-7.6/FR-8.1-8.3).

## What shipped

### `@falcon/wire` (`packages/wire/src/push.ts`)

- `LifecycleKindSchema` (`perm | question | done | failed`) — the shared enum for
  lifecycle events; `updates.ts`'s `attention` ephemeral now imports it instead of
  duplicating the literal union.
- `PushChannelSchema` (`webpush | telegram | ntfy`).
- `PushSubscribeBodySchema` / `PushUnsubscribeBodySchema` — `POST`/`DELETE
  /v1/push/subscribe` bodies.
- `PushPayloadSchema` — the generic `{sessionId, kind}` shape actually delivered over
  Web Push (no title/body/content: the server holds no keys to encrypt anything richer,
  design §5.3).
- Registered all five in `__tests__/schemaRegistry.ts` and re-froze
  `__fixtures__/wire-shapes.json` via `scripts/snapshot-shapes.ts`.

### `packages/server` — dispatch + channels

- `src/app/push/types.ts` — `PresencePort`, `PushChannel`, `PushDispatcherPort`.
- `src/app/push/dispatch.ts` — `buildPushDispatcher(db, presence)`: port of Happy's
  `pushDispatch.ts` model. Presence-suppresses, then fans out to every subscription's
  channel; never rejects (every failure is caught/logged so a broken push path can't
  take down the caller's request); prunes a subscription on a 404/410 "gone" error from
  its channel (mirrors Happy's `DeviceNotRegistered` cleanup).
- `src/app/push/channels/webpush.ts` — full `web-push` implementation, lazy
  `setVapidDetails`, logs-and-skips (doesn't throw) when `VAPID_PUBLIC_KEY`/
  `VAPID_PRIVATE_KEY` aren't configured.
- `src/app/push/channels/telegram.ts`, `ntfy.ts` — stub senders (log-and-drop) per the
  task's explicit scope ("implement webpush fully now, stub telegram/ntfy for later").
  `POST /v1/push/subscribe` already accepts both channels so pairing UI can land ahead
  of the sender.
- `src/config.ts` — `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` (optional) + `VAPID_SUBJECT`
  (defaulted). Missing keys are a capability gap, not a security boundary, so this is
  "log and skip that send," not "fail closed."
- `src/app/events/eventRouter.ts` — new `hasActiveVisibleClient(accountId, sessionId)`.
  Falcon add vs. Happy's account-wide-only `isUserActive`: scoped to the
  `all-interested-in-session` room set and filtered to `user-scoped` connections only
  (session-scoped sockets are CLI processes, not human presence). **Known limitation,
  documented in the method's own comment**: the web app today has no per-session
  "I'm looking at this one" signal (no session detail screen exists yet — only the
  session-list screen), so in practice this currently behaves like Happy's
  "the account has an active tab open somewhere" until a future session-detail screen
  starts joining the per-session room too; no further server change will be needed when
  that lands.
- `src/app/routes/push.ts` — `POST`/`DELETE /v1/push/subscribe`. Upserts on `endpoint`
  (globally unique per schema) idempotently for the *same* account; 409s rather than
  silently reassigning ownership if a different account's endpoint collides.
- `src/app/routes/sessionNotify.ts` — new `POST /v1/sessions/:id/notify {kind: "perm" |
  "question" | "done"}`. This is the generic lifecycle-signal endpoint plan.md §10
  describes — content-free by design (unlike Happy's `push-event` route, which carries
  plaintext title/body since Happy has no E2E encryption). Emits the existing
  `attention` ephemeral and fires `pushDispatcher.dispatch(...)`.
- `src/app/routes/sessionStatus.ts` — wired `pushDispatcher.dispatch({kind: "failed"})`
  into the already-landed `failed`-transition branch, alongside its existing `attention`
  ephemeral emit.
- `src/app/server.ts` — registers the new routes; `buildServer()` gained an injectable
  `pushDispatcher` dep (defaults to a real one built from `db` + the process-wide
  `eventRouter` singleton, mirroring the existing `eventRouter` dep pattern).
- `src/app/routes/testHelpers.ts` — `RecordingPushDispatcher` fake, same shape as
  `RecordingEventRouter`.
- **Bug fix (in scope, needed for `push.ts`'s idempotent-resubscribe path):**
  `src/db/errors.ts`'s `isUniqueViolation` checked `err.code` directly, but drizzle-orm
  0.45 wraps every driver error in a `DrizzleQueryError` whose `.code` is `undefined` —
  the real Postgres SQLSTATE lives on `.cause`. This was a **latent bug** affecting
  `messages.ts`/`sessions.ts`'s own dedup-on-unique-violation paths too (untested there
  — no existing test forced two inserts to race past the pre-check `findFirst`), not
  something this task introduced; fixed to walk the `.cause` chain (bounded, 5 levels)
  and added `src/db/errors.test.ts`.

### `packages/web`

- `src/push/vapid.ts` — `urlBase64ToUint8Array` (VAPID key -> `applicationServerKey`).
- `src/push/subscribe.ts` — `subscribeToPush`/`unsubscribeFromPush`, structured like
  `apiSocket.ts`: platform surface (`navigator.serviceWorker`, `PushManager`) narrowed
  to an injectable `PushEnvironment`, server calls behind an injectable `PushApiPort` —
  fully unit-testable without a real browser or network. `createBrowserPushEnvironment()`
  is the real implementation, defensive against SSR/build-time evaluation (no
  `navigator`/`window`) the same way `visibility.ts` is.
- `public/sw.js` — the service worker itself. Deliberately a plain static file, not part
  of the TS build: Next's static export doesn't bundle `public/`, and there's no
  equivalent of `new Worker(new URL(...))`'s webpack integration for service workers.
  `push` handler decodes the generic `{sessionId, kind}` payload and shows a fixed,
  kind-keyed notification (tagged by `sessionId` so repeat pushes for the same session
  coalesce instead of stacking); `notificationclick` deep-links to `/session/<id>/`,
  preferring to focus/navigate an already-open Falcon tab over opening a new one.
- `src/lib/config.ts` — `VAPID_PUBLIC_KEY` (from `NEXT_PUBLIC_VAPID_PUBLIC_KEY`).
- `src/lib/api.ts` — `subscribePush`/`unsubscribePush`; generalized `postJson`'s
  fetch/error-handling core into `sendJson(method, ...)` so `DELETE` could reuse it.
- `src/app/settings/notifications/page.tsx` — minimal enable/disable toggle so the
  subscribe/unsubscribe plumbing has a real caller (mirrors `settings/recovery`'s
  page structure/conventions). Per-session mute + mute-all (FR-8.3) are explicitly out
  of scope for this task (separate, still-open plan.md §10 checklist item) — this page
  is the on/off switch only.

## Assumptions / deltas from the task description

- **Presence suppression is account-wide in practice today, not truly per-session-room
  yet.** The design text ("skip if any user-scoped socket reports app-state:active with
  the session room joined") implies a per-session visibility signal from the web app,
  but no session-detail screen exists yet (only the session-list screen has landed) and
  no client ever joins a per-session room as a user-scoped connection. I implemented
  `hasActiveVisibleClient` to be scoped correctly by room *and* connection type so it
  will start honoring true per-session visibility the moment a future task adds that
  join — but until then it behaves like "the account has an active tab open," same as
  Happy's own `isUserActive`. This is called out in the method's doc comment.
- **`turn-completed`/`perm`/`question` are exposed via a new generic endpoint
  (`POST /v1/sessions/:id/notify`) rather than being auto-detected server-side.**
  Session content (`session_messages.content`, `sessions.agent_state`) is fully E2E
  encrypted — the server cannot inspect a message's `SessionEvent` union to notice a
  `turn-end` or `perm-request` itself (unlike Happy, which has no E2E encryption and
  detects these server-side). Happy's own actual mechanism is exactly this: a dedicated
  `POST /v1/sessions/:sessionId/push-event` route the CLI calls out-of-band. Falcon's
  version is content-free (`kind` only, no title/body) to match the encryption model.
  Wiring an actual CLI call site to this new route (at turn-end, and from the
  permission pipeline) is out of scope for this task — the worktree is scoped to
  `packages/server` + `packages/web` only, disjoint from CLI-side work — but the
  server-side endpoint exists now so those follow-ups are unblocked, per the task's own
  instruction that the dispatch function's generic `kind` parameter should make this
  "not a hard blocker."
- **`failed` is wired end-to-end today**: `sessionStatus.ts`'s already-landed
  `POST /v1/sessions/:id/status` route (the one existing plaintext lifecycle signal)
  now also calls the push dispatcher.
- **Fixed a latent bug in `db/errors.ts`'s `isUniqueViolation`** (see above) because
  `push.ts`'s idempotent re-subscribe path needed it to actually work; left a
  regression test since it silently affected two other routes' concurrent-write paths
  too.
- No settings UI for per-session mute / mute-all (FR-8.3) or Telegram/ntfy pairing
  flows — both are explicitly separate, still-open plan.md §10 checklist items, and the
  task description scoped this task to "webpush fully now, stub telegram/ntfy
  interfaces for a later task."
- No app icons were added to `public/manifest.webmanifest` (it already had none before
  this task; out of scope — no Falcon logo asset exists to generate them from).
