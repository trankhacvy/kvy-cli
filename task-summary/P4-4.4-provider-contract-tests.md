# P4-4.4-provider-contract-tests — Provider contract tests in CI (daily cron)

## What this adds

1. **`packages/cli/scripts/provider-contract-test.ts`** — a standalone script
   (not a vitest suite) that runs the actual, currently-installed `claude` CLI
   against a small fixture-prompt corpus and asserts three provider contract
   assumptions Falcon's code depends on but doesn't control:
   - **Transcript JSONL shape**: every non-internal line written to
     `~/.claude/projects/<project>/<sessionId>.jsonl` still matches
     `packages/cli/src/claude/types.ts`'s `RawJSONLinesSchema` — the exact
     schema `packages/cli/src/claude/scanner.ts` (the transcript tailer named
     in the task description, ported from Happy's `sessionScanner.ts`) uses
     to derive its dedup keys. Internal event types are skipped using the
     scanner's own `INTERNAL_CLAUDE_EVENT_TYPES` set (now exported) so this
     check can never silently drift from what the scanner itself skips.
   - **Hook event names**: `SessionStart` fires with a UUID-shaped
     `session_id`, and `Stop` fires `"done"` once a turn completes — the two
     hooks `packages/cli/src/claude/hookServer.ts` wires up for local-mode
     session-id discovery and attention signalling.
   - **`--resume` behavior**: resuming with `claude --resume <id>` still
     continues under the *same* provider session id, matching what
     `packages/cli/src/claude/claudeLocal.ts`'s resume handling assumes.

   Every assertion throws a descriptive `ContractViolation` on failure
   (see `assertContract`), and `main()`'s top-level `.catch` turns any
   thrown error into a non-zero exit code with the message on stderr — the
   whole point is to fail loudly, not degrade silently. There is no
   soft-skip when `claude` is missing from `PATH`: this script's only
   caller (the new workflow, below) just installed it, so a missing binary
   there is a real CI misconfiguration, not an expected environment gap.

2. **`packages/cli/scripts/provider-contract/fixtures.ts`** — the
   fixture-prompt corpus: two short, deterministic, tool-free prompts (ask
   for one fixed word, explicitly "do not use any tools"). The second is
   marked `resumeFrom: true` and is run via `--resume <firstSessionId>`,
   exercising the resume-continuity half of the contract. Kept deliberately
   tool-free and minimal — this suite checks *shape*, not the permission
   pipeline (that's `permissionHandler.test.ts`'s job against a fake SDK).

3. **`.github/workflows/provider-contract.yml`** — new workflow, daily cron
   (`17 6 * * *`) + `workflow_dispatch` for on-demand runs. Runs inside a
   pinned `node:20-bookworm` container (not the bare `ubuntu-latest` image)
   so the OS-level environment `claude`'s own behavior depends on is
   reproducible run to run. Steps: checkout → enable corepack → pnpm install
   (frozen lockfile) → `npm install -g @anthropic-ai/claude-code@latest` →
   `claude --version` (visible in logs for triage) → `pnpm run
   contract:provider` (in `packages/cli`, with `ANTHROPIC_API_KEY` from a
   repo secret). `timeout-minutes: 20` bounds a hung/wedged run.

   **"Page/fail loudly" mechanism**: this job has no bespoke
   Slack/PagerDuty/webhook integration — none exists elsewhere in this repo
   to reuse (checked: no existing alerting integration anywhere in
   `.github/workflows/` or `packages/`), and adding a whole new third-party
   integration purely for this one job would be over-engineering for what
   the task actually asks. Instead it relies on GitHub's own documented
   built-in behavior: a failing **scheduled** workflow run automatically
   emails whoever last edited the file's `cron:` line (plus any other repo
   watchers with Actions email notifications enabled) — see
   https://docs.github.com/actions/using-workflows/events-that-trigger-workflows#schedule.
   A plain non-zero exit from the contract script is therefore sufficient to
   page the team; nothing more elaborate was needed.

4. **`packages/cli/src/claude/scanner.ts`**: exported the previously-private
   `INTERNAL_CLAUDE_EVENT_TYPES` set (comment-only visibility change, no
   behavior change) so the new script validates against the exact same
   skip-list instead of maintaining a second copy that could drift.

5. **`packages/cli/package.json`**: added a `contract:provider` script
   (`tsx scripts/provider-contract-test.ts`) — same pattern as
   `@falcon/wire`'s existing `lint:additive` script (`tsx
   scripts/check-additive-vs-base.ts`), which was the direct precedent
   followed for "a script invoked by name, run via tsx directly against TS
   source, outside the normal `test`/`build` pipeline."

## Design choices / why

- **Not a vitest suite.** It makes real, billed network calls against a real
  Claude Code CLI invocation. Vitest's `include` glob
  (`packages/cli/vitest.config.ts`) only picks up `*.test.ts`, and this
  script is named `provider-contract-test.ts` specifically so it is *not*
  matched — it must never run as part of `pnpm test` on every commit or
  every contributor's machine, only from the dedicated daily workflow.
- **Not part of `tsc --noEmit`'s `include` glob either** — same precedent as
  `@falcon/wire`'s `scripts/check-additive-vs-base.ts` (both packages'
  `tsconfig.json` scope `include` to `src/**/*.ts` only). Verified
  correctness manually instead: `npx tsc --noEmit --strict
  --noUncheckedIndexedAccess ...` run directly against the two new files
  (matching this repo's actual `tsconfig.base.json` flags) — caught and
  fixed one real `noUncheckedIndexedAccess` violation
  (`FIXTURE_PROMPTS[index]` needed an explicit guard) before commit.
- **Spawns `claude` directly, not through `claudeLocal.ts`'s wrapper.** The
  point of this suite is to probe the *real provider CLI's own* contract —
  independent of Falcon's own argv-rewriting/launcher-script/fd3-piping
  logic, which already has its own unit tests (`claudeLocal.test.ts`)
  against a fake `spawnImpl`. Keeping this script's `claude` invocation
  direct and minimal (`claude -p <prompt> --settings <path> [--resume
  <id>]`) means a failure here can only mean "the provider changed", not
  "Falcon's wrapper has a bug" — the two failure modes stay cleanly
  separated.
- **`container: node:20-bookworm`** was chosen (over just running on the bare
  `ubuntu-latest` runner) to literally satisfy "in a container" from the
  task description, and to pin the OS environment `claude`'s own runtime
  behavior might depend on.

## Assumptions / known limitations

- Assumes `claude -p` (non-interactive print mode) still writes a normal
  per-session transcript file and still fires `SessionStart`/`Stop` hooks
  the same way interactive mode does. This is exactly the kind of
  assumption this suite exists to keep honest going forward — if a future
  Claude Code release changes print-mode's hook/transcript behavior, this
  job is designed to catch and fail loudly on that, not silently pass.
- Assumes `ANTHROPIC_API_KEY` (or another auth method the CLI supports) is
  configured as a repository secret for the scheduled job to actually
  authenticate. Without it, the job fails loudly on every run — which is
  the correct behavior (a misconfigured secret is itself worth paging on),
  not a silent no-op.
- The daily cron minute (`17 6 * * *`) is an arbitrary off-peak time; no
  significance beyond avoiding the top-of-hour stampede many scheduled jobs
  pick.
