# P0-0.1-docs-stubs — Seed docs/ with protocol.md and encryption.md stubs

**Section:** Phase 0 — Repo & contracts (M0) / §16 0.1 Scaffold, fourth bullet.

## What was done

Created `docs/protocol.md` and `docs/encryption.md` as lightweight
pointer/outline stubs, mirroring Happy's institutional-memory habit of
keeping architecture docs alongside code from day one (`plan.md` §16 0.1).

Each doc:
- States its `Status: stub` and the cross-cutting rule from `plan.md`
  ("`docs/` updated in the same PR as any protocol/crypto change").
- Summarizes the relevant subsections of `falcon-system-design.md` in a
  few sentences each (not a copy — a pointer with enough context to orient
  a reader) and links back to the exact heading anchors.
- Cross-links to each other (`protocol.md` → `encryption.md` for the
  encryption container details, and vice versa).
- Ends with an explicit `TODO` list of what to fill in once the
  corresponding package (`@falcon/wire`, `@falcon/crypto`) actually exists,
  so the stub nature is unambiguous to future readers.

`docs/protocol.md` covers (per design doc §4): encryption container
envelope shape, the provider-agnostic session event envelope, the
server↔client update/ephemeral stream (two-level seq ordering, HTTP-only
writes), RPC contracts (scope-prefixed, idempotency keys, blob offload),
reserved namespaces for deferred features, and the additive-only schema
evolution policy.

`docs/encryption.md` covers (per design doc §5): the `masterSecret` → HKDF
key hierarchy (auth/content/anon/blob-master keys, per-record DEKs), the
three auth flows (sign-up, sign-in, CLI pairing), the published
"what the server can/cannot see" table, and the honest E2E trust-boundary
caveat for the web client (must appear in public security docs).

## Assumptions

- This task is independent of the monorepo scaffold task (per the task
  description) — no `package.json`, `pnpm-workspace.yaml`, or other
  package files were touched or created. The worktree currently has no
  root manifest, so `pnpm build` correctly reports
  `ERR_PNPM_NO_IMPORTER_MANIFEST_FOUND` rather than compiling anything;
  there is nothing in a docs-only change for a build step to verify.
  Verification here was: both files render as valid Markdown, all internal
  links point at real headings in `falcon-system-design.md` (checked by
  reading the doc's actual section titles), and cross-links between the
  two new docs resolve to real files in the same directory.
- Kept both docs intentionally short and pointer-heavy rather than
  duplicating the full §4/§5 content from the design doc, per the task's
  "lightweight pointer/outline docs now, expanded as each area is
  implemented" instruction. Full detail (binary layout diagrams, concrete
  schema names, request/response examples) is deferred to when
  `@falcon/wire` and `@falcon/crypto` land (0.2 and 0.3 in `plan.md`), at
  which point these stubs should be expanded in the same PR.
- Did not create `docs/adoption.md` or `docs/rpc.md` (also listed in the
  monorepo layout in the design doc §3) — out of scope for this task,
  which names only `protocol.md` and `encryption.md`.
