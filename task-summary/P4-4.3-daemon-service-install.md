# P4-4.3-daemon-service-install — Daemon service install: launchd plist (macOS) / systemd-user unit (Linux)

**Section:** Phase 4 — Ship / 4.3 Distribution & self-host
**Refs:** falcon-prd.md FR-4.1 ("installable as a login service (launchd / systemd-user) [P1]"),
falcon-system-design.md §8 ("Service install (P1): launchd plist / systemd-user unit / schtasks,
all labeled `dev.falcon.daemon`"), plan.md §16 "4.3 Distribution & self-host".

## What was built

`falcon daemon service install|uninstall|status` — registers the daemon as a login-managed OS
service so it auto-starts on login and is supervised/restarted by the OS, instead of relying on
`falcon`'s own `ensureDaemonRunning()` auto-start (which only fires the next time a `falcon`
command runs).

- **macOS (launchd):** writes `~/Library/LaunchAgents/dev.falcon.daemon.plist` and registers it
  via the modern `launchctl bootstrap gui/<uid>` (the documented replacement for the deprecated
  `launchctl load`). `RunAtLoad` + `KeepAlive` are both `true`. Status is read via
  `launchctl print gui/<uid>/dev.falcon.daemon`.
- **Linux (systemd --user):** writes `~/.config/systemd/user/dev.falcon.daemon.service` and
  registers it via `systemctl --user daemon-reload` + `enable --now`. `Restart=on-failure`,
  `RestartSec=5`. Status is read via `systemctl --user is-active`/`is-enabled`. The install
  success message includes a note to run `loginctl enable-linger $USER` for headless/pre-login
  start (not run automatically — it needs sudo-adjacent policy on some distros, so this stays an
  explicit, printed instruction rather than a silent side effect).
- Both platforms point the service straight at `falcon daemon start-sync` — the daemon's own
  long-running process body (`daemon/commands.ts`) that already exists and blocks until shutdown.
  `falcon daemon start`'s own detach-and-poll dance is unnecessary once the OS is supervising
  restarts.
- Windows (`schtasks`) is out of scope, same precedent as the rest of the CLI at this phase
  (`processScan.ts`, `gitExec.ts` are also POSIX-only) — `falcon-prd.md` FR-1.1 marks Windows
  `[P2]`. Any other `process.platform` throws a clear `UnsupportedPlatformError` rather than
  writing a broken plist/unit.

### Files (new)

- `packages/cli/src/daemon/serviceInstallPaths.ts` (+ `.test.ts`) — platform detection
  (`resolveServicePlatform`), plist/unit path resolution, the shared `dev.falcon.daemon` label,
  and `resolveFalconExecutable` (scans `PATH` for the `falcon` binary — this is what keeps the
  installed service working across `npm i -g falcon` upgrades, the `curl | sh` standalone
  binary, and nvm-managed installs alike, without hardcoding any install layout). Throws an
  actionable error rather than silently writing a service pointed at a nonexistent binary.
- `packages/cli/src/daemon/serviceInstallTemplates.ts` (+ `.test.ts`) — pure string builders for
  the plist XML and systemd unit INI, no I/O of their own (trivially snapshot-testable).
- `packages/cli/src/daemon/serviceInstall.ts` (+ `.test.ts`) — orchestration:
  `installService`/`uninstallService`/`serviceStatus`. Every `launchctl`/`systemctl` call goes
  through an injectable `ServiceExec` (same hand-wrapped-`execFile` shape as `gitExec.ts`'s
  `runGit` / `processScan.ts`'s `runPs`), since neither service manager exists in CI. Plist/unit
  writes are atomic (tmp-file + rename).
- `packages/cli/src/commands/serviceInstall.ts` (+ `.test.ts`) — thin CLI-facing dispatch
  (`runDaemonServiceCommand`), mirroring `commands/shim.ts`'s precedent.

### Files modified (CLI command wiring)

- `packages/cli/src/args.ts` (+ `.test.ts`) — new `daemon-service` command type; `falcon daemon
  service install|uninstall|status` parses via a new `parseDaemonService`, nested under the
  existing `parseDaemon`. Kept as its own command type (not an extra `daemon` action) since "is
  the OS service registered" is a different question from "is the daemon process currently
  running" (`falcon daemon status`, unchanged).
- `packages/cli/src/index.ts` (+ `.test.ts`) — new `runDaemonService` handler wired into the
  top-level `run()` switch; help text updated. Deliberately skips `ensureDaemon()` (same
  rationale as `shim`/`workspace config`): this command only touches the OS service
  registration, not the daemon process itself.

## Design notes / assumptions

- **Command shape:** the task brief said "`falcon daemon install/uninstall` (or similar)". I went
  with `falcon daemon service install|uninstall|status` rather than overloading `falcon daemon`'s
  existing `install`/`status` action space, since `daemon status` already means "is the daemon
  process running" (reads `daemon.state.json` + probes the control server) — a same-named
  `install`/`status` for service registration would be a confusing collision. The nested
  `service` subcommand mirrors the codebase's existing `workspace <verb>` nesting precedent.
- **Idempotent installs:** `install` on launchd always does `bootout` (ignoring its result) before
  `bootstrap`, so re-running `install` after editing config picks up the new plist rather than
  leaving a stale in-memory registration; systemd's `enable --now` is natively idempotent.
- **`falcon` executable resolution:** rather than trying to special-case dev (`tsx`) vs. built
  (`dist/index.mjs` via the `bin/falcon.mjs` shim) vs. curl-installed standalone binary layouts,
  the service always execs whatever `falcon` resolves to on `PATH` at install time — the same
  resolution a shell would do. This is the simplest correct answer and survives every install
  method the PRD lists (FR-1.1). An explicit `falconExecutable` override exists for manual
  installs / tests.
- **No auto-`loginctl enable-linger`:** printed as a note instead of run automatically — running
  it silently would be a surprising side effect on a shared/managed machine, and it isn't needed
  for the common single-user-desktop case (the [P1] target).
- **Uninstall docs / `rm -rf ~/.falcon` cleanup guidance** (the last unchecked 4.3 checklist
  item) is a separate, disjoint task per the plan — this task only lands the
  install/uninstall/status commands themselves, which is what a future docs task would point at.
