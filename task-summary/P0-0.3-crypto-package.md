# P0-0.3-crypto-package — Build @falcon/crypto

**Section:** Phase 0 — Repo & contracts (M0) / plan.md §3.1 + §16 "0.3 @falcon/crypto"

## What was done

Created `packages/crypto` (`@falcon/crypto`), Falcon's E2E encryption primitives,
isomorphic across Node (CLI/server) and browser (web), with no dependency on
`@falcon/wire` (zod-free) as required.

### File layout (`packages/crypto/src/`)

- **`encryption.ts`** (V, verbatim port) — Happy's `happy-cli/src/api/encryption.ts`,
  full MIT license header preserved at the top. Node build: `node:crypto` for
  AES-256-GCM + random bytes, `tweetnacl` for NaCl box/secretbox/sign. All
  functions from the task list ported: `getRandomBytes`,
  `libsodiumPublicKeyFromSecretKey`, `libsodiumEncryptForPublicKey`,
  `encryptLegacy`/`decryptLegacy`, `encryptBlob`/`decryptBlob`,
  `encryptWithDataKey`/`decryptWithDataKey`, `encrypt`/`decrypt` dispatchers,
  `authChallenge`. One addition beyond Happy's file:
  `libsodiumDecryptWithSecretKey` — the missing inverse of
  `libsodiumEncryptForPublicKey` (Happy's CLI never needed to *open* a sealed
  box; Falcon's `unwrapDek` does). Never throws, returns `null`.
- **`encryption.web.ts`** (browser split, per task) — same function surface,
  `libsodium-wrappers` + WebCrypto AES-GCM. Two deliberate signature
  differences from the node build, both forced by browser APIs and called out
  in the file header: `encryptWithDataKey`/`decryptWithDataKey` are `async`
  (Web Crypto has no sync API); everything else is sync once `await ready`
  has resolved (libsodium-wrappers' documented init pattern). The AES-GCM
  bundle layout `[version(1)|nonce(12)|ciphertext|tag(16)]` is byte-identical
  to node's output (WebCrypto's `encrypt()` already returns ciphertext‖tag
  concatenated) — this is what makes the cross-impl vectors work.
- **`base64.ts`** — isomorphic base64/base64url codec, manual lookup-table
  implementation, no `Buffer`/`atob`/`btoa` dependency. Shared verbatim by
  both entry points so encoding is guaranteed byte-identical.
- **`box.ts` / `box.web.ts`** (N) — `seal()`/`open()` EncryptedBox wrappers.
  `open()` returns `null` on any failure, **never throws** (design principle
  #1 — one corrupt record can't poison a sync batch). `box.web.ts` is async
  to match `encryption.web.ts`'s AES-GCM functions.
- **`keys.ts`** (N) — `deriveKeyTree(masterSecret)`, falcon-system-design.md
  §5.1's key hierarchy (`falcon-auth` → Ed25519 signing keypair,
  `falcon-content` → X25519 content keypair, `falcon-anon` → 16-hex anonId,
  `falcon-blob-master` → legacy blob key). The derivation primitive
  (HMAC-SHA512 master-seed expansion) is adapted from Happy's own
  `happy-app/sources/encryption/deriveKey.ts` (the same construction BIP32
  uses for its root key), flattened to Falcon's single-level domain list and
  built on `tweetnacl.hash` (pure JS SHA-512) so this file needs **no**
  node/web split — one implementation, both platforms, fully synchronous.
- **`recovery.ts`** (P, from `happy-app/sources/auth/secretKeyBackup.ts`) —
  `encodeRecoveryCode`/`decodeRecoveryCode`, grouped Base32 (11 groups,
  five-char groups except a two-char final group — 32 bytes → 52 base32
  chars), error-tolerant normalization (0→O, 1→I, 8→B, 9→G). Delta from
  Happy: operates directly on raw masterSecret bytes (this package owns the
  bytes end-to-end, no base64url round-trip needed), and
  `decodeRecoveryCode` returns `null` instead of throwing.
- **`dek.ts` / `dek.web.ts`** (N) — `wrapDek`/`unwrapDek`, sealed-box DEK
  wrap with version byte `0x00` per falcon-system-design.md §5.1
  (`[0x00 | ephPub32 | nonce24 | ct]`). Built on `libsodiumEncryptForPublicKey`
  / `libsodiumDecryptWithSecretKey`; sync on both platforms (NaCl box ops
  don't need WebCrypto).
- **`types.ts`** — `EncryptedBox`, `BoxKeyPair`, `SignKeyPair`, `KeyTree`.
  Deliberately zod-free, structurally identical to `@falcon/wire`'s
  `EncryptedBoxSchema` shape by convention, not by import.
- **`index.ts`** / **`index.web.ts`** — the two package entry points (see
  package.json exports below).

### Package export shape

Rather than relying on an unverified `"browser"` condition auto-resolving in
pkgroll/bundlers, `@falcon/crypto` exposes two explicit subpaths (same
pattern Happy's own `happy-cli` package.json uses for `"."` / `"./lib"`):

```jsonc
"exports": {
  ".":      { /* node build: index.mjs / index.cjs */ },
  "./web":  { /* browser build: index.web.mjs / index.web.cjs */ }
}
```

Node consumers (CLI, server) `import from '@falcon/crypto'`; the web app
`import from '@falcon/crypto/web'`. Explicit, safe, and easy for a bundler to
tree-shake without guessing at condition resolution.

### Dependency version note: libsodium-wrappers

Started with `libsodium-wrappers@0.7.15` per the version pinned in Happy's
CLI-adjacent code, but its **published npm tarball is missing a file its own
ESM bundle needs** (`dist/modules-esm/libsodium-wrappers.mjs` does
`import e from "./libsodium.mjs"` — a same-directory relative import — but
`libsodium.mjs` isn't in the package's `files` allowlist, so it 404s on
import under Node ESM/pnpm's isolated node_modules; confirmed the same defect
exists in the latest 0.7.x, 0.8.4 too... except **0.8.x fixed it**: its `.mjs`
does `import e from "libsodium"` — a bare specifier resolved through normal
node_modules resolution against the separate `libsodium` dependency, which
works correctly). Switched to `libsodium-wrappers@^0.8.2` — the same exact
version Happy's own `happy-app/package.json` already pins. Also dropped the
`@types/libsodium-wrappers` devDependency: 0.8.x ships its own
`.d.ts`/`.d.mts` files (visible in its `exports` map), so the separate
`@types` package is unnecessary and would only risk stale/conflicting types.

### Cross-impl test vectors

`cross-impl.test.ts` runs both builds for real inside the same vitest run
(Node 20+ exposes `crypto.subtle` as a global, and libsodium-wrappers is WASM
— platform-agnostic — so neither needs to be mocked or run in a browser):
node-encrypts→web-decrypts and web-encrypts→node-decrypts for
`encryptWithDataKey`/`decryptWithDataKey`, `libsodiumEncryptForPublicKey`/
`libsodiumDecryptWithSecretKey`, `encryptLegacy`, `encryptBlob`, `seal`/`open`,
and `wrapDek`/`unwrapDek`. All pass.

## Assumptions

- `@falcon/crypto` version pinned at `0.1.0`, `private: true` (not yet
  published; matches the other Falcon packages' convention established in
  0.1).
- `tsconfig.json` for this package overrides `lib` to `["ES2022", "DOM"]`
  (the base config only has `["ES2022"]`) — needed for `encryption.web.ts`'s
  `crypto.subtle`/`CryptoKey`/`BufferSource` types. Verified this doesn't
  introduce duplicate-global conflicts with `@types/node`'s own `crypto`
  ambient declaration.
- `getRandomBytes` in `keys.ts`'s tests, and `deriveKeyTree`'s internal
  X25519 derivation, deliberately import `tweetnacl` directly rather than
  going through `encryption.ts`/`encryption.web.ts` — keeps `keys.ts` (and
  `recovery.ts`) genuinely platform-independent with zero split, since
  `tweetnacl` itself is pure JS and runs identically in Node and browsers
  (the task's mandate to use libsodium-wrappers on the browser build applies
  to the *public* `encryption.web.ts` surface, not to this package's own
  internal derivation math).
- No `lint` script was added to `packages/crypto/package.json` — the root
  Biome/ESLint setup (0.1 TODO item) hasn't landed yet; turbo correctly skips
  packages missing a task's script rather than erroring, confirmed via
  `pnpm lint` from the root (0 tasks executed, exit 0).
- Left `turbo.json`'s pre-existing `test` task `outputs: ["coverage/**"]` as
  inherited from 0.1 scaffold; `vitest run` without `--coverage` doesn't
  produce that directory, so turbo prints a harmless "no output files found"
  warning. Not in this task's scope to change 0.1's turbo pipeline config.
