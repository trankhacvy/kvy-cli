# P2-2.3-timeline-live-wire — Wire SessionTimelineScreen to the real sync engine

## What changed

`packages/web/src/components/timeline/SessionTimelineScreen.tsx` no longer renders the
hand-built `demoRenderItems` fixture or defaults `useControl` to `useMockSessionControl`.
Both are now backed by real, already-merged plumbing (sync engine, `apiSocket`, the
session RPC client, the crypto-bridge worker):

- `items` now comes from a new `useLiveRenderItems(sessionId)` hook
  (`packages/web/src/features/session-control/use-live-render-items.ts`).
- `useControl` now defaults to a new `useLiveSessionControl` hook
  (`packages/web/src/features/session-control/use-live-session-control.ts`), which is
  exactly the `(id) => sessionRpcToActions(createSessionRpcClient({...}))` swap the
  screen's own prior docstring called out as the one-line follow-up.
- `packages/web/src/components/timeline/demo-items.ts` is deleted. `useMockSessionControl`/
  `createMockSessionControl` (`mock-actions.ts`) are kept (docstring updated) — they're no
  longer the screen's default but remain available for tests/standalone review, same as
  every other screen's mock-source pattern in this codebase (`features/session-list`,
  `features/new-session`).

## New files

- `packages/web/src/features/session-control/use-session-crypto.ts` — the shared plumbing
  both live hooks build on:
  - `useSyncSnapshotQuery()` (private): connects `apiSocket` with the stored auth token
    (`@/lib/session`'s `getToken()`), creates a `createSyncEngine(queryClient, apiSocket)`
    instance for the component's lifetime (disposed on unmount), and runs a
    `useQuery(['sync'], ...)` against the new `GET /v1/sync` client (`lib/api.ts`'s
    `getSync`). This is the one call site (so far) that actually wires up the engine +
    socket pair `sync/index.ts`'s own docstring has always described.
  - `useSessionCrypto(sessionId)`: finds `sessionId`'s `SessionRow.dek` in that snapshot,
    unwraps it via a per-component `CryptoBridgeClient` (`@/lib/use-crypto-bridge.ts`,
    already merged) calling `setSessionKey(decodeBase64(dek))`, and returns the bridge only
    once that resolves `true` — `null` otherwise. Both `useLiveRenderItems` and
    `useLiveSessionControl` call this independently with the same `sessionId`, so they
    always agree on which session's key is loaded even though each owns its own worker
    instance (kept independent for simplicity — see Assumptions).
- `packages/web/src/features/session-control/use-live-render-items.ts` — fetches the
  session's most recent page of `GET /v1/sessions/:id/messages` via `useInfiniteQuery`
  (shape matches `sync/engine.ts`'s expected `MessagesQueryData` exactly, so the engine's
  `message-new` fast path patches the same cache entry this hook reads), decrypts every
  row's `content` box via the new `decryptMessageBatches`, and reduces the result through
  the already-merged `reduceEnvelopes`. Live `message-new` updates flow straight into
  `RenderItem[]` updates with no extra plumbing.
- `packages/web/src/features/session-control/use-live-session-control.ts` — the real
  `UseSessionControl`. Returns a `pendingSessionControl()` (every method rejects with a
  clear "not ready yet" error) until `useSessionCrypto` resolves, then
  `sessionRpcToActions(createSessionRpcClient({socket: apiSocket, crypto, sessionId}))`.
- `packages/web/src/sync/messages.ts` (+ `messages.test.ts`) — pure, framework-agnostic
  `decryptMessageBatches(pages, crypto)`. Each message row's `content` box decrypts to a
  `SessionEnvelope[]` *batch*, not a single envelope (confirmed by reading
  `packages/cli/src/api/outbox.ts`: the HTTP outbox coalesces up to 20 envelopes/300ms into
  one `seal(batch, dek)` POST) — this function opens every row, validates each batch against
  `SessionEnvelopeSchema` (zod), and flattens everything across every page into one
  `SessionEnvelope[]`, ready for `reduceEnvelopes` (which dedupes by id and stable-sorts by
  `time` internally, so cross-row/cross-page ordering doesn't matter). A row that fails to
  decrypt or fails schema validation is logged (`console.error`) and dropped, matching the
  existing `apiSocket.ts` idiom for malformed wire payloads — one bad row never blanks the
  whole timeline, but never fails silently either.

## Modified files

- `packages/web/src/lib/api.ts` — two new thin fetch wrappers, `getSync` (`GET
  /v1/sync?since=0`) and `getSessionMessages` (`GET /v1/sessions/:id/messages`), matching
  this module's existing no-client-validation style.
- `packages/web/src/sync/index.ts` — exports `decryptMessageBatches`/`MessageDecryptor`.
- `packages/web/src/features/session-control/index.ts` — exports the two new live hooks.
- `packages/web/src/app/session/[id]/page.tsx` — docstring only (no behavior change):
  `generateStaticParams`'s `demo` placeholder id is still needed to give Next's static
  export a concrete route to prerender the HTML/JS shell for, but the screen itself always
  renders live data now regardless of which id the URL actually carries at runtime.

## Assumptions / scope decisions

- **Auth gating is out of scope.** Per `CLAUDE.md`/`progress.md`, "auth-gating the Home
  route" is a separate, still-planned item. `useSessionCrypto`/`useLiveRenderItems`/
  `useLiveSessionControl` all degrade gracefully with no token (`enabled: false` on the
  queries, `pendingSessionControl()`'s rejected promises) rather than redirecting to
  `/signin/` — consistent with this task's narrow scope (wire the screen to live data, not
  add a new auth flow).
- **Two independent crypto-bridge workers per session view.** `useLiveRenderItems` and
  `useLiveSessionControl` (via `SessionControlProvider`) each call `useSessionCrypto`
  independently, so each spins up its own `CryptoBridgeClient` Worker and its own
  `createSyncEngine` instance. This is redundant but verified safe: both engines write to
  the *same* shared `QueryClient` cache and both subscribe to that same cache, so a
  `message-new` applied by one engine is observed as a no-op duplicate by the other (its
  own `lastMsgSeq` tracker is updated by the cache-subscription side-effect before its own
  socket handler runs). Sharing one bridge/engine across both hooks via context would save
  a Worker but adds real complexity for a screen that only ever mounts one of each; not
  worth it here.
- **Only the newest page of messages is fetched.** `Timeline.tsx` has no "load more"/
  infinite-scroll wiring yet, so `useLiveRenderItems` doesn't call `fetchNextPage()` either
  — older history beyond the first `GET /v1/sessions/:id/messages` page (50 messages) isn't
  loaded. Adding pagination to `Timeline` itself is a separate, not-yet-scoped UI task.
- **`demo-items.ts` deleted, not just unused.** No test file referenced it (`grep` came back
  empty before deletion), so parity was confirmed structurally — every `RenderItem` kind
  the fixture exercised is still covered by `sync/reducer`'s own golden/reduce tests, which
  are unaffected by this change.
