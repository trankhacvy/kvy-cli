# U1.4 — lifecycle-status (W1.4+B15 — session ended/failed status on the PTY path)

Plan reference: `plan-v2.md` §"W1.4 (A4 + B15) Session lifecycle status:
ended/failed on the PTY path", unit list entry "U1.4 `[solo]` "lifecycle-status"".

## What landed

### 1. `packages/cli/src/api/sessionStatus.ts` — `reportSessionStatus`
- Generalized the crash-only `reportSessionFailed` into `reportSessionStatus(deps,
  { sessionId, status: "failed" | "ended", error? })` — same fetch/timeout/typed-result
  handling (`ok` / `http-error` / `network-error`, never throws).
- `reportSessionFailed` is now a thin `status: "failed"` wrapper over
  `reportSessionStatus`, so its existing callers (`claude/sessionExit.ts`, which is
  itself still unwired/orphaned from before this task — confirmed by grep, not touched)
  and tests are untouched.
- New `ReportableSessionStatus` type (`"failed" | "ended"`) exported for `start.ts`.

### 2. Server status route — additive `"ended"` + fan-out
- `packages/wire/src/rows.ts`: `SessionStatusSchema` widened to `["active", "archived",
  "failed", "compacted", "ended"]` — additive only (verified against
  `wire/src/__tests__/additiveOnly.test.ts`'s compatibility checker: enum widening is
  explicitly allowed). No DB migration needed — `sessions.status` is a plain
  `text()` column, not a DB-level enum.
- `packages/server/src/app/routes/sessionStatus.ts`: body/response schemas widened to
  `z.enum(["failed", "ended"])`. The idempotent-no-op check now compares
  `session.status === status` (any already-set status short-circuits, not just
  `"failed"`). `session-update` fans out for **both** statuses; the `attention`
  ephemeral + push dispatch (`kind: "failed"`) still fire **only** for `"failed"` —
  ending a session isn't itself attention-worthy the way a crash is, and
  `LifecycleKindSchema` (`perm|question|done|failed`) has no `"ended"` member to extend
  (deliberately out of scope; see the route's updated doc comment).

### 3. `packages/cli/src/commands/start.ts` — `reportStatusOnce` + signal handlers + exit-code mapping
- New injectable `reportSessionStatus` dep (defaults to the real client).
- `reportStatusOnce(status, error?)` closure, guarded by a `statusReported` flag so a
  signal racing a normal exit (or vice versa) never double-reports. Wired once, right
  after bootstrap succeeds (matches the plan's `:308` snippet placement), before the
  Outbox/session client are created.
- `SIGTERM`/`SIGHUP` handlers registered on the wrapper process (`SIGINT` isn't handled
  here — it reaches the PTY child directly via raw-mode byte forwarding, and that
  child's own exit flows through the normal exit-code mapping instead): report `"ended"`
  then `process.exit(0 | 1)`. Both listeners are removed in the outer `finally` so they
  never leak across the process's own retry paths (or across unit tests running in the
  same worker).
- Both flows now map their exit code the same way: `runLocalPty` (`ptySession.done`)
  and `runRemoteLoop` (`runLoop(...)`'s return) each report `code === 0 ? "ended" :
  "failed"`, attaching `new Error("claude exited with code <n>")` on the failed branch.

### 4. Web — Home chip + timeline banner + disabled controls
- `packages/web/src/features/session-list/status.ts`: new `SessionListStatus` member
  `"ended"`, checked right after `"failed"` in `deriveSessionStatus` (a distinct
  terminal row state from `"completed"`, which describes a turn outcome or an
  archived/compacted row on a session that's still otherwise controllable). New
  `SESSION_STATUS_META.ended` entry (`"Ended"`, `bg-slate-500`, no pulse) — the Home
  chip needs no other wiring since `session.status` already flows through
  `live-source.ts`'s existing `['sync']`-snapshot plumbing untouched.
- `packages/web/src/components/timeline/SessionTimelineScreen.tsx`: reads the session
  row's own `status` off the same `['sync']` snapshot `live-source.ts` already uses
  (`useSyncSnapshotQuery()`, safe to mount from more than one component per its own doc
  comment), defaulting to `"active"` until loaded. Renders a banner ("Session
  ended"/"Session failed — this session can no longer be controlled from the web.")
  when `status` is `"ended"`/`"failed"`, and passes `disabled={status !== "active"}`
  to both `ControlBar` and `Composer`.
- `ControlBar.tsx` / `Composer.tsx`: new optional `disabled` prop (defaults `false`)
  disabling every action (interrupt, mode select, take-control / send, attach) —
  additive, backward-compatible prop.

### 5. Tests
- `packages/cli/src/api/sessionStatus.test.ts`: new `reportSessionStatus` describe
  block — `ended` body with/without `error`, `http-error`/`network-error` paths.
- `packages/cli/src/commands/start.test.ts`: `reportSessionStatus` added to the default
  test deps (never hits a real backend from a unit test, same rule every other
  injected dep here follows); new exit-code → status-mapping tests for both the PTY
  flow (`ended` on code 0, `failed` + exit-code error message on non-zero) and the
  remote/`--starting-mode remote` flow (same mapping via `runLoop`'s return code).
- `packages/server/src/app/routes/sessionStatus.test.ts`: new tests — a fresh session
  marked `"ended"` fans out `session-update` only (no ephemeral, no push dispatch call)
  and is idempotent on retry.
- `packages/web/src/features/session-list/status.test.ts`: `"ended"` row status test.
- Skipped: `[human]` sub-task 6 (live Ctrl-C / `kill -TERM` → web "Ended" verification)
  per instructions — no automated test drives real OS signals against this process
  (the existing code review would require mocking `process.exit`, which the plan's own
  test-scope line for this unit ("exit-code → status mapping") doesn't ask for).

## Drift from the plan's snippets
- The plan's `start.ts` snippet numbers (`:308`, `:489`, `:466`) reference an earlier
  revision of the file; the actual insertion points (right after the "starting session"
  write, and inside `runLocalPty`'s/`runRemoteLoop`'s own try/finally around their
  respective exit awaits) match the plan's *description* exactly, just at different
  line numbers after Wave-1/prior units' edits.
- Server route: the plan's one-line summary ("fans out session-update ... exactly as
  failed does today") was read literally — `session-update` fans out for both statuses,
  but the `attention` ephemeral + push dispatch stay `"failed"`-only, since (a) the
  wire's `LifecycleKindSchema` has no `"ended"` member and widening it wasn't asked for,
  and (b) a normal/resumable exit isn't attention-worthy the way a crash is.
