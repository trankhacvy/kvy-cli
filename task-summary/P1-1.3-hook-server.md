# P1-1.3-hook-server — Local-mode SessionStart hook server

## Task

plan.md §1.3 bullet: "Hook server: loopback HTTP receiving `SessionStart` → learn
provider session UUID → metadata CAS update **(P)**". Design doc §7.4/§8: the
Claude adapter's local mode injects "a `SessionStart` hook via temp `--settings`
file (reports the real provider session UUID to a loopback hook server)".

## What was built

- `packages/cli/src/claude/hookServer.ts`:
  - `startHookServer(deps: { onSessionId, logger? })` — a Fastify server bound
    to `127.0.0.1:0` (OS-assigned ephemeral port), exposing
    `POST /hook/session-start`. Body is validated with a zod schema
    (`{ session_id: string, ...passthrough }`) mirroring the real Claude Code
    `SessionStart` hook payload (`session_id`, `transcript_path`, `cwd`,
    `hook_event_name`, `source` — only `session_id` is actually read; every
    other field passes through unvalidated so a future Claude Code field
    addition/rename never breaks this handler). On a valid POST, invokes the
    injected `onSessionId(sessionId)` callback and returns `{ status: "ok" }`.
    Returns the resolved `port` plus a `stop()` that closes the Fastify
    instance.
  - `writeHookSettingsFile(dir, port)` — writes a temp Claude Code
    `--settings` JSON file (design §7.4) into a caller-supplied directory,
    configuring a `SessionStart` hook (`matcher: "*"`) whose `command` points
    at a small companion forwarder script (`falcon-hook-forwarder-<id>.cjs`,
    written into the same directory) that reads the hook's stdin JSON and
    POSTs it verbatim to `http://127.0.0.1:<port>/hook/session-start`. Returns
    `{ path, cleanup() }`; `cleanup()` best-effort-removes both the settings
    file and the forwarder script.

  This exactly mirrors the already-merged `packages/cli/src/daemon/controlServer.ts`'s
  pattern: Fastify-on-ephemeral-port, `fastify-type-provider-zod` for
  schema-validated bodies, promise-wrapped `listen()`/`resolve({ port, stop })`,
  and every side effect (`onSessionId`) injected via a `deps` object rather than
  owned by the module — so this can be wired into the real launcher later
  without touching this file.

- `packages/cli/src/claude/hookServer.test.ts` (11 tests): starts the server,
  POSTs a synthetic `SessionStart` payload (including realistic extra fields
  like `transcript_path`/`cwd`/`source`), asserts `onSessionId` fires with the
  right UUID; asserts 400 on a missing `session_id`; asserts passthrough
  tolerance of unknown fields; asserts 404 for unregistered routes; asserts
  `stop()` closes the listener; asserts two concurrently started servers get
  distinct ports — the same shape of coverage as `controlServer.test.ts`.
  Also covers `writeHookSettingsFile`: the generated settings JSON's hook
  command embeds the given port and references an actually-existing forwarder
  script; `cleanup()` removes both files; two calls never collide (unique
  `pid + randomUUID()` per pair). One end-to-end test actually spawns the
  generated forwarder script as a real child process, pipes it a synthetic
  hook JSON payload on stdin exactly as Claude Code would, and asserts the
  hook server's `onSessionId` callback fires — proving the settings file +
  forwarder + server actually work together, not just in isolation.

## Why a companion forwarder script instead of an inline shell command

Claude Code's "command" hooks receive the hook payload as JSON on stdin and
otherwise do nothing themselves — there's no way to express "POST this to a
port" as a single portable shell one-liner without either depending on `curl`
being present or writing a fragile, hard-to-escape inline `node -e` string
embedded in a JSON string value. Instead, `writeHookSettingsFile` writes a
tiny `.cjs` forwarder (an inline adaptation of happy-cli's
`session_hook_forwarder.cjs`) alongside the settings file itself, at runtime,
in the caller-supplied directory — not checked into the repo under
`packages/cli/scripts/`, which avoids any file-ownership collision with the
separate, unmerged `P1-1.3-claude-launcher-script` worktree that owns that
directory for `falcon_claude_launcher.cjs`.

## Explicitly out of scope (per task description — documented follow-ups, not faked)

- **`PUT /v1/sessions/:id/metadata` CAS update.** `onSessionId`'s caller is
  expected to eventually turn a learned session UUID into a metadata
  CAS-update call against the server, but that HTTP route does not exist on
  `main` yet — it's part of the still-unmerged `P1-1.2-server-write-http`
  worktree. `startHookServer` only ever invokes the injected callback; it has
  no knowledge of the server API at all.
- **Wiring into `claudeLocal.ts` / the real launcher spawn flow.** Both the
  `claudeLocal.ts` port and the `falcon_claude_launcher.cjs` launcher script
  are separate, currently in-flight plan bullets (the launcher exists
  unmerged in `.worktrees/P1-1.3-claude-launcher-script`). Nothing in this
  change starts a hook server automatically or calls `writeHookSettingsFile`
  from any spawn path — both are pure, independently testable, unwired
  building blocks, exactly as the task asked.

## Assumptions

- The `SessionStart` hook payload's session-id field is Claude Code's
  documented `session_id` (snake_case), matching both the real Claude Code
  hook contract and happy-cli's `SessionHookData.session_id`. Validated as a
  non-empty string (not strictly UUID-shaped via `.uuid()`) to stay
  defensive against any future format change, consistent with this repo's
  existing `.passthrough()`-heavy house style in `src/claude/types.ts`.
- `writeHookSettingsFile` takes the target directory as a parameter rather
  than resolving `~/.falcon/tmp/hooks` itself, keeping it decoupled from
  `resolveHomeDir` — the eventual launcher-wiring task decides where temp
  hook files live.
- The forwarder script is written with executable mode (`0o755`) but is
  always invoked explicitly via `node <path> <port>`, so it works
  identically whether or not the executing OS/filesystem honors the
  execute bit (e.g. exec-format concerns on Windows are moot since it's
  never exec'd directly).
