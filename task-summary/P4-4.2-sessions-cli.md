# P4-4.2-sessions-cli — `falcon sessions list` / `falcon resume <id>` terminal commands

Section 4.2 Adoption Tier 3 + polish. `falcon sessions`/`falcon resume` were
already anticipated in `args.ts`'s doc comment, type union, and parser
(`parseSessions`/`parseResume`), and in `index.ts`'s dispatch switch — both
previously called a `"not implemented yet"` stub. This task replaces both
stubs with real implementations, following `commands/shim.ts`'s
already-landed pattern (a thin `commands/*.ts` module wired into
`index.ts`'s per-subcommand runner).

## What was built

### `packages/cli/src/commands/sessionsList.ts` — `runSessionsListCommand`

Lists sessions from two independent sources, since neither alone answers
"what can I `falcon resume`":

- **Local**: `adopt/listSessions.ts`'s `listAdoptableSessions` — the exact
  building block `falcon adopt --list` already uses. Plain (unmanaged)
  Claude Code transcripts for cwd's workspace, on this machine only.
- **Remote**: `GET /v1/sessions` (already landed,
  `server/src/app/routes/sessions.ts`) — every session row this account
  owns, on any machine, via a bearer token (`auth/credentials.ts`'s
  `readCredentials().token`, same header convention as
  `api/sessionStatus.ts`).

Skipped (not an error) when not logged in; a network/HTTP failure on the
remote half is reported inline and the command still returns `0` — the
local half stays useful on its own, same "never hard-fail over the network"
philosophy as `api/sessionStatus.ts`.

**Assumption / scope cut**: remote rows are listed by `id`/`tag` (both
plaintext on the wire), not a decrypted title. `SessionRow.metadata` is an
opaque encrypted box (design §5.3) — decrypting it needs the per-session
DEK-unwrap chain the web client carries (`crypto/worker-handler.ts`'s
`unwrapDek`, keyed off the account's content key tree via
`deriveKeyTree`), which this CLI package doesn't have wired up yet. Adding
that felt like a separate, larger task (it's the same crypto machinery
`falcon auth status` only partially exercises today for display purposes)
rather than something to bolt on inside a listing command. `tag`/`id`/
`provider`/`status`/`updatedAt` are enough to pick a target for `falcon
resume <id>`.

### `packages/cli/src/commands/resume.ts` — `runResumeCommand`

Dispatches on whether `<session-id>` matches a *local* plain transcript:

- **local** (`listAdoptableSessions` finds a match): spawns
  `claude --resume <id>` with inherited stdio, blocking until it exits —
  the same already-landed pattern `commands/adopt.ts`'s local resume path
  uses (verbatim `claude --resume` is how Claude Code's own CLI performs
  the session-flag interception `claude/claudeLocal.ts`'s module doc
  describes; the direct spawn mirrors `adopt.ts`'s precedent rather than
  routing through the still-unwired `falcon_claude_launcher.cjs`/
  `claudeLocalLauncher.ts` orchestration, since general provider spawning
  is separate, later work — `index.ts`'s `runStart` is still an honest
  "not implemented yet" stub, and wiring the full launcher here would mean
  building that out prematurely, inside a resume command).
- **daemon-managed** (no local match): calls `daemon/resumeSession.ts`'s
  `resumeSession()` directly — the exact function the (also not-yet-wired-
  to-a-live-connection) `resumeSession` machine RPC wraps — against a
  `SessionRegistry` built via `createSessionRegistry({homeDir}).restore()`,
  the same durable-store restore `falcon daemon start-sync` performs at
  boot. `resolveDirectory` defaults to the invoking terminal's own cwd (the
  common case: you `cd` into the project and `falcon resume`), honestly
  matching every other "no real workspace-lookup default yet" seam already
  documented in this package (`commands.ts`'s `resolveResumeDirectory`,
  `providerSessionResolver.ts`) rather than inventing a new one.

  **Safety guard**: before calling `resumeSession()`, checks whether a
  currently-*running* daemon (`daemon/state.ts`'s `readDaemonState` +
  `isProcessAlive`) already tracks `<session-id>` live via its control
  server's `POST /list`. If so, refuses with an honest error instead of
  risking two processes racing ownership of the same session's DEK/seq
  (`resumeSession.ts`'s own module doc explains why that's unsafe) — this
  command runs as a *separate* process from any already-running daemon and
  has no IPC path to delegate the resume to it (no control-server route
  exists for `resumeSession` — see "Known limitation" below), so this is
  the one place doing the safe thing matters.

### `packages/cli/src/index.ts`

- Imports and wires `runSessionsListCommand`/`runResumeCommand` into the
  existing `runSessions`/`runResume` handlers (both already called
  `ensureDaemon()` first, per PRD FR-1.2 — untouched).
- Updated the two `--help` lines to describe the real behavior instead of
  the old stub wording.

  `"disabled"` result doesn't block the command from actually running.

## Known limitation (pre-existing, not introduced by this task)

`resumeSession()`'s re-spawned child process reports back to whichever
daemon's control server `daemon.state.json` currently points at — but this
command never starts its own control server, and provider spawning for
`--starting-mode remote` (what the re-spawned child would actually run) is
itself still an honest stub (`index.ts`'s `runStart`: "provider spawning not
implemented yet"). So the daemon-managed path today is *fully wired and
correctly composed* — same "landed, not yet end-to-end live" bar as
`daemon/resumeSession.ts`/`machineRpc.ts` themselves already carry per this
repo's `CLAUDE.md` — but will currently time out after 15s waiting for a
`/session-started` webhook that has nothing upstream to send it, once real
provider spawning exists. That's a follow-on consequence of provider
spawning being unimplemented, not something introduced or masked here.
