## W2.4 — ControlBar honesty: real mode, real capabilities

**1. Mode display — kill the hardcoded `"default"`.**

- New `deriveCurrentPermissionMode(items): PermissionMode` in
  `packages/web/src/features/session-control/session-state.ts` (placed next
  to `deriveControlMode`, matching the plan's intent — the plan named a
  new file `status.ts`, but the real code already has `deriveControlMode`/
  `isTurnOpen` living in `session-state.ts`, not a `status.ts`; adapted to
  the existing file rather than introducing a second one for the same
  concern — noted as drift).
- **Real derivation differs from a literal read of the plan's one-line
  description** ("fold `mode-switch` + `perm-resolve{kind:"mode"}`
  envelopes"): the wire's `mode-switch` event only ever carries
  `control: "local"|"remote"` (`packages/wire/src/session.ts`), never a
  `PermissionMode` value — so a `mode-switch` item can't itself set the
  *value*. The only place a `PermissionMode` value actually appears is a
  `perm-resolve` decision of kind `"mode"`, which the reducer applies onto
  whichever `PermissionInfo` it belongs to (a `perm-placeholder` or a
  `tool` item — never its own top-level render-item kind). Implemented as a
  single forward walk (same style as `deriveControlMode`): a `mode-switch`
  item resets the running value to `"default"` (crossing a local/remote
  control boundary makes the previously-known mode stale/unknowable until
  the new controller's own decision lands); a `tool`/`perm-placeholder`
  item whose `permission.decision.kind === "mode"` sets the running value to
  `decision.mode`. Defaults to `"default"` with no items. Exported through
  `features/session-control/index.ts`.
- `SessionTimelineScreen.tsx`: computes `permissionMode =
  deriveCurrentPermissionMode(items)` alongside the existing `controlMode`,
  threads it through `SessionTimelineBody` as a new `permissionMode` prop,
  and passes it to `<ControlBar mode={permissionMode} .../>` in place of the
  literal `"default"`.

**2. Take-control visibility — this was inverted in the pre-existing code,
not just missing.** `ControlBar.tsx` previously rendered the "Take control"
button when `controlMode === "local"` — backwards from the plan's intent.
Cross-checked against `packages/cli/src/commands/start.ts`:
`runLocalPty`'s `takeControl` handler is a permanent
`async () => ({ ok: true })` no-op ("the human is already at this
terminal — there is no remote turn to reclaim from"), while
`runRemoteLoop`'s handler genuinely emits a `takeControlSignal` the live
loop listens on. So a PTY/local session's button was previously *always
shown* despite being *always meaningless*, and a remote-loop session's
(the one case where it does something) was hidden. Fixed via an exported
pure predicate, `shouldShowTakeControl(controlMode)`, `true` only for
`"remote"`.

**3. Mode-selector mutation — same local/remote split, independently
confirmed against `start.ts`.** `runRemoteLoop`'s `setMode` handler calls
the live ACP session's real `setMode`; `runLocalPty`'s honestly returns
`{ok: false}` always ("the live TUI owns its own permission mode"). Added
`canMutateMode(controlMode)` (`true` only for `"remote"`): when true, the
existing `<select onChange=…>` mutating flow is unchanged; when false, the
selector degrades to a plain `<span>Mode: {label}</span>` read-only
display — no `setMode` call is ever attempted for a PTY session, so there's
nothing to show an error for after the fact (per the plan's instruction).
Both predicates are exported from `ControlBar.tsx` for direct testing
without needing to render the component.

## Testing approach (all three sub-tasks' tests)

None of this feature area's components render in the test suite today —
`packages/web`'s vitest config is `environment: "node"` and the existing
precedent (`ThinkingBlock.test.ts`, `Timeline.test.ts`) is to import and
test small pure/exported helper functions straight out of a `"use client"`
component file rather than mount the component (which here would also need
a live `QueryClientProvider` + `SessionControlProvider`, neither of which
any existing test wires up). Followed that precedent exactly:

- `packages/web/src/components/timeline/PermCard.test.ts` (new): plan
  render — `isExitPlanTool` (both name spellings, and false for an ordinary
  tool) and `extractPlanMarkdown` (real plan string for both name
  spellings; `null` for a non-plan tool even with a coincidental `plan`
  field; `null` for a non-string/absent `plan` on the real tool name, i.e.
  an adapter contract violation).
- `packages/web/src/features/session-control/__tests__/session-state.test.ts`
  (extended): selector derivation — `deriveCurrentPermissionMode` defaults
  to `"default"`; picks up a mode decision on a `tool` item; picks it up on
  a `perm-placeholder` item; takes the most recent of two; ignores a
  non-`"mode"` decision (`allow`/`deny` don't carry a mode); resets to
  `"default"` on a `mode-switch` even after a known decision.
- `packages/web/src/components/timeline/ControlBar.test.ts` (new):
  visibility rules — `shouldShowTakeControl`/`canMutateMode` both `false`
  for `"local"`, `true` for `"remote"`.
