# P1-1.6-crypto-worker — Web crypto-bridge Worker: in-memory keys + seal/open message API

**Section:** 1.6 Web app v1 read-only (plan.md §8.3, line 701) — **(N)** new code.

## What was built

`packages/web/src/crypto/`:

- **`protocol.ts`** — the postMessage RPC contract between main thread and worker:
  `InitRequest` / `SetSessionKeyRequest` / `SealRequest` / `OpenRequest` / `ClearRequest`,
  and `CryptoWorkerOkResponse` / `CryptoWorkerErrResponse`. Every response shape is
  structurally incapable of carrying raw key bytes — only `EncryptedBox` ciphertext,
  decrypted view-model data, booleans, or `null`.
- **`key-storage.ts`** — `KeyStorage` interface with two implementations:
  `createIndexedDbKeyStorage()` (real, used by the worker at runtime — plain `indexedDB`
  API, no new dependency) and `createMemoryKeyStorage()` (used by tests, which run
  outside a browser).
- **`worker-handler.ts`** — the core worker logic, `createCryptoWorkerHandler(storage)`.
  Holds `keyTree` (derived via `@falcon/crypto`'s `deriveKeyTree`) and `activeDek` in a
  closure — nothing exported from this module can read them back out; every request
  type's result is checked to be free of that closure state. Handles:
  - `init` — persists the master secret to storage and derives the key tree in memory.
  - `setSessionKey` — unwraps a per-session DEK (`unwrapDek`, content secret key) and
    holds it as the active key. Never-throws convention (matches `@falcon/crypto`):
    a foreign/corrupt wrapped DEK resolves `{ok: true, result: false}`, not an error.
  - `seal` / `open` — delegate to `@falcon/crypto/web`'s `seal`/`open` (AES-256-GCM via
    WebCrypto) under the active DEK.
  - `clear` — wipes both the in-memory state and persisted storage (logout).
  - Lazy startup load: the first RPC call that needs a key tree triggers
    `storage.load()` once, so a fresh worker (page reload) picks up a previously
    provisioned secret without an explicit `init` call — design §9.1 "keys ... loaded
    from IndexedDB at startup".
- **`worker.ts`** — the actual Worker entry point. Deliberately thin: wires
  `createCryptoWorkerHandler(createIndexedDbKeyStorage())` to `self.onmessage` /
  `self.postMessage`. This is the only file that runs inside the worker thread.
- **`client.ts`** — main-thread `WorkerLike`-based RPC client
  (`createCryptoBridgeClient`): `init`, `setSessionKey`, `seal`, `open`, `clear`,
  `terminate`. Request-id-keyed pending-promise map; `WorkerLike` is a minimal
  interface (`postMessage`/`onmessage`/optional `terminate`) so tests can swap in an
  in-process double instead of a real `Worker`.
- **`factory.ts`** — `createCryptoBridge()`: what app code will actually call —
  `new Worker(new URL("./worker.ts", import.meta.url), { type: "module" })` wrapped in
  the typed client. Kept separate from `client.ts` so the RPC logic is testable without
  a real Worker (unavailable under Vitest's node environment).
- **`index.ts`** — public barrel (`createCryptoBridge`, `CryptoBridgeClient`, protocol
  types).

`packages/web/package.json` — added `"@falcon/crypto": "workspace:*"` as a dependency
(the first cross-package workspace dependency wired up in the monorepo so far; Turborepo's
existing `dependsOn: ["^build"]` pipeline picked this up automatically — `@falcon/crypto`
now builds before `@falcon/web`, no `turbo.json` changes needed).

## Tests (`packages/web/src/crypto/__tests__/`)

- **`loopback.ts`** — test double for `WorkerLike`: wires the client interface directly
  to a `CryptoWorkerHandler` in-process (no real Worker thread), round-tripping every
  message through Node's `structuredClone` (same algorithm real Workers use) so a value
  that couldn't actually survive a postMessage crossing would fail here too. Records
  every request/response for inspection.
- **`bytes-scan.ts`** — `containsSecretBytes(value, secret)`: recursively scans any
  value (including nested objects/arrays/Uint8Arrays) for a byte sequence.
- **`worker-handler.test.ts`** (8 tests) — drives the handler directly with in-memory
  storage: seal/open round-trip, `setSessionKey` never-throws on a foreign DEK, `open`
  never-throws on ciphertext sealed under a different DEK, `not-initialized` /
  `no-active-session-key` error paths, `clear()` wiping storage, and lazy startup-load
  from a pre-populated store (simulating a worker restart / page reload).
- **`client.test.ts`** (4 tests) — end-to-end through the loopback: seal/open round-trip
  via the client API, `open()` resolving `null` (not rejecting) for a bad box, the
  client's promise rejecting on an RPC-level error, and the key test: **iterates every
  response the loopback worker ever posted back and asserts none of them contain the
  raw master secret, the derived signing/content secret keys, or the session DEK
  anywhere in the (deep-scanned) payload** — the concrete verification of the
  "main thread never receives raw key bytes" requirement.

All 12 new tests pass; full `packages/web` suite is 26/26.

## Assumptions / scope decisions

- **Single active session DEK, not a per-session cache.** The task description's API
  surface is literally `seal(data)` / `open(box)` with no session parameter. Real
  message envelopes are encrypted per-session (DEK wrapped to the content keypair per
  §5.1/§9.1), so the worker holds one "current" unwrapped DEK at a time, set via
  `setSessionKey(wrappedDek)`, and `seal`/`open` operate against it. A richer
  multi-session DEK cache (keyed by session id) is left for the sync-engine bullet
  (plan.md 1.6, not yet started) which will actually need to juggle multiple sessions'
  keys concurrently — adding that here would be guessing at a shape the sync engine
  hasn't defined yet.
- **`init(masterSecret)` is exposed on the client**, i.e. the main thread can send raw
  key material *into* the worker. This doesn't violate the trust boundary in §5.3/§9.1
  — the guarantee is one-directional (worker never emits key bytes back out); the
  master secret has to originate somewhere during auth/recovery-code-import (plan.md
  700, not yet built) and get handed to the worker once. What this task guarantees and
  tests is that once inside the worker, it never comes back out.
- **No new dependencies.** `key-storage.ts` uses the plain `indexedDB` global (already
  available via the existing `"dom"` lib in `packages/web/tsconfig.json`) rather than
  pulling in `idb` or similar. Tests inject `createMemoryKeyStorage()` instead of
  `fake-indexeddb`/`jsdom`, so no new devDependencies were needed either — the whole
  suite runs under the existing `environment: "node"` Vitest config.
- **Worker TS typing avoids the `dom`/`webworker` lib conflict.** `worker.ts` uses only
  `self.onmessage` / `self.postMessage`, which type-check fine under the existing `dom`
  lib (no `webworker` lib added, which would conflict with `dom`'s global declarations
  in the same tsconfig).
- Nothing in `packages/web/src/app/` was wired up to call `createCryptoBridge()` yet —
  that's the auth-pages bullet (plan.md 700) and outside this task's scope, which is
  the worker + client plumbing itself.
