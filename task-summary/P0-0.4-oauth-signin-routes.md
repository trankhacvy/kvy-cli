# P0-0.4-oauth-signin-routes — OAuth sign-in routes (Google/GitHub/email)

Adds `POST /v1/auth/register` to `@falcon/server`: the sign-up route from
falcon-system-design.md §5.2 ("Sign-up (web-first): browser generates masterSecret →
derives keys → OAuth (Google/GitHub/email) binds an identity for recovery/contact →
`POST /v1/auth/register {oauthProof, signPubKey, contentPubKey}` → server creates
Account keyed by `signPubKey`, returns JWT"). Falcon-specific new code
(plan.md line 646, tagged **(N — DELTA D5)**) — not a port from Happy; Happy has no
server-side OAuth-identity-binding route (its `authRoutes.ts` OAuth material is a
client-side Claude.ai *provider* OAuth flow, unrelated to account sign-up).
Email+password is deferred per falcon-plan.md §1.2 ("OAuth binding … stored on account
for recovery only. Defer email+password.") — Google and GitHub only.

## Implementation notes

- **Route**: `POST /v1/auth/register`, body `{ oauthProvider: "google"|"github",
  oauthProof, signPubKey, contentPubKey }` — field names match the design doc's quoted
  shape exactly (`signPubKey`/`contentPubKey`, not `publicKey`/`contentPublicKey` as in
  the sibling `/v1/auth` challenge-response route — a deliberate, separately-documented
  contract for this endpoint, not an inconsistency).
- **`oauthProof` verification is provider-specific and lives in `auth/oauth.ts`**,
  injected into the route the same way `db` already is (`buildOAuthRoutes(db, verifier)`,
  defaulting to `defaultOAuthVerifier`) so tests never touch the network:
  - **Google**: `oauthProof` is an OpenID Connect ID token (JWT) obtained by the browser
    from Google's sign-in flow. Verified with `jose`'s `jwtVerify` against Google's
    JWKS (`https://www.googleapis.com/oauth2/v3/certs`, fetched lazily via
    `createRemoteJWKSet` — never at module import time), checking `issuer` (Google's two
    documented issuer strings) and `audience` (`GOOGLE_OAUTH_CLIENT_ID`). **Fails
    closed**: if `GOOGLE_OAUTH_CLIENT_ID` isn't configured, every Google proof is
    rejected outright rather than verifying signature/issuer while skipping the
    audience check — skipping audience would accept a token minted for any unrelated
    app that also uses Google sign-in as proof of this account.
  - **GitHub**: `oauthProof` is a GitHub OAuth access token. GitHub tokens are opaque
    (no local signature), so verification is a live call to `GET
    https://api.github.com/user` with `Authorization: Bearer <token>` — a forged/expired
    token gets a 401 straight from GitHub. `id` from the response becomes
    `oauthSubject`.
  - Both verifiers follow the codebase's "unwrap never throws" convention: any failure
    (bad signature, wrong audience, expired, network error, malformed body) collapses to
    `null`, never a thrown exception — the route turns `null` into a 401, never a 500.
- **Account upsert**: same shape as `/v1/auth`'s — `db.insert(accounts).values({
  signPublicKey, contentPubKey, oauthProvider, oauthSubject }).onConflictDoUpdate({
  target: accounts.signPublicKey, set: {...} }).returning()`. Re-registering the same
  `signPubKey` (e.g. re-running sign-up, or switching which OAuth account is bound)
  rebinds `oauthProvider`/`oauthSubject` and refreshes `contentPubKey` on the existing
  row rather than creating a second one — same row `/v1/auth` logs into afterward
  (verified by an integration test that registers then immediately does a
  challenge/response login and asserts the same `accountId`).
- **`signPubKey` structural validation**: decoded and length-checked against
  `tweetnacl.sign.publicKeyLength` (32 bytes) before spending a network round-trip on
  OAuth verification — a malformed key is a client bug (400), not an OAuth failure (401).
  `@falcon/crypto`'s `decodeBase64` never throws (documented "never throw" package
  convention), so no try/catch is needed around it, matching `auth.ts`'s style.
- **No proof-of-possession signature on this route.** The design doc's quoted body
  shape (`{oauthProof, signPubKey, contentPubKey}`) has no challenge/signature field,
  unlike `/v1/auth`. This is intentional per §5.2: registration establishes the
  `signPubKey` identity anchor; every *subsequent* login re-proves possession via
  `/v1/auth`'s challenge/response. I did not add an extra signature requirement beyond
  what the design doc specifies.
- **`toHex` extracted to `app/routes/hex.ts`** — was a private helper duplicated between
  `auth.ts` and the new `oauth.ts`; pulled out once both routes needed it rather than
  copy-pasting a second copy.

## Testing

- `auth/oauth.test.ts` (10 tests, no network): `verifyGoogleIdToken` against a
  locally-generated RS256 keypair + `jose`'s `createLocalJWKSet` (valid token; wrong
  audience; wrong issuer; expired; malformed string; and — via `vi.resetModules()` +
  fresh dynamic import, since `config.ts` parses `process.env` once at import time —
  the fail-closed case when `GOOGLE_OAUTH_CLIENT_ID` is unset). `verifyGithubAccessToken`
  against a stubbed `fetchUser` (200 with numeric id; non-2xx; missing id; fetch
  rejects).
- `app/routes/oauth.test.ts` (5 tests, `@electric-sql/pglite` in-memory Postgres, same
  pattern as `auth.test.ts`, plus a fake `OAuthVerifier` so no test touches the
  network): successful registration binds `oauthProvider`/`oauthSubject` and returns a
  verifiable JWT; invalid proof → 401; malformed `signPubKey` → 400; re-registering the
  same `signPubKey` under a different provider rebinds the row instead of duplicating
  it; and a registered account can immediately log in via `/v1/auth`'s
  challenge/response with the same `accountId`.

## Assumptions

- Only Google and GitHub are wired up as OAuth providers (`OAuthProvider = "google" |
  "github"`), per falcon-plan.md §1.2's explicit "Defer email+password" — the task
  title's "(Google/GitHub/email)" lists the design doc's full aspirational provider set,
  but the plan doc's own note scopes this task down to the two OAuth providers.
- `GOOGLE_OAUTH_CLIENT_ID` is the only new required-for-production config; there's no
  equivalent GitHub client id needed server-side because verifying a GitHub access token
  is a live API call, not a local signature check.
- No rate limiting on this route, matching `/v1/auth` — plan.md §16 lists "Rate limits
  on auth + ingest" as a separate Phase 1 bullet (§4.3), not part of this task.
- Re-registration (same `signPubKey`, new/different OAuth proof) is treated as a
  legitimate rebind, not rejected — consistent with "OAuth binds an identity for
  recovery/contact" (not identity dedup) and with `/v1/auth`'s existing idempotent-upsert
  precedent.
