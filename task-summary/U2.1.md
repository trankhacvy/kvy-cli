## Drift from the plan's snippets (and why)

The plan's W2.1 code snippets were written against an OLDER shape of
`pretoolPermissionBridge.ts` where `handlePreToolUse` did all the work. By the
time this unit started, U1.2 ("perm-routing") had already landed and split the
bridge into two hooks:
- `handlePreToolUse` — always defers `ask` (Claude Code's own permission engine
  decides), *except* for `AskUserQuestion`.
- `handlePermissionRequest` — the new hook that owns the local-vs-web fork for
  every other tool (fires only for prompts Claude Code itself would show).

Per plan-v2.md's own W1.1 section ("`PreToolUse` (existing) — returns `ask`
for everything except the `AskUserQuestion` special case (Wave 2.1)"), the
special case still belongs on `handlePreToolUse`, so the plan's original
intent was preserved — I adapted the snippets to the *current* method/pending
map shapes rather than the ones the snippets were written against:
- `handleAskUserQuestion()` is a new private method called from
  `handlePreToolUse`, using the pre-existing (previously-unpopulated) `pending`
  map exactly as that map's own doc comment predicted ("Wave 2.1's
  `AskUserQuestion` special case is the intended future occupant of this map").
- `mapDecision()`'s question branch was added as the *first* check inside the
  existing method (which already handles the generic allow/deny/mode cases for
  that same `pending` map via `resolve()`), rather than as a whole separate
  function.
- `AskQuestion`/`composeAskAnswerReason`/`ASK_FALLBACK_REASON`/
  `isAskUserQuestion` are unchanged from the plan's snippet in spirit; `AskQuestion.options`
  keeps the plan's `Array<{label,description?}|string>` union on the CLI side.
- On the web side, `parseAskQuestions` normalizes options to `AskQuestionOption[]`
  (`{label, description?}[]`, always, options never left as a string) up front —
  a small adaptation so `AskUserQuestionCard` doesn't need to re-branch on
  option shape when rendering.
- This repo's web package has **no component-render test infrastructure**
  (`vitest.config.ts` runs `environment: "node"`, no `@testing-library/react`,
  no `.test.tsx` files anywhere — confirmed by inspecting the existing
  `ThinkingBlock.test.ts`/`Timeline.test.ts` precedent, which extract pure
  functions from `.tsx` files and test those). So:
  - `AskUserQuestionCard`'s interactive logic (selection toggling, "all
    answered" gating, building the answers map, building the wire-shaped
    decision, extracting answers back out of a decision) was pulled into a new
    pure module, `features/session-control/ask-question-state.ts`, mirroring
    the existing `perm-card-state.ts` pattern — this is what "Tests: ... card
    interactions" actually exercises.
  - "dispatch" tests (`PermPlaceholder`/`ToolCardShell`/registry routing
    `AskUserQuestion` to the right card) call the exported component functions
    directly and inspect the returned `React.createElement(...)` plain object's
    `.type` — the same technique this codebase already uses to test `.tsx`
    logic without a DOM (no new test infra invented).

## Sub-task 1 — Bridge (`packages/cli/src/claude/pretoolPermissionBridge.ts`)

- `isAskUserQuestion(name)` — matches `"AskUserQuestion"` / `"ask_user_question"`.
- `AskQuestion` type, `composeAskAnswerReason(questions, answers)` — Claude
  Code's own native answer format (`- {question}\n  → {labels}`), and
  `ASK_FALLBACK_REASON` — the plain-text-re-ask fallback string, deliberately
  **not** run through `appendDenyGuard` (it already tells the model exactly
  what to do next; appending the generic anti-workaround sentence would muddy
  that specific instruction).
- `handlePreToolUse` now dispatches `isAskUserQuestion(tool_name)` to the new
  private `handleAskUserQuestion()` before its generic always-`ask` path.
- `handleAskUserQuestion()`: local turn → `ask` ("answer the widget at the
  terminal", `onPromptLikely` fires); web turn → emits a `perm-request` with
  `modes: []` (a question offers no mode switches), populates the `pending` map
  with the new `isQuestion`/`questions` fields, and blocks for an answer or a
  timeout (→ `ASK_FALLBACK_REASON`, exactly, no anti-workaround suffix).
- `PendingPreToolRequest` gained optional `isQuestion?: boolean` /
  `questions?: AskQuestion[]`.
- `mapDecision()` gained a first branch for `pending.isQuestion`: an
  `allow` with `updatedInput.answers` composes the deny-with-answer reason; a
  `deny` uses the decision's own message (or the fallback); anything else
  (bare allow with no answers, a mode switch — neither makes sense for a
  question) degrades to `ASK_FALLBACK_REASON`.
- Updated the class-level doc and `remotePermissionHook.ts`'s doc to describe
  the new split accurately (both previously said `PreToolUse` "always defers").
- No `hookServer.ts`/`remotePermissionHook.ts` wiring changes needed —
  `handlePreToolUse` is already the generic entry point for every `PreToolUse`
  call (settings matcher is `"*"`), so `AskUserQuestion` already reaches it.
- No `@falcon/wire` changes — `PermDecisionSchema`'s existing
  `allow.updatedInput: z.unknown().optional()` already carries `{answers}`.

## Sub-task 2 — Web

- `parseAskQuestions` / `parseAskAnswers` / `isAskUserQuestion` added to
  `packages/web/src/lib/tool-args.ts` (same defensive-parsing convention as
  every other `parse*Args` there — degrades to `[]`/`undefined` on a shape
  mismatch, never throws).
- `features/session-control/ask-question-state.ts` (new): pure
  `toggleAskSelection` / `allAskQuestionsAnswered` / `buildAskAnswers` /
  `buildAskAnswerDecision` (produces the exact
  `{kind:"allow",scope:"once",updatedInput:{answers}}` shape) /
  `extractAskAnswers`. Exported from `features/session-control/index.ts`
  alongside the existing `perm-card-state.ts` exports.
- `components/timeline/AskUserQuestionCard.tsx` (new): single/multi/multiSelect
  question rendering, reuses `useSessionControl()` +
  `applyAnswerResult`/`fromError`/`PermCardPhase` exactly like `PermCard`;
  renders `AskAnsweredSummary` (handles `permission.decision` canonical +
  optimistic `answered`/`lost-race` phases, showing "Answered on another
  device" for the lost-race case).
- Dispatch: `PermPlaceholder.tsx` routes `isAskUserQuestion(item.name)` to
  `AskUserQuestionCard` *before* the decision-based branch (the card handles
  its own pending/answered/lost-race states internally, unlike the
  `PermCard`/raw-`JsonBlock` split the placeholder otherwise uses).
  `ToolCardShell.tsx`'s permission section does the same swap in place of
  `PermCard` when `item.permission.decision === undefined`.
- `tool-cards/AskUserQuestionToolCard.tsx` (new) + `registry.tsx` entry (both
  tool-name spellings) — read-only Q&A summary for a locally-answered
  question, replacing the `McpGenericCard` JSON-dump fallback. Shows "Waiting
  for an answer…" instead of duplicating the question list when
  `item.permission` is still pending (the interactive card below already
  covers that case) and falls back to a raw `JsonBlock` of the tool-end output
  when `parseAskAnswers` can't recognize the shape (design principle: unknown
  shapes are shown, never hidden — the exact real Claude Code tool-result
  shape for `AskUserQuestion` is unverified here; that's explicitly this
  unit's `[human]` sub-task, not implemented).
