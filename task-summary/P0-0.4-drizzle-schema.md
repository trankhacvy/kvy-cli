# P0-0.4-drizzle-schema — Drizzle schema + initial migration for falcon-server

Adds the Drizzle ORM data model to `@falcon/server` per
`falcon-system-design.md` §6.1 / `plan.md` §3.2: the nine tables (`accounts`,
`machines`, `workspaces`, `sessions`, `sessionMessages`, `unmanagedSessions`,
`pairRequests`, `pushSubscriptions`, `blobs`), a shared `bytea` custom Drizzle
type for every `EncryptedBox` column, the generated initial SQL migration,
and a migration-on-boot runner wired into `main.ts`.

This worktree was branched from `P0-land-phase0-worktrees` (not `main`),
since that branch is where `packages/server` (task P0-0.4-server-skeleton)
currently lives — per the task instructions, `main` has no `packages/server`
yet.

## Implementation notes

- **Schema is a direct, faithful port of design §6.1**, not the abridged
  §3.2 plan.md snippet — I used the full table definitions (all columns,
  indexes, FKs) from `falcon-system-design.md` lines 331–416, since that's
  explicitly called out there as the canonical source
  (`plan.md` §3.2: "full version in `falcon-system-design.md §6.1`").
- **`bytea` custom type**: `customType<{ data: Uint8Array }>({ dataType: () =>
  'bytea' })`, exactly as specified in both docs. Verified end-to-end against
  a real Postgres 16 container: insert with a `Uint8Array`, read back via
  `db.query.accounts.findFirst`, got back a `Buffer` that `instanceof
  Uint8Array` and round-trips byte-for-byte. `drizzle-kit generate` emits the
  column type as the string `"bytea"` (quoted) rather than the bare `bytea`
  keyword — this is a cosmetic quirk of how drizzle-kit renders custom-type
  `dataType()` strings it doesn't recognize as builtin; quoting a
  lowercase identifier in Postgres is semantically identical to leaving it
  unquoted (`\d accounts` on the applied migration shows the columns as
  plain `bytea`, confirmed against a live container — see Verification).
- **`pairRequests` / `pushSubscriptions` / `blobs`**: the design doc gives
  these three tables only as inline comments (`/* id, ephPub unique, state,
  response bytea, token, expiresAt */` etc.), not full column definitions
  like the other six. I fleshed them out from that comment plus
  cross-referencing Happy's `TerminalAuthRequest`/`AccountPushToken` Prisma
  models (`happy/packages/happy-server/prisma/schema.prisma`) for the shape,
  and plan.md §16's explicit callout that `pairRequests.expiresAt` is
  **required** ("add `expiresAt` TTL, one of the reported Happy vulns") — so
  `expires_at` is `NOT NULL` with no default (the pairing-endpoint task will
  set it). `pushSubscriptions.keys` is `jsonb`, not `bytea` — per §5.3's
  trust-boundary table, webpush subscription keys are transport metadata the
  server legitimately needs to read to call the Push API, not user content.
- **Two-level seq allocation (`headerSeq` / `msgSeq`)**: columns are in
  place (`accounts.headerSeq`, `sessions.msgSeq`) per DELTA D2, but
  `seq.ts`'s `allocMsgSeq`/`allocHeaderSeq` helpers are **out of scope** for
  this task — they're a separate, later checklist line in `plan.md` §16
  (0.4 Server foundation) and this task's description only covers schema +
  migration + boot runner.
- **Migration-on-boot runner** (`src/db/migrate.ts`): a short-lived
  `postgres()` connection with `max: 1` (drizzle's documented pattern for
  migrations — avoids holding a pooled connection open across the whole
  migration run), calls `drizzle-orm/postgres-js/migrator`'s `migrate()`,
  then always closes the connection (`finally`). Wired into `main.ts` as
  `await runMigrations()` before `buildServer()`/`app.listen` — a failure
  here hard-exits via the existing top-level `.catch()` rather than starting
  a server against an unmigrated DB. **Deliberately not** inside
  `buildServer()` itself: `server.test.ts`'s existing tests build+inject the
  app without a live Postgres, and keeping `buildServer()` DB-free preserves
  that (matches P0-0.4-server-skeleton's design: DB/auth wiring is
  explicitly left to later tasks).
- **`migrationsFolder` path resolution**: `path.resolve(process.cwd(),
  "drizzle")`. This assumes the process is started with cwd =
  `packages/server/` — true both for `pnpm --filter @falcon/server dev|start`
  and for the eventual production Docker image (design §6.5: single app
  process, WORKDIR mirroring the package with `dist/` and `drizzle/` copied
  in as siblings). Not resolved via `import.meta.url` because `pkgroll`
  bundles all of `src/` into one `dist/main.js`, which would collapse the
  `src/db/migrate.ts` → `../../drizzle` relative path down to `dist/main.js`
  → `../drizzle`, i.e. two different relative paths depending on
  dev-vs-built context; cwd-relative is the one path that's stable across
  both.
- **`DATABASE_URL`**: added to `config.ts`'s zod `EnvSchema` (`.min(1)`,
  defaults to `postgres://falcon:falcon@localhost:5432/falcon` — matching
  the credentials the sibling `docker-compose.dev.yml` task is expected to
  use). Existing `config.test.ts` had an exact `toEqual({...})` assertion on
  the full parsed env object, so I added `DATABASE_URL` to both the
  "defaults" and "fully-specified" test cases, plus one new test
  (`throws when DATABASE_URL is an empty string`) for symmetry with the
  existing `HOST` empty-string test.
- **Driver choice**: `postgres` (postgres.js), not `pg`/`node-postgres`.
  It's the driver Drizzle's own docs lead with for `drizzle-orm/postgres-js`,
  is TS-native (no `@types/pg` needed), and is what I benchmarked/tested
  against in Verification below.
- **`db:generate`/`db:migrate` package scripts**: added for local iteration
  (`pnpm --filter @falcon/server db:generate` after editing `schema.ts`;
  `db:migrate` to apply migrations standalone outside the boot path, e.g. in
  CI or a manual `migrate` step). Neither is wired into the root `turbo.json`
  pipeline — they're one-off/manual commands, not part of `build`/`test`.

## Assumptions

- `DATABASE_URL` default points at `localhost:5432` with `falcon`/`falcon`
  creds — no docker-compose file exists yet in this worktree (that's task
  P0-0.4-docker-compose-dev, unmerged); chose credentials that read as an
  obvious placeholder and are easy to align once that compose file lands.
- Kept `pairRequests.token` and `.response` nullable (state starts
  `'pending'` with neither set) since the design's pairing flow (§5.2) only
  populates them once a request is approved — schema-level nullability
  matches the state machine, enforcement of "must have `response`+`token`
  when `state='authorized'`" is application logic for the pairing-endpoints
  task, not a DB constraint.
- Did not add a `drizzle` dependency section to root `CLAUDE.md`'s "planned"
  package-layout line beyond noting Drizzle has landed (kept the edit
  minimal — full auth/Socket.IO wiring is still genuinely planned).

## Verification

- `pnpm build` (root, turbo) — all 3 packages green, `@falcon/server`
  recompiles cleanly with the new `db/` module folded into `dist/main.js`
  via pkgroll.
- `pnpm typecheck` — green.
- `pnpm test` (root) — 23/23 `@falcon/server` tests pass (was 19; +4 new in
  `schema.test.ts`), 65/65 `@falcon/crypto`, 61/61 `@falcon/wire`, all
  unaffected.
- `npx drizzle-kit generate` — ran successfully against `schema.ts`,
  produced `drizzle/0000_thin_synch.sql` (9 `CREATE TABLE`, 6 FKs, 9
  indexes) + journal/snapshot metadata.
- **Live Postgres round-trip** (docker `postgres:16`, not committed to the
  repo — used only to verify locally):
  - `runMigrations()` applied the generated SQL cleanly; `\dt` shows all 9
    tables; `\d accounts` / `\d sessions` confirm `bytea` columns are the
    real Postgres `bytea` type (not a broken custom-type reference) despite
    the quoted `"bytea"` in the generated SQL.
  - Re-ran `runMigrations()` a second time against the now-migrated DB:
    idempotent (drizzle's own migrations-tracking table short-circuits;
    only Postgres `NOTICE`s about `IF NOT EXISTS`-style skips, no errors).
  - Inserted an `accounts` row via `db.insert(schema.accounts).values({...,
    settings: new Uint8Array([1,2,3,4,5]) })`, read it back via
    `db.query.accounts.findFirst`: cuid2 `id` was minted, `headerSeq`
    defaulted to `0`, and `settings` round-tripped as a `Buffer`
    (`instanceof Uint8Array`) with the exact original bytes.
  - Container removed after verification; nothing left running.
- `pnpm lint` — fails with `[warn] Linter process terminated abnormally
  (possibly out of memory)` in this sandbox, reproduced on a single
  untouched pre-existing file too (`packages/server/src/app/api/health.ts`)
  — confirmed pre-existing/environmental, not introduced by this change (the
  prior task's summary notes the same issue).
