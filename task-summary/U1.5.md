# U1.5 — "timeline-fixes" (bundle: W1.6 + W1.8)

`components/timeline/Timeline.tsx` gets stick-to-bottom auto-follow +
"Jump to latest" (W1.6) and an in-timeline pulsing "Working…" row (W1.8),
plus the `working` prop plumbing from `SessionTimelineScreen` both rely on.
One worktree, one combined pass, per plan-v2.md's file-locality bundling.

## W1.6 — auto-scroll + scroll-to-bottom button

**Why.** `Timeline.tsx` never scrolled — a long-running session's tail was
invisible unless the user manually dragged the scrollbar every time.

**What.** Implemented per plan-v2.md's snippet, essentially verbatim:
- `following` state (default `true`).
- A `useEffect` keyed on `[items.length, following, virtualizer]` that calls
  `virtualizer.scrollToIndex(items.length - 1, { align: "end" })` while
  following.
- **rAF re-call** (plan.md risk register #3): the effect also schedules a
  `requestAnimationFrame` that re-runs `scrollToIndex` once more, correcting
  for `@tanstack/react-virtual`'s known dynamic-measurement quirk where an
  unmeasured row makes the first call land short. Cleaned up via
  `cancelAnimationFrame` on the effect's cleanup path.
- `onScroll` computes `distanceFromBottom` and calls `setFollowing`; the
  bottom-proximity threshold itself is factored out as an exported pure
  function, `isNearBottom(distanceFromBottom, viewportHeight)`, rather than
  inlined, so it's unit-testable (see Tests below).
- A floating "↓ Jump to latest" button renders when `!following`, resuming
  `following` and re-scrolling on click.
- `working` prop added to `Timeline`'s signature (`{ items, working = false }`)
  and threaded through in `SessionTimelineScreen.tsx`'s existing call site
  (`<Timeline items={mergedItems} working={working} />` — `working` was
  already computed there via `ephemeralWorking || isTurnOpen(items)` for
  `ControlBar`/the header, just not passed to `Timeline` yet).

**Drift from the plan's snippet.** The plan's snippet showed the scroll
container itself carrying `relative flex-1 overflow-hidden` with the
`overflow-y-auto` div nested one level in — the real pre-existing
`Timeline.tsx` had collapsed those into a single div
(`relative flex-1 overflow-y-auto px-4 py-4`). Restructured into the plan's
two-div shape (outer `relative flex-1 overflow-hidden` wrapper, inner
scrollable `overflow-y-auto` div holding the virtualized content) so the
"Jump to latest" button can `absolute`-position against the outer wrapper
without being affected by the inner div's own scroll offset — otherwise the
button would scroll away with the content instead of staying pinned.

## W1.8 — in-timeline activity row

**Why.** The only "the agent is working" signal was the header's static
"Working…" text — with W1.6 making the tail visible, a live in-timeline row
completes the picture per the plan.

**What.** A pulsing "Working…" row (pulsing dot + text, exact classes from
the plan's snippet) renders inside the scrollable container, after the
virtualized block but still inside the `overflow-y-auto` div — so it scrolls
with the container's natural content flow (following keeps it visible) while
staying outside the virtualizer's measured/absolutely-positioned block
(never affects `measureElement` sizing). Gated by an exported pure function,
`shouldShowActivityRow(working, items)`, matching the plan's "render a
pseudo-row after the last item when `working && last item is not a running
tool`" condition: `false` when not working, `false` on an empty timeline
(no pre-existing card content), `false` when the last `RenderItem` is a
`ToolItem` with `status: "running"` (that card already carries its own
in-progress affordance — a second "Working…" row directly under it would be
redundant), `true` otherwise.

## Tests

Both `isNearBottom` and `shouldShowActivityRow` are exported from
`Timeline.tsx` specifically so the follow/pause/resume and
activity-row-suppression behaviors are unit-testable without a component
render — `packages/web/vitest.config.ts` runs `environment: "node"` and only
collects `src/**/*.test.ts` (no jsdom, no `@testing-library/react` in
`package.json`), so, matching `ThinkingBlock.tsx`'s `thinkingBlockLabel`
precedent from U1.1, the plan's "component test with a scrollable fixture"
bullet is realized as pure-logic unit tests over the extracted predicates
rather than a full DOM render (no test infra exists in this repo for the
latter yet).

New `Timeline.test.ts`:
- `isNearBottom`: at-bottom → follow; within half a viewport → follow; past
  half a viewport → pause; and a scroll-up-then-back-down sequence
  (pause, then resume) exercising the same predicate at two distances —
  covering the plan's "appending while at bottom keeps bottom / appending
  while scrolled up shows the button / clicking resumes" intent at the
  threshold-decision level (the click handler itself is a two-line
  `setFollowing(true)` + `scrollToIndex` call with no independent logic to
  unit test beyond that).
- `shouldShowActivityRow`: hidden when not working; hidden on an empty
  timeline even while working; shown for a finished text item; shown for a
  completed tool; suppressed when the last item is a running tool.
