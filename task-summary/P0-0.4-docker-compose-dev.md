# P0-0.4-docker-compose-dev — Add docker-compose.dev.yml for local Postgres

**Section:** Phase 0 — Repo & contracts (M0) / §16 0.4 Server foundation, last bullet.

## What was done

Created a root-level `docker-compose.dev.yml` with a single `postgres:16`
service for local development, per `falcon-system-design.md` §6.5's
self-host compose shape ("**docker-compose, Postgres included**"; "one SQL
dialect, one drizzle-kit migration set forever").

This is explicitly the **dev-only precursor** described in the task: it
gives contributors a real Postgres 16 to point `packages/server`'s Drizzle
config at (§3.2/§4 work, not yet started) without requiring
`packages/server` to exist. The fuller `deploy/docker-compose.yml` (Phase
4, §13 of `plan.md`) will later add the `server` service (build from
`../packages/server`, `env_file`, migrate-on-boot) and optional `minio`
for blob storage — this file does not attempt either.

Service shape:
- `postgres:16` image (matches the pinned major version used everywhere
  else in the design docs — `falcon-system-design.md` §6.5, §7.5 R5).
- `POSTGRES_USER=falcon`, `POSTGRES_PASSWORD=falcon`, `POSTGRES_DB=falcon`
  — a fixed, obviously-dev-only credential set (no secrets to manage
  locally); the resulting local connection string is
  `postgres://falcon:falcon@localhost:5432/falcon`.
- Port `5432` published to the host so a locally-run (non-composed)
  `packages/server` process can connect directly.
- Named volume `falcon-pg-dev` for data persistence across
  `docker compose down`/`up` cycles (explicitly *not* shared with any
  prod/self-host volume name, to avoid future collisions with
  `deploy/docker-compose.yml`).
- `pg_isready` healthcheck so a future `server` service (or a dev script)
  can `depends_on: { postgres: { condition: service_healthy } }`.
- `restart: unless-stopped` for a persistent local dev daemon.

Verified with `docker compose -f docker-compose.dev.yml config` (installed
Docker CLI, no daemon required) — the file parses and resolves cleanly.

Also ran `pnpm build` at the repo root to confirm the existing workspace
(`@falcon/wire`, `@falcon/crypto`) still builds; this change touches no
application code so the build result is unaffected (both packages built
successfully, cache hits from a prior run).

### Live runtime verification (follow-up)

An earlier pass of this task could only run `docker compose config` because
the Docker daemon was unreachable in that sandbox. With a reachable daemon,
the full boot was re-verified:

- `docker compose -f docker-compose.dev.yml up -d` — pulled `postgres:16`
  and started the `postgres` service.
- `docker inspect --format='{{.State.Health.Status}}'` on the container
  reported `healthy` (via the compose file's own `pg_isready` healthcheck)
  within one 5s interval of starting.
- `docker exec <container> psql -U falcon -d falcon -c "SELECT 1"` —
  succeeded, confirming the `falcon`/`falcon`/`falcon` user/password/db
  triplet from the compose file is live and query-able inside the
  container.
- `docker compose -f docker-compose.dev.yml down -v` — clean teardown,
  container and named volume removed.

Note for contributors: on a host that already runs a native Postgres
bound to loopback (e.g. `brew services start postgresql@16`, common on
macOS), that process can win the `localhost:5432` / `127.0.0.1:5432`
connection ahead of Docker's port-published container, because the OS
prefers a socket already bound to the specific loopback address over
Docker's wildcard (`0.0.0.0`/`::`) bind. This is a host-machine port
conflict, not a defect in `docker-compose.dev.yml` — the fix, if hit, is
to stop the native `postgres` service (or change the host port in the
`ports:` mapping) rather than change this file. Connecting via
`docker exec ... psql` (as above) always reaches the compose service
directly regardless of any such conflict.

Out of scope, confirmed still out of scope: there is no automated/CI
check keeping this file in sync with `deploy/docker-compose.yml`, because
that file does not exist yet (Phase 4, §13 of `plan.md`). A sync check
has nothing to compare against until then; adding one now would be
speculative. When Phase 4 introduces `deploy/docker-compose.yml`, that
task should add a lint/CI step (e.g. diff the shared `postgres` service
block, or extract it into a common compose fragment) so the two files
can't silently drift.

## Assumptions

- No `.env` / `.env.example` file was added. The task description scopes
  this strictly to the compose file itself ("standalone infra file — no
  application code depends on it yet"); `packages/server`'s env handling
  (§4/§16 0.4, not yet built) is the right place to define and document
  `DATABASE_URL` conventions when it lands. The connection string implied
  by this compose file's credentials is noted in the file's header comment
  for discoverability.
- Did not check off the `plan.md` §16 0.4 checkbox for this item. Per this
  repo's established convention (see `80b5d15 docs: check off plan.md §16
  boxes for merged 0.1/0.2/0.3 work`), checkbox updates happen in a
  separate commit once work is merged to `main`, not inside the
  implementing worktree's commit.
- Named the service `postgres` (not `db`) to match the naming already used
  in `plan.md`'s §13 `deploy/docker-compose.yml` sketch, so the two files
  stay recognizably siblings when Phase 4 adds the fuller one.
- No `network` or `container_name` overrides — left to Compose's project-
  name-derived defaults, since this is a single-service dev file with
  nothing else to name-collide with.
