## Files created

- `packages/cli/src/remote/pushableAsyncIterable.ts` — `PushableAsyncIterable<T>`, the `query({prompt})` streaming-input side. **(V)** port, with one bugfix: Happy's `push()` checked `isDone` before `error`, so a push after `setError()` reported the misleading "Cannot push to completed iterable" instead of the real error (`setError` also sets `isDone`). Caught by a unit test; fixed by checking `error` first.
- `packages/cli/src/remote/outgoingQueue.ts` — `OrderedEnvelopeQueue`: strict incremental-order FIFO drain; every `tool-start` envelope is held back (default 250ms, Happy's constant) until either its delay elapses or a `tool-end` sharing its `call` id arrives, releasing them back-to-back. **(P)** port — reshaped from Happy's `{delay, toolCallIds}` options bag to derive delay/release-key directly from the envelope's own `ev.t`/`ev.call`, and drops Happy's `AsyncLock` (unneeded on a single-threaded event loop; `queueMicrotask` batching is enough).
- `packages/cli/src/remote/sdkToEnvelope.ts` — `SdkToEnvelopeConverter`: the `SDKToEnvelope` converter design/plan call for. **(P)** port, reshaped rather than translated line-for-line: instead of a second independent SDK→log mapper, it converts each live `SDKMessage` into the same `RawJSONLines` shape the local-mode tailer already produces and hands it to the **already-ported** `mapClaudeToEnvelopes` (`claude/envelopeMapper.ts`) — so local and remote mode share one, already-tested mapping implementation and can never drift apart. `result` messages are the remote path's own `turn-end` signal (closes the turn via the already-exported `closeClaudeTurnWithStatus`); plain-string-content `user` messages are intentionally NOT converted here (see `send()` below); `stream_event` (partial/streaming deltas) is intentionally never handled since `includePartialMessages` is never set.
- `packages/cli/src/remote/permissionStub.ts` — `createStubCanUseTool`: fail-closed `CanUseTool` stub (denies every tool call with a clear message + warn log) standing in for the not-yet-landed permission pipeline (plan.md §2.3/design §7.6), per the task's explicit instruction to stub this with a clear TODO/interface rather than block on it. `startClaudeRemote`'s `canUseTool` option makes swapping in the real one a drop-in change.
- `packages/cli/src/remote/claudeRemote.ts` — `startClaudeRemote(opts, deps)`: wraps `@anthropic-ai/claude-agent-sdk`'s `query()` with `resume: providerSessionId` support, a `PushableAsyncIterable` prompt stream, and the converter → `OrderedEnvelopeQueue` → `onEnvelopes` pipeline. Returns a `{send, interrupt, setMode, stop}` handle matching design §7.3's `RemoteHandle` shape (one `query()` instance spans many user turns via repeated `send()` calls, mirroring how Happy's `claudeRemoteLauncher.ts` keeps one `claudeRemote()` call alive across its own turn loop). `send()` emits the human-typed prompt's `user text` envelope directly (closing any prior open turn first) rather than relying on the SDK to echo it back — see `sdkToEnvelope.ts`'s header for why. `stop()` best-effort interrupts, ends the prompt stream, force-closes any open turn, flushes the outgoing queue, and calls `query.close()`, resolving with the last-known `providerSessionId` (for the future local↔remote resume flow, design §6.7).
- `packages/cli/src/remote/messageBuffer.ts` — `MessageBuffer` **(V)** port of Happy's pub/sub buffer, plus `summarizeEnvelope`/`pushEnvelopeToBuffer` — a Falcon-specific replacement for Happy's `formatClaudeMessageForInk` that summarizes the **same** `SessionEnvelope`s already flowing to the outbox, rather than re-deriving a second formatting of the raw SDK stream.
- `packages/cli/src/remote/remoteModeKeypress.ts` — `interpretRemoteModeKeypress` **(V)** port (Happy's own "extracted so we can unit-test the reduce-style logic without Ink/React" pure function), split into its own non-`.tsx` module for exactly that reason. Implements all three required gestures: double-space-within-15s confirms switching to local ("Ctrl-T to take back" per design §7.4), Ctrl-T switches immediately with no confirmation, double-Ctrl-C-within-15s exits, any other key resets a pending confirmation.
- `packages/cli/src/remote/RemoteModeDisplay.tsx` — the Ink status view: bordered log pane (streamed `MessageBuffer` summaries) + a bottom status bar reflecting confirmation/in-progress state, wired to `interpretRemoteModeKeypress` via `useInput`. **(P)** port (adapted to `messageBuffer.ts`'s `kind` field naming and Falcon's own copy).
- `packages/cli/src/remote/index.ts` — barrel export.
- `packages/cli/src/rpc/sessionRpc.ts` — `registerSessionRpcHandlers(deps)`: registers the five session RPCs design §4.4 lists (`message`, `interrupt`, `takeControl`, `setMode`, `perm.answer`) by emitting `rpc-register {target: "s:<sessionId>:<method>"}` on every `connect` (matching Falcon's **already-landed** server-side `rpcHandler.ts`, which reads `data.target` — a deliberate delta from Happy's own `{method}` payload), and answering `rpc-request` by decrypting `EncryptedBox` params (`@falcon/crypto`'s `open`, the session DEK), validating against the matching `@falcon/wire` zod schema, running the handler, validating its result against its own result schema, and sealing the reply back. Every failure mode (unknown method, malformed/undecryptable/schema-invalid params, a throwing handler, a handler returning the wrong shape) replies with a sealed `{ok:false, error}` rather than leaving the caller hanging or crashing the process.
- `packages/cli/src/rpc/index.ts` — barrel export.

Plus one test file per module (`*.test.ts`), all colocated per repo convention.

## Key design deltas from Happy (beyond what's inline in each file's header)

1. **Registration payload field name.** Happy's CLI-side `RpcHandlerManager` emits `rpc-register {method}`; Falcon's own server (`packages/server/src/app/socket/rpcHandler.ts`, already landed, itself ported wholesale from Happy's *server*) reads `data.target`. Followed the already-landed server code, not Happy's CLI-side historical convention.
2. **`EncryptedBox` objects, not opaque base64 strings**, for every RPC param/result — matches `@falcon/wire`'s `RpcCallSchema` and design §4.4 exactly.
3. **SDKToEnvelope reuses the existing envelope mapper** instead of re-implementing turn/subagent/tool-id tracking a second time — see `sdkToEnvelope.ts`'s header for the full rationale. This is a stronger property than Happy has (its local `sessionProtocolMapper` and remote `SDKToLogConverter` are two independent implementations that could drift).
4. **`canUseTool` is an explicit, documented stub** (`permissionStub.ts`) rather than any real permission logic — per this task's own instructions, since plan.md §2.3 (permission pipeline) isn't landed yet. Fails closed (denies), never hangs, never silently auto-approves.
5. **No mode-switch orchestration** (`loop.ts`/`claudeLocalLauncher`/`claudeRemoteLauncher`-equivalent) — deliberately out of scope; this task delivers the SDK wrapper + converter + queue + Ink display + RPC registration as reusable, independently-tested building blocks for that separate, not-yet-landed task (plan.md §2.2) to wire together.

## Assumptions / notes for the follow-up tasks this unblocks

- `startClaudeRemote`'s `ClaudeRemoteOptions.onProviderSessionId` and `stop()`'s returned `providerSessionId` are the hook point for §2.2's remote→local mode-switch (`claude --resume <newId>`, design §7.5) — no orchestration logic assumes anything about *when* `send()`/`stop()` are called.
- `RemoteModeDisplay`'s `onExit`/`onSwitchToLocal` props are plain callbacks; wiring them to an actual process-exit / mode-switch trigger, and rendering the component via `ink`'s `render()`, is the future launcher's job (mirrors how Happy's own `RemoteModeDisplay.tsx` is orchestrated by the separate `claudeRemoteLauncher.ts`).
- `registerSessionRpcHandlers`'s `handlers.message`/`.interrupt`/`.takeControl`/`.setMode` are exactly the hooks the future mode-switch/permission-pipeline tasks need to fill in with real behavior (e.g. `message` pushing onto a queue the launcher's `nextMessage()`-equivalent reads from, `interrupt`/`setMode`/`takeControl` calling into a live `ClaudeRemoteHandle`); this task deliberately leaves those as an injected `SessionRpcHandlers` interface rather than assuming a particular session-process shape.
