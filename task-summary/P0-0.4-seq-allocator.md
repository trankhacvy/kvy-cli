# P0-0.4-seq-allocator — seq.ts: allocMsgSeq (per-session) + allocHeaderSeq (per-account)

Implements the atomic `UPDATE ... RETURNING` seq allocators in
`packages/server/src/db/seq.ts` per `plan.md` §3.2 (line 643 of the §16
checklist) and `falcon-system-design.md`'s two-level sequencing (§4.3, §6.1
— DELTA D2 from Happy's single `allocateUserSeq`/`allocateSessionSeq`).

This worktree was branched from `P0-0.4-drizzle-schema` (not `main`), per the
task instructions — that's where `schema.accounts.headerSeq` /
`schema.sessions.msgSeq` already exist; `main` doesn't have `packages/server`
at all yet, and this task explicitly does not re-implement the schema.

## What was added

```
packages/server/src/db/
```

## Implementation notes

- **`allocMsgSeq(tx, sessionId)`** — `UPDATE sessions SET msg_seq = msg_seq + 1
  WHERE id = $1 RETURNING msg_seq`, scoped to exactly one `sessions` row.
  **`allocHeaderSeq(tx, accountId)`** — same shape against
  `accounts.header_seq`. Both are near-verbatim the snippet in `plan.md` §3.2
  (lines 196–203), which is called out there as `(N — DELTA D2)`: new code
  vs. Happy, not a port, since Happy used one global-ish counter and Falcon
  deliberately splits it two ways so chatty sessions never serialize on a
  shared counter (design §4.3's "Ordering contract (two-level)").
- **`Executor` type** — `type Executor = Database | Parameters<Parameters<Database["transaction"]>[0]>[0]`.
  Both functions accept either the shared pool (`db`) or an open
  `db.transaction(async (tx) => ...)` callback param, since Drizzle's `tx`
  and `db` expose the same query-builder surface. In real call sites (per
  plan.md §4, the message-ingest route) this runs inside the larger ingest
  transaction alongside the dedup check and insert — but the function itself
  doesn't force that, so it's also usable standalone (e.g. structural-update
  routes that only need `allocHeaderSeq`, no dedup/insert involved).
- **Null-safety** — if the target row doesn't exist, `.returning()` comes
  back empty; both functions throw (`allocMsgSeq: no session found for id
  ...` / `allocHeaderSeq: no account found for id ...`) rather than silently
  returning `undefined` or `NaN` (project convention, per this repo's
  null-safe / no-silent-failures rule for `(N)` code).
- **Why row-level locking is enough, no explicit `SELECT ... FOR UPDATE` or
  `SERIALIZABLE`**: a single `UPDATE ... RETURNING` statement is atomic —
  Postgres takes the row lock as part of the statement itself, holds it only
  for that statement's (or, inside a transaction, that transaction's)
  duration, and only on the one row matched by `WHERE id = $1`. No read
  step to reconcile, no retry-on-serialization-failure loop needed (this is
  exactly the "default READ COMMITTED + row-lock via the atomic UPDATE (no
  Serializable retry storms)" note in design §6.1).

## Concurrency test (`seq.test.ts`)

Five tests, all against a real Postgres 16 (drizzle-orm's query builder
can't be faithfully mocked for row-level lock behavior — `.mock()` doesn't
model Postgres locking at all). Structured as an integration test that
**skips itself** (not fails) when `DATABASE_URL` doesn't point at a reachable
Postgres, matching `schema.test.ts`'s existing note that DB-backed behavior
isn't wired into the no-infra default test run:

- Availability probe (`select 1`) runs at **module top level** via a
  top-level `await`, not inside `beforeAll` — `describe.skipIf(...)` is
  evaluated at collection time, before any hook runs, so the check has to
  happen before the `describe` block is even declared.
- **Gapless/unique under N-way concurrency** (`msgSeq` and `headerSeq`,
  N=25 each): fires 25 concurrent `allocMsgSeq`/`allocHeaderSeq` calls
  (each in its own `db.transaction`) at the same row, asserts the returned
  set is exactly `{1..25}` — no duplicates, no gaps.
- **Cross-session non-contention (the task's explicit ask)**: opens a
  transaction against session A, calls `allocMsgSeq`, then holds the
  transaction open (unreturned, uncommitted — lock still held) for 400ms via
  `setTimeout`. While that lock is held, concurrently allocates against
  session B in a separate transaction and asserts it completes in well under
  400ms (`elapsedMs < HOLD_MS - 50`) and that session A's transaction hadn't
  finished yet — proof the row lock on session A never blocks session B.
- **Same-session contention (the contrapositive, for confidence the lock is
  real and not a no-op)**: identical held-transaction setup, but the second
  concurrent caller targets the *same* session row. Asserts it has to wait
  for the full hold (`elapsedMs >= HOLD_MS - 100`) and gets `seq === 2` only
  after the first transaction's `seq === 1` commits.
- **Unknown id throws**: both functions reject (don't hang, don't return
  `undefined`) for a session/account id that doesn't exist.

Verified locally against a scratch `postgres:16` docker container (port
5433, not the dev-default 5432, to avoid clobbering any other local
Postgres): all 5 tests pass, full `@falcon/server` suite is 28/28 green with
the DB reachable. Also verified the skip path: with `DATABASE_URL` left at
its default (`localhost:5432`, which on this machine has a Postgres running
without the `falcon` role) the whole file reports "5 skipped", not a
failure — the suite stays green in environments with no Postgres, e.g. the
current CI workflow, which has no Postgres service yet.

## Assumptions

- No changes to `.github/workflows/ci.yml` to add a Postgres service — out
  of scope for this task (a separate concern from implementing the
  allocators), and the skip-on-unavailable design means CI stays green
  either way. If/when a Postgres service is added to CI (or
  `docker-compose.dev.yml` lands and a dev workflow runs against it), this
  test starts exercising its real assertions with zero code changes.
- Both allocator functions are exported for use by later tasks (the
  message-ingest route, session/account-metadata routes) but aren't wired
  into any route themselves — that wiring is explicitly a separate `plan.md`
  §16 checklist line (§1.2 "Server write path (HTTP)").
- Kept the `Executor` type structural (derived from `Database["transaction"]`'s
  own parameter type) rather than importing Drizzle's internal
  `PgTransaction<...>` generic directly, to avoid having to thread through
  Drizzle's query-result-HKT and schema generic parameters by hand.
