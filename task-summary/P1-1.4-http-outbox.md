# P1-1.4-http-outbox — HTTP outbox: coalescing + disk-backed retry queue

## What was already sitting in the worktree (untracked, uncommitted)

Two support modules already existed on disk under `packages/cli/src/api/` but were not part
of any commit and had no dependent code:

- `httpClient.ts` — thin `fetch` wrapper: `postMessages(sessionId, {localId, content}) →
  {ok, status}`. Used as-is (its own doc comment already matches design §4.3 exactly).
- `queue.ts` — disk persistence primitives for the 10MB-capped JSONL queue: `loadQueue`,
  `persistQueue` (atomic write-temp-then-rename), `appendWithCap` (evicts oldest first, but
  never evicts the newest entry even if it alone exceeds the cap), `makeQueuedBatch`,
  `outboxQueuePath`. Used as-is.

Neither file had a corresponding `outbox.ts` that actually used them, nor any test coverage
exercising them together — that's the piece this task built.

## What was built

**`packages/cli/src/api/outbox.ts`** — the `Outbox` class (plan.md §6.5 pseudocode, made concrete):

- `enqueue(events: SessionEnvelope[])` buffers envelopes in memory; flushes immediately once
  `maxBatchSize` (default 20) is reached, otherwise arms a `flushMs` (default 300) timer on
  the *first* buffered envelope (`this.timer ??= setTimeout(...)` — later enqueues before the
  timer fires don't re-arm it, matching "whichever first").
- `flush()` seals the buffered envelopes into one `EncryptedBox` via `@falcon/crypto`'s
  `seal(batch, dek)`, mints a cuid2 `localId`, appends the sealed batch to the disk-backed
  queue (`appendWithCap` + `persistQueue`) **before** attempting any network call — the
  durability guarantee is "queued survives a crash", not "sent survives a crash" — then kicks
  off the drain loop.
- The drain loop is a strict FIFO: one batch in flight at a time (`draining` reentrancy guard),
  retried forever with backoff on **any** non-2xx status or thrown error — "blind retry until
  2xx" per the task brief, deliberately not special-casing 4xx as permanent (a prior sketch of
  this in `falcon-plan.md` §2.3 did treat 4xx as terminal; the task description and
  plan.md §6.5's actual pseudocode/design don't, and the server-side `localId` idempotency is
  what makes blind retry safe regardless of status code). A batch is dequeued (and the disk
  file rewritten) only once the POST returns `ok`.
- Constructor calls `loadQueue()` immediately and starts draining any batches left over from a
  prior process — this is the crash/restart recovery path; no `enqueue()` call is needed to
  resume sending what's already on disk.
- `dispose()` stops the flush timer and the retry loop (does not drop buffered/queued data —
  it's for clean test/process teardown, not data loss).
- Exposes `bufferedCount`/`queuedBatchCount` getters purely for test introspection (real
  callers don't need them).

**`packages/cli/src/api/outbox.test.ts`** — 6 tests, all passing:

1. Flushes immediately at the `maxBatchSize` threshold without waiting for the timer.
2. Flushes after `flushMs` elapses when the count threshold is never reached (also checks
   nothing is sealed before the timer fires).
3. Documents the literal defaults (300ms / 20 events) as a regression guard.
4. **Disk persistence/replay across a simulated restart**: instance A flushes a batch against
   an always-throwing HTTP client, the batch lands on disk (`existsSync` + parses the raw JSONL
   line), instance A is disposed (simulating the process dying mid-retry) — then a brand-new
   instance B, constructed against the same `homeDir`/`sessionId`, is shown to load that batch
   from disk automatically and successfully drain it against a working client, after which the
   queue file is removed. Also round-trips the on-disk ciphertext through `@falcon/crypto`'s
   `open()` to confirm the replayed content really is the original envelope.
5. Retry-until-success scripted through 500 → 429 → thrown network error → 404 → 200, asserting
   all 5 attempts happen and the batch is finally dequeued.
6. A dedicated test that a *persistent* 4xx (400 three times, then 201) is still retried rather
   than given up on early — the "blind retry" contract explicitly called out in the task brief.

## Assumptions / decisions

- **Blind retry includes 4xx.** The task description says "retry with backoff until a 2xx
  response ('blind retry until 2xx')" and asks for tests under "simulated 4xx/5xx/network-failure
  responses" that all eventually succeed — so no status code is treated as permanently
  un-retryable. This is a deliberate divergence from the earlier, superseded sketch in
  `falcon-plan.md` §2.3 (Phase 2 draft) which had an `isPermanent(e)` branch for 4xx; that
  sketch predates and is superseded by plan.md §6.5's actual `Outbox` pseudocode (no such
  branch) and by this task's explicit instructions.
- **Backoff is exponential, 1s → 30s cap**, matching the guidance in `falcon-plan.md` §2.3
  ("1s → 30s cap"). It's injectable via `OutboxOptions.backoffMs` so tests don't have to wait
  through real multi-second backoffs.
- **Only sealed batches are disk-persisted, not the raw pre-flush envelope buffer.** The task
  says "unflushed/unacked batches survive a crash" — read as: once a batch has been sealed and
  queued (i.e. "flushed" out of the in-memory buffer into the disk queue), it's durable even if
  not yet acked. The sub-300ms window where envelopes sit in the in-memory `buf` before the
  timer/count threshold fires is not separately persisted — this matches the already-existing
  `queue.ts` module's scope (`QueuedBatch` = sealed content only) and keeps the write path
  simple (one seal + one disk write per network attempt cycle, not one disk write per
  `enqueue()` call).
- Added `@falcon/crypto`, `@falcon/wire`, and `@paralleldrive/cuid2` as `packages/cli`
  dependencies (workspace deps for the first two, matching the version `@falcon/server`
  already pins for the third) — the CLI package previously depended on none of them.
