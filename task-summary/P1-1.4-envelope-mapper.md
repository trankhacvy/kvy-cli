## Mapping rules preserved (plan.md §16 wording)

- assistant `text` block → `text`
- `thinking` block → `text{thinking:true}`
- non-`Task` `tool_use` → `tool-start`
- `Task` `tool_use` → subagent registration, **no parent card**; children of a
  not-yet-registered `Task` are **buffered** and replayed (in order) once it
  registers
- `tool_result` → `tool-end` (or, for a hidden `Task` call, `sub-stop` instead —
  the Task's own result never gets a card since its call never got one)
- sidechain `user` message → subagent-scoped `text`
- provider ids → cuid2 via a `Map<string,string>` so envelope/call/subagent ids
  are stable for the life of the session

Subagent resolution itself is a faithful, if renamed, port of Happy's chain:
explicit `parent_tool_use_id`/`parentToolUseId` first, then inheritance through
`parentUuid` (a child's `uuid` → provider-subagent mapping is recorded on every
message, buffered or not), then — only for `isSidechain` messages — matching the
sidechain's root `user` prompt text against a queued `Task` prompt, falling back
to "exactly one `Task` is pending" as a last resort. `task_non_sdk.jsonl` is the
golden fixture that actually exercises this whole fallback chain end-to-end
(explicit ids are absent throughout).

## Deltas from Happy (driven by `@falcon/wire`'s existing schema, not a new design)

- **No provider ids ever cross the wire.** `packages/wire/src/session.ts`'s own
  header comment states this as policy. Happy's mapper let raw `toolu_*` ids sit
  directly in `call`/emitted as-is; here every provider id (`tool_use.id`,
  `tool_result.tool_use_id`, and the `Task` id used as a subagent scope key) is
  translated through a `Map<string,string>` that mints a cuid2 the first time an
  id is seen and returns the same cuid2 thereafter. Two separate maps are kept
  (`providerCallIds`, `providerSubagentIds`) since a `Task`'s `tool_use.id` needs
  both identities.
- **A subagent/call cuid2 is minted for *every* `tool_use` block**, not only
  `Task`'s — this is kept from Happy's design even though only `Task` visibly
  triggers subagent scope here, because it's what stops an orphaned child
  (referencing some `parent_tool_use_id`) from buffering forever if that parent
  call turns out not to be a `Task`. See the file header comment for the full
  rationale.
- **No `usage` field.** `SessionEnvelope` (this repo's wire package) carries no
  token-usage field at all, so Happy's usage-attachment logic (walk backwards
  to find the last envelope that can "carry" usage) has no equivalent and was
  dropped entirely — not stubbed, not left as dead code.
- **No subagent title.** `SessionEventSchema`'s `sub-start` has no `title` field
  (unlike Happy's `{t:'start', title?}`), so `pickTaskTitle`/a `subagentTitles`
  map has no equivalent. The first thing a client sees in a subagent's scope is
  its prompt text (emitted as the sidechain root's `text` envelope), not a title.
- **`text{md}` not `text{text}`.** `SessionEventSchema`'s text event field is
  named `md`, matching the wire package as already merged.
- **Only `Task` triggers subagent scope**, not Happy's `Agent`+`Task` pair —
  Claude Code's current tool set only emits `Task`, and the task description
  calls out `Task` specifically.
- **`SessionTurnEndStatus`** isn't exported by `@falcon/wire` as its own type
  (only inline in `SessionEventSchema`'s discriminated union), so it's derived
  locally via `Extract<SessionEvent, {t:"turn-end"}>["status"]` rather than
  patching the wire package for one type alias.

## API shape

```ts
export function createClaudeEnvelopeMapperState(): ClaudeEnvelopeMapperState;

export function mapClaudeToEnvelopes(
  message: RawJSONLines,
  state: ClaudeEnvelopeMapperState,
): SessionEnvelope[];

export function closeClaudeTurnWithStatus(
  state: ClaudeEnvelopeMapperState,
  status: SessionTurnEndStatus,
): SessionEnvelope[];
```

`state` is mutated in place (turn id, provider-id maps, subagent tracking) so a
caller (the future `tailer.ts` from plan.md §6.4) holds one `state` per session
and calls `mapClaudeToEnvelopes(raw, state)` for every scanner `onMessage`,
exactly matching the plan's sketch (`const envelopes = mapClaudeToEnvelopes(raw)`
— elided there, `state` is the second arg here since it can't live in a closure
without also owning the scanner's lifecycle, which is out of scope for this
task). Every returned envelope is guaranteed schema-valid: `createEnvelope`
(from `@falcon/wire`) always runs `SessionEnvelopeSchema.parse` internally, so a
bug that produced a malformed event would throw immediately at mapping time,
never silently corrupt the outbox stream.

## Assumptions / scope notes

- `tool-start`'s optional `risk` field (`read|write|exec|network`) is left
  unset — inferring risk from a tool name/args is permission-pipeline work
  (plan.md §9), out of scope here.
- `output` on `tool-end` is only included when the `tool_result` block actually
  has a `content` field, matching the schema's `.optional()`.
- The mapper does no zod validation of its own on the raw line — it trusts the
  scanner (already merged) to have filtered via `RawJSONLinesSchema.safeParse`
  first. Untyped/passthrough fields (`message.*`, `parentUuid`, `isSidechain`,
  `parent_tool_use_id`) are read through narrow local casts, the same approach
  Happy's own mapper uses for the same reason (the scanner's schema
  intentionally doesn't validate them).
- Wiring this into the scanner's `onMessage` callback and the HTTP outbox
  (plan.md §6.4/§6.5 `tailer.ts`/`outbox.ts`) is separate, not-yet-started work
  — this task is scoped to the mapper itself, matching how `sessionScanner`/
  `startFileWatcher` landed as their own task ahead of this one.
