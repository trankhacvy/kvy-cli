# P1-1.4-transcript-scanner — Port sessionScanner + startFileWatcher

**Section:** 1.4 Transcript pipeline (plan.md §6.4/§6.5, task-list lines 682-683)

## What was ported

Source: `happy/packages/happy-cli/src/claude/utils/sessionScanner.ts` and
`happy/packages/happy-cli/src/modules/watcher/startFileWatcher.ts` (MIT).

New files, all under `packages/cli/src/claude/`:

- **`types.ts`** — `RawJSONLinesSchema` (zod), trimmed from Happy's version to
  only the fields the scanner reads (message-identity for dedup keys:
  `uuid` for user/assistant/system, `leafUuid`+`summary` for summary lines).
  Everything else passes through via `.passthrough()`.
- **`fileWatcher.ts`** — `startFileWatcher(file, onFileChange, options)`,
  ported near-verbatim. Watches a single file via `fs.watch()`, treats
  `ENOENT` as "file absent" (vs. transient watch errors), backs off
  exponentially (1s → 15s capped) between retries, and calls `onGaveUp()`
  exactly once if the file stays absent past `missingFileTimeoutMs`
  (default 60s). Returns a disposer safe to call more than once.
- **`scanner.ts`** — `createSessionScanner(opts)`, ported with one
  intentional scope cut (see below). Preserves the two load-bearing
  behaviors called out in the task:
  - `processedEntryKeys`: a dedup `Set` keyed on message identity so a
    process restart (full file re-read from byte 0) or an overlapping
    poll tick never re-emits an already-handed-off entry.
  - `deadSessions`: once a session's `fileWatcher` gives up (its
    transcript never appeared), the session id is blacklisted so the
    periodic poll loop stops resurrecting a watcher for it — this is the
    actual fix for the "dead instance" CPU-spin bug (fileWatcher's backoff
    alone isn't enough; something has to stop *re-creating* the watcher
    every poll tick, which is what this guard does).
  - `onNewSession(sessionId, { treatExistingAsProcessed? })`: announces a
    new/resumed session id, moves the previous current session into
    `pendingSessions` (Claude Code can keep appending to the pre-resume
    file), revives a previously-dead id if re-announced, and optionally
    pre-marks existing on-disk entries as processed (used on reconnect, so
    history already known to the caller isn't replayed as new).

## Deliberate scope cut (per task description)

This task explicitly does **not** depend on `mapClaudeToEnvelopes` (a later
task) — the scanner only emits raw parsed JSONL entries via `onMessage`.
Consequently, Happy's `ScannerTranscriptEvent` / `onTranscriptEvent` /
`claudeGoalStatus` side channel (which exists solely to feed that later
mapper) was **not** ported. `readSessionEntries` here only ever returns
`RawJSONLines` messages.

## Implementation notes / deltas from Happy

- **No `InvalidateSync`/`backoff` utility classes.** Happy's scanner relies
  on a generic `InvalidateSync` (coalescing invalidate + `backoff` retry
  wrapper) from `happy-cli/src/utils/sync.ts`. Since nothing else in this
  codebase needs that abstraction yet, the coalescing behavior (concurrent
  `invalidate()` calls collapse into exactly one more run after the
  in-flight sync finishes) is inlined directly in `scanner.ts` as a small
  private closure, and sync-pass failures are caught + logged rather than
  retried with exponential backoff — `readSessionEntries` already swallows
  its own errors (missing file, bad JSON, unknown message shape), so the
  sync command essentially cannot throw in normal operation; the try/catch
  is a last-resort guard, not a load-bearing retry path.
- **`getProjectPath`** (Claude Code's project-directory hashing scheme) is
  ported into `scanner.ts` and exported, since it's small and currently
  only consumed here; future tasks (hook server, bootstrap) can import it
  from this module.
- **Testability hook:** `SessionScannerOptions` adds `env?: NodeJS.ProcessEnv`
  (threaded into `getProjectPath` for `CLAUDE_CONFIG_DIR` resolution),
  `pollIntervalMs?: number` (Happy hardcodes 3s), and `logger?: Logger`
  (reuses `packages/cli/src/logger.ts`'s `Logger` interface; defaults to a
  no-op). None of these change production defaults — they just make the
  dedupe/guard timing exercisable in unit tests without waiting on the real
  3s poll or 60s missing-file timeout.
- **Dependency added:** `zod` (`^4.0.0`, matching the version already used
  by `@falcon/wire` and `@falcon/server`) added to `packages/cli/package.json`.

## Tests

- **`fileWatcher.test.ts`** — ported from Happy's own test file near
  verbatim: gives up exactly once when a file never appears; recovers if
  the file shows up within the grace window; never gives up when the file
  exists from the start; dispose is idempotent and suppresses any later
  give-up.
- **`scanner.test.ts`** (new, per task requirement to simulate incremental
  writes / restart dedupe / dead-instance guard):
  - Incremental appends: entries appended after scanner construction are
    emitted exactly once each; entries already on disk at construction
    time are treated as history, not new messages; further no-op poll
    ticks never re-emit.
  - Restart dedupe: a first scanner instance processes some appended
    entries and is torn down; a second, fresh instance (simulating a new
    CLI process) pointed at the same, now-longer transcript file treats
    everything already on disk as history again (no replay), and only
    emits genuinely new content appended afterward.
  - Dead-instance guard: announcing a session whose transcript file never
    appears results in `fileWatcher` starting exactly once and giving up
    exactly once — verified by asserting the "starting watcher" and
    "dropping" debug log lines each occur exactly once even after ~2.5s
    of poll ticks (50ms interval) past the give-up, i.e. no CPU-spin
    re-creating the watcher.
  - Revival: re-announcing a previously-dropped session id via
    `onNewSession` (after switching `currentSessionId` away first, since
    re-announcing the same-as-current id is a no-op) clears the blacklist
    and, once the file actually exists, the session resumes being watched
    and its contents are emitted.

All 4 new `scanner.test.ts` cases + 4 `fileWatcher.test.ts` cases pass
(66/66 tests in `packages/cli` overall).

## Assumptions

- The task's "no dependency on `mapClaudeToEnvelopes`" note was read as
  license to drop the entire `ScannerTranscriptEvent`/`claudeGoalStatus`
  side channel, not just the mapper call — that channel has no consumer
  until the mapper task lands, and porting it here would mean porting
  `claudeGoalStatus.ts` too, which is out of scope.
- `pollIntervalMs` defaults to 3000ms (matching Happy's hardcoded interval)
  and is overridable only for tests; production callers (a later task,
  `tailer.ts`) are expected to leave it at the default.
