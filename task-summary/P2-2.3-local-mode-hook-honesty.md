# P2-2.3-local-mode-hook-honesty

**Task**: Wire Claude Code lifecycle hooks to attention ephemerals for local-mode honesty
**Section**: Phase 2 §2.3 Permission pipeline, plan.md line 732 ("Local-mode honesty" bullet)
**Scope**: `packages/cli/src/claude/hookServer.ts` + `hookServer.test.ts` only, per the
task's own file-scope note — no changes to `packages/web` or `packages/cli/src/daemon`.

## What was already there

`hookServer.ts` only handled the `SessionStart` hook (loopback Fastify server +
generated `--settings` file + a stdin-forwarding `.cjs` script), used purely for provider
session-id discovery. No `Notification`/`Stop` hook wiring existed anywhere in `packages/cli`.

## What this change adds

1. **Two new hook routes** on the same loopback server: `POST /hook/notification` and
   `POST /hook/stop`, alongside the existing `/hook/session-start`.
2. **`attentionKindFromNotificationMessage(message)`** — a small, directly-unit-tested,
   exported heuristic that derives which `AttentionKind` (`"perm" | "question" | "done"`,
   the subset of `@falcon/wire`'s `LifecycleKind` that `POST /v1/sessions/:id/notify`
   accepts) a `Notification` hook firing represents. Claude Code's `Notification` hook
   fires for two distinct situations — a tool-permission prompt ("Claude needs your
   permission to use Bash") or a plain idle-wait nudge ("Claude is waiting for your
   input") — and exposes no separate boolean for which one it is, so the hook's
   `message` text is the only available signal: `perm` if it matches `/permission/i`,
   `question` otherwise (including when `message` is missing/undefined — never silence).
3. **`Stop` always reports `"done"`** unconditionally — no message parsing needed, since
   the hook firing at all means the turn ended.
4. **`onAttention?: (kind: AttentionKind) => void`** added to `HookServerDeps`, mirroring
   the existing `onSessionId` callback-injection pattern exactly. It's optional so
   existing `SessionStart`-only callers/tests are unaffected. Both new routes call
   `onAttention?.(kind)` and are 200-OK no-ops if it's omitted.
5. **`writeHookSettingsFile`** now writes all three hooks (`SessionStart`, `Notification`,
   `Stop`) into the generated `--settings` file, all pointing at the same loopback port
   but each hook's own endpoint path, sharing one forwarder script. The forwarder script
   was generalized to take the target hook path as a second CLI arg (`argv[3]`, after the
   port) instead of hard-coding `/hook/session-start`, so one script serves all three hooks.

## Why `onAttention` doesn't itself call the notify HTTP route

Actually calling `POST /v1/sessions/:id/notify` (or emitting over the session-scoped WS
client, `packages/cli/src/session/sessionClient.ts`) needs Falcon's own server-assigned
`sessionId` and an auth token. This loopback hook server is a per-Claude-Code-*process*
singleton with no Falcon identity of its own (that only exists after
`session/bootstrap.ts` runs, at a different layer) — so, exactly like `onSessionId`
today (which doesn't call the not-yet-built CAS metadata-update route either), the actual
network call is the responsibility of whatever wires `startHookServer` into the real
`claudeLocal.ts` spawn flow, which remains a separate, currently-unbuilt plan bullet
(confirmed via `grep`: `startHookServer`/`writeHookSettingsFile` still aren't called from
any real spawn path in `packages/cli`, only from this module's own tests). This task's
scope note ("Scope is limited to packages/cli/src/claude/hookServer.ts (+ tests)")
confirms that launcher-wiring is intentionally out of scope here.

This keeps the module's existing decoupled-callback design fully intact: whichever
follow-up task wires the real launcher can pass an `onAttention` that POSTs to
`/v1/sessions/:id/notify` (or emits over `sessionClient.ts`'s socket) without any change
to this file.

## Testing

Added to `hookServer.test.ts`:
- `POST /hook/notification` with a permission-shaped message → `onAttention("perm")`.
- `POST /hook/notification` with an idle-wait message → `onAttention("question")`.
- `POST /hook/notification` with no `message` field → `onAttention("question")` (safe default).
- `POST /hook/notification` is a 200 no-op when `onAttention` isn't supplied.
- `POST /hook/stop` → `onAttention("done")`, with and without a body.
- Unit tests for `attentionKindFromNotificationMessage` in isolation (case-insensitivity,
  undefined message).
- `writeHookSettingsFile` now also asserts the `Notification`/`Stop` entries exist, point
  at their own endpoint paths, and share one forwarder script with `SessionStart`.
- A new end-to-end test spawning the generated forwarder script against a live server to
  confirm the `Stop` hook path really reaches `onAttention("done")` (mirrors the existing
  `SessionStart` end-to-end test, updated for the forwarder's new 3-arg command shape).

All 22 tests in `hookServer.test.ts` pass (11 pre-existing + 11 new); full workspace
`pnpm build` (5/5 packages) and `pnpm --filter falcon test` (55 files / 551 tests) are
green, no regressions. `./node_modules/.bin/biome check` is clean on both touched files
(ran the binary directly — `pnpm lint`/`npx biome` were hitting an environment-level OOM
in this sandbox unrelated to these changes; direct invocation of the biome binary worked
fine and found two real formatting issues, since fixed with `--write`).

## Assumptions

- Claude Code's actual `Notification` hook message copy ("Claude needs your permission to
  use `<tool>`" for permission prompts) is stable enough to substring-match on
  `/permission/i`; this is undocumented in this repo's `happy-research.md`/design docs
  (no vendored Happy source exists in this worktree to port the exact heuristic from), so
  it's a best-effort heuristic rather than a verbatim port. It degrades safely (always
  `question`, never silence) if Claude Code changes this copy.
- `matcher: "*"` was kept on the new `Notification`/`Stop` hook entries for consistency
  with the existing `SessionStart` entry's shape, even though Claude Code's hook matcher
  semantics are primarily meaningful for tool-scoped hooks (`PreToolUse`/`PostToolUse`) —
  harmless either way.
- Left `packages/cli/src/claude/claudeLocal.ts`/the launcher untouched, per this task's
  explicit scope note; wiring `startHookServer`'s new `onAttention` into a real notify
  HTTP/WS call is the next follow-up, not this one.
