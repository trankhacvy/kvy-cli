# P4-4.4-rpc-integration-tests — RPC integration tests: dead-daemon fast-fail, reconnect storm, double-takeover race

**Section:** Phase 4 — Ship (M4) / §16 "4.4 Hardening & release gate": "RPC integration
tests: dead-daemon fast-fail <2s, reconnect storm, double-takeover race" (plan.md line
803; falcon-system-design.md §13 item 5: "RPC integration tests — dead-peer fast-fail
(<2s), reconnect grace, presence flap"). Greenfield — no prior branch or task-summary
covered this.

## What was done

Three new integration-style test suites covering the RPC layer
(`packages/server`'s `rpcHandler` + `packages/cli`'s daemon `machineRpc`), plus two
small, targeted production fixes the tests required to actually hold under real
concurrency/timing rather than just sequential retry-after-the-fact.

### 1. Dead-daemon fast-fail (<2s) — `packages/server/src/app/socket/rpcHandler.integration.test.ts`

Real Fastify server + two real `socket.io-client` connections (target + caller,
mirroring `rpcHandler.test.ts`'s existing harness). Registers a target that never acks,
kills its connection ~100ms into an in-flight call, and asserts the caller's error
response (`{ok:false, error:"RPC target disconnected"}`) lands within **2000ms of the
kill** — Happy's own postmortem-hardened design (happy-research.md §7/§11.3) measured
this at "1.6s vs 30s" against a real 2-replica cluster; that's the number this test
holds the port to.

The prior port's `RPC_PRESENCE_POLL_MS` (2000ms, requiring 2 consecutive misses to
avoid false positives) meant a **worst case of ~4s** to detect a dead peer — comfortably
over the design's stated SLO. Tuned down to 800ms → 700ms (worst case ~1.4-1.6s, matching
Happy's own measured number) with `RPC_PRESENCE_FETCH_TIMEOUT_MS` correspondingly
tightened to 400ms so a slow adapter fetch itself can't blow the budget. The
"2 consecutive misses" debounce (protects against a single transient fetch timeout —
falcon-system-design.md's own "presence flap" concern) is unchanged. Measured locally:
1483ms (well under 2000ms, ~500ms margin). The pre-existing `rpcHandler.test.ts` dead-
peer test still passes unchanged (it only asserts the eventual outcome, not timing) and
now also runs faster (1.4s vs its previous ~4s).

### 2. Reconnect storm — same file, second test

Drives 25 rapid, back-to-back reconnects of the *same* machine-scoped identity (closing
the previous connection before the next one is up, mirroring a flaky-network/daemon-
restart-loop shape rather than a clean handoff), re-registering the RPC target on every
new connection. Asserts:

- An `rpc-call` issued once the storm settles reaches the **final** connection exactly
  once (`deliveryCount === 1`, and the echoed payload proves it was iteration 24, not an
  earlier ghost).
- `console.warn` was never called with `"Multiple sockets in <room>"` — the one signal
  `rpcHandler.ts` would emit if a stale/leaked socket were still sitting in the room
  alongside the live one.

No production changes were needed here — Socket.IO's own room bookkeeping (auto-leave on
disconnect) already holds; this test exists to pin that behavior down as a regression
guard, per the design's "room membership as truth, no TTLs, no registry state" invariant
(`rpcHandler.ts`'s own header comment).

### 3. Double-takeover race — `packages/cli/src/daemon/machineRpc.takeoverRace.test.ts`

Uses the same in-process `FakeSocket` harness as `machineRpc.test.ts` (no real transport
needed — this race lives entirely in `machineRpc.ts`'s own synchronous cache logic) plus
a manually-resolvable "deferred" `adoptTake` mock so both concurrent calls are provably
still in flight before either is allowed to settle. Four scenarios:

- Two concurrent `adopt.take` calls with the **same** `idempotencyKey` (duplicate
  submission / client-side retry racing itself) collapse into one real attempt; both
  callers get the identical result.
- Two concurrent calls with **different** `idempotencyKey`s for the **same**
  `providerSessionId` — the realistic "two devices both hit take-over" shape — also
  collapse into one attempt, both getting the exact same result including any mid-turn
  `warning`. This is the actual "double-takeover race" the task names.
- Two concurrent calls for **different** `providerSessionId`s are *not* collapsed —
  proves the guard doesn't over-serialize unrelated takeovers.
- A rejected attempt is never cached and doesn't permanently wedge a `providerSessionId`
  — both concurrent callers see the same failure, and a later retry (new
  `idempotencyKey`, arriving after the failure settled) runs fresh.

**Why this needed a production fix, not just a test:** `machineRpc.ts`'s existing
`withIdempotencyCache` (backing `adopt.take`/`adopt.mirror`) and `handleSpawn`'s own
cache only stored the *settled* result, set *after* `await fn(params)` resolved. Two
calls arriving back-to-back — before the first had actually finished — both saw a cache
miss and both ran the handler: a genuine double-spawn / double-kill-and-continue race
that the existing (sequential-only) unit tests in `machineRpc.test.ts` never exercised.
Fixed by caching the **in-flight `Promise`** instead, set synchronously before any
`await` — the second caller now finds the first's promise already in the map and joins
it. A rejected attempt is still evicted immediately (never cached), preserving every
existing "does NOT cache a failure" test's behavior.

That alone only covers same-`idempotencyKey` concurrency (a retry racing itself). The
actual "two devices" shape mints two *different* keys, which the idempotency cache
never sees as the same call — so a second, resource-keyed guard,
`withProviderSessionGuard` (keyed on `providerSessionId`, not `idempotencyKey`), was
added specifically for `adopt.take`, layered under the idempotency cache. This directly
protects the design's FR-9.4 invariant ("never two live continuations of the same
history") that `adoptTake.ts`'s own header comment already names but had no
concurrency-safe enforcement for.

`spawn` and `adopt.mirror` did not need the resource-keyed guard: `spawn` has no shared
"target" two independent callers would collide on (each spawn is its own new session),
and `adopt.mirror` is a read — a redundant concurrent read is wasteful, not unsafe.

## Files changed

- `packages/server/src/app/socket/rpcHandler.ts` — tuned `RPC_PRESENCE_POLL_MS`
  (2000ms → 700ms) and `RPC_PRESENCE_FETCH_TIMEOUT_MS` (500ms → 400ms) to bring dead-peer
  detection under the design's <2s SLO; comments updated to cite the SLO and Happy's own
  benchmark instead of the previous (inaccurate) "~1s" note.
- `packages/server/src/app/socket/rpcHandler.test.ts` — one comment update (no behavior
  change); the existing dead-peer test still passes and now runs faster.
- `packages/server/src/app/socket/rpcHandler.integration.test.ts` — **new**: dead-daemon
  fast-fail + reconnect-storm tests.
- `packages/cli/src/daemon/machineRpc.ts` — `withIdempotencyCache` and `handleSpawn` now
  cache in-flight promises instead of settled values (closes the same-key concurrent-
  retry race); new `withProviderSessionGuard` wraps `adopt.take` specifically
  (closes the cross-device double-takeover race). Header comment extended to document
  both.
- `packages/cli/src/daemon/machineRpc.takeoverRace.test.ts` — **new**: double-takeover
  race tests.

## Assumptions / scope notes

- "Two clients calling `adopt.take` concurrently" was read as the realistic shape: two
  different devices, each minting its own `idempotencyKey`, targeting the same
  `providerSessionId` — not merely a retried request. Both that shape and the simpler
  same-key retry-race are tested and protected.
- "Dead-daemon fast-fail" is scoped to the RPC layer's presence-poll death detection
  (mid-call target death) per Happy's own historical benchmark and the design's explicit
  "dead-peer fast-fail (<2s)" wording — not the separate, deliberately generous 15s
  reconnect-grace window for a target that was already gone *before* the call started
  (falcon-system-design.md §13's own "reconnect grace" is a distinct, intentionally
  slower entry on the same list).
- "Reconnect storm" is scoped to the server's room-membership bookkeeping (the
  `rpcHandler`/Socket.IO layer both `packages/server` and `packages/cli` sides of this
  task ultimately depend on for correctness) rather than duplicating a CLI-side
  reconnect test — `packages/cli/src/daemon/machineClient.integration.test.ts` already
  covers a single real reconnect end-to-end at the machine-client layer; this task's
  25-iteration storm stresses the higher-volume case the existing single-reconnect test
  doesn't.
- No new top-level `deploy/integration-tests/` directory was created (unlike Happy's own
  `happy-server/deploy/integration-tests/`, which targeted a real 2-replica minikube
  cluster) — this repo has no equivalent multi-replica test environment (falcon-system-
  design.md ⚠ DELTA D3/D5: single docker-compose Postgres, not Kubernetes), so the tests
  are colocated per-package `vitest` files (`*.integration.test.ts` for the real-
  transport server suite, matching `packages/cli/src/daemon`'s own existing naming
  convention for that suffix; the takeover-race suite is plain `*.test.ts` since it uses
  no real transport, same convention `machineRpc.test.ts` itself already follows).
