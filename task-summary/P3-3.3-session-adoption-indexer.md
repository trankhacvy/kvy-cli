# P3-3.3-session-adoption-indexer — Daemon transcript indexer for unmanaged sessions

Implements the daemon-side half of plan.md §16 "3.3 Session adoption (UC9)" /
falcon-system-design.md §8 ("Transcript indexer (adoption Tier 1)") / §11 ("Session
adoption — UC9"): an fs-watch indexer over registered workspaces' Claude Code transcript
directories that upserts `unmanagedSessions` rows (encrypted summary, 2s debounce) and
derives a best-effort liveness signal via the existing process-scan utilities.

Scoped strictly to the indexer, per the task brief — **not** `adopt`/`adopt.take` RPC and
**not** the web UI (both separate, later §3.3 bullets).

## What was built

### 1. `packages/server/src/app/routes/unmanagedSessions.ts` (new) + registered in `server.ts`

`POST /v1/unmanaged-sessions` — the write path the indexer needed but that didn't exist
yet (the wire contract and Drizzle table were already merged, but nothing accepted a
write). Upsert-by-`(machineId, providerRef)` — the schema's own unique index is the dedup
mechanism, so unlike `machines.ts` this is a plain last-write-wins upsert, not a
CAS-versioned update (this row has no client-visible version to race over: only the
indexer writes it on a normal tick, and a future `adopt.take` would update it terminally,
not concurrently with the indexer for the same row). `machineId` must belong to the
caller's account (same ownership check as `machines.ts`'s CAS path) — 404 otherwise. Fans
out `unmanaged-new` (insert) / `unmanaged-update` (update) through the existing
`eventRouter`, with `accounts.headerSeq` allocated via the existing `allocHeaderSeq`.
Tests in `unmanagedSessions.test.ts` (insert + fan-out, upsert-of-same-row + fan-out,
account-ownership 404) using the existing PGlite `testHelpers.ts` harness.

### 2. `packages/cli/src/daemon/processScan.ts` (extended) — `resolveProcessCwd(pid)`

New export alongside the existing `listProcesses`: resolves a pid's cwd via
`/proc/<pid>/cwd` (linux) or `lsof -a -d cwd -p <pid> -Fn` (darwin) — `ps` alone never
exposes cwd, and the indexer's liveness check needs to know *where* a candidate `claude`
process is running, not just that it exists. Best-effort like the rest of the file:
resolves `null` on any failure (pid gone, permission denied, unsupported platform)
rather than throwing. Platform is an injectable parameter (defaults to `process.platform`)
so tests are deterministic regardless of the host OS. Tests added to the existing
`processScan.test.ts`.

### 3. `packages/cli/src/daemon/unmanagedSessionClient.ts` (new)

HTTP client for the new route: mints a fresh per-row DEK, seals the plaintext summary
(`{title, lastActivity, running}`) under it (`@falcon/crypto`'s `seal`), wraps the DEK to
the account's content public key (`wrapDek`), and POSTs — the same encrypt-then-POST
shape `session/bootstrap.ts` uses for session metadata. Best-effort: logs and resolves
`false` on any network/HTTP failure rather than throwing, so one failed upsert never
crashes the indexer's watch loop. `unmanagedSessionClient.test.ts` verifies the request
shape and, round-trip, that the sealed summary is recoverable with the content secret key
(the actual crypto, not a mock).

### 4. `packages/cli/src/daemon/transcriptIndexer.ts` (new) — the indexer itself

- `startTranscriptIndexer(deps)` fs-watches each registered workspace's Claude Code
  project transcript dir (reusing `claude/scanner.ts`'s `getProjectPath`), debounced
  `debounceMs` (default 2000ms) per session file so a burst of appends during one active
  turn produces one upsert, not dozens.
- `parseTranscript()` parses a JSONL transcript into `{title, lastActivity}`: prefers
  Claude Code's own generated `{"type":"summary",...}` line as the title (the most
  human-readable signal available), falls back to the first user message's text
  (truncated to one line, 120 chars), falls back to `"Untitled session"` — never a
  null/empty title. Unparsable/unrecognized lines are silently skipped (same tolerance as
  `scanner.ts`'s reader), matching a file being written incrementally by a live process.
- Liveness (`computeRunning`): a bare `claude` process (via `processScan.ts` +
  `markers.ts`'s `classifyFalconCommand`, which excludes anything Falcon itself launched,
  e.g. `falcon claude ...`) whose resolved cwd matches the workspace path, **and** whose
  transcript is the most-recently-modified `.jsonl` file in that workspace's project
  dir — both conditions are required since a live process alone doesn't say *which*
  transcript (of possibly many historical ones) it's writing to.
- `watchDirectoryForever`: retries forever with capped exponential backoff on any error
  (including "directory doesn't exist yet" — a registered workspace may not have a
  project dir until the first session runs there), unlike `claude/fileWatcher.ts`'s
  per-session watcher, which gives up permanently. Its `onReady` hook re-runs a
  readdir-based catch-up scan before every (re)attach attempt, closing the race window
  where a workspace's directory (and a transcript in it) can appear during the backoff
  wait, before `fs.watch` starts observing it (fs.watch never replays history).
- 13 tests in `transcriptIndexer.test.ts` (real tmp directories, real fs, short
  debounce/backoff-tolerant timings — same style as `claude/scanner.test.ts`): initial
  scan on startup, debounce coalescing, `isManaged` skip, running/not-running by
  most-recent-file + live-process-cwd match, Falcon-managed processes never counted as
  "running" (only bare `claude`), new files picked up via fs-watch after startup, and
  tolerating a workspace whose project dir doesn't exist yet.

## Assumptions / seams left for later tasks (documented in-file)

- **`listWorkspaces: () => Promise<RegisteredWorkspace[]>`** has no real default and must
  be supplied by the caller (mirrors `session/bootstrap.ts`'s `getAuthToken` seam).
  Nothing in the codebase yet persists "which workspace paths are registered" — that
  bookkeeping naturally belongs to the spawn-RPC task (plan.md §16 "3.1 Remote spawn"),
  which is what actually knows a workspace's path/id when a session is spawned into it.
  Inventing a standalone workspace-registration store here would risk conflicting with
  how that task ends up modeling it, so this task deliberately does not build one.
- **`isManaged: (providerRef) => boolean | Promise<boolean>`** defaults to "nothing is
  managed yet" (`() => false`) — the lineage store it would consult
  (`providerSessionLineage`) is built by the other half of §3.3 (`adopt.take` +
  `falcon adopt`), explicitly out of scope here.
- The indexer is not yet wired into `daemon/commands.ts`'s `runDaemonStartSync` — neither
  is `machineClient.ts`'s `startMachineClient` (per that file's own comments, session
  tracking/spawning wiring is separate, in-flight work). Wiring both together, once
  workspace registration exists, is a follow-on integration step, consistent with this
  codebase's existing pattern of landing fully-tested standalone modules ahead of their
  final wiring point.
- Only the Claude Code transcript directory is watched (Codex's `app-server` adapter,
  plan.md §16 "3.4 Codex adapter", isn't built yet in this codebase).

## Verification

- `pnpm build` — green (all 5 packages, including `@falcon/server`/`falcon` picking up the
  new files).
- `pnpm typecheck` — green (9/9 tasks).
- `pnpm test` — green: `falcon` (cli) 574/574 tests, `@falcon/server` 233/233 tests
  (807 total), run twice to confirm the new fs-timing-sensitive tests aren't flaky.
- `pnpm lint` — could not get a clean run in this sandbox: `npx biome check` (even on a
  single file) consistently hit `[warn] Linter process terminated abnormally (possibly
  out of memory)`, including after the documented auto-retry and after killing what
  stray biome processes this session's permissions allowed. This matches the class of
  transient/environmental failure this repo's own `CLAUDE.md` already documents for
  `pnpm lint` (biome daemon contention), not a defect introduced by this change — no
  edits here should be biome-unfriendly (existing project conventions were followed
  throughout: file-based JSDoc headers, `Logger`/dependency-injection seams matching
  `machineClient.ts`/`kill.ts`, etc).
