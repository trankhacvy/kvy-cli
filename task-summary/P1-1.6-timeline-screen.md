# P1-1.6-timeline-screen — Session timeline (chat) screen

**Section:** Phase 1 §1.6 — Web app v1 (read-only)
**References:** falcon-system-design.md §9.2 "Session" row, falcon-prd.md FR-7.2, plan.md §8.4

## What this is

A read-only, virtualized session-timeline screen in `packages/web` that renders the
already-landed sync reducer's `RenderItem[]` output as a structured chat transcript:
markdown (via a `unified`/`remark`/`shiki` pipeline compiled straight to React elements),
collapsible thinking blocks, and a `ToolCard` registry (Bash, Edit/Write/MultiEdit + diff,
Read, Grep/Glob, TodoWrite checklist, Task/subagent nesting, MCP generic fallback). No
composer, permission-approval actions, or control bar — those are Phase 2, per the task
description.

## Route

- `src/app/session/[id]/page.tsx` — server component, `generateStaticParams()` returns a
  single `{ id: "demo" }` (static export has no live session ids yet — see "Known gap"
  below), awaits the (Next 15) async `params`, renders `<SessionTimelineScreen sessionId>`.
- `src/components/timeline/SessionTimelineScreen.tsx` — client shell: header + `<Timeline>`.

## Components (`src/components/timeline/`)

- `Timeline.tsx` — the virtualized root list, `@tanstack/react-virtual` with
  `measureElement` dynamic sizing (item heights vary hugely: a one-line service marker vs.
  a Bash card with a large stdout blob).
- `TimelineRow.tsx` — dispatches a `RenderItem` to its component by `kind`, with an
  exhaustive `never` check so a future reducer-added kind fails to compile here rather than
  silently rendering nothing.
- `MessageText.tsx` / `ThinkingBlock.tsx` / `Markdown.tsx` — chat bubbles; `thinking: true`
  items render inside a closed-by-default `Collapsible` (Radix, wrapped in
  `components/ui/collapsible.tsx`).
- `ServiceLine.tsx` — the shared low-emphasis marker for `service`, `mode-switch`,
  `turn-start`/`turn-end`, `sub-start`/`sub-stop`. Every `RenderItem` kind renders
  *something* (no silent data loss), even if it's deliberately the quietest thing on screen.
- `PermPlaceholder.tsx` / `PermissionBadge.tsx` / `OrphanToolEnd.tsx` — read-only display of
  the reducer's "surfaced, not dropped" edge cases (an unmatched perm-request, an orphaned
  tool-end). No Allow/Deny actions anywhere — intentional, per task scope.
- `SubagentGroup.tsx` / `NestedItems.tsx` — a standalone `subagent-group` (never linked to a
  parent tool) renders as its own card; a `ToolItem.subagent` scope renders nested inside
  `tool-cards/ToolCardShell.tsx` generically (any tool can carry a linked subagent, not just
  `Task` — matches how `reduce.ts` actually links scopes).
- `DiffView.tsx` + `src/lib/diff.ts` — a hand-rolled LCS line diff (capped at 4M table
  cells, falls back to remove-all/add-all beyond that so a huge pasted file can't hang the
  tab) for `Edit`/`Write`/`MultiEdit` cards. The design doc allows `@pierre/diffs` *or* "a
  custom unified renderer" — went custom to avoid an unverified external dependency.
- `JsonBlock.tsx` — collapsible raw-JSON fallback used by every tool card for any
  `args`/`output` shape a specific card doesn't have a dedicated field for. Nothing is ever
  hidden, just possibly unformatted.

## ToolCard registry (`tool-cards/`)

`registry.tsx` maps tool name → card: `Bash`, `Edit`/`MultiEdit`/`Write` (all through one
`EditCard` — diff rendering), `Read`, `Grep`/`Glob`, `TodoWrite`, `Task`. Anything named
`mcp__*`, plus anything else unrecognized, falls back to `McpGenericCard`. `ToolCardShell`
is the shared chrome (icon, name/title, running/done/failed badge, read-only permission
badge, and the generic nested-subagent slot).

`src/lib/tool-args.ts` has the defensive readers (`parseBashArgs`, `parseEditArgs`, etc.) —
`args`/`output` are `unknown` on the wire (adapter-specific shapes), so every reader
degrades to `undefined` on a mismatch rather than throwing; callers fall back to
`JsonBlock` when a field is missing.

## Markdown pipeline (`src/lib/markdown.ts`)

`unified().use(remarkParse).use(remarkGfm).use(remarkRehype).use(rehypePrettyCode).use(rehypeReact)`
— shiki via `rehype-pretty-code` (the "unified+shiki" combo the design calls for), compiled
straight to **React elements** via `rehype-react`, not to an HTML string. `Markdown.tsx`
renders the result directly (`{node}`) — there is no `dangerouslySetInnerHTML` anywhere in
this feature. `remarkRehype`'s `allowDangerousHtml` is pinned at its default `false`
explicitly, so literal HTML in a transcript (e.g. `<script>`, `<img onerror=...>`) never
becomes an element in the first place; `lib/markdown.test.ts` has an explicit adversarial
test for this. Single theme (`github-dark`) for now, since the app only ever renders
`.dark` (no appearance toggle yet); switching to a light/dark pair is a one-line change
noted in a comment when that toggle lands.

Content is cached by exact markdown string for the tab's lifetime (`Markdown.tsx`'s
`nodeCache`) — reducer items are immutable once landed, so this is safe and avoids
re-running the pipeline on every virtualization-triggered remount.

## Demo data, and the one real gap

The sync engine (live per-session `RenderItem[]` from the server) is a separate,
still-in-flight task (plan.md §8.1) — not landed on `main` as of this task. So
`SessionTimelineScreen` reads from a hand-built fixture,
`src/components/timeline/demo-items.ts`, covering every `RenderItem` kind and every
registered `ToolCard` (including a nested Task→Bash subagent, a standalone orphaned
subagent-group, an unresolved perm-placeholder, an orphan-tool-end, a file attachment, a
running tool, and a cancelled turn) so the screen is reviewable end-to-end today. The route
(`/session/[id]`, `generateStaticParams` → `demo`) and the screen's prop shape
(`RenderItem[]`) are the real, load-bearing interface; wiring live data is only a matter of
swapping `SessionTimelineScreen`'s data source once the sync engine lands — nothing else
here should need to change.

## Assumptions

- Tool arg/output field names follow Claude Code's actual tool conventions
  (`file_path`/`old_string`/`new_string` for Edit, `command`/`description` for Bash,
  `todos[].content/status/activeForm` for TodoWrite, etc.) since the wire schema leaves
  `args`/`output` as adapter-specific `unknown` — the parsers in `lib/tool-args.ts` degrade
  gracefully if a different adapter (e.g. Codex) uses different field names.
- No DOM-rendering test infra (jsdom/@testing-library) exists in this package yet (the
  existing `button.test.ts` only tests `cva` class strings) — followed that convention and
  kept new tests to pure-logic modules (diff, tool-args, format, markdown-pipeline-output),
  verifying actual component rendering visually in a browser instead.
