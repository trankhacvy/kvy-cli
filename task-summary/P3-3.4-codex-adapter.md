# P3-3.4-codex-adapter — Codex app-server JSON-RPC stdio client adapter

**Section:** Phase 3 §3.4 Codex adapter (plan.md §16; design §7.7/§12)

## What was built

A new, fully independent `packages/cli/src/codex/` directory — no changes
outside `packages/cli` except a `CLAUDE.md` package-map update, and no file
overlap with the in-flight spawn-RPC (§3.1) or session-adoption (§3.3) work.

Ported (adapted) from `slopus/happy`'s `packages/happy-cli/src/codex/` (MIT),
fetched live from GitHub for this task since no vendored Codex source existed
in the worktree yet (only Claude-side files were previously cached under
`/private/tmp/happy-src`). Read in full: `codexAppServerClient.ts` (1600
lines), `codexAppServerTypes.ts`, `runCodex.ts`, and
`utils/{permissionHandler,sessionProtocolMapper,reasoningProcessor,
diffProcessor}.ts` — see each new file's header for exactly which parts were
ported faithfully vs. deliberately scoped down.

- **`codexAppServerTypes.ts`** — cherry-picked TS types (Happy's own header
  already describes its source as "cherry-picked from `codex app-server
  generate-ts`"; this trims further, down to only what the client below
  calls): thread/turn lifecycle params+responses, the two approval request
  shapes, `ReviewDecision`, and the JSON-RPC 2.0 envelope types.
- **`codexAppServerClient.ts`** — the hand-rolled newline-delimited JSON-RPC
  2.0 stdio client. Faithfully ported: the request/notify/respond/handleLine
  transport (pending-map + per-request timeout, epoch-tagged so a stale
  process-exit can't reject a later generation's requests), and
  server→client approval routing for **both** the legacy
  (`execCommandApproval`/`applyPatchApproval`) and v2
  (`item/commandExecution/requestApproval`/`item/fileChange/requestApproval`)
  method names, plus the decision→wire mapping. Deltas (all documented in the
  file header): no sandbox re-exec wrapping, no MCP elicitation routing, no
  fork/rollback/inject/goal RPCs (none of those have a Falcon design-doc
  equivalent), and an injectable `spawn`/process-shape seam
  (`CodexProcessLike`) replacing Happy's direct `cross-spawn` call, so tests
  drive a fake stdio pair instead of shelling out to a real `codex` binary.
- **`permissionHandler.ts`** (`CodexPermissionHandler`) — approval routing
  (plan's "`exec:request`/`patch:request` → permission pipeline"). This is a
  Codex-specific **parallel** to `../claude/permissionHandler.ts` (per that
  file's own header: "Codex is a separate, not-yet-built adapter... that
  will need its own mapping layer"), not a generalization of it — Claude's
  handler is typed against the Claude Agent SDK's `CanUseTool`/
  `PermissionResult`, which have no Codex equivalent. Same shape otherwise:
  cuid2 `reqId` per request (no provider ids on the wire), a pending-approval
  map, first-wins `resolve()`, `perm-request`/`perm-resolve` envelope
  emission, and an allow-for-session mechanism (exec literal matching /
  patch-kind allowlisting). The one real design decision: since Codex has no
  equivalent to Claude's four SDK modes, `perm-request`'s `modes` field
  (typed as `PermissionMode[]`, Claude's own four-value enum — unchanged by
  this task) reuses just the two values with an honest meaning for Codex —
  `bypassPermissions` (auto-approve everything) and `acceptEdits`
  (auto-approve patches, still prompt exec) — documented at length in the
  file header, including why `default`/`plan` aren't offered as switch
  targets.
- **`envelopeMapper.ts`** (`mapCodexEventToEnvelopes` /
  `codexEnvelopeMapper`) — maps Codex `codex/event` notifications onto
  `@falcon/wire`'s `SessionEnvelope`: `task_started`/`task_complete`/
  `turn_aborted` → turn lifecycle; `agent_message` → `text`; `agent_reasoning`
  → `text{thinking:true}` (deltas/section-breaks are dropped — Codex always
  follows them with one final `agent_reasoning` carrying the complete text,
  same reason Happy's own UI skips deltas); `exec_command_begin/end` →
  `tool-start`/`tool-end` (`risk:'exec'`); `patch_apply_begin/end` →
  `tool-start`/`tool-end` (`risk:'write'`); `turn_diff` → a synthetic
  `codex-diff` tool-start+tool-end pair emitted only when the cumulative
  unified diff actually changes (porting Happy's `DiffProcessor` pattern,
  since Falcon has no dedicated "diff" wire event). Every provider `call_id`
  is minted through a `Map<string,string>` → cuid2, same rule
  `../claude/envelopeMapper.ts` follows and a deliberate delta from Happy's
  *current* code (which passes Codex's raw `call_id` straight through).
- **`codexProviderAdapter.ts`** — `detect()` (shells out to `codex
  --version` with a 3s timeout, mirroring `claudeCliLocator.ts`/
  `claudeAuth.ts`'s own version-check timeout) and `startLocal()`, which
  **always returns `null`** per design §7.3's own comment ("`null` ⇒
  provider has no local TUI (codex)") and §7.7 ("Codex has no local
  interactive mode... `startLocal()` returns null and the CLI prints an
  honest note"). `CODEX_NO_LOCAL_MODE_NOTE` is the printed note.
- **`codexRemote.ts`** (`startCodexRemote`) — wires the client + permission
  handler + envelope mapper into one `CodexRemoteHandle`
  (send/interrupt/setMode/resolvePermission/stop), the Codex parallel to
  `../remote/claudeRemote.ts`, reusing the same provider-agnostic
  `OrderedEnvelopeQueue`. Same scope note as `claudeRemote.ts`'s own header:
  owns one thread's lifecycle; the `falcon codex` entrypoint wiring that
  decides *when* to construct one (a `loop.ts`-equivalent orchestrator)
  hasn't landed for Claude's own remote mode yet either, so it's out of
  scope here too.
- **`index.ts`** — barrel export for the whole module.
- **`packages/cli/src/index.ts`** — `falcon codex [args...]` already parsed
  via `args.ts` (pre-existing); `describeStart()` now prints
  `CODEX_NO_LOCAL_MODE_NOTE` when `command.provider === "codex"`, and the
  `--help` text marks the `codex` line `(beta, no local TUI)`. Two new tests
  in `index.test.ts` cover both the note appearing for `codex` and NOT
  appearing for `claude`.

## What was *not* built (and why)

- **The `falcon codex` CLI command's actual provider spawn.** Neither
  provider's spawn is wired into `runStart()` yet — `describeStart()` still
  says "(provider spawning not implemented yet)" for both `claude` and
  `codex` (pre-existing state; see `index.ts`'s own file-header scaffolding
  note). This task adds the codex-specific honest note *on top of* that
  existing scaffold, matching scope, rather than building the missing
  Claude-side orchestration first.
- **A provider option in the web spawn flow.** Checked: `packages/web/src`
  has no "new session"/spawn UI at all yet in this worktree (confirmed via
  `find` — nothing named `*new-session*`/`*spawn*`). That flow is §3.1's
  daemon-spawn-RPC work, explicitly called out as a separate in-flight
  worktree this task must not overlap with. Adding a placeholder web flow
  here would either duplicate or conflict with that task's actual UI when it
  lands, so it's left for §3.1 (or a follow-up) to add the provider picker +
  beta banner once the spawn flow itself exists.
- **MCP tool-call approvals** (`mcpServer/elicitation/request`) — plan.md
  only names `exec:request`/`patch:request`; dropped per the client's file
  header.
- **Codex collab-agents/subagents** (`collab_agent_begin/end`,
  `subAgentActivity`) — a newer Codex feature with no design-doc mention;
  Claude's `Task` tool is the only cross-provider subagent concept the
  design doc calls out, and it has no Codex parallel yet.

## Assumptions

- Codex event field names (`call_id`/`callId`, `exit_code`/`stdout`/`stderr`,
  `success`, `unified_diff`, etc.) are taken directly from Happy's own
  `runCodex.ts` event-handling code and `codexAppServerTypes.ts` comments —
  no local `codex` CLI was available to record a real transcript against,
  so field-name assumptions are defensive (multiple aliases tried via
  `pickString`/`pickNumber` helpers) rather than schema-validated.
- `CodexPermissionHandler`'s reuse of `PermissionMode` (rather than a new
  Codex-specific mode enum) is a deliberate choice to avoid touching
  `@falcon/wire` (out of scope / shared contract) — flagged at length in the
  file's own header for whoever revisits this when Codex's approval-policy
  needs grow beyond allow/deny.
