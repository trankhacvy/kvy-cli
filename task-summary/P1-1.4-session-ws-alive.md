# P1-1.4-session-ws-alive — Session-scoped WS client + `alive` keepalive emits

**Task:** plan.md §16 Phase 1 §1.4 line 688 — `` `alive` keepalive emits (working flag from
fd3 thinking state) over WS ``. Design refs: falcon-system-design.md §4.3 (`ClientEmit`
wire shape), §8 (persistent-connection expectations for the analogous machine-scoped client).

**Classification:** (N) new code — no direct Happy source to port from 1:1 (Happy's
`apiSession.ts` bundles the alive keepalive into a much larger class covering messaging,
RPC, metadata/state CAS, attachments, etc. — all separate, later plan bullets). Consulted
`happy/packages/happy-cli/src/api/apiSession.ts`'s `keepAlive()` method for the general
shape (`socket.volatile.emit(...)` for a droppable presence signal) but did not port it
verbatim, since Falcon's wire contract for this event (`falcon-system-design.md` §4.3)
differs from Happy's (`session-alive` with `{sid, time, thinking, mode}`).

## What was built

`packages/cli/src/session/sessionClient.ts` — new module, `falcon`/`packages/cli` package:

- `startSessionClient(deps): SessionClientHandle` — opens the already-landed `/v1/stream`
  Socket.IO endpoint (`packages/server/src/app/socket.ts`, unmodified) with
  `auth: { token, clientType: "session-scoped", sessionId }`, matching that endpoint's
  existing handshake validation (session-scoped clients require `sessionId`).
- Emits an `alive` event via `socket.volatile.emit` — droppable, matching design §4.3's
  "volatile keepalive" note — immediately on every `connect` and then on a configurable
  interval (`deps.aliveIntervalMs`, default 20s via `createSessionClientDeps`). Payload is
  `{ sessionId, working }`, i.e. design §4.3's `ClientEmit` variant
  `{ e: 'alive'; sessionId; working }` with the `e` discriminator folded into the Socket.IO
  event name itself (mirrors how `machineClient.ts` emits `machine-alive` as an event name
  rather than a tagged payload field).
- `getWorking: () => boolean` is an **injectable dependency**, not a real fd3 reader. The
  task explicitly calls for this: the real thinking-state signal is parsed off Claude's
  stdio fd3 in the still-unmerged `claudeLocal.ts` (`P1-1.3-claudelocal-spawn`, not landed
  on `main`). This client takes the flag as a callback so a future caller can pass
  `() => claudeLocal.isThinking()` (or similar) without touching this module — same pattern
  as `machineClient.ts`'s injectable `buildMetadata`/`buildRuntimeState`.
- Reconnect handling deliberately mirrors `machineClient.ts` line for line: socket.io-client's
  built-in reconnection handles ordinary transport drops; the `disconnect` handler calls
  `socket.connect()` explicitly only to cover the one case the client library does NOT
  auto-retry (`reason === "io server disconnect"`), gated on an internal `stopped` flag so a
  deliberate `.stop()` never resurrects the socket. The keepalive timer is stopped on
  `disconnect` and restarted on `connect`, so a dead connection never keeps reporting itself
  "alive" server-side while down.
- `connect_error` is logged via `deps.logger.warn` (no-silent-failures — an auth/config
  problem must be visible even though socket.io-client itself retries silently).
- `createSessionClientDeps(required, overrides)` factory supplies test/production-friendly
  defaults (real `socket.io-client` `io()` factory, file-only `Logger` no-ops, 20s interval,
  `getWorking` defaulting to `false`) — same shape as `machineClient.ts`'s
  `createMachineClientDeps`.

`packages/cli/src/session/sessionClient.test.ts` — 8 unit tests against a `FakeSocket`
(mirrors `machineClient.test.ts`'s fake, extended with a `.volatile.emit` stub): handshake
shape, alive-on-connect with the injected working flag, alive-on-interval re-reading
`getWorking` live, `stop()` closing the socket and halting the timer, `disconnect` halting
the timer and (selectively) reconnecting, and `connect_error` logging.

`packages/cli/src/session/sessionClient.integration.test.ts` — 2 tests against a real
`socket.io` `Server` bound to `/v1/stream` (mirrors `machineClient.integration.test.ts`'s
approach): proves the handshake and `alive` payload actually round-trip over a real
WebSocket, and that a forced server-side disconnect is followed by an automatic reconnect
that resumes the keepalive stream under the same `sessionId`.

## Assumptions / scope notes

- **Not wired into any command yet.** Same as `machineClient.ts` in its own worktree: this
  is a standalone client module. Wiring a session process's entrypoint to call
  `startSessionClient` (once `claudeLocal.ts`/session-bootstrap land) is out of this task's
  scope — plan.md lists those as separate, still-open bullets.
- **No message/RPC/metadata traffic.** Happy's `ApiSessionClient` is a large class covering
  messaging, RPC handler registration, metadata/agentState CAS, attachments, usage
  reporting. Only the connection lifecycle + `alive` keepalive is in scope here per the task
  description ("Add the CLI session process's session-scoped WS client... emit periodic
  'alive' keepalive events"); the rest is separate plan.md bullets (HTTP outbox already
  landed as `P1-1.4-http-outbox`/unlanded, RPC registration is a later §1.5/§4.4 item).
- **Wire event name `alive` with a bare `{ sessionId, working }` payload**, not a
  `{e:'alive', ...}` tagged object — Socket.IO's own event-name mechanism already serves as
  the `e` discriminator from design §4.3's `ClientEmit` union, and this is consistent with
  how the sibling `machineClient.ts` handles its own (differently-shaped) heartbeat.
- **No server-side listener exists yet** for the `alive` event — `packages/server/src/app/socket.ts`
  and `eventRouter.ts` don't currently register one (confirmed by grep). This client emits
  it regardless; the presence bookkeeping consumer (§6.3: "`alive` pings ... update an
  in-memory presence cache") is out of scope for this task and unaffected either way since
  Socket.IO simply drops unhandled custom events server-side.
- **`now`/timestamp field intentionally omitted from the payload** — design §4.3's literal
  `ClientEmit` shape for `alive` is exactly `{ sessionId, working }`, no timestamp. (Contrast
  with `machineClient.ts`'s `machine-alive`, which does include `time` — that's a
  machine-scope-specific choice already baked into that module, not part of the `alive`
  contract this task implements.)
