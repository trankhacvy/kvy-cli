# P0-0.2-wire-package — Build @falcon/wire

**Section:** Phase 0 — Repo & contracts (M0) / plan.md §2 + §16 "0.2 @falcon/wire"

## What was done

Created `packages/wire` — the single source of truth for every Falcon
package's wire contracts (`cli` for encrypt/relay, `server` for validation +
Drizzle JSON typing, `web` for the reducer), per plan.md §2/§16 and
falcon-system-design.md §4.

### Package skeleton
- `package.json`: `@falcon/wire`, `type: module`, dual CJS/ESM `exports`
  (`types` condition listed first — a plain `import`/`require` ordering
  produced an esbuild warning that `types` would never be selected), built
  with `pkgroll`. **Only** production deps: `zod ^4` and
  `@paralleldrive/cuid2 ^2.2.2`, matching the task's "zod + cuid2 as the
  only deps" constraint. Dev deps: `pkgroll`, `shx`, `typescript`, `vitest`,
  `@types/node` (needed for `console` in the test-only additive-only
  tooling — the package's runtime code itself uses no Node globals, staying
  isomorphic).
- `tsconfig.json` extends the root `tsconfig.base.json` with the `@/` path
  alias convention established by 0.1.
- `vitest.config.ts`, matching Happy's `happy-wire/vitest.config.ts`.

### Schemas (`src/`)
- **`box.ts`** — `EncryptedBoxSchema` (`{t:'enc', v:1, c:string}`) and a
  `VersionedSchema(inner)` factory + `Versioned<T>` type for the
  optimistic-concurrency wrapper (`{value, version}`) used by
  metadata/state/session-update.
- **`permissions.ts`** — `PermissionModeSchema` (4 modes) and
  `PermDecisionSchema` (discriminated union: `allow`/`deny`/`mode`, per
  design §4.2/§7.6). Task called these out as a separate deliverable from
  `SessionEventSchema`, but they're a dependency of it (`perm-request.modes`,
  `perm-resolve.decision`), so they live in their own file and are imported
  by `session.ts` and `rpc.ts`.
- **`session.ts`** — `SessionEventSchema`: a discriminated union on `t` with
  **12** literal variants (`text`, `service`, `tool-start`, `tool-end`,
  `file`, `turn-start`, `turn-end`, `perm-request`, `perm-resolve`,
  `mode-switch`, `sub-start`, `sub-stop`) — this is the exact set in
  falcon-system-design.md §4.2's `SessionEvent` union; plan.md's task
  description says "11 event types" but literally lists `sub-start/sub-stop`
  as two, and the design doc's union has 12 pipe-separated members, so I
  implemented all 12 (the "11" in the plan appears to undercount by
  one — I followed the design doc, which is the authoritative source, and
  the plan's own bullet list, which itemizes both `sub-start` and
  `sub-stop`). `SessionEnvelopeSchema` (`id`/`time`/`role`/`turn?`/
  `subagent?`/`ev`) and `createEnvelope(role, ev, opts)` — cuid2-mints `id`
  when omitted, always round-trips through `.parse()` so a malformed event
  throws at creation time rather than downstream in a reducer (ported from
  Happy's `happy-wire/src/sessionProtocol.ts` `createEnvelope` pattern, but
  without Happy's extra role/event-compat `superRefine` — that business rule
  isn't in falcon-system-design.md and wasn't asked for, so I left it out to
  stay minimal rather than invent an undocumented invariant).
- **`rows.ts`** (new, not explicitly named in the task but required to type
  `UpdateSchema`'s bodies) — `SessionRowSchema`, `MachineRowSchema`,
  `UnmanagedSessionRowSchema`, `SessionStatusSchema`: the wire-visible
  projections of the Drizzle tables in falcon-system-design.md §6.1 (every
  content column becomes an opaque `EncryptedBox`/`Versioned<EncryptedBox>`,
  never plaintext). Design §4.3 only says "rows carry EncryptedBox fields"
  without giving exact field lists, so these are my best-effort mapping from
  the §6.1 schema — `dek` included as an opaque string (the sealed-box wrap
  the client needs to unwrap its own DEK).
- **`updates.ts`** — `UpdateBodySchema` (9-member discriminated union:
  `session-new/-update/-delete`, `message-new`, `machine-new/-update`,
  `unmanaged-new/-update`, `account-update`) + `UpdateSchema`
  (`{seq?, ts, body}` — **⚠ DELTA D1/D2**: `seq` optional, absent on
  `message-new` which carries its own `msgSeq` instead) and
  `EphemeralSchema` (`activity`/`machine-presence`/`attention`, exactly as
  design §4.3).
- **`rpc.ts`** — `RpcCallSchema` (`{target, method, params}`); machine RPC
  param/result schemas for `spawn` (`SpawnParams` incl. `idempotencyKey`),
  `stopSession`, `resumeSession`, `listSessions`, `git.status`, `git.diff`,
  `fs.read`, `adopt.list`, `adopt.take`; session RPC param/result schemas
  for `message`, `perm.answer` (with first-wins `{ok:false, reason:
  'already-answered', decision}` result per design §7.6),
  `interrupt`, `takeControl`, `setMode`.
- **`reserved.ts`** — doc-only file (no exports beyond `export {}` to stay a
  module) reserving `checkpoint:*`/`preview:*`/`voice:*` per design §14 and
  prd.md §6.4, with the additive-only warning about never repurposing a
  shipped `t` literal.
- **`index.ts`** — re-exports everything, with the package-level "additive
  only forever" header comment (Happy convention, called for by the task).

### Assumption worth flagging: `idempotencyKey` scope
Design §4.4's own prose says "**mutating** RPCs carry idempotency keys" and
only shows `idempotencyKey` on `SpawnParams`. The task description,
however, explicitly says: *"machine RPC params incl. idempotencyKey for
spawn/adopt.\*/git.\*/fs.read"* — i.e. including the read-only `git.status`,
`git.diff`, `fs.read` calls, not just mutating ones. I followed the task's
literal, more specific instruction over the design doc's general rule
(idempotency keys let the daemon dedupe/replay results for any
caller-retriable RPC, not only mutating ones — reasonable given the
dead-peer-fast-fail race described in §4.4 can plausibly re-issue any
in-flight call). `stopSession`/`resumeSession`/`listSessions` were **not**
in the task's list, so they don't carry one. Documented in `rpc.ts`'s
section comment.

### Additive-only-forever snapshot tests (design §5.3)
This is the part with real design work. A plain `vitest`
`toMatchSnapshot()` would fail on legitimate field *additions* too (it's
exact-match), which isn't what "CI fails if a field is removed/retyped"
asks for. Instead, `src/__tests__/`:
- **`schemaShape.ts`** — `describeShape(schema)` recursively fingerprints a
  zod schema into a plain-JSON `ShapeDescriptor` (object fields, union
  options, optional/nullable/array/record wrappers, literal values, enum
  options, leaf primitive kind). Built on zod v4's **public** `.def.type`
  discriminator plus public accessors (`.shape`, `.options`, `.element`,
  `.unwrap()`, `.keyType`/`.valueType`) — verified these are documented,
  non-underscore-prefixed APIs (the same ones `zod-to-json-schema` relies
  on), not `_def` internals that could break on a patch bump.
  `isCompatible(prev, next)` recursively checks that `next` is a
  backward-compatible evolution of `prev`: every field/option/enum-value
  `prev` requires must still be present in `next` with a compatible kind;
  `required -> optional` is allowed (safe widening), the reverse is not;
  brand-new fields/options in `next` are ignored entirely (additions never
  fail).
- **`schemaRegistry.ts`** — explicit name -> schema map of every top-level
  schema covered by the compat check (36 schemas).
- **`scripts/snapshot-shapes.ts`** — a deliberate, manually-run generator
  (`pnpm --filter @falcon/wire exec tsx scripts/snapshot-shapes.ts`) that
  writes `src/__tests__/__fixtures__/wire-shapes.json`, the frozen baseline.
  Never auto-run by the test suite — regenerating it is the explicit act of
  "I am deliberately freezing this new shape," analogous to Happy's
  "golden fixtures per version" (design §13).
- **`additiveOnly.test.ts`** — for every schema name in the frozen fixture:
  asserts it's still exported, and asserts `isCompatible(frozen, live)`.
  Also warns (doesn't fail) on schemas present in the registry but not yet
  frozen, so new schemas can be added freely and get folded into the
  fixture on the next deliberate freeze.
  **Verified this actually catches regressions**, not just green-by-default:
  temporarily deleted `EncryptedBoxSchema`'s `c` field and reran the suite —
  6 dependent schema tests failed with a clear "lost or retyped a field ...
  design §5.3" message; reverted and confirmed all 61 tests pass again.

### Functional unit tests
`box.test.ts`, `permissions.test.ts`, `session.test.ts`, `updates.test.ts`,
`rpc.test.ts` — parse/reject round-trips for every schema and event variant
(ported the shape of Happy's `sessionProtocol.test.ts`), plus a dedicated
check that `idempotencyKey` is actually required on the six RPC params the
task specified.

## Assumptions

- Based this worktree on the `P0-0.1-monorepo-scaffold` branch (not `main`)
  since `pnpm-workspace.yaml`/`turbo.json`/`tsconfig.base.json` don't exist
  on `main` yet and this package needs them to build/typecheck/test through
  the shared pipeline.
- `LocalSessionInfo`, `FileStatus`, `ProviderSessionSummary` result shapes
  aren't fully specified in the design docs beyond scattered prose
  (`git.status` -> `branch/ahead/behind/files`; the `unmanaged_sessions`
  table comment `// enc: title, lastActivity, running?` directly informed
  `ProviderSessionSummary`). Filled in reasonable minimal fields for the
  rest; these are cheap to extend additively later without breaking anyone
  since nothing produces them yet.
- No superRefine business-rule validation (e.g. Happy's "service events
  require role=agent") was added to `SessionEnvelopeSchema` — not specified
  in falcon-system-design.md, so left out per "no over-engineering."
- `dist/` is `.gitignore`d (inherited from the 0.1 scaffold); only source
  files, the frozen JSON fixture, and configs are committed.
