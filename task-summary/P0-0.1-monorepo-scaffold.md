# P0-0.1-monorepo-scaffold — Init pnpm monorepo scaffold with turbo pipelines

**Section:** Phase 0 — Repo & contracts (M0) / §16 0.1 Scaffold (plan.md §1, §16 first bullet)

## What was done

Created the foundational monorepo scaffold that every other Falcon package
(`packages/wire`, `packages/crypto`, `packages/cli`, `packages/server`,
`packages/web`) will be created inside. Scope was deliberately narrow — only
the three files called out in the task description, plus the minimal root
`package.json` required for pnpm/turbo to function:

- **`pnpm-workspace.yaml`** — `packages: ['packages/*']`, matching Happy's
  workspace pattern (`happy/pnpm-workspace.yaml`) but generalized to a glob
  since Falcon's packages don't exist yet (Happy lists each package
  explicitly because pnpm globs alone wouldn't exclude `codium`/`happy-app-logs`
  from being built by default — not a concern for Falcon's flat 5-package layout).
- **`turbo.json`** — defines the four task pipelines named in the task:
  - `build`: `dependsOn: ["^build"]`, `outputs: ["dist/**"]` — dependency
    packages (e.g. `@falcon/wire`) build before dependents, matching Happy's
    "build wire first" convention, now expressed declaratively instead of via
    a hand-rolled postinstall order.
  - `typecheck`: `dependsOn: ["^build"]` — packages import types from a
    dependency's built `dist/*.d.ts` (per the `exports` pattern in
    `packages/wire/package.json`, see plan.md §1), so typecheck needs
    dependencies built first, same as `build`. No `outputs` since none of our
    packages use TS `incremental`/`composite` mode (mirrors
    `happy-wire/tsconfig.json`), so `tsc --noEmit` writes no cache files.
  - `test`: `dependsOn: ["build"]` — needs the package's own build output;
    transitively pulls in `^build` because `build` itself depends on `^build`.
  - `lint`: no `dependsOn` — lints run in parallel across all packages, no
    build output needed.
  - Followed the `turborepo` skill's guidance: package tasks (not root
    tasks), `turbo run <task>` (not the `turbo <task>` shorthand) in root
    `package.json` scripts, explicit `outputs` per task.
- **`tsconfig.base.json`** — shared strict-mode compiler options every
  package's `tsconfig.json` will extend (`"extends": "../../tsconfig.base.json"`),
  modeled on `happy/packages/happy-wire/tsconfig.json`'s strict block
  (`strict`, `noImplicitAny`, `strictNullChecks`, `strictPropertyInitialization`,
  `noImplicitThis`, `alwaysStrict`, `noImplicitReturns`) plus a few additional
  strict flags Happy didn't set (`strictFunctionTypes`, `strictBindCallApply`,
  `noUncheckedIndexedAccess`, `noFallthroughCasesInSwitch: true`) since Falcon
  is a fresh codebase with no legacy code to accommodate.
  `noEmit: true` at the base (packages that need emit, e.g. `wire` via
  `pkgroll`, don't invoke `tsc` for emit anyway — `pkgroll` handles that; `tsc`
  is used for the `typecheck` task only).
  **`@/` path alias convention** (not enforced by the base file itself, since
  `paths`/`baseUrl` are inherently per-package — each package's own `src/`
  root differs): every future package's `tsconfig.json` is expected to add
  ```json
  {
    "extends": "../../tsconfig.base.json",
    "compilerOptions": {
      "rootDir": "src",
      "paths": { "@/*": ["./src/*"] }
    },
    "include": ["src/**/*.ts"]
  }
  ```
  i.e. `@/foo` inside any package always resolves to that package's own
  `src/foo`, never across package boundaries (cross-package imports go
  through the package's public `exports`, e.g. `@falcon/wire`). This is the
  same convention `happy-wire/tsconfig.json` uses (`"@/*": ["./src/*"]`).
- **Root `package.json`** — `private: true`, `type: "module"`, scripts
  `build`/`test`/`typecheck`/`lint` all delegate to `turbo run <task>` (per
  turborepo skill: root scripts must not bypass turbo), `turbo` +
  `typescript` as the only root devDependencies (per turborepo skill: keep
  root dependencies to repo tooling only — no app/package deps at root).
  `packageManager: "pnpm@10.15.0"` pinned to the pnpm version available in
  this environment (Happy pins `pnpm@10.11.0`; either works, pinned the
  locally verified one to keep `pnpm install` reproducible here).

`.gitignore` already had `node_modules/`, `dist/`, `build/`, `.turbo/`,
`*.tsbuildinfo` covered (inherited from the repo-wide `.gitignore` already
present in this worktree) — no changes needed there.

## Explicitly out of scope (left for their own tasks)

Per the task boundary ("It is the blocking dependency for ... so it should
land first and unblock the rest"), the following were intentionally **not**
done here, even though plan.md §16 lists them under the same "0.1 Scaffold"
heading:
- Biome/ESLint+Prettier setup, CI workflow — separate 0.1 bullet.
- Root `postinstall` building `@falcon/wire` first — separate 0.1 bullet;
  meaningless until `packages/wire` exists.
- `docs/protocol.md` / `docs/encryption.md` stubs — separate 0.1 bullet
  (already being handled in a sibling worktree, `P0-0.1-docs-stubs`).
- Root `CLAUDE.md` — explicitly called out in plan.md as "last task of 0.1,
  once the scaffold exists."
- Creating `packages/wire`, `packages/crypto`, `packages/cli`,
  `packages/server`, `packages/web` themselves — separate tasks (0.2, 0.3,
  etc.) that will each add their own directory under `packages/` and their
  own `tsconfig.json`/`package.json` following the conventions established
  here.

## Verification

Ran in the worktree (`pnpm install` succeeded, `pnpm-lock.yaml` generated):
- `pnpm build` → `turbo run build` → exit 0, "0 packages" (expected — no
  package dirs exist yet, this only proves the pipeline wiring is valid).
- `pnpm typecheck` → exit 0.
- `pnpm test` → exit 0.
- `pnpm lint` → exit 0 (verified via `rtk proxy pnpm lint` — the bare `pnpm
  lint` invocation was intercepted by an unrelated local shell hook
  (`rtk`, a token-optimization CLI proxy in this environment) whose own
  internal linter crashed; that failure is unrelated to this repo's turbo/lint
  config, confirmed by re-running the identical command with the hook
  bypassed).
- All three new JSON config files (`turbo.json`, `tsconfig.base.json`,
  `package.json`) parse as valid JSON.

## Assumptions

- No packages exist yet in `packages/`, so `pnpm-workspace.yaml`'s
  `packages/*` glob currently matches nothing — this is expected and will
  resolve itself as 0.2+ tasks land.
- `turbo` pinned to `^2.5.0` (installed: 2.10.5), `typescript` to `^5.9.0`
  (installed: 5.9.3) — matches the version Happy uses for `happy-wire`
  (`typescript: 5.9.3`).
- Used pnpm's `packageManager` field pinned to the pnpm version already
  installed in this environment (`10.15.0`) rather than Happy's `10.11.0`,
  so `pnpm install` doesn't need corepack to fetch a different version.
