# P17-2.0-claim-store — Send-idempotency claim store

**Section:** §17 v2 ACP migration — Phase 2.0 foundation
**Design authority:** `falcon-system-design.md` v0.3 §7.10 ("Send-idempotency claim"), §7.2
(local state layout), plan.md §16 Phase 2.0 first bullet.

## What was built

`packages/cli/src/claims/claimStore.ts` — a claim-before-execute, tri-state
(`claimed` / `completed` / `in-progress`) idempotency store for the future `message`
session RPC, keyed per session and persisted under `~/.falcon/claims/<sessionId>.json`.

Public API:

- `claimMessageSend(sessionId, envelopeId, options?) => Promise<ClaimOutcome>` — looks up
  `envelopeId` in the session's claim file:
  - no entry yet → durably writes a fresh claim, returns `{status:'claimed', claimId}`.
    The caller now owns executing the send and must eventually call
    `completeMessageSend` with that `claimId`.
  - a recorded result → returns `{status:'completed', result}` (duplicate send; replay,
    never re-execute).
  - a live claim with no result → returns `{status:'in-progress'}` (indeterminate —
    the original claimant may have crashed mid-turn; **must not** be treated as safe to
    execute).
- `completeMessageSend(sessionId, envelopeId, claimId, result, options?) => Promise<void>`
  — atomically verifies the active claim's `claimId` still matches before recording the
  terminal result (transitions the entry from the pending to the completed shape).
  Throws if there is no active claim, or one exists under a different `claimId`
  (guards against a stale/superseded claimant recording a result it doesn't own).
- `readClaims(sessionId, options?)` / `clearClaims(sessionId, options?)` — introspection
  and whole-file cleanup (e.g. on session archive), matching the read/clear helper shape
  `sessionsStore.ts` and `workspace/registry.ts` already establish in this package.

## Reference semantics

Ported (with changes) from mobvibe's `apps/mobvibe-cli/src/wal/wal-store.ts`
(`claimMessageSend`/`completeMessageSend`): INSERT-OR-IGNORE the claim, then
verify-claimId-then-record-result atomically. mobvibe backs this with a SQLite WAL and a
real DB transaction; Falcon's design instead calls for a plain per-session JSON file
under the existing lock-file pattern (design §7.10: "atomic tmp-write+rename under the
existing lock-file pattern"). So the storage engine and concurrency primitive differ —
an exclusive `O_CREAT|O_EXCL` lock file guarding the whole read-prune-mutate-write
section stands in for the SQL transaction, copied verbatim (same retry/stale-reclaim
constants and structure) from `persistence.ts`'s `acquireLock`/`workspace/registry.ts`'s
own duplicate of it, per this codebase's established "each file owner duplicates the
small lock helper locally" convention (see `workspace/registry.ts`'s own doc comment
making that call explicit).

The tri-state claim semantics themselves — INSERT-OR-IGNORE claim, verify-claimId before
recording a result, a pre-existing unresolved claim is indeterminate and must never be
silently re-executed — are faithful to mobvibe's reference.

## Design deltas / assumptions

- **Retention policy:** the design says "bounded retention window (claims are
  one-per-human-send; volume is tiny)" without specifying the exact rule. I implemented
  time-based pruning (`CLAIM_RETENTION_MS = 7 days`, mirroring `sessionsStore.ts`'s own
  `MAX_SESSION_AGE_MS` convention in this package) that **only** evicts `completed`
  entries older than the window. Pending (`'claimed'`, no result) entries are **never**
  pruned by age — evicting an indeterminate claim would make a later retry look "fresh"
  and silently re-execute it, which is exactly the failure mode §7.10 says must never
  happen. Pruning runs opportunistically on the next write to a session's file (same
  lazy-expiry pattern `sessionsStore.ts`'s `readPersistedSessions` already uses in this
  package), not via a background sweep.
- **`claimId` field:** the design's compact literal shows entries as
  `{envelopeId → {claimedAt} | {result, completedAt}}` with no explicit `claimId` field,
  but the task description explicitly asks for mobvibe's verify-claimId-then-record-result
  semantics, which requires persisting a claim id somewhere to verify against at
  completion time. I added `claimId` to the pending-entry shape (dropped again once the
  entry transitions to `completed`, matching mobvibe's own claim-row deletion on
  completion) — a necessary implementation detail of the referenced semantics, not a
  deviation from them.
- **`result: unknown` and `undefined`:** `completeMessageSend` stores `result ?? null`
  rather than the raw value, because `JSON.stringify` silently drops an `undefined`
  property — storing the raw value would make a completed entry with an `undefined`
  result round-trip as if the entry had never been written, defeating duplicate
  detection. Covered by a dedicated test.
- **No wiring to `deliverMessage()`** — explicitly out of scope per the task
  description (that lands in Phase 2.2). This module has no dependency on any other
  Phase 2.0 item and nothing in the codebase calls it yet.

## Tests

`packages/cli/src/claims/claimStore.test.ts` (17 tests, all passing) covers:

- fresh claim (new envelope id → `claimed` with a durable on-disk record)
- duplicate claim (an envelope id whose send already completed replays `completed` +
  the recorded result, not a fresh claim)
- claim with no completion (indeterminate — a second `claimMessageSend` call returns
  `in-progress`, and the original pending entry is left untouched)
- concurrent claims for the same envelope id (via the file lock, exactly one of two
  parallel `claimMessageSend` calls wins `claimed`, the other sees `in-progress`)
- claim isolation across envelope ids and across sessions
- `completeMessageSend` rejecting a missing claim, a `claimId` mismatch, and a
  double-completion attempt — none of which corrupt the still-pending/completed entry
- the `undefined`-result round-trip edge case
- corrupt-file and wrong-shape-entry resilience (never throws, drops only the bad entry)
- retention/pruning: a completed entry past the 7-day window is pruned on the next
  write; a completed entry still inside the window is kept; a pending (uncompleted)
  claim is **never** pruned regardless of age
- `clearClaims` deletes the whole file and is safe to call twice
