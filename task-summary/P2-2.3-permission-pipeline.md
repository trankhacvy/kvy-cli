# P2-2.3-permission-pipeline

Task: port Happy's `PermissionHandler` + `getToolDescriptor`, replace remote
mode's fail-closed `permissionStub.ts` placeholder with real first-wins
permission logic (plan.md §16 "2.3 Permission pipeline"; design §7.6).

## Files created

- `packages/cli/src/claude/getToolDescriptor.ts` — verbatim port **(V)** of
  `happy-cli/src/claude/utils/getToolDescriptor.ts`: classifies a tool name
  as `edit`/`exitPlan`/`dangerous` for the auto-rules below.
- `packages/cli/src/claude/getToolDescriptor.test.ts` — 4 tests covering all
  four branches.
- `packages/cli/src/claude/permissionHandler.ts` — the `PermissionHandler`
  class, ported (adapted) **(P)** from
  `happy-cli/src/claude/utils/permissionHandler.ts`. Owns: auto-rules
  (`bypassPermissions` → allow all; `acceptEdits` → allow edit tools; `plan`
  → allow non-dangerous tools; `AskUserQuestion`/`ExitPlanMode` always
  prompt), Bash literal/prefix allow-lists, the pending-request `Map`, and
  first-wins `resolve()`.
- `packages/cli/src/claude/permissionHandler.test.ts` — 15 tests: auto-rules
  per mode, always-prompt tools, allow-for-session (Bash literal vs. other
  tools), `allowBashPrefix`, `mode`-decision resolution, first-wins
  resolution (winner vs. loser, unknown reqId, envelope content), and
  `reset()`.

## Design deltas from Happy (documented in `permissionHandler.ts`'s header)

- **`reqId` is a fresh cuid2 per request** (design §7.6: "reqId = cuid2"),
  not Happy's `agentID:toolUseID` composite — Falcon's wire schema treats
  `reqId` as an opaque adapter-minted string, so there's no need to
  disambiguate sub-agent calls by composing an id from SDK fields.
- **No provider ids on the wire / no `call` id on `perm-request`.**
  `envelopeMapper.ts` mints its own cuid2 `call` id for `tool-start` from a
  mapping private to the converter; `permissionHandler.ts` doesn't reach
  into that. The reducer (`packages/web/src/sync/reducer/reduce.ts`) already
  matches a call-less `perm-request` to its eventual `tool-start` by
  name+args — that fallback path is the intended one, not a workaround.
- **`perm-request`/`perm-resolve` are `SessionEnvelope`s emitted via an
  injected `emitEnvelope` callback**, not Happy's own push+RPC transport.
  Ordering/encryption/delivery are the caller's job — `claudeRemote.ts`
  threads them through the same `OrderedEnvelopeQueue` as every other
  envelope.
- **`agentState` CAS persistence is an injectable seam
  (`onAgentStateChange`), not a network write.** Falcon has no
  session-scoped `agentState` CAS HTTP client in `packages/cli` yet (only
  the machine-scoped one, `daemon/machineClient.ts`) — the server-side route
  already exists (`packages/server/src/app/routes/sessionCas.ts`,
  `PUT /v1/sessions/:id/state`), but nothing in the CLI calls it. This
  mirrors the exact seam pattern `sessionClient.ts` already uses for
  `getWorking` (a documented, deliberate "not built yet, here's a plug"
  rather than a silent gap).
- **No Codex mode mapping** (`isClaudeBypassEquivalent`/`mapToClaudeMode` in
  Happy) — Falcon's wire `PermissionMode` already *is* the four Claude
  modes; Codex is a separate, not-yet-built adapter (plan.md §12).
- **First-wins resolution is new** (design's own "Falcon add", not in
  Happy): atomic check-and-delete on the pending map. A second `perm.answer`
  for an already-resolved `reqId` gets `{ok:false, reason:'already-answered',
  decision}` — the decision that actually won, looked up from a
  `completedRequests` record kept for exactly this purpose — instead of an
  error or a hang.
- **No `getResponseForToolUseId`/`isAborted` lookups.** Happy's transcript
  renderer used these to annotate a tool call after the fact; Falcon's
  timeline is built entirely from the envelope stream by the (already
  landed) reducer, so there's no second lookup path to maintain.

## Assumptions made where the spec was underspecified

- **`perm-request.modes`** (the array of `PermissionMode`s the reducer
  attaches to a `PermissionInfo` for the client's mode-switch UI): populated
  with all four modes for a normal request, and the three non-`plan` modes
  for `ExitPlanMode`/`exit_plan_mode` (switching *to* plan mode isn't a
  sensible way to resolve exiting it). Not otherwise specified in the wire
  schema or design doc.
- **`PermDecision{kind:'mode'}` resolution semantics**: generalized Happy's
  ExitPlanMode-only "approve + switch mode" flow to *any* pending request —
  choosing a mode is treated as itself resolving (allowing) the request that
  prompted it, since Falcon's `PermDecision` schema doesn't special-case
  ExitPlanMode the way Happy's ad hoc `response.mode` field did.
- **`PermDecision{kind:'allow', scope:'session'}` for `Bash`**: allow-lists
  only the *exact literal command*, not a prefix pattern — the wire schema
  carries no granular prefix string (unlike Happy's `Bash(cmd:*)` allow-tool
  strings), so a literal is the safe, honest interpretation. `canUseTool`
  still checks a `allowedBashPrefixes` set (ported from Happy, per the task
  description's explicit "Bash literal/prefix allowlists"), and
  `allowBashPrefix()` is exposed publicly for a future, more granular action
  to call — nothing calls it yet.
- **Local-mode honesty**: verified by construction rather than by adding new
  code — `PermissionHandler`/`getToolDescriptor` are only ever reached via
  `claudeRemote.ts`'s `canUseTool`, so local mode (which spawns the real
  Claude CLI via `cross-spawn` and never intercepts its permission prompts)
  is entirely unaffected; there is no fake remote-answering path to remove
  because none existed. The other half of that plan bullet — `Notification`/
  `Stop` provider hooks firing attention events so the dashboard can show
  "waiting at terminal" — is genuinely not built (only the `SessionStart`
  hook exists, for session-id discovery) and is out of this task's file
  scope; left unchecked in `plan.md` with a note rather than marked done.

## Why `claudeRemote.ts` was touched despite the task's file list

The task's own "Touches" list names only `permissionHandler.ts`,
`getToolDescriptor.ts`, and `permissionStub.ts` (swap-out). Making the swap
real (not just present-but-unreachable) required wiring the constructed
`PermissionHandler` into `startClaudeRemote`'s `canUseTool` and exposing its
`resolve()` as `ClaudeRemoteHandle.resolvePermission` — otherwise the "real
first-wins logic" would exist as dead code nothing ever calls, which would
violate "no half-finished code". `loop.ts` and the mode-switch launcher
files (P2.2's scope, explicitly called out as disjoint) do not exist yet in
this worktree and were not touched. The still-missing piece is wiring
`ClaudeRemoteHandle.resolvePermission` to the actual `perm.answer` session
RPC (`packages/cli/src/rpc/sessionRpc.ts`'s `SessionRpcHandlers.permAnswer`)
— that requires a live `ClaudeRemoteHandle` instance to exist somewhere,
which only `loop.ts` (P2.2, not yet built) will create.
