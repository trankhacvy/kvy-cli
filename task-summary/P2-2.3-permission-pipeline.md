# P2-2.3-permission-pipeline (land task)

Task: land the existing `P2-2.3-permission-pipeline` worktree/branch (tip
`3ce8a39`, cut from cycle-52 `main` tip `3444d37`, 2 commits ahead) onto
current `main` (tip `49ddb8c`, cycle 53). The branch already fully
implements plan.md §16 "2.3 Permission pipeline" — see the git history for
the original implementation commits (`feat: … Port PermissionHandler +
getToolDescriptor …`, `refactor: … code review fixes`) and their own
description of what was built. This task is the rebase/reconcile/land step
only; no product code was re-implemented.

## What this task did

1. **Rebased** the branch onto `main`'s current tip (`git rebase main`).
   Zero conflicts — the two intervening `main` commits (`P2-2.2-mode-switching`
   feat + its code-review-fixes refactor) only touched
   `packages/cli/src/claude/{loop,claudeLocalLauncher,claudeRemoteLauncher}.ts`,
   disjoint from this branch's `permissionHandler.ts`/`getToolDescriptor.ts`/
   `claudeRemote.ts` edits. `plan.md` itself also merged clean (no line-level
   overlap between the two branches' narrative edits).

2. **Fixed a post-rebase type error** that the clean rebase didn't surface as
   a *conflict* but did surface as a *build break*: `P2-2.2-mode-switching`
   (already on `main`) added `packages/cli/src/claude/{loop,
   claudeRemoteLauncher}.test.ts`, both of which construct fake
   `ClaudeRemoteHandle` objects. This branch's `claudeRemote.ts` adds a new
   required member to that interface — `resolvePermission()` — so both fakes
   were missing a property TypeScript now requires. Added a
   `resolvePermission: () => ({ ok: false })` stub to each fake (matching
   `PermAnswerResultSchema`'s shape; never actually exercised by either
   test's assertions, so a fixed `{ok:false}` is sufficient and honest).

3. **Updated `plan.md`'s §2.3 section** per this land task's own scope:
   - Checked the first three bullets (`PermissionHandler` port,
     `getToolDescriptor` port, first-wins resolution) — these are what the
     branch actually built and tested.
   - Left `perm-request`/`perm-resolve` envelopes into the timeline
     **unchecked**, correcting the original branch's own `plan.md` edit
     (which had marked it `[x]`). Verified directly: the CLI-side
     `permissionHandler.ts` does emit `perm-request`/`perm-resolve`
     `SessionEnvelope`s (confirmed via `grep` — `createEnvelope("agent",
     {t: "perm-resolve", ...})` / `{t: "perm-request", ...}`), but that's
     existing envelope-emission plumbing every other event type already
     uses. The bullet's evident intent — these events rendering live in the
     *web* timeline — isn't satisfied yet: `packages/web/src/sync/reducer/`
     and `PermPlaceholder.tsx` already know how to interpret these event
     types (landed via the reducer-port/timeline-screen tasks), but the
     timeline screen still runs off a hand-built demo fixture
     (`components/timeline/demo-items.ts`), not the live sync engine/socket.
     Left unchecked pending that live-wiring follow-up.
   - Left "Local-mode honesty" unchecked, unchanged from the original
     branch's own (already-correct) assessment — hooks firing attention
     events for local-mode "waiting at terminal" is genuinely not built
     (`hookServer.ts` only handles `SessionStart`).

4. **Re-ran the full verification suite** post-rebase-and-fix:
   - `pnpm build` — 5/5 packages green (`falcon` cli, `@falcon/{wire,crypto,
     server,web}`).
   - `pnpm exec turbo run typecheck --force` — 9/9 tasks green.
   - `pnpm exec turbo run test --force` — 9/9 tasks green: `falcon` cli
     55/55 test files, 539/539 tests (incl. the 16 `permissionHandler.test.ts`
