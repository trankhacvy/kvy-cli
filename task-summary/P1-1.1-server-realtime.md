# P1-1.1-server-realtime — Socket.IO read-path: handshake auth, eventRouter, rpcHandler

Ports Happy's Socket.IO relay onto the already-landed Fastify/auth foundation
(`packages/server`): the `/v1/stream` handshake (auth in `io.use()` middleware,
three client scopes, `app-state` tracking), the room-based `eventRouter`
(`emitUpdate`/`emitEphemeral` with recipient filters), the `rpcHandler`
(room-based RPC forwarding, reconnect grace window, presence-poll dead-peer
race, Prometheus counters), machine online/offline ephemeral broadcasts, and
ephemeral backpressure coalescing. This is the READ-only WS path — no
message-write handlers (writes are HTTP, sibling task 1.2 per DELTA D1).

## Implementation notes / deltas from Happy

- **Path**: `/v1/stream` per this task's spec (Happy used `/v1/updates`).
- **Identity**: `userId` → `accountId` throughout, matching the rest of
  `@falcon/server` (`request.accountId` from `app.authenticate`). Auth itself
  reuses the already-landed `verifyToken` (JWT HS256, design §5.2/DELTA D5) —
  there's no separate Ed25519-challenge path on the socket handshake, since
  Falcon's WS auth is the same bearer token minted by `/v1/auth`.
- **No Redis/cluster adapter**: Happy's `socket.ts` wires a
  `@socket.io/redis-streams-adapter` for multi-process delivery. Dropped here —
  falcon-system-design.md §6.4 explicitly defers that to "single app process at
  MVP (cluster adapter + Redis reserved behind an env flag)". `rpcHandler`'s
  `fetchSockets()`/room calls work unchanged against the default in-memory
  adapter; re-enabling Redis later is additive (add the adapter in `socket.ts`,
  no changes needed in `eventRouter`/`rpcHandler`).
- **No non-read-path handlers**: Happy's `socket.ts` also wires
  `sessionUpdateHandler`, `usageHandler`, `pingHandler`, `machineUpdateHandler`,
  `artifactUpdateHandler`, `accessKeyHandler`. None of those are message-write
  or out-of-scope handlers ported here — task scope is strictly handshake +
  eventRouter + rpcHandler + machine presence + backpressure.
- **`eventRouter` payload shapes**: Happy's `UpdateEvent`/`EphemeralEvent`
  unions (Prisma-shaped) are replaced by `@falcon/wire`'s `Update`/`Ephemeral`
  (design §4.3) — already on `main`. Only `buildMachinePresenceEphemeral` is
  defined here (the one builder this task's scope needs); the rest of Happy's
  `build*Update`/`build*Ephemeral` helpers are for update types this task
  doesn't emit (sessions/messages/machines/artifacts — those land with the
  HTTP write routes in 1.2).
- **`rpcHandler` room key**: Happy registers a room per already-prefixed
  `method` string (e.g. `cm9xyz123:bash`, stripped for metrics via
  `baseMethodName`). Falcon's wire protocol (`RpcCallSchema`, already on
  `main`) separates this into `target` (scope-prefixed: `m:<machineId>:<method>`
  / `s:<sessionId>:<method>`) and a bare `method`. The room key here is
  `rpc:<accountId>:<target>`; the bare `method` travels alongside for metrics
  labels and the forwarded `rpc-request` payload, so no prefix-stripping helper
  is needed. `rpc-register`/`rpc-unregister` take `{ target }` (not Happy's
  `{ method }`) to match. All constants (30s call timeout, 2s presence-poll
  interval, 2-consecutive-miss threshold, 15s reconnect grace, exponential
  lookup backoff 2s/4s/8s) are copied verbatim from Happy's `rpcHandler.ts`,
  per plan.md's "copy it wholesale" instruction.
- **Ephemeral backpressure (marked (N) in plan.md — no Happy equivalent)**:
  `eventRouter.emitEphemeral` resolves the target room(s) to local sockets and,
  for `activity`/`attention` payloads only, checks each socket's engine.io
  `writeBuffer.length` against a threshold (16). Under threshold: emit
  immediately (unchanged fast path). Over threshold: keep only the latest
  payload per `(type, sessionId)` key in a per-socket pending map and flush it
  once the socket's `conn` fires `drain`, discarding whatever was superseded in
  between. `emitUpdate` (persistent, never-dropped) is untouched — plain
  room broadcast via `io.to(rooms).emit(...)`, matching Happy exactly.
- **Logging**: `rpcHandler.ts` uses `console.warn`/`console.error` (no `log`
  util was carried over from Happy, and biome's `noConsole` rule already
  allows `warn`/`error`). `socket.ts` uses `app.log` (Fastify's pino instance)
  since it's constructed from a `FastifyInstance`.

## Testing

`packages/server` test suite: 71/71 passing (11 files), including 3 new files
(16 new tests) added by this task:
- `eventRouter.test.ts` — room-scheme routing against a real Socket.IO
  server/client pair (a fake `Socket` wouldn't exercise real room-join
  behavior), plus a deterministic backpressure-coalescing test (fakes a full
  write buffer by pushing placeholder entries, then manually fires `drain`).
- `socket.test.ts` — handshake accept/reject for all three client scopes
  against a real listening server + `socket.io-client`, plus machine
  online/offline ephemeral broadcast (and confirms the machine's own socket
  doesn't get its own presence echo).
- `rpcHandler.test.ts` — successful round-trip, invalid-params fast-fail,
  self-call rejection, and the presence-poll dead-peer detection (disconnects
  the target mid-call, asserts `RPC target disconnected` within ~4s instead of
  the 30s ack timeout). The "target never registers, wait out the full 15s
  reconnect grace window" path is intentionally not covered by a test (it's
  inherent, ported-verbatim behavior — a dedicated test would just add 15s of
  real wall-clock time to the suite for no additional coverage over the
  dead-peer test above).

`pnpm build` (root, Turborepo): all 5 packages build clean.
`pnpm test` (root): all 9 test tasks pass, 172 tests total across the repo.
`pnpm lint`: could not be verified in this environment — biome's linter
process aborts with "terminated abnormally (possibly out of memory)" even on
files this task didn't touch (e.g. `packages/wire/src/index.ts` unmodified on
`main`), so this is a pre-existing sandbox resource constraint, not something
introduced here.

## Assumptions

- The socket handshake's `token` is the same bearer JWT minted by
  `/v1/auth`/OAuth sign-in (already-landed `auth` module) — there is no
  separate WS-specific credential.
- `rpc-register`/`rpc-call`'s `target` field is exactly `@falcon/wire`'s
  `RpcCallSchema.target` shape (`m:<machineId>:<method>` /
  `s:<sessionId>:<method>`), minted by the daemon/session process registering
  it — no validation of the scope prefix's structure happens server-side
  (the relay is a dumb forwarder per design §4.4, "the relay stays a dumb
  forwarder").
- Backpressure threshold (16 queued engine.io write-buffer entries) and the
  coalesce key (`type:sessionId`) are this task's own judgment call — plan.md
  specifies the *behavior* ("coalesce latest-wins per session when send buffer
  exceeds a threshold") but not the exact threshold value, since Happy has no
  equivalent to crib from.
