# P1-1.3-claude-launcher-script — Port falcon_claude_launcher.cjs (fd3 fetch-patch thinking signal)

**Section:** 1. Mirror — 1.3 CLI skeleton + local mode, plan.md §6.3

## What was done

Ported Happy's `happy-cli/scripts/claude_local_launcher.cjs` verbatim into
`packages/cli/scripts/falcon_claude_launcher.cjs`.

- **Fetch patch (verbatim mechanics):** `global.fetch` is wrapped before the
  real Claude CLI is loaded. Every outbound call emits a
  `{type:'fetch-start', id, hostname, path, method, timestamp}` line on fd 3
  when it starts, and a `{type:'fetch-end', id, timestamp}` line on fd 3 when
  the underlying promise settles (success or failure — both paths call the
  same `sendEnd` handler). URL parsing uses `new URL(url, 'http://localhost')`
  for privacy: only `hostname` + `pathname` are ever recorded, never the
  request body or query/search params beyond what's in the path. `fs.writeSync`
  failures (fd 3 not open) are swallowed silently in `writeMessage` — no
  fallback to stdout/stderr, and no throw.
- **`DISABLE_AUTOUPDATER`:** set to `'1'` on `process.env` at module load,
  before the real CLI is required, exactly as in Happy.
- **`getClaudeCliPath()` — local stub, not the full resolver:** per the task
  description, the cross-install-method resolver (npm/Bun/Homebrew/native
  installer detection — Happy's `claude_version_utils.cjs`) is a separate,
  already-in-flight bullet (there's a sibling `P1-1.3-provider-detection`
  worktree). Duplicating it here would just create a merge conflict at
  integration time. Instead this file has a small local stub:
  `getClaudeCliPath()` returns `process.env.FALCON_CLAUDE_PATH || 'claude'`.
  A minimal `runClaudeCli(cliPath)` mirrors the JS-file branch of Happy's
  version (dynamic `import()` so the interceptors above stay active in the
  CLI's module scope); the binary-file/cross-spawn/signal-forwarding branch
  is explicitly left to the full resolver bullet (throws a clear "not yet"
  error if ever handed a non-`.js`/`.cjs` path).
- **Testability guard:** added `if (require.main === module) { runClaudeCli(...) }`
  around the launch call so the module can be `require()`d from tests without
  triggering an actual CLI launch. This is the only behavioral deviation from
  Happy's verbatim script (which calls `runClaudeCli(getClaudeCliPath())`
  unconditionally at the bottom) — necessary because the task explicitly asks
  for unit tests around the fetch patch, and Happy's own script has no test
  coverage to model this on.
- Not wired into `claudeLocal.ts` — that's explicitly a later 1.3 bullet.

## Files created

- `packages/cli/scripts/falcon_claude_launcher.cjs` — the ported launcher.
- `packages/cli/scripts/__tests__/falcon_claude_launcher.test.ts` — 12 unit
  tests covering: `DISABLE_AUTOUPDATER` is set on require; `global.fetch` is
  replaced with a new wrapper function; a well-formed `fetch-start` JSON line
  (parseable, newline-terminated, correct fields) is written to fd 3 before
  the real fetch runs and the real fetch is still called with the original
  arguments; a matching `fetch-end` line (same `id`) is written after the
  fetch resolves; `fetch-end` is still emitted when the underlying fetch
  rejects; fetch ids increase monotonically across concurrent calls; **fd 3 is
  the only channel touched** — `process.stdout.write` / `process.stderr.write`
  are asserted never called, both during normal fetch flow and when
  `writeMessage` swallows a `fs.writeSync` error (fd 3 unavailable); URL
  fallback behavior for a missing/`null` first fetch arg (resolves against the
  `http://localhost` base) and for a genuinely unparseable URL string
  (`hostname: 'unknown'`, `path` = raw input); `getClaudeCliPath()` default
  and `FALCON_CLAUDE_PATH` override.
