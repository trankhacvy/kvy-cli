## What was built

### 1. A `cli-latest` rolling release tag (`.github/workflows/release.yml`, `scripts/build-binaries.sh`)

The task brief explicitly asks for a "`cli-latest` rolling tag/version endpoint", which
didn't exist yet — `P4-4.3-standalone-binaries`'s `release.yml` only ever tagged
`vX.Y.Z`. Added:

- `scripts/build-binaries.sh` now also writes a plain-text `dist-binaries/VERSION`
  file (just the semver string, e.g. `0.1.0`) alongside the three compiled binaries.
- `release.yml` gained a new `publish-cli-latest` job (parallel to `github-release`/
  `publish-npm`, depends only on `build-binaries`): re-publishes the same
  binaries + checksums + `VERSION` file under a **fixed** `cli-latest` tag via a
  second `softprops/action-gh-release@v2` step, on every real `vX.Y.Z` release. This
  gives the CLI one stable, unauthenticated download root
  (`github.com/<repo>/releases/download/cli-latest/...`) that always reflects the
  most recently published version, without the update checker needing to know the
  exact version tag ahead of time (that's what makes it "rolling" rather than a
  regular versioned release).
- `scripts/install.sh` (the `curl | sh` installer) is unchanged — it already used
  GitHub's own `releases/latest` computed pointer, which is a different, adjacent
  mechanism that still works fine for a fresh install; `cli-latest` is specifically
  the self-update codepath's own stable asset root.

### 2. `packages/cli/src/update/` — the self-update engine (new directory, 9 files + 9 test files)

- **`versionCompare.ts`** — hand-rolled semver comparison (`parseVersion`,
  `compareVersions`, `isNewerVersion`). No dependency added; tolerates malformed/
  missing components as `0` rather than throwing, since a corrupt version string
  anywhere in this pipeline must never crash the update check.
- **`config.ts`** — env resolution: `resolveUpdateRepo()` (`FALCON_REPO`, defaulting
  to `falcon-dev/falcon`, the exact slug `scripts/install.sh` and
  `packages/cli/package.json`'s `repository.url` already use), `isUpdateOptedOut()`
  (`FALCON_NO_UPDATE`, same permissive truthiness as `FALCON_NO_SERVICE`/
  `FALCON_DEBUG` elsewhere in this codebase), `isBackgroundUpdateRun()`
  (`FALCON_UPDATE_SILENT`, an internal-only env var — see below), timeout/interval
  constants, and `releaseAssetUrl()` (the `cli-latest` URL builder).
- **`platformAsset.ts`** — `detectPlatformAsset()`: maps `process.platform`/
  `process.arch` to the exact `falcon-$platform-$arch` asset-name convention
  `scripts/build-binaries.sh` publishes; `null` for anything unsupported (Windows,
  linux-arm64 — the same gap `scripts/install.sh` already documents).
- **`installKind.ts`** — `detectInstallKind()`: `"standalone-binary"` (a
  `bun build --compile` executable — detected via a boolean the caller passes in,
  since `__FALCON_CLI_VERSION__` is only ever declared in `index.ts`'s own module
  scope), `"npm"` (a built `dist/index.mjs` exists on disk but isn't a compiled
  binary), or `"dev"` (running straight from TypeScript source — `tsx`/`vitest`,
  nothing to replace). Each apply strategy in `applyUpdate.ts` branches on this.
- **`fetchLatestVersion.ts`** — reads `cli-latest`'s `VERSION` asset over `fetch`,
  bounded by an `AbortController` timeout (default 5s). Every failure mode (HTTP
  error, network error, timeout, empty body) collapses to `null`, never a thrown
  error — the fail-safe contract starts here.
- **`downloadAndVerify.ts`** — downloads a `cli-latest` asset + its `.sha256`
  sidecar in parallel, verifies the checksum via `node:crypto`'s `createHash`, and
  only returns the bytes if they match (`DownloadVerificationError` otherwise) —
  same trust model `scripts/install.sh` already applies to the `curl | sh` path,
  reused here so self-update never installs an unverified download.
- **`applyUpdate.ts`** — the actual "atomically replace the running binary/npm
  install" step, branching on `installKind`:
  - `standalone-binary`: downloads+verifies the platform binary, writes it to a
    sibling `<execPath>.update-tmp` file, `chmod +x`, then `rename()`s it over
    `execPath` (`process.execPath`, which for a `bun build --compile` binary *is*
    the running executable — there's no separate node runtime). `rename` is atomic
    on POSIX, so a concurrently-starting `falcon` never observes a half-written
    executable, and the *currently running* process is unaffected (it already
    holds the old inode open) — the new binary only takes effect on the next
    invocation, by design.
  - `npm`: shells out to `npm install -g falcon@<version>` via an injectable
    `runNpmInstall` (defaults to a real `execFile`) — this is the "reuse the npm
    publish pipeline from `P4-4.3-standalone-binaries`" half of the task: the
    `VERSION` string served off `cli-latest` is the exact same value that
    release run's `publish-npm` job published to the npm registry (both jobs run
    off the same tag push), so `npm install -g falcon@<version>` always resolves.
  - `dev`: no-op with an honest message pointing at `git pull`/`pnpm install`.
- **`runUpdateCommand.ts`** — the shared check-then-apply orchestration used by
  both `falcon update` (explicit, foreground) and the background auto-update child
  (silent). Fails safe end-to-end: dev mode short-circuits before any network call;
  a failed version check, an unsupported platform, or a failed apply all resolve to
  a clear `{code, message}` result rather than throwing. `silent` (driven by
  `FALCON_UPDATE_SILENT=1`) suppresses the message text and downgrades failure
  exit codes to `0`, since nothing reads a detached background child's exit code or
  stdout anyway.
- **`autoUpdateTrigger.ts`** — `maybeTriggerAutoUpdate()`, the actual
  "auto-update-on-start" entry point (see wiring below). Does **no network I/O
  itself** — it only (a) checks `FALCON_NO_UPDATE`/dev-mode, (b) rate-limits via a
  new `lastUpdateCheckAt` timestamp in `settings.json` (24h default interval, so a
  stream of `falcon` invocations doesn't hammer GitHub), and (c) spawns `falcon
  update` as a **detached, unref'd background child** with `FALCON_UPDATE_SILENT=1`
  — mirroring `daemon/commands.ts`'s existing `defaultSpawnStartSync()` precedent
  for "re-launch this same entrypoint as a background process". The whole function
  is wrapped in one top-level try/catch that logs and swallows any failure
  (corrupt settings file, spawn failure, etc.) — it always resolves, never rejects.

### 3. Why the "never block a session start" requirement is genuinely satisfied

The actual network check + download + apply all happen inside the **detached child
process**, not the parent `falcon` invocation. The parent-side trigger
(`maybeTriggerAutoUpdate`) only touches the filesystem (one small JSON read/write)
and calls `spawn(...).unref()` — no network call, no `await` on the child's
completion. This is a stronger guarantee than "awaited-with-a-timeout": it's not
just bounded, it's structurally incapable of blocking on network conditions,
regardless of how slow or unreachable GitHub is.

### 4. CLI wiring (`packages/cli/src/args.ts`, `packages/cli/src/index.ts`)

- `args.ts`: new `{ type: "update" }` command, parsed from `falcon update` (no
  flags — the silent/background variant is driven entirely by the internal
  `FALCON_UPDATE_SILENT` env var the background spawn sets, not a public CLI flag,
  since it's not meant to be typed by a human).
- `index.ts`:
  - `isCompiledBinary()`: small new helper (`typeof __FALCON_CLI_VERSION__ !==
    "undefined"`) shared between `runUpdate()` and `ensureDaemon()`'s auto-update
    trigger call, since `update/installKind.ts` can't reference that
    compile-time-define identifier directly (it only exists in `index.ts`'s module
    scope, same reasoning `readVersion()`'s own doc comment already explains).
  - `runUpdate()`: the `falcon update` handler — thin wiring over
    `runUpdateCommand()`, printing its message to stdout regardless of exit code
    (matching every other command handler's existing convention in this file, e.g.
    `runKill`/`runDaemon`/`runDoctorCommand`). Deliberately does **not** call
    `ensureDaemon()` (no daemon interaction, and would otherwise re-trigger the
    very auto-update check this command *is*).
  - `ensureDaemon()`: now also calls `maybeTriggerAutoUpdate()` right alongside the
    existing daemon auto-start call — this is the single "auto-update-on-start"
    entry point, since `ensureDaemon()` is already the shared gate every
    agent-invoking subcommand (`start`/`auth`/`sessions`/`resume`/`adopt`) calls
    first (PRD FR-1.2). Commands that deliberately skip `ensureDaemon()`
    (`kill`/`doctor`/`shim`/`workspace *`) correctly skip the auto-update trigger
    too, for the same "no daemon-adjacent side effects" reasoning those commands'
    own doc comments already give.
  - `HELP_TEXT`: added the `falcon update` line (the `FALCON_NO_UPDATE=1` env var
    was actually already documented in the environment line from an earlier task,
    unused until now — this task is what makes it real).

### 5. `packages/cli/src/persistence.ts` — one new `Settings` field

Added `lastUpdateCheckAt?: number` to the existing schema-versioned `Settings`
interface (+ `normalizeSettings()` extraction) — reuses the already-atomic
`readSettings`/`updateSettings` (lock-file-guarded, tmp-write + rename) rather than
inventing a second state file, for the same rate-limit bookkeeping `daemon auto-start`
would have used if it needed one.

## Fail-safe checklist (mapped to the task brief)

- **`FALCON_NO_UPDATE` opt-out** — checked first, before any filesystem or network
  access, in both `maybeTriggerAutoUpdate()` (background path) and
  `runUpdateCommand()` isn't gated by it directly (an explicit `falcon update` should
  still work even with the env var set — the env var only opts out of the *automatic*
  background trigger, not the manual command; this mirrors `FALCON_NO_SERVICE` only
  gating daemon *auto-start*, not `falcon daemon start` itself).
- **Never block a session start on a failed update check** — the background trigger
  does no network I/O in the parent process at all (see §3 above); a failed check
  only affects the detached child, which nothing waits on.
- **Atomic replace** — `rename()` over a same-directory tmp file for the standalone
  binary path (POSIX-atomic); `npm install -g` for the npm path (npm's own install
  is already atomic-enough for a global package swap — same trust boundary every
  other "reinstall a global npm package" tool relies on).
- **Checksum verification** — every downloaded binary is sha256-verified against its
  `cli-latest` sidecar before it touches disk, reusing `scripts/install.sh`'s exact
  trust model.
- **Reuses the npm publish pipeline's artifact naming** — `falcon-$platform-$arch`
  asset names (`platformAsset.ts`) and the `falcon@<version>` npm package name are
  both taken verbatim from `P4-4.3-standalone-binaries`'s existing conventions, not
  reinvented.

## Known limitations / assumptions

- **`pnpm lint`/`biome check` could not be run to completion** — every invocation
  (including scoped to a single new file, and after confirming ~2.6GB free system
  memory) hit `[warn] Linter process terminated abnormally (possibly out of
  memory)`, the same pre-existing sandbox flake `P4-4.3-standalone-binaries` and
  `P4-4.3-docker-compose-selfhost`'s task summaries already documented (multiple
  concurrent worktree sandboxes competing for memory). `pnpm build`/`pnpm
  typecheck`/`pnpm test` (this task's three required checks) all ran to completion
  and are green. Every new/changed file was hand-reviewed against `biome.json`'s
  configured style (double quotes, trailing commas, 100-char width) and this
  repo's own import-ordering convention (external packages before relative
  imports, named imports sorted case-sensitively with `type`-only names compared
  by their bare identifier) — cross-checked directly against a real prior
  `biome check` diagnostic (`daemon/blobClient.test.ts`'s import-sort fix) visible
  in this same lint run's (partial) output before it started OOM'ing on later files.
- **Placeholder GitHub repo slug** — `FALCON_REPO` defaults to `falcon-dev/falcon`,
  same placeholder `P4-4.3-standalone-binaries` already documented (`git remote -v`
  is empty in this worktree; no real origin configured yet). Trivially overridable.
- **`falcon update`'s npm-install path assumes global installs are via `npm`** —
  it always shells out to `npm install -g falcon@<version>`, even if the user
  originally installed via `pnpm add -g`/`yarn global add`. This matches
  `packages/cli/package.json`'s own documented install instructions (`npm install
  -g falcon`) and keeps the apply step simple/predictable; a pnpm/yarn-specific
  global-install detector was judged out of scope for a first cut (`npm install -g`
  still installs and links a working `falcon` binary regardless of which tool the
  user originally used, since it's all resolving the same published npm package).
- **No `bun`/real network access in this sandbox** to exercise the actual
  `cli-latest` HTTP round-trip end-to-end (same limitation `P4-4.3-standalone-
  binaries` already hit for `bun build --compile` itself) — every network-touching
  function (`fetchLatestVersion`, `downloadAndVerify`, `applyUpdate`'s standalone
  path) is unit-tested against an injected `fetchImpl` instead (18 new test files'
  worth of coverage across `packages/cli/src/update/`), and the
  `.github/workflows/release.yml` change was verified by hand-reading the YAML,
  not a real Actions run.
- **`falcon update` always attempts a fresh check, ignoring the rate-limit window**
  — only the *automatic* background trigger (`maybeTriggerAutoUpdate`) is
  rate-limited; an explicit `falcon update` always hits the network, since a user
  who explicitly ran the command clearly wants an up-to-date answer regardless of
  when the last automatic check happened.
