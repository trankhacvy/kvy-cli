# P17-2.0-message-rpc-tristate

**Task:** `message` session RPC reply becomes tri-state (additive wire change) + web
composer handling — plan.md §17 v2 ACP migration, Phase 2.0 foundation.

## What changed

### `@falcon/wire` (`packages/wire/src/rpc.ts`)

Added a new `MessageRpcStatusSchema = z.enum(["queued", "duplicate", "outcome-unknown"])`
and an **optional** `status` field on `MessageRpcResultSchema`:

```ts
export const MessageRpcResultSchema = z.object({
  queued: z.boolean(),          // unchanged, still required
  status: MessageRpcStatusSchema.optional(),  // new, additive
});
```

`queued: z.boolean()` is untouched and still required — the additive-only wire policy
(design §5.3) forbids retyping an already-shipped required field, and the additive-only
compat lint (`packages/wire/src/__tests__/additiveOnly.test.ts`, backed by the frozen
`wire-shapes.json` fixture) enforces exactly that. `status` had to be **optional**
rather than required: the CLI's actual `message` RPC producer
(`packages/cli/src/commands/start.ts`'s `rpcHandlers.message`) still only ever returns
`{queued}` today — wiring the send-idempotency claim store into `deliverMessage()` so a
producer can *compute* `status` is explicitly Phase 2.2, disjoint from this task. Had
`status` been required, the CLI's existing (untouched, in-scope-excluded) handler would
have started failing its own result-schema validation
(`packages/cli/src/rpc/sessionRpc.ts`'s `spec.resultSchema.safeParse(result)`) — a
regression this task must not cause. A reply that omits `status` entirely (every
producer today) is therefore still valid, and the web composer explicitly falls back to
the legacy `queued`-only behavior when it's absent.

Regenerated the frozen shape fixture (`pnpm --filter @falcon/wire exec tsx
scripts/snapshot-shapes.ts`) to freeze the new `status` field and the new
`MessageRpcStatusSchema` registry entry as the new compat baseline — `git diff` on
`wire-shapes.json` is purely additive (19 insertions, 0 deletions), matching precedent
(`SpawnResultSchema`'s `requiresApproval`, `AdoptTakeResultSchema`'s `warning`).

Added `MessageRpcResultSchema`/`MessageRpcStatusSchema` tests to `rpc.test.ts` (legacy
queued-only shape still valid, all three status values valid, unrecognized status
rejected, `queued` still required) and registered `MessageRpcStatusSchema` in
`schemaRegistry.ts`.

### `@falcon/web`

- **`packages/web/src/features/session-control/optimistic-composer.ts`** — two new pure
  functions (kept pure/testable, matching this file's existing style — logic factored
  out of the hook so it composes without rendering):
  - `reconcileByStatus(pending, localId, result)`: `'queued'` (or the legacy
    status-less shape) updates the matching pending entry's `queued` flag exactly as
    before. `'duplicate'` drops the pending entry immediately (reconciled as success) —
    since this only ever *updates* an existing entry rather than creating one, no new
    optimistic entry is ever produced for a duplicate reply. `'outcome-unknown'` leaves
    the pending list untouched — the entry keeps its normal path to reconciliation via
    `reconcilePending` if/when the real transcript echo lands, and is never proactively
    dropped, retried, or resent.
  - `deliveryNotice(result)`: returns a non-blocking notice string only for
    `'outcome-unknown'`, `null` otherwise.
- **`use-composer-state.ts`** — both mutation paths (`send`/`sendAttachment`) now call
  `reconcileByStatus`/`deliveryNotice` instead of the old bare `if (result.queued)`
  check; a new `notice: string | null` state is cleared at the start of each send and
  set from the RPC reply. `ComposerState` gained a `notice` field. Crucially, neither
  mutation path has (or gained) any retry logic that would mint a fresh envelope id on
  `outcome-unknown` — the non-blocking notice is the only effect of that outcome, so a
  blind resend under a fresh id is structurally impossible here, not just discouraged.
- **`Composer.tsx`** / **`SessionTimelineScreen.tsx`** — `notice` threaded through as a
  new prop, rendered as a plain muted-text line (deliberately distinct from the
  destructive-styled `error` line — non-blocking, not a failure).
- **`mock-actions.ts`** — the demo `sendMessage` mock now returns `{queued: false,
  status: "queued"}` instead of the old status-less shape, so the mock composer path
  exercises the new field shape too.
- **`sync/sessionRpc.ts`** — re-exports `MessageRpcStatus` (`z.infer` of the new wire
  schema) alongside the existing `MessageRpcResult` alias, for callers that want to
  branch on it without importing `@falcon/wire` directly. The RPC caller itself
  (`createSessionRpcClient`) needed no changes — it's already generic over
  `RESULT_SCHEMAS[method]`, so the new field flows through automatically once the wire
  schema validates it.
- New tests in `optimistic-composer.test.ts` covering all three `reconcileByStatus`
  branches (including "no new entry created on duplicate" and "pending list untouched
  and referentially unchanged on outcome-unknown") plus `deliveryNotice`.

## Out of scope (explicitly, per task brief)

- Wiring the CLI's send-idempotency claim store into `deliverMessage()`
  (`packages/cli/src/claude/claudeRemoteLauncher.ts`) so a producer actually *computes*
  `queued`/`duplicate`/`outcome-unknown` — that's Phase 2.2. Today's only real producer
  (`packages/cli/src/commands/start.ts`) is untouched and still returns `{queued}` with
  no `status`; the web composer's fallback path (treat as `'queued'`) is what a legacy
  reply from it hits.
- Any CLI-side changes at all — `packages/cli` was not touched.

## Assumptions

- `status` optional (not required) on `MessageRpcResultSchema` is the only shape that
  satisfies both the additive-only compat lint *and* "don't touch the CLI producer" —
  this is a deliberate reading of "additive-only" applied to the new field itself, not
  just the schema as a whole.
- The non-blocking notice text ("Couldn't confirm this message was delivered —
  reconciling from the transcript.") is a reasonable default copy; no UX copy was
  specified in the design doc beyond "non-blocking notice," so this can be refined by
  whoever lands the Phase 2.2 producer work with more context on what the claim-store
  crash window actually looks like in practice.
