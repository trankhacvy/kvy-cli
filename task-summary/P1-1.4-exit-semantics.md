# P1-1.4-exit-semantics — Session exit semantics: Ctrl-C resumable vs. crash archival (FR-3.7)

## Scope

Phase 1 §1.4 Transcript pipeline (plan.md line 689): "Exit semantics: Ctrl-C keeps
session `active`/resumable; crash → `failed` via best-effort archive POST (PRD
FR-3.7)". Implements the judgment call at the boundary between a local-mode CLI
session process and the backend — how a session process's exit should be
classified and (for a genuine crash only) reported.

## What was built

### Server: `POST /v1/sessions/:id/status`
- `packages/server/src/app/routes/sessionStatus.ts` (+ `sessionStatus.test.ts`,
  5 tests) — a small, narrow status-set route registered in `server.ts`
  alongside the existing `sessionCas.ts` CAS routes. Deliberately **not** a
  generic CAS-versioned setter like `PUT .../metadata|state`: it only ever
  transitions a session to `failed`, takes no `expectedVersion`, and is
  idempotent (a session already `failed` short-circuits to a 200 no-op — no
  second `headerSeq` bump/fan-out). This matches the caller shape it exists
  for: a CLI crash/signal handler's best-effort, possibly-retried POST, with
  no legitimate concurrent writer to race (nothing else on `main` transitions
  `sessions.status` today).
- On a real transition, fans out through the existing `EventRouterPort`:
  `session-update` (`status: "failed"`, already a first-class optional field
  on `@falcon/wire`'s `UpdateBodySchema` — no wire-schema change needed) plus
  an `attention{kind:"failed"}` ephemeral, matching design §6.4's already
  documented "session failed" push-trigger row.
- `error` in the request body is a short diagnostic string, logged
  server-side (`app.log.warn`) but **never persisted** — the E2E model
  (design §5.3/§6.1: content columns are opaque `EncryptedBox` payloads the
  server never reads) stays intact; "surfaced remotely" per FR-3.7 is
  achieved via the status flip + attention ephemeral + push pipeline, all of
  which already only carry `{sessionId, kind}` by design, not free-text
  content. Full rich-content crash-message delivery (e.g. as an encrypted
  transcript envelope) would need the still-unmerged `envelopeMapper.ts`/
  outbox pipeline and is out of this task's scope.
- Explicit archive (`POST .../archive`) is intentionally not implemented —
  called out as out of scope in the task description.

### CLI: crash-report client
- `packages/cli/src/api/sessionStatus.ts` (+ test, 4 tests) — `reportSessionFailed`,
  a best-effort POST client for the route above, matching the existing
  `daemon/notify.ts` style exactly: never throws, every outcome (`ok`,
  `http-error`, `network-error`) is a typed result, timeout-bounded
  (`AbortSignal.timeout`, default 3s) so an unreachable backend can't hang
  process exit. `backendUrl`/`accessToken` are caller-supplied — this CLI has
  no auth-token storage yet (`falcon auth login` is still a stub on `main`),
  so, like `claudeLocal.ts`'s `launcherPath`, this module treats them as a
  given rather than resolving them itself.

### CLI: exit/crash classifier
- `packages/cli/src/claude/sessionExit.ts` (+ test, 9 tests) —
  `createSessionExitTracker`, the piece that actually implements FR-3.7's
  judgment call. Wraps around (does not replace) a `claudeLocal(...)` call:
  - `start()` registers `SIGINT`/`SIGTERM`/`SIGHUP` listeners (so Node's
    default "kill this process on first signal" behavior doesn't fire before
    the wrapper has a chance to see how the child's own exit resolves) plus
    `uncaughtException`/`unhandledRejection` handlers for bugs in Falcon's
    own wrapper code. Returns a cleanup function.
  - Deliberately does **not** forward/force-abort the child on the first
    signal — the real Claude Code TUI already receives SIGINT/SIGTERM
    directly from the terminal (inherited stdio, same foreground process
    group) and owns its own first-vs-second-Ctrl-C UX; forcing it down here
    would violate FR-3.1's "every provider keybinding untouched" fidelity
    requirement.
  - `handleOutcome(sessionId, outcome)` classifies the settled
    `claudeLocal(...)` promise into `clean-exit` / `signal-exit` / `crash`:
    - a signal observed by this tracker (or inferred from the shape
      `claudeLocal.ts` already produces for a signal-terminated child,
      `"Process terminated with signal: X"`, covering ordering races where
      the child's exit settles before this process's own listener runs) →
      `signal-exit`, **no report sent** — session stays `active`/resumable,
      exactly per design §7.5.
    - anything else that rejected (`ExitCodeError`, an unrecognized signal,
      a spawn error) → `crash`, best-effort reports via
      `reportSessionFailed` (swallowing its result either way — this
      function itself never throws).
  - `uncaughtException`/`unhandledRejection` fire the same best-effort report
    (using whatever session id was last recorded via `handleOutcome`) before
    calling an injectable `exitOnUncaught` (default `process.exit(1)`).

## Wiring note (explicitly out of scope, not faked)

`packages/cli/src/index.ts`'s `runStart` is still the pre-existing
"provider spawning not implemented yet" stub — there is no live call site on
`main` yet that actually invokes `claudeLocal(...)` for a real session. This
task builds the exit-semantics module ready to wrap that call once it lands
(same "treated as a given" pattern `claudeLocal.ts`/`hookServer.ts` already
use for their own not-yet-landed dependencies), rather than half-wiring it
into a stub that would immediately be replaced. The intended call shape is
documented at the top of `sessionExit.ts`.

## Assumptions / judgment calls

1. **No new encrypted/plaintext error column.** The task text says "with the
   error surfaced remotely" but the enumerated concrete ask is only the
   status-update endpoint ("sessions.status already exists... but nothing
   currently transitions it to `failed`"). Rather than add a new DB column
   (plaintext, breaking the "server never reads content" invariant) or wire
   the error into `agentState`/`metadata` (which would need real E2E
   encryption plumbing plus CAS semantics that don't fit a signal-handler's
   best-effort POST), "surfaced remotely" is implemented via the existing,
   already-designed status+ephemeral+push signal path — same shape design
   §6.4 already specifies for every other attention kind (`{sessionId,
   kind}`, no content).
2. **Status route has no CAS/`expectedVersion`.** Unlike `sessionCas.ts`'s
   metadata/state routes, this is a one-way, idempotent transition with a
   single legitimate caller shape (best-effort crash report) and no
   concurrent writer to race against on `main` today.
3. **No signal forwarding to the child.** The tracker only *observes*
   signals on the wrapper process; it never calls `child.kill()` or aborts
   the `AbortController` on a bare Ctrl-C, preserving the real Claude Code
   TUI's own native double-Ctrl-C confirmation UX (FR-3.1).
4. **`claudeLocal.ts` was not modified.** It already treats
   `SIGTERM && abort.aborted` as a clean resolve (for the pre-existing
   programmatic mode-switch shutdown path) and otherwise rejects on any
   signal-terminated or non-zero exit. `sessionExit.ts` reinterprets that
   rejection shape from the outside (via its own signal tracking, plus a
   string-match fallback on `"Process terminated with signal: X"` for
   ordering races) rather than changing `claudeLocal.ts`'s own contract,
   keeping this change additive and not touching already-landed, tested
   code.
5. **`falcon auth login`/backend URL config don't exist on `main` yet**, so
   `reportSessionFailed`'s `backendUrl`/`accessToken` are caller-supplied
   rather than resolved internally — consistent with how `claudeLocal.ts`
   already treats `launcherPath` and `hookServer.ts`'s wiring as given.
