# P4-4.3-docker-compose-selfhost — Self-host docker-compose stack (server + postgres + optional minio)

**Section:** Phase 4 — §4.3 Distribution & self-host
**Status:** implemented, verified end-to-end against real Docker containers (not just unit tests). `pnpm build`/`pnpm typecheck` green across all 5 packages; `pnpm test` green (see "Verification" below for the one unrelated flake).

## What was built

`deploy/docker-compose.yml`: `postgres` + `server` + `web` (three core services), plus `minio`/`minio-init` gated behind `docker compose --profile minio` — the S3-compatible target for the already-landed `P4-4.3-blob-storage` driver. Leaving `S3_BUCKET` unset (the default) keeps blobs on local disk, no MinIO required, per the existing driver-selection design.

### 1. `deploy/server.Dockerfile` — `@falcon/server` runtime image

Three-stage build (`deps` → `builder` → `runner`), all on `node:20-slim` — this workspace has no `requiresBuild: true` entries in `pnpm-lock.yaml`, so no python3/build-essential is needed anywhere (unlike Happy's own `Dockerfile.server`, which needed those for its dependency tree). `builder` runs `pnpm exec turbo run build --filter=@falcon/server...`, which resolves the `@falcon/wire` → `@falcon/crypto` → `@falcon/server` build order from `turbo.json`'s `dependsOn: ["^build"]` graph. `runner` copies root `node_modules` (pnpm's real package content lives in `node_modules/.pnpm/*`) plus each needed package directory *whole* (not just `dist/`) — each package's own `node_modules/<name>` entries are symlinks into that root store, so both must land at the same relative paths they had at build time or module resolution breaks. Confirmed this the hard way: an earlier draft that copied only `dist/` + `package.json` per package left `@falcon/crypto`'s own `tweetnacl`/`libsodium-wrappers` symlinks missing.

**Migrate-on-boot** needed no new logic: `packages/server/src/main.ts` already calls `runMigrations()` (`db/migrate.ts`, advisory-lock-guarded, idempotent) before `app.listen`, on every process start — that's the entire "migrate runs on boot" story per falcon-system-design.md §6.5's own words ("no separate migration step"). `deploy/server-entrypoint.sh` is a thin, documented `exec node dist/main.js` wrapper — a hook point for operators, not a place that re-runs migrations (which would just mean acquiring the same Postgres advisory lock twice for no benefit). Verified this actually works: built the image, ran it against a real `postgres:16` container with no schema, and confirmed all 10 tables (`accounts`, `blobs`, `machines`, `sessions`, ...) existed after boot via `psql \dt`.

### 2. `deploy/web.Dockerfile` + `deploy/web/` — split-origin static web with strict CSP + SRI

`@falcon/web` is already a Next.js static export (`output: "export"`) per its own doc comment ("served from an origin separate from the API"). The Dockerfile builds it (same turbo-filter pattern as the server image) with `NEXT_PUBLIC_API_URL`/`NEXT_PUBLIC_FALCON_API_URL` passed as build `ARG`s (Next inlines these at build time — there's no server at request time for a static export to read env from, so **the image must be rebuilt whenever the API origin changes**), then serves `out/` from `nginx:1.27-alpine`.

- **SRI**: `packages/web/next.config.ts` gained `experimental.sri.algorithm: "sha256"` — Next now stamps a build-time `integrity` hash on every `<script>`/`<link>` tag it emits. Confirmed via `next build` output (`grep -o 'integrity="[^"]*"' out/index.html`).
- **CSP**: `deploy/web/default.conf.template` (nginx's official `envsubst`-on-templates mechanism) sets a strict `Content-Security-Policy` — `default-src 'self'`, `connect-src 'self' ${API_ORIGIN} ${API_ORIGIN_WS}`, `frame-ancestors 'none'`, `object-src 'none'`, plus `X-Content-Type-Options`/`X-Frame-Options`/`Referrer-Policy`/`Permissions-Policy`. `script-src`/`style-src` need `'unsafe-inline'` — documented in the template itself: this is a purely static export with no per-request server able to mint a CSP nonce, and Next's App Router embeds its RSC/hydration payload as inline `<script>` even in static builds. SRI is the compensating control for that: a tampered/substituted *external* bundle from a compromised static host/CDN still fails to execute even with inline same-origin script allowed.
- `deploy/web/docker-entrypoint.sh` derives `API_ORIGIN_WS` (the `ws://`/`wss://` form) from the operator-set `API_ORIGIN` (`http://`/`https://`) via `sed`, before chaining into nginx's own official entrypoint — so `connect-src` can allowlist both the REST fetch scheme and the Socket.IO WebSocket scheme from one configured value instead of asking for two.

### 3. `@falcon/server` — HTTP CORS for the split-origin shape

Split origin means the plain HTTP REST routes need a real CORS allowlist too, not just the `/v1/stream` Socket.IO endpoint (`app/security/cors.ts` already had `buildCorsOriginValidator`, built for `P4-4.4-security-pass`'s wildcard-CORS removal, but it was only wired into `socket.ts`). Added `@fastify/cors` (new dependency) and registered it in `server.ts`, reusing the exact same `CORS_ALLOWED_ORIGINS`-driven validator — one allowlist governing both transports, not two independently-drifting lists. `credentials: false` throughout: auth is a bearer token in the `Authorization` header, never a cookie, so there's no session to leak and no reason to ever send `Access-Control-Allow-Credentials`.

`@fastify/cors`'s origin-function callback shape (`(err, origin: StaticOrigin) => void`, where the second arg becomes the literal allow-origin value or a boolean shorthand) differs just enough from `buildCorsOriginValidator`'s Socket.IO-flavored `(err, allow?: boolean) => void` that TypeScript won't structurally unify the two — this surfaced as a real `tsc` failure inside the Docker build (overload-resolution error on `app.register(cors, ...)`), not something caught by a quick glance. Fixed with a thin inline adapter in `server.ts` (`isAllowedOrigin(origin, (err, allow) => callback(err, allow ?? false))`) rather than changing `cors.ts`'s public shape (which `socket.ts` and its own tests still depend on).

5 new tests in `server.test.ts`: allowlisted origin reflected, non-allowlisted origin gets no CORS header, `Access-Control-Allow-Credentials` never set, preflight `OPTIONS` answered correctly for an allowed origin, preflight rejected for a spoofed one.

### 4. `deploy/docker-compose.yml`, `.env.example`, `README.md`

- `postgres`/`server`/`web` come up with `docker compose up -d --build`; `minio`/`minio-init` only with `--profile minio`.
- Optional env vars (`S3_*`, `VAPID_*`, OAuth ids, Telegram/ntfy) use compose's bare-key `environment:` list syntax (`- S3_BUCKET`, not `S3_BUCKET: ${S3_BUCKET}`) so an unset variable is genuinely *absent* inside the container rather than set to an empty string — the latter would fail `config.ts`'s `z.string().min(1).optional()` checks (empty string is defined-but-invalid, not absent). Verified via `docker exec ... printenv | grep S3_` returning nothing when `.env` left them unset.
- `minio-init` (a `minio/mc` one-shot) creates the `S3_BUCKET`-named bucket idempotently on every start.
- `FALCON_MASTER_SECRET` uses compose's `${VAR:?message}` syntax so a missing secret fails the `docker compose up` invocation itself with a clear message, before any container even starts (belt-and-suspenders alongside `config.ts`'s own production refine).
- `deploy/README.md`: quick start, the split-origin CSP/SRI rationale, migrate-on-boot explanation, local-disk-vs-MinIO blob storage guidance (including the "MinIO's `S3_ENDPOINT` must be externally reachable, not the internal `minio` hostname" gotcha — presigned URLs go straight to browsers/CLIs outside the Docker network), and a troubleshooting section.
- `docker-compose.dev.yml`'s header comment updated (one line) to stop describing `deploy/docker-compose.yml` as a future "Phase 4" thing now that it exists.
