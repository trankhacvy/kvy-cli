## Sub-task 1 — W3.8: scanner.ts final flush + rotation follow

- **Final `syncNow()` in `cleanup()`.** `cleanup()` used to just clear the
  interval, stop watchers, and return — anything appended to the transcript
  in the brief window right before shutdown was never mapped. Added
  `currentSyncPromise` (the in-flight `runSyncCoalesced()` promise, tracked
  from `invalidate()`) so `cleanup()` can `await` any sync already running
  (never run `readSessionEntries`/watcher bookkeeping concurrently — the
  existing coalescing guard's own invariant) and then run **one more**
  `runSync()` pass itself before tearing down watchers — the exact "shutdown
  tail" fix W3.8 asks for.
- **Rotation fallback.** New `watchProjectDirectoryForNewSessions()` watches
  the project transcript directory (`fs.watch`, mirroring `fileWatcher.ts`'s
  retry-with-backoff style but with no give-up — this watcher is meant to
  outlive the whole session and the directory will exist by the time any
  session writes its first entry) for `rename` events on `*.jsonl` files.
  Each new filename's session id (minus extension) is debounced 2s
  (`NEW_SESSION_ROTATION_DEBOUNCE_MS`, guards against reacting to a file
  that's still mid-write) before being handed to a new shared
  `announceNewSession()` — the exact body the public `onNewSession` used to
  inline, factored out so both the caller-driven path (a `SessionStart` hook)
  and this fallback path share identical dedup/pending bookkeeping. Logs at
  `info` (visible without `FALCON_DEBUG` — a genuinely rare, notable event)
  with `newSessionId`/`previousSessionId` whenever it actually triggers, per
  the plan's "debounce 2s and log when it triggers." `cleanup()` also stops
  this watcher and clears its debounce timers.
- Adaptation note: the plan's prose says "a new file whose first record's
  sessionId differs" — Claude Code's JSONL entries carry no `sessionId`
  field in this codebase's own `RawJSONLinesSchema` (only the filename
  encodes it, verified in `types.ts`), so "differs" is evaluated against the
  filename-derived id compared to `currentSessionId`, matching how every
  other part of this module already identifies a session (by filename, not
  by an in-record field). Not a deviation from intent, just the concrete
  mechanism available in the real schema.

## Sub-task 2 — W3.9: injectionController.ts + ptyClaudeSession.ts + start.ts

- **`injectionController.ts`**: `dispose(): void` → `dispose():
  PendingInjection[]`. Still clears `cooldownTimer`/`promptOpenFailsafeTimer`
  and splices the queue, but now **also** reports the spliced (never
  injected) messages via a new `InjectionControllerDeps.onDropped` callback
  and returns them. The submit timer (armed by `tryFlush` for a message
  that's already had its text written and is waiting on the Enter keystroke)
  is now **deliberately left uncancelled** by `dispose()` — that message was
  already `shift()`'d off `this.queue`, so it can never appear in
  `dispose()`'s own splice; letting the timer still fire lets its own
  pre-existing `if (this.disposed)` early-return (the "child exited between
  write and submit" / submit-skip path) report *that* message via the same
  `onDropped` callback when it runs, instead of duplicating a
  currently-mid-injection check inside `dispose()` itself. One code path
  owns "a message that will now never be submitted." (Adaptation note: the
  plan's dispose() snippet elides the timer-clearing lines as `/* … existing
  timer clears … */`; the real fix requires *not* clearing exactly the
  submit timer, for the reason above — the two W3.9 bullets only compose if
  the submit timer survives dispose(). Verified against the existing "dispose
  cancels pending timers" test: it only asserts `submit` is never called
  after dispose, which still holds — the early-return still exits before
  `deps.submit()` runs.) The now-write-only `submitTimer` field itself was
  removed (biome's `noUnusedPrivateClassMembers` correctly flagged it once
  nothing read it anymore).
- **`ptyClaudeSession.ts`**: `PtyClaudeSessionOptions` gained
  `onDroppedInjections?: (messages: PendingInjection[]) => void`, wired
  straight to the `InjectionController`'s new `onDropped` dep. The existing
  `cleanups.push(() => controller.dispose())` teardown step is unaffected
  behaviorally (the drop reporting now happens *inside* `dispose()` via the
  callback, not via its return value) but had to be rewritten to discard
  `dispose()`'s new return value (`cleanups` is typed `Array<() => void |
  Promise<void>>`).
- **`start.ts`**: `runLocalPty()`'s `runPtySession({...})` call gained
  `onDroppedInjections: (messages) => { for (const m of messages)
  completeClaim(m.id, { status: "dropped-session-ended" }); }`, exactly per
  the plan's snippet — reusing the already-existing `completeClaim` helper
  (originally built for the `onInjected`/`onTurnSettled` completion paths),
  so a dropped message's send-claim is completed as a terminal, honest
  result instead of left open. A later retry of the same envelope id then
  sees `claimMessageSend` return `'completed'` → the RPC replies `duplicate`
  (existing generic claim-store semantics, no changes needed there — a
  completed claim is a completed claim regardless of which status string is
  inside it).

## Sub-task 3 — tests

- **`scanner.test.ts`** (2 new tests):
  - shutdown tail: appends an entry then immediately calls `cleanup()` with
    a 60s poll interval (long enough that only the final pass inside
    `cleanup()` — never a periodic tick — could have picked it up); asserts
    the entry was still mapped.
  - rotation fallback: starts a session, then writes a **second** `*.jsonl`
    file with a different id and **no** `onNewSession` call (simulating a
    missed `SessionStart` hook); asserts (after the 2s debounce) the new
    session's entries surface, an `info`-level "new transcript file
    detected" log fired exactly once with the right `newSessionId`, and the
    old session is still scanned afterward (moved to pending, not dropped —
    same guarantee an explicit `onNewSession` call gives). `collectingLogger()`
    (the test helper) gained an `infoRecords` capture list alongside the
    existing `debugRecords` one, since the rotation log is intentionally at
    `info`.
- **`injectionController.test.ts`** (new `describe("no silent message loss
  (W3.9)")` block, 4 tests): `dispose()` returns still-queued messages and
  reports them via `onDropped`; `dispose()` with an empty queue reports
  nothing; a second `dispose()` call is a no-op (no double-report); the
  child-exit-mid-inject case — a message already written but not yet
  submitted when `dispose()` runs is reported via `onDropped` (not via
  `dispose()`'s own return value) once the still-pending submit timer fires.
- **`start.test.ts`** (1 new test): `onDroppedInjections` reported from the
  PTY session completes the claim as `dropped-session-ended`, and a retry of
  the same envelope id then sees `{ queued: false, status: "duplicate" }` —
  the exact dropped→duplicate-on-retry contract this sub-task asked for.
