# U1.2 — perm-routing (W1.1 — kill the web-turn permission flood)

Plan A (per U0.4 PASS on claude 2.1.214): split responsibilities across `PreToolUse`
(always defers with `ask`) and the new `PermissionRequest` hook (fires only for calls
Claude Code's own settings/allowlist/mode evaluation decided genuinely need a human —
this is where the web-vs-terminal fork now lives). Web turns therefore see exactly the
prompts a terminal user would see, instead of a PermCard flood for every Read/Grep/Glob.

## Changes

- **`packages/cli/src/claude/hookServer.ts`**
  - Forwarder blocking-path widened: `blocking = hookPath === '/hook/pre-tool-use' ||
    hookPath === '/hook/permission-request'`.
  - New `PermissionRequestHookBodySchema` (passthrough, `tool_name` required) and the
    new `/hook/permission-request` route: calls `onPermissionRequest` if wired, replies
    `204` (no body) when it resolves `undefined` or isn't wired — the forwarder's
    existing "only write stdout on `res.statusCode === 200`" logic already treats a 204
    as "write nothing," so Claude Code's normal TUI dialog renders untouched. No
    forwarder change needed beyond the blocking-path line.
  - `HookServerDeps` gained `onPermissionRequest?: (input) => Promise<output |
    undefined>`.
  - `writeHookSettingsFile` now writes a 5th settings entry, `PermissionRequest` (same
    `matcher: "*"` + `HOOK_COMMAND_TIMEOUT_SECONDS` shape as `PreToolUse`).
  - Updated the module's "four hooks" doc references to five throughout (forwarder
    comment, `writeHookSettingsFile` doc).

- **`packages/cli/src/claude/pretoolPermissionBridge.ts`**
  - New types `PermissionRequestHookInput`/`PermissionRequestHookOutput` (the
    `PermissionRequest` hook's stdin/stdout contract, verified against 2.1.214 per the
    U0.4 probe).
  - New `handlePermissionRequest()`: local turn → `undefined` immediately (no map entry,
    no envelope); web turn → emits `perm-request`, blocks on a new `permRequestPending`
    map until `resolve()`/timeout/`reset()`, same first-wins/timeout/agent-state
    machinery as before.
  - `handlePreToolUse()` collapsed to a single line: always `ask`
    ("Deferred to Claude Code's own permission engine.") — the `AskUserQuestion` special
    case is Wave 2.1 (U2.1), gated on this unit, not built here.
  - `resolve()`/`reset()` now look across **both** pending maps (the original
    `pending` map — kept, currently unpopulated, reserved for Wave 2.1's
    `handleAskUserQuestion` which the plan says reuses this exact pipeline — and the new
    `permRequestPending` map). One `perm.answer` RPC serves both hook types; a
    `{kind:'mode'}` answer still maps to `allow` + fires `onModeChange`. `pendingCount`
    now sums both maps.
  - **Deny-copy guard** (probe finding — the model routed around a denied `Write` via an
    allowlisted `Bash`): new `appendDenyGuard()` helper appends `"Do not attempt this
    action another way."` to every deny message reaching Claude Code — the `mapDecision`
    deny case, `handlePermissionRequest`'s settle-closure deny case, and both `reset()`
    loops. Applied exactly once per authored message (verified no double-wrap: the
    timeout callback and `resolve()` always pass a *raw* message into the settle
    closure, which applies the guard as its own single boundary).
  - Module doc rewritten: two-hooks-one-responsibility-split section, the
    `PermissionRequest` contract (verified shape), and the deny-copy-guard rationale.

- **`packages/cli/src/claude/remotePermissionHook.ts`**
  - `installRemotePermissionHook` now wires `onPermissionRequest: (input) =>
    bridge.handlePermissionRequest(input)` into `startServer({...})` alongside the
    existing `onPreToolUse`. No handle/signature change — `resolvePermission` already
    called the bridge's shared `resolve()`.
  - Module doc updated to describe both hooks.

- **`packages/cli/src/commands/start.ts`** — doc-comment-only: "four Claude Code hooks"
  → "five," naming `PermissionRequest` and its role, so the composition comment stays
  accurate.

## Deviations from the plan-v2.md snippets (all noted as the task allowed)

- The plan's `handlePermissionRequest` snippet inlines a `settle` closure that computes
  `behavior`/`message` per decision kind; I kept that shape but added an explicit `mode`
  branch (`"Switched permission mode to ... and allowed from the Falcon web UI."`)
  instead of falling through to the plain "Allowed" message, since the old
  `mapDecision`'s mode branch already had richer wording and there's no reason the new
  hook's copy should regress it.
- The task's deny-copy requirement ("Deny copy everywhere must end with 'Do not attempt
  this action another way.'") reads broader than just the new hook's own messages, so
  `appendDenyGuard` is applied at every deny-message authoring site I could find —
  `mapDecision`'s deny branch (the pre-existing `PreToolUse`-map path, reserved for Wave
  2.1) and both of `reset()`'s loops, not only `handlePermissionRequest`'s own timeout/
  settle paths.

## Tests

- `pretoolPermissionBridge.test.ts` — rewritten: `handlePreToolUse` reduced to one
  always-`ask` test; all local/web/timeout/first-wins/reset/agent-state branch coverage
  moved onto `handlePermissionRequest` (mirrors the old `handlePreToolUse` suite 1:1,
  plus new assertions that every deny message contains "Do not attempt this action
  another way."); new `resolve()`/`reset()` cross-map tests (unknown reqId →
  already-answered; empty reset() is a no-op; `pendingCount` reflects
  `permRequestPending`).

  `onPermissionRequest` and returns its decision; 204 when unwired; 204 when the handler
  resolves `undefined`; 400 on missing `tool_name`; `writeHookSettingsFile` writes the
  5th `PermissionRequest` entry with a command timeout (and asserts the full 5-key hook
  order); forwarder end-to-end tests for both the real decision path and the
  no-decision-writes-nothing 204 path.
- `remotePermissionHook.test.ts` — rewritten to drive `onPermissionRequest` (local →
  `undefined`; web turn → resolves via `resolvePermission`; `stop()` denies dangling
  `PermissionRequest`s) alongside a slimmed `onPreToolUse` test (always `ask`).
