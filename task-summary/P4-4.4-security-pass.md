# P4-4.4-security-pass — Security pass: pairing-request TTL, wildcard-CORS removal, token-scrubbing in logs, rate limits

Phase 4 — §4.4 Hardening & release gate. Scoped strictly to
`packages/server`'s auth/middleware/logging config, per the task brief:
disjoint from the blob-storage routes work and the workspace-registration
CLI/daemon work, so it could proceed in parallel with both.

## Starting point (what was already done)

Before touching anything I read `packages/server/src/app/api/pair.ts` and
confirmed **pairing-request TTL is already fully implemented and correct** —
landed earlier via `P0-0.4-pairing-endpoints` (plan.md line 647): every pair
request gets `expiresAt = now + 15min` at creation, and all three endpoints
(`POST /v1/auth/pair`, `GET /v1/auth/pair/status`, `POST
/v1/auth/pair/approve`) check `isExpired(row.expiresAt)` live against
`Date.now()` on every read — no background sweep needed, no gap. I left this
code as-is; the only change in `pair.ts` this task made is adding rate
limits (see below), the TTL enforcement itself needed no work.

That left three of the four checklist items genuinely open, which this task
implements:

## 1. Wildcard CORS removal

`packages/server/src/app/socket.ts`'s Socket.IO server had
`cors: { origin: "*", credentials: true, ... }` — a wildcard origin combined
with `credentials: true`, which no compliant browser actually honors for
credentialed requests, so in practice it only ever "protected" non-browser
clients (i.e. protected nothing) while looking like a real access control.

- New `packages/server/src/app/security/cors.ts`: `buildCorsOriginValidator(allowedOrigins)`
  returns a `(origin, callback) => void` function matching the `cors` npm
  package's function form Socket.IO's `cors.origin` option accepts. Exact
  string match against a `Set` — no wildcard/subdomain patterns, since the
  allowlist is a short, operator-provided list of real deployment origins,
  not a public API. Requests with no `Origin` header (same-origin browser
  nav, or any non-browser client — the CLI daemon's machine-scoped socket
  never sends one) are allowed through, since `Origin` is a browser-enforced
  signal for cross-origin browser requests specifically; Falcon's actual
  access control for every socket connection is still the bearer-token
  check in `socket.ts`'s `io.use` middleware, unchanged.
- New env var `CORS_ALLOWED_ORIGINS` in `config.ts`: comma-separated list of
  exact origins, defaulting to `http://localhost:3000` (the Next.js dev
  server's own origin) so local dev keeps working with zero config; every
  real deployment should set this to its actual web origin(s) — same
  "safe default, must-override in prod" posture the file already uses for
  other config.
- `socket.ts` now passes `buildCorsOriginValidator(env.CORS_ALLOWED_ORIGINS)`
  instead of `"*"`.
- Tests: `app/security/cors.test.ts` (5 cases: allow/reject/no-origin/
  multi-origin/no-substring-spoofing) + `config.test.ts` updated for the new
  field (default value, explicit multi-origin parsing, whitespace/empty-entry
  trimming).

I deliberately scoped this to the one actual wildcard instance in the
codebase (Socket.IO). There is no `@fastify/cors` plugin registered on the
HTTP side at all currently (no CORS headers ever sent for HTTP routes) —
that's a separate, not-yet-landed piece of Phase 4.3's "web served from a
separate origin" work, not a wildcard that needs removing.

## 2. Token scrubbing in logs

Read every `app.log`/`console.*` call site in `packages/server/src` first.
None of them currently interpolate a raw token — the real gap was in the
pino `redact` config itself (`packages/server/src/logger.ts`):

- It redacted `req.headers.authorization`/`req.headers.cookie`, but not
  `X-Telegram-Bot-Api-Secret-Token` — the bearer-style secret
  `routes/telegramLink.ts`'s webhook route reads and compares against
  `env.TELEGRAM_WEBHOOK_SECRET`. Added
  `'req.headers["x-telegram-bot-api-secret-token"]'` to the redact paths.
- Added generic `token`/`accessToken` (top-level) and `*.token`/`*.accessToken`
  (one level of nesting) redact paths as defense-in-depth, so any future
  structured log call that happens to pass a `{ token }`/`{ accessToken }`
  object (e.g. around `mintToken`/`verifyToken`, or the GitHub OAuth code
  exchange) is safe by default without the call site needing to know about
  this list.
- `logger.test.ts` updated to assert the full new redact-paths list.

## 3. Rate limiting on auth/pairing/RPC endpoints

**Auth + pairing (HTTP, `@fastify/rate-limit`, already the app's established
pattern via `config: { rateLimit: { max, timeWindow } }` on individual
routes — see `routes/sessions.ts`/`messages.ts` for precedent):**

| Route | Limit | Rationale |
|---|---|---|
| `POST /v1/auth` | 20/min | unauthenticated, keyed by IP |
| `POST /v1/auth/register` | 20/min | unauthenticated, keyed by IP |
| `POST /v1/auth/oauth/github/exchange` | 10/min | holds this server's own client secret |
| `POST /v1/auth/pair` | 60/min | polled repeatedly by a waiting CLI |
| `GET /v1/auth/pair/status` | 60/min | cheap poll, same rationale |
| `POST /v1/auth/pair/approve` | 20/min | authenticated write, mints a token |

These previously had no per-route limit — only the app-wide 300/min global
default (`server.ts`) applied. They're all pre-existing routes; this task
only adds the `config.rateLimit` block to each.

**RPC (Socket.IO `rpc-call`, new — `@fastify/rate-limit` never sees this
traffic at all since it's WS, not HTTP):**

- New `packages/server/src/app/socket/rpcRateLimiter.ts`: `RpcRateLimiter`,
  a small in-memory sliding-window counter keyed by `accountId` (mirrors
  `server.ts`'s HTTP `keyGenerator`), FIFO-evicted past a max key count —
  same "single-process MVP, safe to lose on restart, bounded memory"
  posture as `auth/token-cache.ts`'s `TokenCache`.
  `tryConsume(key): boolean`, always records the attempt (including
  rejections) so repeated hammering past the limit doesn't get a free reset.
- Wired into `rpcHandler.ts`'s `rpc-call` handler: checked right after
  parameter validation (so malformed calls still fail fast with their
  existing `invalid_params` error, not `rate_limited`) and before any room
  lookup/target dispatch — a rate-limited call never even reaches the
  target. `RPC_CALL_RATE_LIMIT_MAX = 300` per minute per account, matching
  `server.ts`'s global HTTP default so RPC traffic gets the same baseline
  throughput budget as everything else. `rpcHandler()` takes the limiter as
  an injectable 4th parameter (default: a module-level singleton) — same
  injectable-with-a-real-default pattern as `db`/`eventRouter` elsewhere in
  this package, kept for testability even though nothing currently injects
  a fake one.
- Tests: `rpcRateLimiter.test.ts` (5 unit cases: max-within-window,
  reject-over-max, per-key independence, window sliding via injectable
  clock, FIFO eviction) + a new integration case in `rpcHandler.test.ts`
  that drives `RPC_CALL_RATE_LIMIT_MAX` real successful calls over a real
  socket connection through a registered target, then confirms the very
  next call is rejected with `{ ok: false, error: "Rate limit exceeded" }`.

## Assumptions / follow-ups left out of scope

- `CORS_ALLOWED_ORIGINS` has no default in a way that fails closed for a
  self-hosted production deployment that forgets to set it — it silently
  falls back to `http://localhost:3000`, which is safe (no real production
  web origin equals that) but not a hard failure like
  `FALCON_MASTER_SECRET`'s production guard. Given the design doc treats
  `PUBLIC_WEB_ORIGIN` the same way (optional, "missing config = missing
  capability, not a crash"), I matched that existing convention rather than
  introducing a new fail-closed pattern unilaterally.
- No `@fastify/cors` plugin was added for the HTTP API surface — see the
  CORS section above for why that's a separate, not-yet-landed piece of
  work (Phase 4.3's "web served from a separate origin"), not part of this
  task's wildcard-removal scope.
- `rpc-register`/`rpc-unregister` are not rate-limited — they only join/leave
  a Socket.IO room (cheap, no downstream work), unlike `rpc-call` which
  drives real cross-socket dispatch and the presence-poll dead-peer logic;
  the task brief's "RPC endpoints" is satisfied by limiting the one event
  that actually does work.
