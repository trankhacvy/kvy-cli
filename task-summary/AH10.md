# AH10 — pin-copy-this-browser-only

## What

Reworded PIN copy so it says the PIN protects **this browser only**, never "the account":

- `packages/web/src/components/auth/pin-setup-form.tsx` (Create-a-PIN paragraph): now reads
  "This PIN protects your keys on **this browser only** — not your whole account. You'll
  re-enter it after a reload. Falcon never stores it, so if you forget it you recover this
  browser by pairing from another device (or resetting keys), without affecting your account
  or your other devices."
- `packages/web/src/components/auth/pin-unlock-form.tsx` (Enter-your-PIN paragraph): now reads
  "Enter the PIN for **this browser** to unlock its encrypted keys for this session."
- `packages/web/src/app/(public)/password/page.tsx` post-login `CardTitle`: "Set up this
  device" / "Unlock this device" → "Set up this browser" / "Unlock this browser", for
  consistency with the rest of the surface (the `CardDescription` right below it, the
  `needs-rotate` body copy, and `oauth-callback-page.tsx`'s "Reset keys for this browser" all
  already said "browser", not "device").

## Why

Plan doc `docs/auth-ux-hardening-plan.md` item 10: "on this device" reads too much like an
account password to users. The PIN only ever wraps this browser's local key material — losing
it loses this browser's access, not the account, and doesn't touch other devices. Matching this
copy makes that blast radius unambiguous everywhere PIN copy appears.

## Assumptions

- The plan's explicit proposed-fix snippets covered only `pin-setup-form.tsx` and
  `pin-unlock-form.tsx`; those two files were already present in the worktree with exactly the
  proposed text when I started this unit (uncommitted). I verified the text matched the plan
  verbatim and left it as-is.
- The plan's "Current behavior" section also flagged the `password/page.tsx` `needs-rotate` body
  copy and the post-login titles (`:173-176`/`:206-209` in the plan's snapshot). The
  `needs-rotate` body copy in the current tree already says "This browser has no key material
  for your account yet. Generate a new set (this signs every OTHER device out...)" — already
  landed by an earlier unit, so no change needed there. The titles ("Set up this device" /
  "Unlock this device") had no explicit fix snippet in the plan, but the "What to verify" bullet
  ("Copy reads 'this browser only' consistently across setup, unlock, and rotate") and the fact
  that every other nearby string already says "browser" made "device" here read as an
  inconsistency the item was meant to catch, so I rewrote those two title strings too. No test
  or snapshot referenced the old "device" title strings.
- Did not touch `oauth-callback-page.tsx` — it already says "Reset keys for this browser".

### Live verification (real stack, Chrome not available — used playwright-cli instead)

The sandboxed Chrome MCP extension was not connected in this environment
("Browser extension is not connected"), so I used the `playwright-cli` skill (a real
Chromium instance via the Playwright runtime already installed at `~/.dev-browser`) driven
against this worktree's own local stack instead — Postgres, `@falcon/server` on :3005 (already
running, cwd verified as this worktree), and `@falcon/web` on :3000. The web dev server's
`.next` cache had been invalidated by the `pnpm build` static-export run above, so I restarted it
(`pnpm --filter @falcon/web dev`, cwd/PID verified before killing the old one) to get a clean
dev server serving the current source.

Drove the real sign-up/PIN/reload/unlock flow end-to-end:

1. Opened `http://localhost:3000/password/` — confirmed the live-rendered accessibility snapshot
   shows the new `PinSetupForm` copy verbatim: "This PIN protects your keys on **this browser
   only** — not your whole account. ... without affecting your account or your other devices."
2. Filled a throwaway email/password + PIN (`123456`/`123456`), submitted "Set PIN" — this
   really calls `completePasswordSignUp` against the local server (registers the account,
   generates `masterSecret`, PIN-wraps it, binds the key epoch) — landed authenticated on Home
   (sidebar showed "Account g8kbxx3l — End-to-end encrypted").
3. Reloaded the page (the documented "reload clears the crypto worker" behavior) — confirmed the
   `PinUnlockForm` now renders the new copy verbatim: "Enter the PIN for **this browser** to
   unlock its encrypted keys for this session."
4. Entered the PIN and clicked "Unlock" — this really calls `bridge.unlock(pin)` against the
   local worker/IndexedDB state — landed back on the authenticated Home page (session list,
   account chip), confirming the copy change didn't regress the real unlock flow.

Not independently re-verified live: the reworded `needs-rotate`/rotate-step titles ("Set up this
browser" / "Unlock this browser"). I attempted a follow-up "Forgot your PIN?" click to reach

`onForgotPin`/`startRotate` handler in `password/page.tsx` is a pure local `setStatus` call with
no navigation, so it cannot have caused a cross-origin jump on its own. I stopped there rather
than continuing to poke at another worktree's live session, and closed my browser tab. The title
copy itself is a pure two-string swap already covered by `pnpm build`/`typecheck`/the full
`@falcon/web` test suite (all green) and by visual inspection of the source; I'm reporting the
rotate-title screen specifically as **not independently live-verified** rather than claiming it
