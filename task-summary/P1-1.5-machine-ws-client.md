# P1-1.5-machine-ws-client

**Task:** plan.md §1.5's "Machine-scoped WS client: register, heartbeat 60s,
encrypted metadata/daemonState CAS sync (P from `ApiMachineClient`)" bullet —
Phase 1, §1.5 Daemon v1.

## What was built

New module `packages/cli/src/daemon/machineClient.ts`, ported with changes from
Happy's `ApiMachineClient` (`happy-cli/src/api/apiMachine.ts`):

- **Registration/resume + CAS sync is HTTP, not WS** — the biggest delta from
  Happy. Happy drives two separate WS acks
  (`machine-update-metadata`/`machine-update-state`) with unbounded backoff.
  Falcon's write path is HTTP-only end to end (design DELTA D1): both fields
  are CAS'd together in one already-merged route, `POST /v1/machines`
  (`packages/server/src/app/routes/machines.ts`). `registerOrResumeMachine(deps,
  existingMachineId)`:
  - No remembered `machineId` → a plain insert (`dek` + `metadata` +
    `daemonState`, `expectedVersion: 0` — no CAS race possible, matches the
    route's own doc comment).
  - A remembered `machineId` → `casUpdateMachine`, an update loop that retries
    a `409 {current}` conflict by re-reading the server's current
    `metadata`/`daemonState` versions from the response body and resubmitting,
    up to `deps.maxCasRetries` attempts total (default 3 — design §4.3:
    "retrying (x3)"). Both fields travel on every call since the route's
    `metadata` is mandatory even when only `daemonState` changed.
    A `404 not-found` (remembered id belongs to a different account, or the
    row is otherwise gone) falls back to a fresh registration rather than
    failing outright, mirroring Happy's re-auth-conflict handling in `api.ts`.
  - `pushRuntimeState(deps, identity, daemonState)` reuses the same CAS-retry
    path to push a fresh `daemonState` at any time (used on every socket
    (re)connect) without re-deriving `metadataVersion` from scratch.
- **`machineId` persistence via the already-merged `daemon/state.ts`**, not a
  new file: `startMachineClient` reads `daemon.state.json`'s optional new
  `machineId` field (added here, backward-compatible — every existing caller
  that constructs a `DaemonState` without it still typechecks) to resume, and
  `persistMachineId` merges the server-assigned id back in after a successful
  register/resume. A no-op if the file doesn't exist yet (matches
  `state.ts`'s "dumb, no locking" contract; in the real boot order,
  `commands.ts`'s `runDaemonStartSync` already writes this file before a
  machine client would ever start).
- **Connection lifecycle**: `startMachineClient(deps)` registers/resumes over
  HTTP first, then opens the `/v1/stream` socket (`socket.io-client`) with
  `auth: { token, clientType: "machine-scoped", machineId }` — the exact shape
  the already-merged `packages/server/src/app/socket.ts` middleware expects.
  On every `connect` (including reconnects): starts the 60s heartbeat
  (`socket.emit("machine-alive", { machineId, time })`, design §8: "heartbeats
  every 60 s") and re-pushes `daemonState` via `pushRuntimeState` — always an
  *update* against the remembered `machineId`, never a fresh insert, so a
  dropped-and-restored connection cannot duplicate the machine row. On
  `disconnect`, stops the heartbeat and explicitly calls `socket.connect()` —
  required because socket.io-client does **not** auto-reconnect when the
  server-side calls `socket.disconnect(true)` (`reason === "io server
  disconnect"`), only on transport-level drops; this is a persistent
  connection, so it must always keep retrying regardless of why it went down.
  `handle.stop()` tears down the heartbeat and closes the socket for good.
- RPC handler registration (`spawnSession`/`stopSession`/`resumeSession`/...)
  is explicitly **out of scope** — a separate, later plan bullet per §4.4/§8.
  This module only owns the connection lifecycle + registration + heartbeat +
  CAS sync, matching the bullet text exactly.

### `state.ts` change

Added an optional `machineId?: string` field to the existing `DaemonState`
interface (and its runtime type guard) — backward compatible, every
pre-existing `writeDaemonState`/`DaemonState` literal in `commands.ts`/
`commands.test.ts` still typechecks unchanged.

### New dependencies

`packages/cli/package.json`: `@falcon/crypto` (encrypt/decrypt + base64,
workspace) and `socket.io-client` (runtime, `^4.8.1` — matches the version
`@falcon/server` already pins) as dependencies; `socket.io` (`^4.8.1`) as a
devDependency for the integration test's real WS server. All three versions
were already present in `pnpm-lock.yaml` (server's own deps/devDeps), so
`pnpm install` resolved without adding new package versions to the tree.

## Tests

- `machineClient.test.ts` (17 unit tests, mocked `fetchImpl` + a fake
  Socket.IO-shaped object — same DI style as `notify.test.ts`/
  `controlServer.test.ts`):
  - `registerOrResumeMachine`: fresh registration sends `dek` + `expectedVersion:
    0`; resume-via-update sends `machineId` with no `dek`; a `409` is retried
    with the server's `current` versions and succeeds within
    `maxCasRetries`; a persistent `409` exhausts exactly `maxCasRetries`
    attempts and returns `ok:false`; a `404` on resume falls back to a fresh
    registration; a network error returns `ok:false` without retrying.
  - `pushRuntimeState`: sends the identity's tracked versions.
  - `persistMachineId`: no-op when `daemon.state.json` doesn't exist; merges
    `machineId` in without disturbing other fields; no rewrite when already
    current.
  - `startMachineClient`: opens the socket with the exact
    `clientType: "machine-scoped"` auth shape; starts a 60s heartbeat on
    connect (`vi.useFakeTimers`); pushes `daemonState` via CAS on connect and
    updates the returned handle's `identity`; `stop()` clears the heartbeat
    and closes the socket; `disconnect` stops the heartbeat; persists the
    resolved `machineId` into a pre-existing `daemon.state.json`; returns
    `ok:false` and never opens a socket when registration itself fails.
- `machineClient.integration.test.ts` (1 test): a real `socket.io` `Server` on
  `/v1/stream` (not a mock — proves the handshake auth round-trips over an
  actual WebSocket) plus a minimal in-memory `POST /v1/machines` HTTP mock
  replicating just the already-merged route's CAS semantics
  (create-if-absent/update-with-`expectedVersion`/`409 {current}`). Proves:
  one `startMachineClient` call registers exactly once; force-disconnecting
  every server-side socket (`socket.disconnect(true)`) and waiting for the
  client's reconnect shows the **same** `machineId` reconnecting and the
  mock's `createdCount` still at 1 (no duplicate row); the on-(re)connect
  `daemonState` CAS push keeps bumping the same row's version; and
  `daemon.state.json` ends up with the persisted `machineId`, proving a
  simulated daemon restart would resume the same row.

`falcon` (cli) package: 199/199 tests green (18 new: 17 unit + 1 integration).
Workspace-wide `pnpm build` / `pnpm exec turbo run typecheck` / `pnpm exec
turbo run test --force`: all green — 7/7 typecheck tasks, 9/9 test tasks, 339

## Explicitly out of scope (per task instructions and plan.md's own bullet list)

- RPC handler registration (`spawnSession`/`stopSession`/`resumeSession`/
  `listSessions`/`gitStatus`/`gitDiff`/`readFile`/...) — a distinct, later
  plan bullet (design §4.4/§8's "Spawner"), not part of this bullet's text.
- Wiring `startMachineClient` into `commands.ts`'s `runDaemonStartSync` (the
  actual daemon boot path) — that requires the auth module (masterSecret →
  encryption key, wrapped DEK for the account's public key), which isn't
  merged on `main` yet (`P1-1.3-cli-auth-login` is a separate, still-unmerged
  worktree). `MachineClientDeps` accepts `encryptionKey`/`encryptionVariant`/
  `dek`/`token` as plain injected values for exactly this reason — whichever
  task lands the auth module can wire real values in without touching this
  module.
- Listening for inbound `update` events (`t: "machine-update"`) to sync
  externally-made metadata/daemonState changes (e.g. a rename from the web
  app) into the local cache — the bullet only asks for this client's own
  register/heartbeat/CAS-sync; inbound sync is a natural follow-on, not
  required here.
