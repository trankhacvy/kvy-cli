# P3-3.2-daemon-durability

Daemon durability: `sessions.json` persistence, `resumeSession` RPC, self-update, `falcon doctor`/`clean`.

Section: plan.md §16 Phase 3, "3.2 Durability" (§7.4). Fresh implementation — no
prior branch/worktree existed for this task.

## What was built

### 1. `sessions.json` persistence — `packages/cli/src/daemon/sessionsStore.ts`

Ported (adapted) from Happy's `persistence.ts` (`readPersistedSessions`/`persistSession`).
`~/.falcon/sessions.json` stores, per session id: `provider`, opaque `metadata`, the
`SessionEncryptionData` (wrapped DEK + seq + metadataVersion + agentStateVersion), and
`savedAt`. Same tmp-write + rename atomicity as `state.ts`/`persistence.ts`; unlike
`settings.json` this file has exactly one writer process (the daemon), so instead of a
cross-process lock file it uses an in-process write queue (`serialize()`, keyed by
`homeDir`) so two overlapping `persistSession` calls never race each other's
read-modify-write. Entries older than 14 days (matching Happy's `SESSION_MAX_AGE_MS`) are
silently dropped on read. `persistSession`/`removePersistedSession`/`clearPersistedSessions`
are all safe to call more than once. A missing/corrupt file, or a well-formed-JSON-but-
wrong-shape entry, is treated as absent rather than thrown — same "no state == no trust"
stance as `state.ts`.

### 2. Session registry — `packages/cli/src/daemon/sessionRegistry.ts`

Pulls Happy's inline `pidToTrackedSession`/`sessionIdToFinishedSession` maps
(`daemon/run.ts`) out into an injectable module with three responsibilities, matching
`controlServer.ts`'s `ControlServerDeps` callback shapes exactly (no adapter needed):

- `getSessions()`/`stopSession()` — the live, pid-tracked half, wired straight into the
  control server.
- `onSessionStarted()` — the `/session-started` webhook handler: updates the live map and,
  whenever the report carries encryption material, persists it to `sessions.json`.
- `restore()`/`findResumable()` — the durable half `resumeSession.ts` looks sessions up
  against, seeded from disk once at boot (`restore()`), kept current as live sessions die
  (`pruneDeadSessions()`, design §8: "prunes stale session pids via `kill(pid,0)`").

Wired into `daemon/commands.ts`'s `runDaemonStartSync`: the registry is created and
`restore()`d **before** the control server starts serving any request, then its
`getSessions`/`stopSession`/`onSessionStarted` replace the previous honest stand-ins.
`spawnSession` (the HTTP loopback `/spawn-session` path) stays an honest stand-in — actual
tmux/detached spawning-from-a-remote-RPC needs a registered-workspace lookup
(`workspacePath.ts`'s `WorkspaceRootLookup`) that doesn't exist yet either; that's separate,
later integration work, same boundary the already-landed spawn-RPC task (`P3-3.1`) drew.

### 3. `resumeSession` RPC — `packages/cli/src/daemon/resumeSession.ts` + `machineRpc.ts`

`resumeSession(sessionId, deps)` re-spawns the provider process for a session the daemon
still remembers (live-tracked or purely resumable from `sessions.json`), reusing the exact
same building blocks as the already-landed `spawn` RPC: `processLauncher.ts`'s
tmux-preferred launch and `spawnAwaiter.ts`'s pid↔webhook matching. It stops any still-live
process for that session first (two processes must never share ownership of one session's
DEK/seq counters), then hands the relaunched child `FALCON_RECONNECT_SESSION_ID`/
`FALCON_RECONNECT_ENCRYPTION_KEY`/`FALCON_RECONNECT_SEQ`/`FALCON_RECONNECT_METADATA_VERSION`/
`FALCON_RECONNECT_AGENT_STATE_VERSION` — Falcon's own env-var naming for what Happy calls
`HAPPY_RECONNECT_*`. Directory resolution is an injected seam (`resolveDirectory`) since a
persisted session's `metadata` shape isn't defined at this layer yet.

`machineRpc.ts` (`packages/cli/src/daemon/machineRpc.ts`) now registers `resumeSession`
alongside `spawn` in `MACHINE_RPC_METHODS`, decrypting/validating against `@falcon/wire`'s
already-existing `ResumeSessionParamsSchema`/`ResumeSessionResultSchema` (`{sessionId}` →
`{ok:true}`). Unlike `spawn`, there's no idempotency-key replay cache — the wire contract
itself carries no `idempotencyKey`, and a retried resume is safe by construction (it always
stops-then-relaunches). Like `spawn` before it, this RPC handler is real and fully
unit-tested but **not yet wired to a live machine WS connection** — `machineClient.ts`'s
socket is itself not started anywhere in `commands.ts` yet (confirmed before starting: no
existing code calls `startMachineClient`/`registerMachineRpcHandlers`), so full end-to-end
wiring is a separate, later integration task, matching the precedent the spawn-RPC task
(`P3-3.1`) already set.

### 4. Self-update — `packages/cli/src/daemon/selfUpdate.ts` + `commands.ts`

`captureBundleMtimeMs`/`hasBundleBeenReplaced` watch the installed CLI bundle
(`dist/index.mjs`) mtime — not the `package.json` version string, per the design's
explicitly-called-out Happy `#1107` lesson (a republish bumping `package.json` without
rebuilding `dist/` produced an infinite restart loop under version-string comparison).
`index.ts` computes the bundle path correctly in both dev and prod (one level below the
package root in both `src/index.ts` and the pkgroll-bundled `dist/index.mjs` — the same
trick `readVersion()` already used, documented inline) and passes it into
`createDaemonCommandDeps({ bundlePath, ... })`; `commands.ts`'s own default is only
dev-correct (same caveat as its existing `readCliVersion()`).

`start-sync`'s heartbeat (shared with dead-session pruning, one `setInterval`) checks each
tick whether the bundle changed; once it has **and** the session registry reports no live
sessions (`hasLiveSessions()` — "restart when idle", not immediately), it triggers the same
shutdown path, then — after control-server stop, lock release, and state clear — calls the
already-existing `spawnStartSync()` to hand off to a fresh daemon. Ownership is released
before the new daemon spawns (mirrors Happy's own documented ordering fix).

### 5. `falcon doctor` / `falcon doctor clean` — `packages/cli/src/daemon/doctor.ts`

Ported (with changes) from Happy's `daemon/doctor.ts`. `falcon doctor` is purely diagnostic:
reports daemon state (`daemon.state.json` + liveness probe), how many sessions are
resumable (`sessions.json`), and every Falcon-owned process from a `ps` scan
(`processScan.ts`/`markers.ts` — the same discovery mechanism `kill.ts` uses, so it works
even when the daemon itself is wedged or dead). `falcon doctor clean` targets **runaway**
processes specifically — every daemon-classified process, plus daemon-*spawned* sessions
only (`spawnedByDaemon: true`) — and kills them SIGTERM-then-SIGKILL by reusing `kill.ts`'s
`killGraceful` (now exported). Deliberately narrower than `falcon kill all`: a session
started directly from a terminal is never "runaway" just because a daemon happens to be
running too.

Wired into `args.ts`/`index.ts` as `falcon doctor [clean]`; `markers.ts`'s
`ADMIN_SUBCOMMANDS` gained `"doctor"` so a running `falcon doctor` invocation classifies
itself as `other`, not `session`, in its own process scan.

### 6. Chaos test suite — `packages/cli/src/daemon/durability.chaos.test.ts`

Exercises the design's failure matrix (§11) against the real registry/store/resume modules
with fully injected process/spawn fakes (no real subprocesses, no real `ps`, no real
network — consistent with every other test file in this package):

- **Kill daemon mid-turn**: a session started with encryption on one `SessionRegistry`
  instance; a brand-new instance pointed at the same `homeDir` restores it from
  `sessions.json` alone.
- **Kill session process**: a live pid dies; `pruneDeadSessions` graduates it into the
  resumable set rather than losing it.
- **Sleep/wake**: repeated heartbeat prune ticks across a simulated suspend never
  spuriously drop a still-alive session.
- **Server restart**: `resumeSession` successfully re-spawns purely from local disk state —
  no server URL, fetch impl, or credential is anywhere in its dependency graph.
- An end-to-end crash→restart→resume→re-report test confirming exactly one durable record
  survives (no duplication).

This lives inside `packages/cli/src/daemon/` rather than standing up the design's top-level
`e2e/` package (§2's repo layout — reserved for the full scripted-agent conformance
harness). Nothing in this codebase has created that workspace yet; inventing its build/
workspace wiring here would have been scope creep for a durability task, and the actual
recovery logic is exercised identically either way.

## Assumptions / deliberately out of scope

- **Full machine-WS wiring** (`machineClient.ts`'s socket → `registerMachineRpcHandlers` →
  live `resumeSession`/`spawn` calls) is not wired into `commands.ts`. This was already true
  before this task (verified: no existing call site for `startMachineClient`/
  `registerMachineRpcHandlers` anywhere in `packages/cli/src`) and is explicitly out of this
  task's scope per the same boundary the landed spawn-RPC task drew — it needs auth/
  credential plumbing this task doesn't touch.
- **`resumeSession`'s directory resolution** is an injected seam (`resolveDirectory`), not a
  concrete implementation reading a real workspace/metadata schema — that schema doesn't
  exist yet (`workspacePath.ts`'s registry has no real default either, by the same existing
  admission in this codebase).
- **The session process side** that would read `FALCON_RECONNECT_*` env and actually
  reconnect (rather than bootstrap a new session row) is not built — that's `claude/loop.ts`/
  `session/bootstrap.ts`'s own resume wiring, a separate task.
- The `e2e/` top-level package from the design's repo layout was not created (see above).
