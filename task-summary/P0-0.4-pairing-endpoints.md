# P0-0.4-pairing-endpoints — Auth pairing endpoints (device linking)

**Section:** plan.md §16 "0.4 Server foundation" —
`- [ ] Pairing endpoints: POST /v1/auth/pair, GET /v1/auth/pair/status, POST /v1/auth/pair/approve`
(now checked off). Branched from `P0-land-0.4-worktrees` (tip `82188b4`), which already
carries the `pairRequests` Drizzle table + migration.

## What was built

`packages/server/src/app/api/pair.ts` — a Fastify plugin (`pairRoutes`), registered in
`server.ts` right after `healthRoutes`, implementing all three endpoints from
falcon-plan.md §1.2 / plan.md line 647, ported from Happy's
`happy-server/sources/app/api/routes/authRoutes.ts:41-166` (`/v1/auth/request*`),
Prisma → Drizzle:

- **`POST /v1/auth/pair`** `{ ephPub }` → upserts a `pairRequests` row keyed on
  `ephPub` (`insert().onConflictDoNothing({ target: ephPub })`, mirroring Happy's
  `upsert({ update: {}, create: {...} })` — first POST creates the row with a 15-minute
  `expiresAt`, every later POST for the same key is a no-op read). Same endpoint serves
  both polling and completion: returns `{ state: 'pending' }`, `{ state: 'expired' }`,
  or `{ state: 'authorized', token, response }` once approved.
- **`GET /v1/auth/pair/status?ephPub=`** — cheap polling variant, same state machine,
  collapsed to `{ status: 'not_found' | 'pending' | 'authorized' | 'expired' }`. A
  malformed `ephPub` reports `not_found` (200), matching Happy, rather than a 401 —
  this endpoint never asserts about key validity.
- **`POST /v1/auth/pair/approve`** `{ ephPub, response }`, requires `app.authenticate`
  (the approver must already hold a valid JWT — they're the device with the master
  secret). Mints a fresh JWT for `request.accountId` and writes `{ response, token,
  state: 'authorized' }` in a single atomic `UPDATE ... WHERE ephPub = $1 AND response
  IS NULL`. 404 if no matching request exists, 410 if it has expired.

### Falcon hardening vs. Happy (the task's required delta)

`pairRequests.expiresAt` is a **required** column (already enforced by the schema —
see `schema.test.ts`'s `requires expiresAt on pair requests` test). All three endpoints
check `expiresAt < now()` on every read (no background sweep/cron — TTL is enforced
live, not via row mutation) and treat an expired row as `state: 'expired'` /
`status: 'expired'` / `410 Gone`, closing the "QR auth never expired" vuln Happy's
security reporter filed against the un-bounded original flow.

### First-approval-wins, made atomic (not just ported)

Happy's approve handler is read-then-write (`if (!authRequest.response) { update(...) }`,
`authRoutes.ts:159-164`) — a genuine TOCTOU race under two concurrent approvals. This
port expresses the same "only write if not already set" intent from the task
description as a single atomic conditional `UPDATE ... WHERE response IS NULL`: a second
concurrent approve matches zero rows and silently no-ops (both callers still get
`{ success: true }`, matching Happy's idempotent-looking response), with no race window.
Covered by a dedicated test (`first-approval-wins: a second approve does not overwrite
the sealed box`).

### Wire shape for `response`

The `response` sealed box travels over the wire as a base64 string (matching Happy) and
is stored in the `bytea` column as decoded raw bytes (`@falcon/crypto`'s
`decodeBase64`/`encodeBase64`, the same isomorphic codec used elsewhere in the repo).
The server never inspects its contents — routes ciphertext only, per
falcon-system-design.md §5.3.

### Dependency added

`@falcon/crypto` is now a `workspace:*` dependency of `@falcon/server` (previously
unused there), for `decodeBase64`/`encodeBase64` — used both to validate that `ephPub`
decodes to exactly 32 bytes (an X25519 public key length check, the same weak-but-cheap
validation Happy does with `tweetnacl.box.publicKeyLength`) and to encode/decode the
`response` sealed box for wire transport.

## Bug fixed along the way: concurrent `runMigrations()` race

Adding a second Postgres-integration test file (`pair.test.ts`, alongside the existing
`seq.test.ts`) that also calls `runMigrations()` at module load exposed a latent race:
drizzle's migrator has no locking of its own, so two callers hitting a **freshly
created, unmigrated** database at the same time can both observe "not yet migrated" and
issue the same `CREATE TABLE`, which fails on Postgres's own catalog uniqueness
constraint. This isn't test-only — it's the same hazard multiple server replicas would
hit booting simultaneously against a fresh database (design §6.5: "migrate runs on
boot"). Fixed in `packages/server/src/db/migrate.ts` with a session-level Postgres
advisory lock (`pg_advisory_lock`/`pg_advisory_unlock`) held by the migration client's
single (`max: 1`) connection for the duration of the migration — concurrent callers now
serialize instead of racing; the second one simply finds the migration already applied
(the existing idempotency guarantee still holds). No other file needed to change —
`seq.test.ts` picks up the fix for free since it imports the same `runMigrations()`.

## Tests

`packages/server/src/app/api/pair.test.ts` — 13 new tests, gated on Postgres
reachability exactly like `seq.test.ts` (`describe.skipIf(!dbAvailable)`, probed via
`select 1` against `DATABASE_URL`, migrations run once at module load under the new
advisory lock). Covers: malformed-key 401/`not_found` handling on all three endpoints,
fresh-request creation, upsert idempotency (no duplicate row), the full
request→approve→poll→status happy path (sealed box round-trips byte-for-byte, a fresh
token is returned), 404 on approving a nonexistent request, 410 on an expired one, and
the first-approval-wins race guard.

Locally verified against a real `postgres:16`-equivalent (a local Postgres with a
`falcon`/`falcon` role+db matching `DATABASE_URL`'s default) rather than relying on the
skip path — all 68 `@falcon/server` tests pass, including the 13 new ones, on a freshly
recreated (unmigrated) database, confirming the advisory-lock fix actually closes the
race rather than just working around it once.

## Assumptions / follow-ups (out of scope here)

- `POST /v1/auth` (Ed25519 challenge/response → account upsert) and the OAuth sign-in
  routes are separate, still-unchecked items in the same plan.md section — deliberately
  left untouched. `pairRequests` has no FK to `accounts`, so this task didn't need
  either of them: `approve`'s token is minted directly from `request.accountId` (the
  authenticated caller's own JWT claim), with no account-table lookup.
- No cleanup job for expired `pairRequests` rows — the TTL is enforced live on read
  (every endpoint treats an expired row as gone), so stale rows are inert, just not
  physically deleted. A periodic sweep (or an index on `expiresAt` for one) would be a
  reasonable follow-up once retention/ops tooling exists (plan.md's M4 retention section
  is the natural home for this).
