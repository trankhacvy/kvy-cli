# P3-3.1-web-new-session-flow

Web "New Session" flow: machine → directory picker → provider/mode/model → spawn, plus the
two remaining unchecked plan.md §16 "3.1 Remote spawn" bullets this depended on:

- `[ ] Web "New Session" flow: machine → directory picker (daemon fs RPC) → provider/mode/model → spawn; 409 directory-creation approval loop`
- `[ ] Branch/worktree option (-b): git worktree add via daemon`

## Context

`P3-3.1-daemon-spawn-rpc` (merge `b2795bd`, on `main`) landed the daemon-side `spawn` RPC
(idempotency replay, workspace-path validation, tmux-preferred spawner, PID-matched webhook
awaiter) but explicitly left two things out of scope, both closed by this task:

1. The daemon had no RPC for *browsing* a filesystem to pick a brand-new directory —
   `fs.read` (already in `@falcon/wire`) reads file content inside an already-registered
   worktree, which is a different, later concern (§4.1 git panel). Picking a workspace
   directory has to work *before* any workspace is registered.
2. `SpawnParams.branch: {name, createWorktree}` was already defined in the wire schema, but
   nothing on the daemon side consumed it — `spawnEngine.ts` never created a worktree or
   checked out a branch.

## What was built

### `@falcon/wire` (packages/wire/src/rpc.ts)

- **`FsListParamsSchema`/`FsListResultSchema`** (+ `FsEntrySchema`) — a new `fs.list` machine
  RPC contract: `{idempotencyKey, path?}` → `{path, parent, entries: {name, isDirectory}[]}`.
  Deliberately *not* scoped to a `worktree` like `fs.read` — this browses arbitrary
  directories on the paired machine.
- **`FsMkdirParamsSchema`/`FsMkdirResultSchema`** — `fs.mkdir`: `{idempotencyKey, path}` →
  `{ok}`. Backs the create-directory-approval loop.
- **`SpawnResultSchema` extended, additively** — `sessionId` widened from required to
  optional (a legal narrowing per the additive-only compat check — see
  `schemaShape.ts`'s `isCompatible`), plus a new optional `requiresApproval: {action:
  "create-directory", directory}` field. This is the wire-safe equivalent of the daemon's
  existing loopback-HTTP `SpawnSessionResult` union
  (`packages/cli/src/daemon/types.ts`'s `requestToApproveDirectoryCreation` case) — a true
  discriminated union isn't legal here because the wire schema registry's additive-only test
  (`additiveOnly.test.ts`) forbids retyping an already-shipped `object` schema into a
  `union`.
- Regenerated `src/__tests__/__fixtures__/wire-shapes.json` via `scripts/snapshot-shapes.ts`
  to freeze the new/changed shapes. All 47 additive-only compat tests pass (including the
  new schemas), confirming the `SpawnResultSchema` change is backward-compatible.
- New tests in `rpc.test.ts` for the fs.list/fs.mkdir schemas and the two `SpawnResultSchema`
  shapes.

### Daemon (`packages/cli/src/daemon/`)

- **`fsBrowse.ts`** (new) — `listDirectory()`/`createDirectory()`: plain `node:fs/promises`
  wrappers (`realpath` + `readdir` + `mkdir -p`), directories-only, sorted alphabetically,
  parent-path derivation (`null` at the filesystem root). Throws typed `FsBrowseError` on
  failure (not-found, not-a-directory, relative path). Not scoped to a registered workspace
  root — `spawn`'s own `workspacePath.ts` validation remains the actual "no
  arbitrary-directory execution" boundary (design §12); this module only lets the caller
  see/create directories, never launches anything.
- **`gitWorktree.ts`** (new) — `ensureBranchWorkspace()`: resolves `SpawnParams.branch` into
  the directory the session should actually launch in.
  - `createWorktree: false` → `git checkout [-b] <branch>` in place (repo directory
    unchanged).
  - `createWorktree: true` → `git worktree add <repo>/.worktrees/<branch> [-b]` (mirrors
    this very monorepo's own `.worktrees/<task>` convention). Idempotent: a pre-existing
    worktree directory short-circuits without re-invoking git (safe for a retried `spawn`
    idempotency-key replay). Branch names are checked for `..` path-escape segments.
  - Every git call goes through an injectable `GitExec` (hand-wrapped `execFile`, same
    non-`promisify` mockability convention as `processScan.ts`'s `runPs`).
- **`spawnEngine.ts`** (modified):
  - When `validateSpawnWorkspace` returns `{ok:false, reason:"not-found"}` (the target
    directory doesn't exist yet), `spawnSession()` now **returns**
    `{requiresApproval: {action:"create-directory", directory}}` instead of throwing — every
    other validation failure (unregistered workspace, outside-root escape, ...) still throws
    `SpawnError` as before.
  - After successful validation, if `params.branch` is set, calls `ensureBranchWorkspace()`
    and launches the provider process in the *returned* directory (the worktree path, or the
    unchanged repo root) instead of always using `validation.realDirectory`. A
    branch/worktree setup failure wraps into `SpawnError` and never launches.
  - New/updated tests cover both behaviors, including the macOS `/private` symlink
    resolution gotcha (existing `workspacePath.test.ts` convention).
- **`machineRpc.ts`** (modified) — generalized from a spawn-only dispatcher to a small
  per-method table (`spawn`/`fs.list`/`fs.mkdir`), each with its own params/result Zod schema
  and handler, sharing one decrypt → validate → run → seal pipeline. `listDirectory`/
  `createDirectory` are optional deps defaulting to the real `fsBrowse.ts` implementations,
  so every existing spawn-only test call site kept working unchanged. Idempotency-key replay
  stays spawn-only (listing/mkdir are naturally idempotent, no cache needed). Updated/added
  tests for the new methods and the (now 3-target) `rpc-register` registration.

### Web (`packages/web/src/`)

- **`sync/machineRpc.ts`** (new) — typed caller-side client for the daemon's machine-scoped
  RPCs (`spawn`/`fs.list`/`fs.mkdir`), mirroring `sync/sessionRpc.ts`'s shape exactly (seal
  under the crypto client's active key, `apiSocket.rpcCall` to `m:<machineId>:<method>`,
  open + schema-validate the result). `MachineRpcCrypto` is the same narrow seal/open seam as
  `SessionRpcCrypto` — a machine's DEK unwraps via the same primitive as a session's DEK
  (`MachineRow.dek` is the same opaque sealed-box wrap as `SessionRow.dek`), so no crypto
  worker changes were needed.
- **`features/new-session/`** (new feature, following `session-list`/`session-control`
  conventions):
  - `types.ts` — view-model types (`NewSessionMachine`, `DirectoryListing`, `SpawnRequest`,
    `SpawnOutcome`) and the injectable seams `UseNewSessionMachines`/`UseNewSessionActions`
    (mirrors `UseSessionListSnapshot`/`UseSessionControl`).
  - `wizard-state.ts` — pure step/form logic (`WIZARD_STEPS`, `canAdvance`, `nextStep`/
    `previousStep`, `buildSpawnRequest`), fully unit-tested, no React.
  - `spawn-flow.ts` — `runSpawnFlow()`: the "409 directory-creation approval loop" itself,
    pulled out of the screen component so the branching logic is unit-testable without
    React. Calls `spawn`; on `requiresApproval`, asks the caller to confirm, calls
    `createDirectory`, and retries `spawn` once. Throws `SpawnFlowError` if the directory is
    still reported missing right after creation (shouldn't happen — `fs.mkdir` is `mkdir
    -p`).
  - `mock-source.ts` — default data source: a small in-memory fake filesystem + fake
    machines, same latency-simulating pattern as `session-control/mock-actions.ts`. The mock
    actions hook is `useMemo`'d on `machineId` so its mutable state (created directories)
    survives re-renders.
  - `live-actions.ts` — `machineRpcToActions()`: adapts a `MachineRpcClient` to
    `NewSessionActions` (mirrors `session-control/live-actions.ts`'s
    `sessionRpcToActions()`). `workspaceId` is set to the chosen `directory` itself — there's
    no workspace registry yet (`workspacePath.ts`'s `resolveWorkspaceRoot` is an injectable
    seam with no real default, a separate later task), so the directory stands in as its own
    stable workspace identity.
  - `components/machine-step.tsx`, `components/directory-step.tsx`,
    `components/options-step.tsx` — the three wizard steps (machine picker, directory
    browser with parent/child navigation + manual path entry, provider/permission-mode/
    model/branch form).
  - `new-session-screen.tsx` — the four-step wizard (machine → directory → options →
    review), owning form state and orchestrating `runSpawnFlow` with an inline
    create-directory approval panel (not a native `confirm()` — resolved via a ref-held
    Promise so the UI can render Allow/Cancel buttons). On success, links to
    `/session/<id>/`.
  - `index.ts` — barrel export.
  - 23 unit tests across `wizard-state`, `spawn-flow`, `mock-source`, and `live-actions`.
- **`app/session/new/page.tsx`** (new route) — renders `NewSessionScreen`.
- **`features/session-list/session-list-screen.tsx`** (modified) — added a "New session"
  button (empty state and the populated-list header) linking to `/session/new/`, so the flow
  is reachable from Home.

## Assumptions / deltas from a literal reading of the task brief

- **"the daemon's existing `fs` RPC"**: no directory-*listing* RPC actually existed yet
  (`fs.read` reads file *content* inside an already-registered worktree, and even that
  wasn't wired into `machineRpc.ts`'s method table — only `spawn` was). This task adds
  `fs.list`/`fs.mkdir` as new machine RPCs, following the same conventions as the already-
  defined-but-unwired `fs.read`/`git.*` schemas the wire package's comments call out as
  "separate, later plan bullets."
- **Workspace registry**: `packages/cli/src/daemon/workspacePath.ts`'s
  `resolveWorkspaceRoot` and the whole "registered workspace" concept remain an injectable
  seam with no real implementation (explicitly flagged as out of scope elsewhere in this
  codebase — CLAUDE.md: "workspace registration and managed-session lineage are separate,
  later tasks"). The web flow's `workspaceId` is therefore the chosen directory path itself,
  not a real workspace-registry id, matching the same-shaped simplification already used by
  `features/session-list/mock-source.ts`'s arbitrary `workspaceId` strings.
  `daemon/commands.ts`'s `runDaemonStartSync` also does not wire `registerMachineRpcHandlers`
  into the running daemon process yet — that composition-root wiring was already flagged as
  out of scope by the prior `P3-3.1-daemon-spawn-rpc` task ("session spawning is not
  implemented yet" stub) and stays that way; this task only extends the RPC surface and unit
  tests it in isolation, per the same pattern.
- **Machine DEK in the web crypto client**: no new crypto-worker plumbing was added.
  `MachineRow.dek` is the same opaque sealed-box wrap as `SessionRow.dek`
  (`packages/wire/src/rows.ts`), so a real integration loads a machine's DEK via the crypto
  bridge's existing `setSessionKey(machineRow.dek)` the same way a session's DEK loads today
  — documented in `sync/machineRpc.ts`'s `MachineRpcCrypto` doc comment.
- **Create-directory approval UI**: implemented as an inline panel in the review step (not a
  native `window.confirm`), so it's stylable and testable; the actual approval *decision*
  flow (`spawn-flow.ts`'s `runSpawnFlow`) is transport-agnostic and fully unit-tested
  independent of the UI.
- Session-import ("continue from recent") is explicitly a separate, later plan bullet
  (§4.2 "Session import in New-Session flow") and was not built here.
