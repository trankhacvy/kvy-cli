# P2-2.4 — Web control surface: Composer, PermCard, ControlBar, attention indicators

Phase 2 — Control (M2), plan.md §2.4 / §16 "2.4 Web control surface". Built fresh in
`packages/web`, disjoint from the CLI-side `P2-2.3-permission-pipeline` branch.

## What was built

### 1. Session RPC transport (`packages/web/src/sync/`)
- **`apiSocket.ts`**: added `rpcCall(target, method, params): Promise<RpcCallResult>` to the
  `ApiSocket` interface — emits the WS `rpc-call` event with an ack callback (a real
  `socket.io-client` socket treats a trailing function argument as the ack natively; no new
  `SocketLike` API needed), with a client-side 35s timeout as a last-resort guard beyond the
  server's own 30s cap (design §4.4). Never rejects; always resolves `{ok: true/false}`.
- **`sessionRpc.ts`** (new): typed caller-side client for the five session RPC methods (`message`,
  `interrupt`, `takeControl`, `setMode`, `perm.answer` — design §4.4), mirroring
  `packages/cli/src/rpc/sessionRpc.ts`'s registration side. Seals params / opens+validates results
  via an injected `SessionRpcCrypto` (structurally satisfied by the real `CryptoBridgeClient`).
  Throws `SessionRpcError` only for transport-level failure; an application-level "lost the
  first-wins race" `perm.answer` result returns normally (never thrown).
- Both fully unit-tested (`__tests__/apiSocket.test.ts` additions, new `__tests__/sessionRpc.test.ts`).
- Added `zod` as a direct dependency of `@falcon/web` (needed to resolve `z.infer` on `@falcon/wire`'s
  exported schemas — same pattern `cli`/`server` already use).

### 2. `features/session-control/` (new) — control-surface logic, hooks, and the injectable seam
- **`attention.ts`**: `deriveAttention()` — FR-8.1's rule (pending-perm ∨ pending-question ∨
  completed-and-unseen), computed from the reduced `RenderItem[]` + the `attention` ephemeral +
  per-device last-seen, never stored (design principle #3). `ATTENTION_META` maps each state to a
  label/glyph/color.
- **`last-seen.ts`**: per-session, per-device "last seen" timestamp in `localStorage` (guarded for
  SSR exactly like `lib/session.ts`).
- **`session-state.ts`**: `deriveControlMode()` (local/remote, from the latest `mode-switch` item)
  and `isTurnOpen()` (fallback "working" signal alongside the droppable `activity` ephemeral).
- **`optimistic-composer.ts`**: `buildMessageEnvelope`/`reconcilePending`/`pendingToRenderItem` — the
  optimistic-insert-reconciled-by-echo-update logic (design §9.1), keyed by the composer-minted
  envelope id.
- **`perm-card-state.ts`**: `PermCard`'s local phase machine (`idle` → `submitting` → `answered` /
  `lost-race` / `error`) — pure, so the first-wins-across-devices branch (design §7.6) is testable
  without mounting a component.
- **`use-session-ephemerals.ts`**: subscribes to `apiSocket`'s `ephemeral` stream for one session's
  `activity`/`attention` signals.
- **`use-composer-state.ts`**: the Composer's `useMutation` (TanStack Query) calling the `message`
  session RPC, with optimistic insert + reconciliation + a `queued` flag.
- **`tab-attention.ts`** (pure) + **`use-tab-attention.ts`** (DOM effect): tab title prefix + a
  colored-dot SVG-data-URI favicon reflecting the session's attention/working state (FR-7.9),
  restored on unmount.
- **`session-control-context.tsx`**: `SessionControlProvider`/`useSessionControl()` — makes
  `sessionId` + the five RPC actions available to `Composer`/`PermCard`/`ControlBar` without prop
  drilling through `Timeline`/`TimelineRow`/every `ToolCard`.
- **`types.ts`** / **`live-actions.ts`** / **`mock-actions.ts`**: the `SessionControlActions` /
  `UseSessionControl` injectable-hook seam (mirrors `features/session-list`'s
  `UseSessionListSnapshot` pattern exactly) — `sessionRpcToActions()` adapts a real
  `SessionRpcClient` (one-line wiring once a live per-session crypto client exists);
  `useMockSessionControl` is the screen's current default, simulating realistic latency.
  `demo-items.ts`'s standalone pending permission (`reqId: "req-1"`) is special-cased to always
  resolve as "answered on another device" — a deliberate demo showcase of the first-wins-losing
  path, which is otherwise a rare race to hit by hand.
- All logic modules are pure and unit-tested (45 new tests); hooks/context are thin, untested
  `.tsx`/DOM-effect wrappers, matching this codebase's existing `.ts`(tested)/`.tsx`(untested)
  convention (no React Testing Library / jsdom in this package's vitest config).

### 3. Components (`packages/web/src/components/timeline/`)
- **`Composer.tsx`** (new): follow-up message textarea + send button + a "Queued — the agent is
  finishing its current turn" badge when the RPC's `{queued: true}` comes back; purely
  presentational, driven by `useComposerState`.
- **`PermCard.tsx`** (new): Allow / Allow-for-session / mode-switch (one button per offered
  `PermissionMode`) / Deny, calling `perm.answer`. Renders the edit-preview diff (via `DiffView` +
  `parseEditArgs`) when `showPreview` and the tool is `Edit`/`MultiEdit`/`Write`. Once
  `permission.decision` is canonical (from the reducer) it falls through to the existing read-only
  `PermissionBadge` — always authoritative regardless of this card's own optimistic phase.
  Renders "Answered on another device" + the winning decision for the first-wins-loser case
  (design §7.6). `showHeader`/`showPreview` let the two call sites avoid duplicating chrome.
- **`ControlBar.tsx`** (new): Interrupt (disabled unless working), a permission-mode `<select>`
  (optimistic with rollback on `setMode` failure), and "Take control" (shown only while
  `controlMode === "local"`, since there's nothing to take once already remote).
- **`PermPlaceholder.tsx`** (edited): renders `PermCard` while `permission.decision` is undefined
  instead of the old read-only-only display.
- **`tool-cards/ToolCardShell.tsx`** (edited): renders an interactive `PermCard` action row (with
  `showPreview={false}`, since the tool's own body — e.g. `EditCard`'s diff — already shows `args`)
  below the body while a decision is pending; the header keeps the existing read-only
  `PermissionBadge` regardless of state.
- **`SessionTimelineScreen.tsx`** (edited): wires everything together — `SessionControlProvider`
  (defaulting to `useMockSessionControl`, an injectable `useControl` prop for swapping in the real
  thing later), `useComposerState`, `useSessionEphemerals`, `deriveControlMode`/`deriveAttention`,
  `markSeenNow` on mount, `useTabAttention`, and renders `ControlBar` + `Timeline` (fed the
  composer's merged/reconciled items) + `Composer`.
- **`demo-items.ts`** (edited): added one more fixture item (`e21`, a running `Bash` call with a
  pending permission) so the embedded-in-`ToolCardShell` `PermCard` path is exercised in the demo
  alongside the pre-existing standalone-`PermPlaceholder` path.

### 4. App wiring
- **`app/providers.tsx`** (new) + **`app/layout.tsx`** (edited): added a root `QueryClientProvider`
  — nothing in the app previously mounted one, so `useMutation` would have thrown at runtime the
  moment `Composer`/`PermCard`/`ControlBar` rendered. Created lazily via `useState` so the
  static-export prerender doesn't share a client across routes.

## Key design decisions / assumptions

1. **RPC vs HTTP for `message`.** The design doc's §9.1 "optimistic timeline insert reconciled by
   echo update" phrasing is written for the general HTTP write path, but §4.4 explicitly registers
   `message` as a **session RPC** (`registered by the session process`), and the task description
   says so too. Read together: the composer's RPC delivers the text straight to the live session
   process (so it can inject it as agent input, returning `{queued}` if mid-turn) — the resulting
   canonical transcript entry then arrives through the normal `message-new` update path once the
   session process's own tailer picks it up, exactly like locally-typed terminal input. This is why
   reconciliation is needed at all.
2. **Reconciliation key.** `reconcilePending` matches by `RenderItem.id === (the envelope id the
   composer minted)`, assuming the session process preserves that id end-to-end into the canonical
   transcript (the same way it would for terminal-typed input). If a future landing mints a new id
   at capture time instead, only that one line needs updating.
3. **Injectable seam, mock by default.** `SessionTimelineScreen` still runs off `demo-items.ts` (a
   separate, already-"planned" task per the root `CLAUDE.md`) — real `apiSocket` + a per-session
   crypto client with the unwrapped DEK aren't wired into this screen yet. `SessionControlActions`/
   `UseSessionControl` is the same injectable-hook pattern `features/session-list` already
   established for exactly this reason; `sessionRpcToActions()` + `createSessionRpcClient()` are
   fully built and unit-tested, ready for a one-line swap once that data layer lands (as the task
   description itself anticipates: "full end-to-end PermCard behavior should be re-verified once
   §2.3 lands").
4. **Current permission mode.** The wire protocol has no first-class "current mode" fact (only
   `perm-resolve`'s `{kind:'mode'}` decision, or a future dedicated event) — `ControlBar`'s mode
   selector is passed `mode="default"` from the screen today and manages its own optimistic
   selection locally. Deriving the *true* current mode from history is future work once the data
   layer lands.
5. **No new Radix/shadcn primitives.** The design doc suggests a shadcn `Dialog` for PermCard, but
   no Dialog/DropdownMenu primitive was installed in this package yet; used inline `Card`-style
   layout + a plain `<select>` instead of adding new dependencies for this task alone.
6. **No Zustand.** The design doc earmarks Zustand for stream-shaped state, but it isn't a
   dependency of `@falcon/web` yet and no other landed task introduced it — ephemeral state here
   uses a plain `useEffect`/`useState` hook subscribed to `apiSocket`, consistent with how
   `apiSocket`/the sync engine are themselves plain TS modules, not Zustand stores.
7. **Tab title/favicon scope.** FR-7.9 is implemented per the currently-open session (not a
   cross-session "max attention across the whole account" — that would require the Home screen's
   live data wiring, a separate not-yet-landed task per `CLAUDE.md`). "Max" here means: among a
   single session's simultaneously-possible signals, priority order wins (perm > question > failed
   > done), matching `attention.ts`'s own priority rule.
