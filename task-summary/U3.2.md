## What landed

### W3.2 — image blocks → `t:"file"` envelopes (`packages/cli/src/claude/envelopeMapper.ts`)

- New `RawImageBlock` content-block variant + `pickImageSource()` (validates the
  Claude Code raw transcript shape `{type:"image", source:{type:"base64",
  media_type, data}}`).
- `imageBlockToEnvelope()`: base64 payload ≤256KB (`MAX_INLINE_IMAGE_BYTES`) → a wire
  `file` envelope with `ref: "inline:<base64>"` and a minted `name` (`image.png` /
  `.jpg` / `.gif` / `.webp`, derived from `media_type` via
  `IMAGE_EXTENSION_BY_MEDIA_TYPE`); over the cap → a `service` envelope
  `"image omitted (too large)"`. No wire schema changes needed — `file.ref` is
  already a plain string and `service.text` already exists (both landed earlier,
  during the ACP work).
- Wired into all three content-block loops that can carry an image: the plain
  (non-tool-result) user-message loop, the tool_result's own nested `content`
  array (e.g. `Read` on an image file — appended right after that call's
  `tool-end`, `output` left untouched), and the mixed sidechain/tool-result loop's
  text-sibling case.
- Updated one pre-existing test
  (`"maps non-tool user array content..."`) that had an image block in its fixture
  but asserted the image was silently dropped — it's now asserted to also produce
  the inline `file` envelope, per the new intended behavior.

### W3.3 — static risk map + PTY lifecycle `service` envelopes

- `RISK_BY_TOOL_NAME` (Bash→exec, Edit/Write/MultiEdit/NotebookEdit→write,
  Read/Grep/Glob/LS→read, WebFetch/WebSearch→network), mirroring
  `acp/acpToEnvelope.ts`'s `RISK_BY_KIND` but keyed by Claude Code's raw tool name
  instead of ACP's `kind`. Wired into the `tool-start` envelope push (`risk` is
  omitted, not `undefined`-valued, when the tool isn't in the map).
- `packages/cli/src/commands/start.ts`'s `runLocalPty`: two `service` envelopes via
  `outbox.enqueue([createEnvelope("agent", {t:"service", text})])` —
  `"session started"` right after the PTY session is spawned, and on `ptySession.done`
  resolving, `"session ended"` (code 0) or `"session ended unexpectedly (exit code
  N)"` (non-zero).

  **Adaptation from the plan's three-item list** ("session started", "session
  ended", spawn failures): `ptyClaudeSession.ts`'s `done` promise never rejects —
  its own `run()` setup/spawn-failure path (`node-pty` spawn throwing, etc.)
  resolves `done(1)` internally, the same shape as a genuine non-zero `claude`
  exit. There is no separate signal start.ts could observe to tell those two
  apart, so "spawn failures" collapses into the same non-zero-exit `"session ended
  unexpectedly"` message rather than being a third, distinct code path. Noted here
  per the task instructions rather than inventing a signal that doesn't exist.
- Added an injectable `createOutbox` seam (`OutboxLike` — `enqueue`/`dispose`) to
  `StartClaudeCommandDeps`, defaulting to the real `Outbox`. Not in the plan's
  snippet, but required for testability: before this change nothing in
  `start.test.ts` ever pushed an envelope into the real `Outbox` under its fake
  `/fake/home` homeDir, so `outbox.dispose()`'s flush (only triggered when the
  buffer is non-empty) never touched disk. Now that lifecycle envelopes enqueue
  unconditionally on every `runLocalPty()` call, every existing test needed a safe
  default outbox (`baseDeps()` now defaults `createOutbox` to a no-op in-memory
  fake); the two new lifecycle tests override it to assert on the captured
  envelopes.

### Web — `inline:` ref rendering (`packages/web/src/components/timeline/FileAttachment.tsx`)

- `isInlineFileRef()` / `INLINE_REF_PREFIX` and a new, deliberately hook-free
  `InlineImageAttachment` component: renders `<img src="data:{mimeType};base64,{data}}">`
  directly, no download/decrypt round trip (the bytes are already plaintext in the
  envelope). `inferImageMimeType()` inverts the CLI's extension mapping (reads
  `item.name`'s extension since the wire `inline:` ref carries only base64, no media
  type — matching the plan's literal `ref: "inline:<base64>"` shape).
- `FileAttachment` calls both hooks unconditionally first (Rules of Hooks —
  no conditional hook calls), then branches to `InlineImageAttachment` for an
  `inline:` ref before doing any of the real download-button JSX/logic.
- `InlineImageAttachment` is split out specifically so it's testable the same way
  `tool-cards/registry.test.ts` tests dispatch: call it directly and inspect the
  returned element (`.type`/`.props`) — no DOM/render environment exists in this
  package (`vitest.config.ts`: `environment: "node"`, no `@testing-library/react`).

## Scope notes

- Wire package (`packages/wire`) untouched — `file`, `service`, and `tool-start.risk`
  were all already on the schema from the earlier ACP (`acpToEnvelope.ts`) work, so
  W3.2/W3.3 needed zero wire changes. Additive-only constraint trivially holds.
- Per the plan, `acp/acpToEnvelope.ts` was not touched — it already has its own
  `RISK_BY_KIND` and this bundle's scope is Claude Code's raw-transcript mapper
  only.
- `runRemoteLoop` (the headless `--starting-mode remote` flow) was not given
  lifecycle `service` envelopes — the plan scopes W3.3's lifecycle-envelope item to
  `runLocalPty` specifically.
- `tool-end`'s `output` field keeps a tool_result's raw `content` (images
  included) untouched even after adding the nested-image extraction — the new image
  envelope is additive, not a replacement for existing renderers that read `output`.
