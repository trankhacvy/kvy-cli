# P1-1.6-session-list-screen — Session list (home) screen

Phase 1 §1.6 — Web app v1 (read-only). Reference: falcon-system-design.md §9.2 "Home" row,
falcon-prd.md FR-7.1.

## What was built

`packages/web/src/features/session-list/`:

- **`types.ts`** — view-model types for the screen (`SessionListSnapshot`,
  `SessionListSession`, `SessionListMachine`, `SessionListWorkspace`) plus the injectable
  data-source contract `UseSessionListSnapshot = () => SessionListSnapshot`. Field values are
  the already-decrypted plaintext a real crypto-bridge-backed hook would eventually produce
  (design §5.3) — this task doesn't touch decryption.
- **`status.ts`** — `deriveSessionStatus()`, the FR-7.1 status derivation (`working /
  waiting-for-permission / waiting-for-input / idle / completed / failed / offline`), and
  `SESSION_STATUS_META` (label + dot color/pulse per status). Computed fresh every call from:
  - the session's already-landed reducer output (`RenderItem[]` from
    `packages/web/src/sync/reducer`) — walked to find an open turn, an unresolved permission
    (recursing into subagent scopes), and the outcome of the last closed turn;
  - `machineOnline` (presence, `null` if the session has no machine);
  - `attention` (`"perm" | "question" | "done" | "failed" | null"`), which mirrors
    `@falcon/wire`'s `Ephemeral` `t: "attention"` union — the one signal not recoverable by
    replaying `RenderItem[]` alone, since the wire's `SessionEvent` union has no "agent asked
    a question" variant yet, and "turn completed but unseen" needs a seen/unseen bit no
    `RenderItem` carries.

  Nothing here is stored — every call recomputes from the inputs, per design principle #3.
- **`group.ts`** — `groupSessionsByWorkspace()`: buckets sessions by `workspaceId`, sorts each
  group newest-activity-first, sorts groups by their most recently active session, and puts
  sessions with no resolvable workspace in a trailing "Other sessions" group instead of
  dropping them.
- **`format-relative-time.ts`** — compact `"5m"/"2h"/"3d"` timestamps for session cards.
- **`mock-source.ts`** — `useMockSessionListData`, the default (and, for now, only) data
  source. Builds one fixture session per FR-7.1 status by running real envelopes through the
  landed `reduceEnvelopes()` (not hand-built `RenderItem[]`), so it also serves as an
  end-to-end check that `deriveSessionStatus` composes correctly with the reducer.
- **`components/`** — `SessionStatusDot` (colored dot, pulses for `working`/
  `waiting-for-permission`/`waiting-for-input`), `MachineBadge` (name + online dot),
  `SessionCard` (title, provider badge, status label, machine badge, relative time),
  `WorkspaceSection` (heading + card list for one group).
- **`session-list-screen.tsx`** — `SessionListScreen({ useData = useMockSessionListData })`,
  the top-level screen: groups the snapshot, renders one `WorkspaceSection` per workspace, and
  an empty state when there are no sessions at all.
- **`index.ts`** — barrel export.

`packages/web/src/components/ui/badge.tsx` and `card.tsx` — added (shadcn "new-york" style,
matching `button.tsx`'s conventions); neither existed yet on `main`.

`packages/web/src/app/page.tsx` — now renders `<SessionListScreen />` instead of the scaffold
placeholder.

`packages/web/next.config.ts` — added a `webpack()` hook setting
`resolve.extensionAlias[".js"] = [".tsx", ".ts", ".js"]`. This was required, not optional: the
landed `packages/web/src/sync/reducer/index.ts` uses explicit `.js`-suffixed relative imports
against `.ts` source files (the standard `"moduleResolution": "bundler"` pattern — `tsc` and
`vitest` already resolve it fine). Nothing under `packages/web/src` had ever been imported
into the actual Next app tree before this task, so webpack's default resolver — which does
*not* map bare `.js` imports to `.ts`/`.tsx` files — never hit this. Importing the reducer from
`page.tsx` (via `mock-source.ts`) surfaced it as a hard `next build` failure
(`Module not found: Can't resolve './reduce.js'`); the alias fixes it for anything else under
`packages/web/src` that gets bundled by Next going forward, not just this feature.

## Design decisions / assumptions

- **Status derivation, in priority order** (highest first): terminal session-row state
  (`status === "failed"` → `failed`; `"archived"`/`"compacted"` → `completed`) → machine
  offline → pending permission (session- or subagent-scoped) → pending question (`attention
  === "question"`) → an open turn (`working`) → the last closed turn's outcome (`"failed"` →
  `failed`, unseen `"done"` attention → `completed`) → `idle`. Offline is checked before
  pending-permission: if the owning machine is down, nothing can act on an answer anyway, so
  "offline" is the more useful signal to surface. A failed turn stays `failed` regardless of
  seen/unseen — unlike a clean completion, an error is actionable until the user starts a new
  turn (FR-8.1 only calls out "completed-and-unseen" as an attention driver, not
  "failed-and-unseen", so a failure persists as a status rather than fading once viewed).
- **`attention` as an `Ephemeral`-shaped input, not a new invention.** `@falcon/wire`'s
  `Ephemeral` union already defines `t: "attention", kind: "perm" | "question" | "done" |
  "failed"` as a server-computed, never-persisted signal (design §4.3) — reusing its `kind`
  type (`AttentionKind = Extract<Ephemeral, {t: "attention"}>["kind"]`) keeps the derivation
  grounded in the landed wire contract instead of a bespoke shape, and gives a real
  `apiSocket`-backed source a type it already emits to plug straight in.
- **Injectable data source, no sync engine yet.** `apiSocket` and the sync engine
  (`P1-1.6-sync-engine`) aren't landed on `main`. Rather than block on them or duplicate their
  (unlanded) `QueryClient`-based design, `SessionListScreen` takes a `useData:
  UseSessionListSnapshot` prop defaulting to a static mock snapshot — the same seam
  `createSyncEngine`'s `SyncSocketSource` param uses on the sync-engine branch. A real
  `useSessionListSnapshot()` hook backed by TanStack Query + the sync engine satisfies this
  signature with no adapter needed once both land; swapping it in is a one-line change at the
  `<SessionListScreen useData={...} />` call site.
- **Decrypted view models, not raw wire rows.** `SessionListSession`/`SessionListMachine`/
  `SessionListWorkspace` carry plaintext `title`/`name` fields rather than embedding
  `SessionRow`/`MachineRow` with their `EncryptedBox` metadata columns. The crypto bridge that
  would decrypt those in a real pipeline already exists (`packages/web/src/crypto/`) but
  wiring it into this screen is out of this task's scope (a read-only screen against a mock
  source per the task brief) — a later task threading the sync engine through this screen is
  the natural place to also thread decryption through.
- **`SessionListStatus` is intentionally a separate type from `@falcon/wire`'s `SessionStatus`**
  (the `active/archived/failed/compacted` row enum) to avoid a name collision and because
  they're different concepts: one is what's stored on the row, the other is what's shown to
  the user, derived from it plus live signals.

## Testing

`pnpm build` / `pnpm typecheck` / `pnpm test` all pass across the monorepo (verified from a
fresh `pnpm install` in this worktree). New tests, all vitest (`environment: "node"` — no
DOM/component-render tests, matching the existing `button.test.ts` pattern of testing pure
logic rather than rendering):

- `status.test.ts` (14 cases) — every status transition above, including a pending permission
  nested three levels under a `Task`/subagent tool call, and that a resolved `perm-resolve`
  clears `waiting-for-permission` back to `working`.
- `group.test.ts` (5 cases) — grouping, per-group sort order, group-of-groups sort order, the
  ungrouped bucket (`workspaceId: null` and an unresolvable `workspaceId` both land there), and
  that an empty snapshot / a workspace with no sessions doesn't produce a stray group.
- `format-relative-time.test.ts` (3 cases).

`pnpm lint` (`biome check .`) is clean for every file this task touched (`--write` was run
scoped to just those paths to apply formatter/import-order fixes) — the full-repo `biome check
.` separately reports pre-existing errors in `packages/crypto` (non-null assertions, `any`)
that predate this task and are out of scope. Running `biome check .` through `pnpm lint`/`npx`
intermittently reported "Linter process terminated abnormally (possibly out of memory)" in
this environment even for `--version`; invoking the resolved binary directly
(`node_modules/.bin/biome`) was reliable and is what was used to verify and fix this task's
files — consistent with the transient-OOM note already in `CLAUDE.md`.
