# U4.5 — "pty-setmode" (W4.3 — flag-gated, version-coupled)

Fresh build (no prior commits on this branch — `git log v2-pty-injection..HEAD` was empty
at the start of this task).

## What landed

Real `setMode` for the PTY-injection path (`falcon claude`'s terminal-attached flow),
kept behind a flag on both the CLI and the web until it's been live-soaked, per
plan-v2.md W4.3.

### 1. Bridge `permission_mode` cache (`packages/cli/src/claude/pretoolPermissionBridge.ts`)

- `PreToolPermissionBridge` now caches the last-seen `permission_mode` off **every**
  `PreToolUse`/`PermissionRequest` hook input (both hooks carry it on every call) via
  a new private `cachePermissionMode()`, exposed as `currentPermissionMode` (getter).
  An unrecognized value is ignored rather than corrupting the cache.
- New `waitForModeEcho(timeoutMs)`: resolves with whatever mode is observed on the
  *next* hook input, or `null` on timeout — the "verify via hook echo" half of the
  design (there is no other channel to ask the live TUI its own mode).
- New exports: `PERMISSION_MODE_CYCLE` (the fixed 4-state order Shift+Tab cycles
  through — same order the pre-existing `ALL_MODES` already encoded, now named and
  exported for this purpose) and `permissionModeCyclePresses(from, to)` — forward-only
  press count around that cycle (0 when already there).
- `PermissionRequestHookInput` gained an explicit `permission_mode?: string` field
  (previously only implied by the doc comment / the index signature); `hookServer.ts`'s
  `PermissionRequestHookBodySchema` gained the matching optional zod field.
- `remotePermissionHook.ts`'s `RemotePermissionHookHandle` forwards both new bridge
  members as `getCurrentPermissionMode()` / `waitForModeEcho()`.

### 2. `sendModeCycle(n)` gated idle+no-prompt

- `InjectionController` (`injectionController.ts`) gained a public `canInjectNow`
  getter — the exact idle/no-prompt predicate `canInject()` already used internally,
  minus the queue-length check — so a caller can ask "would an injection happen right
  now" without needing a queued message. `canInject()` itself now delegates to it (no
  behavior change).
- `PtyClaudeSessionHandle` gained `sendModeCycle(presses): boolean`
  (`ptyClaudeSession.ts`): writes `presses` Shift+Tab keystrokes (`\x1b[Z`, xterm's
  back-tab) into the live PTY, gated by `controller.canInjectNow` — the identical rule
  message injection uses (mid-turn or into an open dialog is exactly as unsafe for a
  keystroke as for a message). Returns `false` (writes nothing) when the pty hasn't
  spawned, `presses <= 0`, or the gate is closed.

### 3. `setMode` RPC verify-via-hook-echo (`packages/cli/src/commands/start.ts`)

`runLocalPty`'s `setMode` handler (previously a permanent `{ok:false}`) is now real,
flag-gated behind `FALCON_PTY_SETMODE=1` (`PTY_SET_MODE_ENV_VAR`):

1. Flag off → `{ok:false}` (unchanged default behavior).
2. No `permission_mode` observed yet (bridge cache empty) → `{ok:false}` (can't compute
   a cycle blind).
3. Already at the requested mode → `{ok:true, observedMode: current}`, no keystrokes sent.
4. Otherwise: compute `permissionModeCyclePresses(current, mode)`, send it via
   `ptySession.sendModeCycle()`. If the gate was closed → `{ok:false, observedMode:
   current}`. If sent, await `waitForModeEcho()` (5s timeout,
   `PTY_SET_MODE_VERIFY_TIMEOUT_MS`): a matching echo → `{ok:true, observedMode}`; a
   mismatched echo or timeout → `{ok:false, observedMode: <best available>}`.

Wire: `SetModeResultSchema` (`packages/wire/src/rpc.ts`) gained an additive optional
`observedMode: PermissionModeSchema` field, checked against the additive-only wire
schema test (passes — adding an optional field is a compatible evolution).

### 4. Web re-enable behind flag

- `packages/web/src/lib/config.ts` gained `PTY_SET_MODE_ENABLED` (mirrors
  `NEXT_PUBLIC_FALCON_DEV_AUTH`'s existing pattern), read from
  `NEXT_PUBLIC_FALCON_PTY_SETMODE`.
- `ControlBar.tsx`'s `canMutateMode(controlMode, ptySetModeEnabled = false)` gained a
  second parameter (default `false` — every pre-U4.5 caller, including its own
  existing 1-arg tests, keeps its prior behavior). The component now calls
  `canMutateMode(controlMode, PTY_SET_MODE_ENABLED)`.
- `handleModeChange` now also handles a **resolved** `{ok:false}` (not just a thrown
  error) — reverts the selector to `result.observedMode ?? previous` and shows "Could
  not confirm the mode switch — reverted." This matters because a PTY `setMode` failure
  is a normal resolved value, never a throw; the pre-existing `onError`-only revert
  would have silently left the selector on the unconfirmed target otherwise.

## Deviations / notes for the reviewer

- **Design snippet interpretation**: plan-v2.md's W4.3 prose doesn't give an exact
  code snippet (unlike most other waves), just the design paragraph. I followed it
  literally: cache `permission_mode` off every hook input, gate the keystroke send with
  the same idle/no-prompt rule as message injection, verify via the next hook input's
  echo, revert the web UI on failure via the RPC's own reported `observedMode`.
- **`onModeChange` wiring not touched**: `remotePermissionHook.ts`'s `onModeChange`
  callback (fired when a *permission-answer* decision is `{kind:'mode'}`) is still not
  wired to `sendModeCycle` in `start.ts`'s PTY flow — that's a different feature (best-
  effort TUI sync for a mode chosen while answering a specific permission prompt, not
  the ControlBar's direct "change mode now" action) and isn't named in this unit's
  sub-tasks. Left as-is to avoid scope creep; flagged here in case a later unit wants it.
- **Lint tooling quirk (not a code issue)**: `pnpm lint` / `npx biome check .` both
  reliably fail in this worktree/sandbox with `[warn] Linter process terminated
  abnormally (possibly out of memory)` — reproduced on a full-repo run *and* on a
  15-file subset limited to just the files this task touched, so it isn't about the
  size of the changeset. Invoking the installed binary directly
  (`./node_modules/@biomejs/biome/bin/biome check .`, exit code 0) works fine and finds
  **zero** diagnostics in any file this task touched (127 pre-existing warnings + 1 info
  elsewhere in the repo, none in scope here). Ran `--write` via the direct binary once
  to apply four auto-fixes (import ordering in `pretoolPermissionBridge.test.ts`, plus
  formatter reflows in `start.test.ts`, `ControlBar.tsx`, `lib/config.ts`) — all
  re-verified clean afterward.
- `pnpm build` / `pnpm typecheck` / `pnpm test` all pass clean from the repo root
  (1381 CLI tests + 590 web tests + server/wire/crypto suites, all green). Two CLI
  tests (`index.test.ts`'s `--help`, `sessionRegistry.test.ts`'s webhook-persist test)
  flaked once mid-run under load and passed cleanly on immediate isolated re-run —
  pre-existing timing-sensitive tests neither touched nor caused by this change.
