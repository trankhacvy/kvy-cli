# P0-0.4-auth-challenge-route — POST /v1/auth Ed25519 challenge/response + account upsert

Adds the `POST /v1/auth` route to `@falcon/server`: a near-verbatim port of Happy's
`authRoutes.ts` `POST /v1/auth` handler (`happy/packages/happy-server/sources/app/api/
routes/authRoutes.ts` lines 8–39) — verify an Ed25519 signature over a client-generated
challenge, upsert the `accounts` row keyed by the hex-encoded sign public key, mint a
JWT via the existing auth module's `mintToken()`.

## Worktree setup

This task's own prerequisites (accounts table from `P0-0.4-drizzle-schema`, JWT/token
cache from `P0-0.4-auth-module`) were complete but unmerged in sibling worktrees, and
those two branches diverge from each other (different parents off `main`). Per the task
instructions, I did **not** redo either: created branch `P0-0.4-auth-challenge-route`
off `P0-0.4-drizzle-schema`, then `git merge P0-0.4-auth-module` into it (three
conflicts — `CLAUDE.md`, `packages/server/src/config.ts`, `config.test.ts` — all
mechanical union-of-both-branches resolutions: `config.ts`'s `EnvSchema` keeps both
`DATABASE_URL` and `FALCON_MASTER_SECRET`/the production-secret `.refine()`; `config.
test.ts` keeps both branches' assertions in the shared "defaults"/"fully-specified" test
cases). Merge commit `c86161a`. Worktree then had both the `accounts` table and
`mintToken`/`authPlugin` available, and I added only the route + its test on top.

## Implementation notes

- **Verification**: `tweetnacl.sign.detached.verify(challenge, signature, publicKey)`,
  exactly like Happy's handler — after `@falcon/crypto`'s `decodeBase64` decodes the
  three base64 request fields. `@falcon/crypto` doesn't export a verify function (its
  `authChallenge` is the *client-side* generator — given a secret, mint a fresh keypair,
  a random 32-byte challenge, and sign it; see `packages/crypto/src/encryption.ts:280`),
  and its own test suite verifies with `tweetnacl` directly rather than a package export
  (`packages/crypto/src/__tests__/encryption.test.ts:184`) — I followed that precedent
  instead of adding a new crypto-package export for a one-line call. `tweetnacl` and
  `@falcon/crypto` (for `decodeBase64`) are now direct `@falcon/server` dependencies.
- **`tweetnacl.sign.detached.verify` throws** (doesn't return `false`) on a
  wrong-length signature/key, unlike Happy's original code, which doesn't guard this —
  a malformed request would 500 in Happy. I wrapped the call in try/catch, treating any
  throw as an invalid signature (401), matching this codebase's established "unwrap
  never throws / no silent failures" convention (`tokens.ts`'s `verifyToken` does the
  same collapse-to-null-on-any-failure). This is the one deliberate behavioral delta
  from a strict verbatim port.
- **`contentPublicKey` — the other necessary delta.** Happy's original endpoint only
  ever handled one key (Ed25519 identity). Falcon's `accounts` table (already merged
  from `P0-0.4-drizzle-schema`) has `contentPubKey` as `NOT NULL` with no default —
  required at row-creation time — because Falcon's key hierarchy always derives both a
  sign key and a content (X25519) key together from `masterSecret` (design §5.1). I
  could not satisfy that constraint from a request shaped like Happy's, and the task
  explicitly said not to touch the already-merged accounts table, so I extended the
  request body with a `contentPublicKey` field (base64), stored on `accounts.
  contentPubKey`. It's re-sent (and re-written) on every login, not just account
  creation, which also means a device can rotate its content key without a separate
  endpoint. This is the one place I departed from a literal byte-for-byte port of
  Happy's request shape — noted here since the task labeled this bullet "(V) verbatim".
- **Upsert**: `db.insert(accounts).values({signPublicKey, contentPubKey}).
  onConflictDoUpdate({ target: accounts.signPublicKey, set: { contentPubKey } })
  .returning()`. Idempotent by construction — a second request with the same
  `signPublicKey` updates (not duplicates) the row and returns the same `id`, so the
  same account always gets the same JWT subject.
- **`db` is dependency-injected, not imported as the module singleton.** `buildAuthRoutes
  (db: PgDatabase<any, any>)` is a factory; `server.ts`'s `buildServer()` now accepts an
  optional `{ db }` in a second `deps` argument, defaulting to the existing `db/client.ts`
  singleton — so every existing caller (`main.ts`, `server.test.ts`) is unaffected. This
  exists purely to make the route testable against a real (but in-memory) Postgres
  without touching `DATABASE_URL`/module-cache tricks. The db parameter type erases both
  `PgDatabase` generics to `any` — `insert(accounts)` typing comes from the `accounts`
  table import itself, not from either generic, so nothing is lost, and it lets both
  `PostgresJsDatabase` (production) and `PgliteDatabase` (tests) satisfy the same
  parameter without a driver-specific union type.
- **Route file location**: `packages/server/src/app/routes/auth.ts`, per the task's
  explicit path — a new `routes/` sibling to the existing `api/` (where `health.ts`
  lives). Health is a liveness probe; `routes/` is where the task asked this to live,
  and matches where sibling future tasks (sessions, pairing) will likely land per
  `plan.md`.

## Testing — in-memory Postgres, no Docker/network dependency

The task asked for an integration test proving idempotent upsert + valid JWT on repeat.
There's no Postgres-backed test infrastructure in the repo yet (`docker-compose.dev.yml`
is a separate, still-unmerged task; CI has no Postgres service). Rather than skip the
integration test or add a hard Docker/CI dependency, `auth.test.ts` uses
`@electric-sql/pglite` (WASM-embedded real Postgres) via `drizzle-orm/pglite`, migrated
with the *same* generated SQL that ships to production (`packages/server/drizzle/
0000_thin_synch.sql`, resolved relative to the test file via `import.meta.url`). This is
a real integration test against the real Postgres dialect/migration — not a mock — and
runs identically in CI and locally with no extra services. Added as a `devDependency`
only (not shipped). Three tests, all against one `buildServer({logger:false}, {db})`
instance built with the PGlite-backed `db`:
1. a tampered challenge (signed bytes ≠ the challenge field sent) → 401 `{error:
   "Invalid signature"}`.
2. a fresh `signPublicKey` → 200, `success: true`, and a token that
   `verifyToken()` resolves to a real `accountId`.
3. **the task's explicit scenario**: the exact same signed request posted twice → both
   200 with valid, verifiable tokens whose `accountId`s are equal, and a direct
   `db.select().from(accounts).where(eq(accounts.signPublicKey, ...))` query confirms
   exactly one row exists for that key.

## Assumptions

- `contentPublicKey` (see above) is required on every request, not only account
  creation — simplest single-endpoint shape consistent with both Happy's one-request
  flow and Falcon's two-key account model; no separate `/v1/auth/register` vs.
  `/v1/auth/challenge` split (those are explicitly separate, later plan.md bullets:
  OAuth sign-in and pairing).
- Stored `contentPubKey` as the raw base64 string the client sends (no re-encoding),
  matching the convention already used for `pairRequests.ephPub` ("base64") rather than
  the hex convention the schema comment calls out specifically for `signPublicKey`.
- No rate limiting on this route — `plan.md` §16 lists "Rate limits on auth + ingest"
  as a separate Phase 1 bullet (§4.3), not part of this task.
- No replay/nonce tracking of challenges (the server never sees a challenge twice
  server-side, has nothing to check it against) — this matches Happy's actual behavior
  verbatim; the "challenge" here is a self-generated, self-signed proof of key
  possession, not a server-issued nonce.
