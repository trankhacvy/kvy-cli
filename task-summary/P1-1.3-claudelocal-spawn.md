# P1-1.3-claudelocal-spawn — Port claudeLocal.ts (Claude Code local-mode spawn wrapper)

## Task

plan.md §16 "1.3 CLI skeleton + local mode" (line 679): "`claudeLocal.ts` port: spawn
w/ `stdio ['inherit','inherit','inherit','pipe']`..." + falcon-plan.md §3.2's five
numbered items. Port `happy/packages/happy-cli/src/claude/claudeLocal.ts` (plus its
small `utils/claudeFindLastSession.ts` + `utils/claudeCheckSession.ts` helpers,
folded in) to `packages/cli/src/claude/claudeLocal.ts`.

## What was built

`packages/cli/src/claude/claudeLocal.ts` — exports `claudeLocal(opts, deps)`, plus
`ExitCodeError`, `FALCON_SYSTEM_PROMPT`, and `findLastLocalSession`. Covers all five
falcon-plan.md §3.2 items:

1. **stdin O_NONBLOCK fix** (verbatim, per plan.md's "port these verbatim" instruction
   for this specific item) — `forceStdinBlocking()` calls
   `(process.stdin as any)._handle.setBlocking(true)` right before spawn, guarded by a
   `typeof === 'function'` check and try/catch, exactly mirroring Happy's comment and
   logic (the comment in the source IS the documentation, kept verbatim).
2. **Spawn shape** — `cross-spawn`'s `spawn("node", [launcherPath, ...args], { stdio:
   ['inherit','inherit','inherit','pipe'], signal: abort, cwd, env, windowsHide: true
   })`. `cwd`/`env` (merged `process.env` + `opts.claudeEnvVars`) and the caller's
   `AbortSignal` are wired straight through.
3. **Session-flag interception** — `resolveSessionFlags()` extracts `--session-id
   <uuid>`, `--resume [id]`/`-r [id]`, `--continue`/`-c` from a *copy* of
   `opts.claudeArgs` (the caller's array is never mutated) via a ported `extractFlag`
   helper, then re-injects the flag Claude Code actually understands (`--resume <id>`
   or `--session-id <id>`). "Falcon's own session registry" is Claude Code's own
   on-disk transcript directory for the working directory (`findLastLocalSession`,
   reusing the already-merged `getProjectPath` from `scanner.ts` rather than
   duplicating it) — mirrors Happy's `claudeFindLastSession`/`claudeCheckSession`
   (UUID-shaped session ids only, must contain ≥1 real message entry).
4. **Injections** — `--append-system-prompt <FALCON_SYSTEM_PROMPT>` always; `--settings
   <hookSettingsPath>` when the caller supplies one (wired to the already-merged
   `hookServer.ts`'s `writeHookSettingsFile(...).path` — this module takes the path as
   a plain string, it does not call `writeHookSettingsFile` itself).
5. **Thinking state machine** — reads fd 3 (`child.stdio[3]`) via `readline`, parses
   `fetch-start`/`fetch-end` JSON lines into an `activeFetches` `Set<number>`,
   flips `thinking` true immediately on any active fetch, false after a 500ms debounce
   once the set drains to empty (cleared/restarted if a new fetch arrives mid-debounce);
   force-resets to `false` on child exit.

Exit-code/signal handling (Happy's exact semantics): `SIGTERM` while
`opts.abort.aborted` → clean resolve (the mode-switch/shutdown path terminates the
child this way on purpose); any other signal → reject; non-zero/non-null exit code →
reject `ExitCodeError`; `code === 0` → resolve. Returns the effective session id:
resumed/explicit/minted id in offline mode, or `null` in hook mode for a fresh session
(the hook server's own `onSessionId` callback — not this function — reports the real
id asynchronously).

`packages/cli/src/claude/claudeLocal.test.ts` (23 tests, all mocking the spawned
child — **no real Claude CLI required**): stdin-blocking-before-spawn +
resume-after ordering, spawn argv/stdio/cwd/env/signal shape, `--append-system-prompt`
injection, every session-flag path (`--session-id`, `--resume <id>`, `-r <id>`, bare
`--resume` deliberately left for Claude Code's own picker — see below, `--continue`,
no-flags-mints-new-UUID, prior `opts.sessionId` reused), hook mode (`--settings`
injected, `onSessionFound` never called directly, `--resume` only added when a prior
session is known), all four exit/signal branches, and the fd3 thinking-state machine
(immediate on, debounced off, debounce-reset on new fetch mid-window, forced off on
exit, non-JSON lines ignored) using `vi.useFakeTimers()`.

## A behavioral note worth flagging: bare `--resume`/`-r` never triggers a
`findLastSession` lookup

Happy's own `extractFlag(['--resume','-r'], withValue: true)` only returns
`found: true` when the flag is immediately followed by a non-flag-looking value; a
*bare* trailing `--resume` (nothing after it, or another flag right after) returns
`found: false` and is left untouched in the args array, then passed straight through
to Claude Code, which shows its own interactive resume picker. This is what Happy's
code actually does (verified by tracing `extractFlag`), even though the file's own
comment ("`--resume / -r`: Resume last session ... but we handle") reads as if it
resolves against the last session. plan.md/falcon-plan.md write the flag as
`--resume [id]` (id in brackets, i.e. optional), which could be read either way. I
ported the **actual code behavior** (bare flag → Claude's own picker), not the
arguably-aspirational comment, since:
- the Appendix fidelity table marks this file "port (keep setBlocking fix)", not
  fully verbatim, but porting a *different* behavior than what the reference
  actually does isn't a "port" either;
- falcon-plan.md's own goal for this item is "`falcon --resume` behaves exactly like
  `claude --resume`" — and `claude --resume` (bare) already shows an interactive
  picker, so passing it through unresolved achieves that goal correctly.

If product intent is actually "bare `--resume` picks Falcon's last known session
automatically," that's a one-line change to `resolveSessionFlags()` (call
`extractFlag` with `withValue: false` first as a fallback) — flagging it here rather
than guessing silently.

## Explicitly out of scope / integration gaps (documented, not faked)

- **`deps.launcherPath` is caller-supplied, not resolved here.** The launcher script
  (`falcon_claude_launcher.cjs`) is a separate, still-unmerged plan bullet
  (`.worktrees/P1-1.3-claude-launcher-script`). This module treats its path as a given
  string rather than re-deriving package-root-relative resolution logic that belongs
  to whichever module wires `claudeLocal()` up for real (`index.ts`/`loop.ts`, a later
  task) — avoids duplicating that resolver and avoids a `import.meta.url`-depth
  mismatch between running from `src/claude/` (2 levels deep) vs. a pkgroll-bundled
  single-file `dist/index.mjs` (1 level deep).
- **`deps.findLastSession` defaults to the real fs-based `findLastLocalSession`** but
  is injectable — tests never touch the real filesystem.
- **No `cliLocator.ts` dependency.** `cliLocator.ts` (`.worktrees/P1-1.3-cli-locator`)
  resolves the *real* Claude CLI binary; that resolution happens inside the launcher
  script (a stub today per its own header comment, to be replaced by `cliLocator` at
  integration time), not in `claudeLocal.ts`. This file only ever spawns `node
  <launcherPath>`.
- **No hook-server startup, `writeHookSettingsFile` call, or metadata CAS update
  here.** `hookServer.ts` (already merged on `main`) owns starting the loopback
  server and generating the settings file; `claudeLocal.ts` only accepts the resulting
  `hookSettingsPath` string and injects `--settings <path>`.
- **No `--mcp-config`/`--allowedTools`/sandbox integration** (Happy has both) — neither
  is part of Falcon's current design surface per falcon-plan.md §3.2's five-item scope;
  not ported.
- **Full local-mode integration test** (actually spawning the launcher +
  `cliLocator`-resolved Claude CLI end-to-end) needs both `P1-1.3-claude-launcher-script`
  and `P1-1.3-cli-locator` landed on `main` first — today `claudeLocal.ts` and both are
  unmerged siblings. Flagging per the task's request: **this task needs the launcher
  and cliLocator worktrees landed to be fully integration-tested**, though it is
  independently unit-tested (mocked spawn) and builds/typechecks against `main` as-is.

## Dependency added

- `cross-spawn@^7.0.6` (dependency) + `@types/cross-spawn@^6.0.6` (devDependency) in
  `packages/cli/package.json` — used specifically so `node` resolves correctly on
  Windows (`.cmd` shim resolution), matching Happy's own rationale for using it over
  `node:child_process`'s `spawn` directly.
