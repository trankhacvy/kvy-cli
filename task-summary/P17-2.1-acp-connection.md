# P17-2.1-acp-connection — `cli/src/acp/acpConnection.ts`

Section: plan.md §16 "17. v2 — ACP migration / Phase 2.1 — ACP core", first bullet.
Design authority: `falcon-system-design.md` §7.3 (single `AcpRemote`), §7.4 (Claude via
`claude-agent-acp`), §7.9 (adapter manager), §7.10 (send claim). Porting reference:
mobvibe's `apps/mobvibe-cli/src/acp/acp-connection.ts`.

## What landed

- `packages/cli/src/acp/acpConnection.ts` — the `AcpConnection` class: the ACP transport
  core over NDJSON stdio, standalone (not yet wired into `claudeRemoteLauncher.ts` —
  that's Phase 2.2). Spawns the managed adapter child through the already-landed adapter
  manager's verify-before-spawn seam (`resolveAdapterSpawn`, `../adapters/spawn.ts`) —
  never touches `node_modules` paths directly, never `npx`, no adapter-manager
  duplication. Drives it with `@agentclientprotocol/sdk`'s `client()` builder.
  Implements every item plan.md's bullet lists:
  - `initialize` handshake declaring client capabilities with `fs` unset entirely and
    `terminal: false` (design: "no fs, no terminal initially"). There are no
    `readTextFile`/`writeTextFile`/`createTerminal`/etc. methods on the class at all —
    the fs/terminal client-request-handler surface mobvibe's version has is dropped
    wholesale, not merely disabled.
  - `session/new`, `session/load`, `session/resume` (`createSession`/`loadSession`/
    `resumeSession`) — provider-agnostic: they take a plain optional `meta` param the
    caller populates, rather than hardcoding Claude's `_meta.systemPrompt`/
    `_meta.claudeCode.options.resume` shape here (that wiring is Phase 2.2's job, in
    `claudeRemoteLauncher.ts`). `loadSession`/`resumeSession` gate on the agent's
    advertised `AgentCapabilities` (`supportsSessionLoad()`/`supportsSessionResume()`)
    and throw a clear error rather than letting an unsupported call silently no-op.
  - `session/prompt` — **exactly one in flight per session**: a `Map<sessionId,
    AbortController>` throws if `prompt()` is called again for a session that already
    has one outstanding (a departure from mobvibe's `Set<AbortController>`, which
    tolerates several concurrent turns per session — ACP only allows one; called out
    explicitly in the plan.md bullet). The request's `cancellationSignal` is wired to
    that same controller.
  - `session/cancel` (`cancel()`) — aborts the tracked controller (cooperative:
    sends `$/cancel_request` via the SDK, doesn't itself settle the pending promise)
    *and* sends the explicit `session/cancel` notification, matching mobvibe's
    belt-and-suspenders approach.
  - `session/set_mode` (`setMode()`).
  - `session/request_permission` handler seam (`setPermissionHandler`/
    `PermissionRequestHandler`) — defaults to auto-`{outcome:{outcome:'cancelled'}}`
    when unset; a later task wires it to the §7.6 permission pipeline. Inbound `_meta`
    is bounds-checked before reaching the handler.
  - Session-update listener registered *before* session creation (structurally
    guaranteed — the SDK's `client()` builder requires every `.onNotification`/
    `.onRequest` handler before `.connect()`, and `session/new` only happens after
    `connect()` resolves) **with pre-ready buffering**: `session/update` notifications
    are buffered internally until the connection's own caller makes its first
    `onSessionUpdate()` call (protecting against the real race — an update arriving
    between `createSession()` resolving and the caller's next tick, before it's had a
    chance to subscribe), then flushed in order and delivered live from then on. Capped
    at 500 buffered entries with a warned drop-oldest past that, so a connection nobody
    ever subscribes to can't leak memory unboundedly.
  - Stderr ring buffer (last 20 non-blank lines) attached to every connect failure,
    adapter-unavailable refusal, and unexpected post-ready close/exit
    (`AcpConnectionError.stderrTail`, folded into `.message` too) — design §7.4: "Adapter
    stderr is ring-buffered and attached to connect/exit errors so spawn failures
    surface legibly."
  - Cheap `_meta`-bounds check (`boundMeta`): a single serialized-byte-size cap (16 KiB)
    applied to inbound `session/update` and `session/request_permission` `_meta`
    payloads — the one piece of mobvibe's much larger `sanitizeAcpMessageMeta`/
    `sanitizeAcpMeta` (a full bounded recursive JSON-clone walker with per-key/array/
    depth limits) the task description asked to keep. Drops (never throws on)
    anything that isn't serializable/oversized, logging once via the injected `Logger`.
  - `AcpConnectionOptions.execPath`/`AcpConnectionDeps.execPath`,
    `AcpConnectionDeps.resolveSpawn`, `AcpConnectionDeps.spawn` — full seam parity with
    the codebase's existing `SpawnFn`-injection convention (`daemon/processLauncher.ts`).
    `resolveSpawn` defaults to the real `resolveAdapterSpawn`; `spawn` defaults to plain
    `node:child_process`'s `spawn` (no `cross-spawn` needed — the adapter manager's own
    spawn spec's `command` is always `process.execPath`, never a shell command needing
    Windows `.cmd` shim resolution).
- `packages/cli/src/acp/index.ts` — barrel, matching `adapters/index.ts`'s convention.
- `packages/cli/src/acp/__fixtures__/fakeAcpAdapter.cjs` — a standalone, dependency-free
  fake ACP adapter child (hand-rolled NDJSON JSON-RPC, no `@agentclientprotocol/sdk` of
  its own) so the test suite spawns and talks to a *real* child process over real stdio
  pipes — not just a mocked SDK object — exactly as `AcpConnection` would talk to a real
  `claude-agent-acp`/`codex-acp` install. Behavior is selected via `FAKE_ACP_MODE`
  (`normal`, `crash-on-init`, `crash-after-ready`, `huge-meta`, `permission-request`,
  `slow-prompt`) so one small script covers every scenario the suite needs. Plain
  CommonJS (`.cjs`) rather than ESM, since it's written to disk at the exact
  `dist/index.js`-shaped path `ADAPTER_MANIFEST`'s `binEntry` expects, with no
  `package.json` alongside to mark it `"type": "module"`.
- `packages/cli/src/acp/acpConnection.test.ts` — 20 tests, all against the real spawned
  fixture (via the *real* `resolveAdapterSpawn`, by installing the fixture at the exact
  path the adapter manager's own verify step expects — no spawn-seam bypass in the
  common-path tests): connect success/failure (including "adapter not installed" and
  "adapter crashes before responding to `initialize`" with stderr-tail assertions),
  idempotent reconnect, session create/load/resume + capability gating, prompt resolve/
  one-in-flight-per-session/cancel, `setMode`, pre-ready session-update buffering (both
  "buffered then flushed" and "already subscribed, delivered live"), the `_meta` bounds
  check dropping an oversized blob while still delivering the rest of the update, the
  permission-request seam's default-cancel and injected-handler paths, and post-ready
  crash surfacing via `onError` (plus confirming a deliberate `disconnect()` does *not*
  fire `onError`).
- `packages/cli/package.json` — added `"@agentclientprotocol/sdk": "^1.2.1"` (matching
  mobvibe's own pin; `1.2.1` is also the latest version on the registry as of writing).
  Its `zod` peer dependency (`^3.25.0 || ^4.0.0`) is already satisfied by the workspace's
  existing `zod@^4.0.0`.

## Key implementation notes / deviations from mobvibe

- **SDK API surface differs from mobvibe's own pin.** mobvibe imports `ClientConnection`
  from `@agentclientprotocol/sdk` and calls `client({name}).onRequest(...).onNotification
  (...).connect(stream)` — this exact shape is present and used unchanged in `1.2.1`
  (verified against the real installed package's `.d.ts`, not assumed from mobvibe's
  source). `methods.agent.session.*`/`methods.client.session.*` string-constant tables,
  `RequestError`, `PROTOCOL_VERSION`, and `ndJsonStream(output, input)`'s parameter order
  (first param is the *writable* side the SDK encodes NDJSON *into* — i.e. our child's
  stdin; second is the *readable* side it decodes *from* — the child's stdout) were all
  confirmed directly against the installed `.d.ts` files rather than assumed.
- **No auto-connect.** Unlike mobvibe's `ensureReady()` (which transparently calls
  `connect()` if not ready), every session/prompt/cancel/etc. method here throws a plain
  `"ACP connection is not ready — call connect() first"` if called before `connect()`
  resolves. Deliberate simplification matching the project's "no silent failures"
  principle over mobvibe's convenience-first auto-reconnect.
- **No fs/terminal capability handlers at all**, not merely `false` flags — mobvibe's
  `readTextFile`/`writeTextFile`/`createTerminal`/`getTerminalOutput`/
  `waitForTerminalExit`/`killTerminal`/`releaseTerminal` (~350 lines with symlink/atomic-
  write/path-containment hardening) are entirely absent from this port, per the task's
  explicit instruction.
- **No session/list, session/close, session/delete, authenticate/logout.** Out of scope
  per plan.md's bullet list (only `new`/`load`/`resume`/`prompt`/`cancel`/`set_mode`/the
  permission seam are named); adding them would have been scope creep beyond what this
  task or its immediate Phase 2.2 consumer needs.
- **Error model simplified to one class** (`AcpConnectionError`, message + optional
  `stderrTail`) instead of mobvibe's `ErrorDetail`/`ErrorScope`/`ErrorCode`/`AppError`
  taxonomy — Falcon's CLI has no existing convention for that (checked; nothing similar
  exists anywhere else in `packages/cli` or `packages/wire`), and inventing one wasn't
  this task's job.

## Assumptions

- `@agentclientprotocol/sdk@^1.2.1` is the correct SDK version to pin (matches mobvibe's
  own dependency; `1.2.1` is also the latest published version). Not added to
  `ADAPTER_MANIFEST` (that manifest pins the *adapter packages*, e.g.
  `@agentclientprotocol/claude-agent-acp` — a different, already-landed concern; the SDK
  itself is a `dependencies` entry like any other library).
- `AcpConnectionOptions.clientInfo` is caller-supplied rather than hardcoded to a
  `"falcon"` constant, since this module doesn't know its own package version and
  shouldn't guess — Phase 2.2's `claudeRemoteLauncher.ts` integration will pass the real
  Falcon CLI name/version.
- `createSession`/`loadSession`/`resumeSession` accept an optional `meta` param
  (`Record<string, unknown> | null`) rather than a typed Claude-specific shape, keeping
  this module provider-agnostic per design §7.3's "single `AcpRemote` … shared by every
  provider" — Claude's `_meta.systemPrompt`/`_meta.claudeCode.options.resume` payload
  construction belongs to Phase 2.2, not here.
