## What W3.7 actually needed (grounded against the real code, not just the
## plan snippet)

The plan's pseudocode (`reattachSession(deps, { sessionId, contentKeyPair })`)
implied a network fetch of the existing row. There is no `GET
/v1/sessions/:id` route on the server (only `POST /v1/sessions`
create-or-get and the full-account `GET /v1/sync` snapshot), and adding one
was out of scope for a CLI-only unit. Tracing the actual
`FALCON_RECONNECT_*` contract `daemon/resumeSession.ts` already defines
(`buildReconnectEnv`) showed the wrapped DEK travels via
`FALCON_RECONNECT_ENCRYPTION_KEY` already — the same wrapped-DEK shape
`bootstrapSession`'s existing idempotent-replay path already knows how to
unwrap with the caller's `contentKeyPair.secretKey`. So the re-attach is a
pure local unwrap, no network call at all, which is strictly better than the
plan's literal snippet (no dependency on a not-yet-built server route). Noted
as an adaptation, not a deviation from intent.

## Sub-task 1 — bootstrap.ts / start.ts / resumeSession.ts

- **`session/bootstrap.ts`**: `BootstrapSessionParams` gained an injectable
  `env?: NodeJS.ProcessEnv` (defaults to `process.env`, matching this
  package's existing injectable-env convention). `bootstrapSession()` now
  checks `FALCON_RECONNECT_SESSION_ID` first; when set, it calls the new
  `reattachSession()` helper, which unwraps `FALCON_RECONNECT_ENCRYPTION_KEY`
  (base64 wrapped DEK) with `contentKeyPair.secretKey` and returns `{
  sessionId, dek, tag: "", created: false }` — no `POST /v1/sessions` call.
  Throws honestly (no silent failures, matching the module's existing
  stance) when `FALCON_RECONNECT_SESSION_ID` is set without the encryption
  key, or when the DEK can't be unwrapped. `tag: ""` on this path is
  deliberate and harmless — grepped every caller; only `bootstrap.test.ts`
  asserts on `tag`, and only on the create/replay paths, never the reattach
  path.
- **`commands/start.ts`**: `bootstrapSession()`'s call site now passes
  `env` through in `params` (so the reattach check above actually sees it).
  The terminal PTY flow's `startPtyClaudeSession()` call now passes
  `providerSessionId: env.FALCON_RECONNECT_PROVIDER_SESSION_ID ?? null`
  instead of the hardcoded `null` — `resolveSessionFlags`/
  `ptyClaudeSession.ts` (`:341-352` per the plan, confirmed unchanged in the
  real file) already compose `--resume <id>` from this field, so this is the
  only wiring needed for the terminal flow to resume the provider transcript
  once a caller sets that env var ahead of the spawn. Both reads are
  no-ops (empty string / `null`) on an ordinary fresh start, and the module
  doc comment at the top of `start.ts` now documents the contract.
- **`daemon/resumeSession.ts`**: no behavior change (confirmed correct on
  inspection: this module always relaunches with `--starting-mode remote`
  because the daemon genuinely has no controlling TTY to hand a re-spawned
  process). Added a doc comment directly above the `--starting-mode remote`
  args composition making the headless-vs-terminal decision explicit and
  pointing at the two other files above for the terminal case — so a future
  reader doesn't "fix" this into a conditional by mistake. This *is* the
  "headless-vs-terminal decision" sub-task: the decision was to document,
  not to branch, since branching here is impossible (no TTY available) and
  the terminal case is a different call path entirely
  (`commands/start.ts`'s PTY flow, already covered above).
- Note: `resumeSession.ts`'s `PersistedSession` has no `providerSessionId`
  field (only an opaque `metadata` blob), so the daemon's own resume path
  cannot set `FALCON_RECONNECT_PROVIDER_SESSION_ID` yet — that's an honest
  gap, not silently papered over, and is out of scope here (would need a
  metadata schema decision belonging to a different task, per this
  codebase's existing "workspace registration is separate work" precedent
  for similar seams).
