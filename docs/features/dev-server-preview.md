# Live dev-server preview via secure tunnel (docs/competitive-notes-omnara.md #6)

**Slug:** `dev-server-preview` · **Branch:** `wf/feature-dev-server-preview` · **Target:** `v2-pty-injection`

## Feature description

Live dev-server preview via secure tunnel. The "Preview" tab auto-detects open local ports ("14 ports detected · 0 tunnels active") and, given a port, opens a Cloudflare tunnel so the running dev server is viewable remotely, embedded directly in the dashboard — no manual ngrok/tunnel setup.

## Solution (Opus 4.8)

Feature #6 "Live dev-server preview via secure tunnel" is a NEW machine-RPC family plus a daemon-managed long-lived child-process subsystem plus a web "Preview" tab. It splits cleanly into two capabilities the Omnara UI shows: (a) "14 ports detected" — enumerate the machine's listening TCP ports; (b) "0 tunnels active" + "given a port, open a Cloudflare tunnel" — spawn/track/kill `cloudflared` and return the public URL, embedded in the dashboard.

The whole thing fits the codebase's dominant pattern almost mechanically. Every daemon capability the web needs is a machine-scoped RPC registered in `packages/cli/src/daemon/machineRpc.ts` (`m:<machineId>:<method>`), backed by a small injectable-deps handler module (model: `gitStatus.ts`/`githubChecks.ts`/`slashCommands.ts`), typed on both sides via a paired Zod params/result schema in `packages/wire/src/rpc.ts`, mirrored caller-side in `packages/web/src/sync/machineRpc.ts`, and consumed by a web feature folder with the `live-actions.ts` vs `mock-source.ts` seam (model: `features/git-diff/`, `features/repo-files/`). Crucially, the wire protocol ALREADY reserves the `preview:*` namespace exactly for this (reserved.ts, design §14 "Deferred-Feature Hooks", design line 48 "preview namespaces exist in the schema now"), so this is shipping a designed-for-deferred feature, not inventing one.

Proposed RPC surface (four methods, `preview.*`):
- `preview.ports` (read-only) — lists listening TCP ports on the machine. Handler `portScan.ts` shells out to `lsof -nP -iTCP -sTCP:LISTEN` (macOS/Linux only, same platform caveat as `processScan.ts`) and parses pid/port/process-name/command. No idempotency cache (pure read, same group as `git.status`/`fs.list`).
- `preview.tunnels` (read-only) — lists this machine's currently-active tunnels (port → public URL → status). Reads the tunnel registry.
- `preview.open` (mutating, side-effecting) — given a port, spawn a `cloudflared tunnel --url http://localhost:<port>`, parse the assigned `*.trycloudflare.com` URL from cloudflared's stderr, register it, return the URL. MUST carry `idempotencyKey` and use `withIdempotencyCache` keyed additionally by a per-port guard (mirror `adopt.take`'s `withProviderSessionGuard` resource-keyed in-flight map, keyed on `port`) so two concurrent "open" clicks for the same port collapse into one tunnel rather than spawning two.
- `preview.close` (mutating) — kill the cloudflared child for a port/tunnelId, deregister. Idempotent (closing an already-closed tunnel is a no-op), so it can skip the cache like `fs.mkdir`, but carries the key for uniformity.

The tunnel processes are long-lived daemon-managed children — the ONE genuinely new subsystem, not a clone of an existing handler. The precedent to follow is the session-tracking pair `sessionRegistry.ts` (in-memory pid→record map wired into the control server) + `sessionsStore.ts` (durable `~/.falcon/*.json` with tmp-write+rename, write-queue, expiry): build a `tunnelRegistry.ts` (port/tunnelId → {cloudflared pid, url, startedAt, status}) and decide whether it needs a durable store (see risks — I lean toward in-memory-only for MVP so a daemon restart cleanly drops tunnels rather than resurrecting stale URLs). Child spawn/kill reuses `processLauncher.ts`/`kill.ts` (SIGTERM→SIGKILL escalation). `doctor.ts` gains a cloudflared-health section alongside its existing adapters/providers sections.

Web side: a `packages/web/src/features/preview/` folder (a `PreviewPanel` with a ports list — "N ports detected · M tunnels active" header copy straight from Omnara — an Open/Close button per port, and the embedded live view), a `/session/[id]/preview/` route linked from the timeline header like the git panel's "Files changed" button, `use-preview-panel.ts` with two TanStack Query reads (`preview.ports`, `preview.tunnels`) plus open/close mutations, and the `UsePreviewActions` injectable seam (`live-actions.ts` = `machineRpcToPreviewActions` vs `mock-source.ts`), exactly matching `use-git-panel.ts`.

CRITICAL BLOCKER for "embedded directly in the dashboard": the web app's CSP (deploy/web/default.conf.template line 33) has NO `frame-src` directive, so it inherits `default-src 'self'` and `frame-ancestors 'none'` + `X-Frame-Options: DENY`. A `*.trycloudflare.com` iframe is currently hard-blocked. Embedding requires adding `frame-src https://*.trycloudflare.com` (or the chosen tunnel domain) to the CSP — a deliberate loosening of an intentionally strict, security-reviewed header. This is the single biggest design decision and must be surfaced to the planning pass, not silently chosen. The honest fallbacks are: (1) open the tunnel URL in a new browser tab (no CSP change, loses the "embedded" UX Omnara has); (2) add the narrow `frame-src` allowance and embed; (3) proxy the preview through the API origin (heavy, defeats the point of a direct tunnel). The self-host deploy also templates its CSP via nginx, so any allowance has to flow through `deploy/web/default.conf.template` + `docker-entrypoint.sh` env, not just Next config.

cloudflared is a Go binary, NOT an npm package — so the pinned-manifest npm-install adapter manager (`packages/cli/src/adapters/`) does NOT directly apply, even though it's the natural-looking precedent for "Falcon manages an external binary." Three real options for the planning pass: (a) require the user to install cloudflared themselves and just detect it on PATH (simplest, honest, mirrors how provider CLIs are detected via `ProviderAdapter.detect()`); (b) use the `cloudflared` npm wrapper package that downloads the platform binary on install (fits `~/.falcon/` prefix but adds a network-download-at-install step and a supply-chain surface the manifest's integrity-pinning was built to avoid); (c) Falcon downloads+checksums the binary itself into `~/.falcon/bin/` (most control, most new code). The `doctor.ts`/`adapters` health-report pattern gives a clean home for "cloudflared: installed/missing" regardless of which is chosen.

Security posture: a Cloudflare quick tunnel exposes a local dev server to the PUBLIC internet at an unguessable-but-UNAUTHENTICATED URL. This is a genuine expansion of Falcon's attack surface beyond its E2E model — the tunnel traffic itself is NOT E2E-encrypted (it's plain public HTTP(S) to whoever has the URL), unlike every other RPC body which is sealed under the DEK (design §5.3/§6.1). The RPC that opens it is E2E; the resulting tunnel is not. This should be an explicit, per-open user action with clear "this is publicly reachable" framing, and likely a config gate. It also somewhat contradicts design §12's "no arbitrary-directory execution from remote / 127.0.0.1-bound loopback" ethos — a remote web client is now causing the daemon to expose local services outward. Worth an explicit design-doc note in a new `docs/features/dev-server-preview.md` (the pipeline expects one per `[deep]` slug).

Port detection scope: `lsof -iTCP -sTCP:LISTEN` lists ALL listening sockets on the machine, not just the current session's dev servers. Omnara's "14 ports detected" is machine-wide. Decide whether to filter (e.g. only 127.0.0.1/localhost-bound, exclude well-known system ports, or best-effort-attribute to the workspace's process tree via `processScan.ts`'s pid/ppid data) or show everything. macOS/Linux only, matching `processScan.ts`.

This is a machine-scoped, not session-scoped, capability (ports/tunnels belong to a machine, like `git.*`/`provider.account`), so it needs the machine DEK + `createMachineRpcClient` path already wired for the git panel — no new crypto plumbing. No server changes at all: the relay forwards opaque RPC bytes and never inspects them (rpc.ts header), so `packages/server` is untouched, exactly like every other machine RPC.

Lifecycle/liveness gap vs. Omnara: tunnels are long-lived and cloudflared can crash. The MVP can be pure request/response (web polls `preview.tunnels` via TanStack Query, same as the git panel polls), deferring any push-based liveness. If live status is wanted, the reserved `preview:*` namespace was designed for streaming updates (reserved.ts: "live preview streaming for spawned dev servers") — but that's an ephemeral-channel expansion (`updates.ts`) and should be flagged as a Phase-2, not MVP.

## Plan (Fable 5)

Ship the Omnara-style "Preview" tab: four new machine-scoped RPCs (preview.ports / preview.tunnels / preview.open / preview.close) following the established wire-schema + daemon-handler + web-feature-seam pattern, plus the one genuinely new subsystem — a daemon-managed cloudflared quick-tunnel child registry with spawn/URL-parse/kill lifecycle, shutdown close-all, crash-orphan reaping via a pid journal, and doctor integration. Web side gets a features/preview/ folder (ports list with "N ports detected · M tunnels active", per-open public-exposure consent dialog, polling via TanStack Query), a /session/[id]/preview/ route linked from the timeline header, and — as a final, droppable phase — an embedded iframe view enabled by a narrow frame-src CSP allowance in the nginx deploy template with open-in-new-tab always available as fallback. cloudflared is detected on PATH, never installed by Falcon; quick tunnels only; no server package changes at all.

**Risks:** SECURITY (highest): preview.open exposes a local dev server to the public internet at an unauthenticated URL whose traffic is NOT E2E-encrypted — a deliberate expansion of design §12's loopback-only posture. Mitigations planned (per-open consent dialog, max-tunnels cap, close-all on daemon stop, orphan reaping) reduce but don't remove this; the feature doc must record it as an accepted delta so a future security review isn't surprised.; ORPHANED TUNNELS on daemon SIGKILL/crash: cloudflared children carry no falcon argv marker, so the existing kill.ts/markers.ts discovery can never find them — everything rests on the ~/.falcon/tunnels.json pid journal + boot-time reap + doctor clean. A user who crashes the daemon and never restarts it (or nukes ~/.falcon) leaks a public tunnel until cloudflared dies on its own; pid-recycling makes the verify-command-before-kill check load-bearing.; cloudflared stderr URL-parse fragility: the trycloudflare URL format/output is not a stable API; a cloudflared release changing its log format breaks preview.open at runtime (tests use fixtures, so CI won't catch it). The 30s timeout + stderr-tail-in-error mitigates debuggability but not breakage; quick tunnels are also rate-limited by Cloudflare and can fail under load — surfaced only as the error string.; CSP loosening review risk: adding frame-src https://*.trycloudflare.com to a deliberately strict, security-reviewed header is the one contentious diff; Phase 6 is structured to be droppable (Phase 5's new-tab UX is complete without it), but if it lands, any future tunnel-domain change (named tunnels) requires revisiting the template and likely docker-entrypoint envsubst.; lsof output parsing varies across macOS/Linux versions and lsof may be absent on minimal Linux installs — the ports list then comes back empty rather than erroring (matching processScan's resolve-empty-on-failure convention), which can read as 'no ports' to the user; Windows is explicitly unsupported, matching processScan.ts.; Embed may silently fail even after the CSP change: the tunneled dev server's own X-Frame-Options/CSP, or an app that hard-navigates, breaks the iframe — hence the mandatory in-frame failure fallback; also mixed-content is avoided only because trycloudflare is https.; Wire-compat process risk: the snapshot fixture regeneration must be run and committed in the same change as preview.ts, and status fields must be multi-value z.literal from day one — using z.enum would freeze the wrong kind and block future additive growth (SpawnResult.action precedent).; Polling staleness: a cloudflared child dying between 5s tunnel polls leaves the UI claiming an active tunnel that 404s; acceptable for MVP but the reserved preview:* streaming namespace is the real fix and is explicitly out of scope.
