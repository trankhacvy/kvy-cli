# Session lifecycle actions (docs/competitive-notes-omnara.md #10)

**Slug:** `session-lifecycle-actions` · **Branch:** `wf/feature-session-lifecycle-actions` · **Target:** `v2-pty-injection`

## Feature description

Session lifecycle actions. A session's context menu (right sidebar list) has one-click Restart, Stop, Pin, Rename, and Mark done — the last of which moves it to a dedicated "Completed Chats" (archived sessions) view with a Restore action.

## Solution (Opus 4.8)

Feature #10 "Session lifecycle actions" (Restart, Stop, Pin, Rename, Mark done + Completed Chats view with Restore) is NOT a greenfield build — roughly half of it already exists on this branch, and the honest job is to (a) identify the ~3 genuinely-new pieces, (b) wire up existing-but-unconnected pieces, and (c) repackage the current two-icon-button UI into a proper context menu. Map of each sub-action to reality:

1. STOP — already exists. The session `stop` RPC (`StopRpcParamsSchema`, registered by the LIVE session process, packages/wire/src/rpc.ts:641) is the "end the underlying process" path and is already callable from the web over apiSocket (`sync/sessionRpc.ts` lists `stop`). The context-menu Stop just reuses it. Gap: a stopped/detached session with no live session-RPC target needs the MACHINE `stopSession` RPC — its wire schema exists (`StopSessionParamsSchema`, rpc.ts:93) but it is deliberately NOT yet registered daemon-side (machineRpc.ts:28 "stopSession/listSessions/adopt.list are separate, later plan").

2. RESTART — half exists. The machine `resumeSession` RPC IS registered daemon-side (packages/cli/src/daemon/machineRpc.ts:203/446; daemon/resumeSession.ts re-spawns with FALCON_RECONNECT_* and already "stops any still-live process for that session" first, so it doubles as kill+relaunch). Wire schema exists (`ResumeSessionParamsSchema`, rpc.ts:99). Gap: the WEB machine-RPC caller (packages/web/src/sync/machineRpc.ts) does NOT list `resumeSession` (only spawn/fs.*/git.*), so it must be added there, plus a UI action. Bigger blocker: the web has no live per-machine machine-RPC/crypto client wired in yet (documented gap in session-list-screen.tsx and CLAUDE.md — machineClient socket "not yet started from commands.ts", adopt actions are `actionsDisabled`). So Restart is blocked on the same machine-RPC-transport wiring that adopt.take/mirror wait on; Stop-of-a-live-session is NOT (it goes over the session RPC path that works today).

3. RENAME — write path fully exists, no client caller. Title lives in the session's encrypted metadata blob `{title, path, providerSessionId?, model?}` (cli/src/api/sessionMetadata.ts:13). The CLI's `createSessionMetadataUpdater` already does exactly the seal + `PUT /v1/sessions/:id/metadata` CAS-with-409-conflict-retry loop for `model` — a sibling `updateTitle` is a near-copy. On the web, the crypto bridge exposes both `setSessionKey` + `seal` (crypto/client.ts:38/113), so a web-side rename mutation is feasible; it would be the FIRST web-side encrypted-metadata WRITE (today the web only reads/decrypts titles via `useSessionTitle`/live-source.ts; every metadata write comes from the CLI). It must re-open the current box, patch only `title`, re-seal under the per-session DEK, and PUT with `expectedVersion`, reconciling 409s exactly like sessionMetadata.ts.

4. PIN — does not exist anywhere (no field, no route, no UI). Pure client-side ordering nicety. Recommended home: a new field on the encrypted metadata blob (`pinned?: boolean`), written via the same metadata-CAS path as Rename — needs NO schema migration, NO new server route, NO new wire field, and reuses the rename write plumbing. Home/Completed grouping sorts pinned-first client-side. (Alternative — a plaintext `sessions.pinned` column + toggle route mirroring archive — is rejected below.)

5. MARK DONE / ARCHIVE + COMPLETED CHATS + RESTORE — archive itself already exists end-to-end: `POST /v1/sessions/:id/archive` (server/src/app/routes/sessionArchive.ts, idempotent, fans out `session-update{status:"archived"}`), the `useArchiveSessionMutation` + `SessionCardActions` archive button, status `"archived"` in SessionStatusSchema, and status.ts rendering it as "completed". Three real gaps remain: (a) Home does NOT filter archived out — group.ts has no status filter, so archived sessions still render inline with a grey "Completed" dot; (b) there is NO dedicated "Completed Chats" route/screen; (c) there is NO unarchive/Restore route or action (grep confirms none). So this sub-feature needs: filter `status==="archived"` out of Home grouping; a new `/completed` (or `/archived`) route + screen reusing WorkspaceSection/SessionCard over the archived subset; and a Restore path — either a new `POST /v1/sessions/:id/unarchive` route or generalizing the archive route into a status toggle.

UI repackaging: today SessionCardActions is two inline icon buttons (Archive, Delete). Feature #10 wants a single context menu ("···" → dropdown). Replace with a shadcn DropdownMenu holding Rename / Pin / Stop / Restart / Mark done (archive) / Delete, plus an inline-edit affordance (or small dialog) for Rename, reusing the existing delete-confirm Dialog pattern.

Recommended sequencing for the planning pass: land the pure-web, already-transport-supported pieces first (Completed Chats view + archived filter + Restore route + Rename + Pin, all of which ride the session-RPC/HTTP paths that work today), and gate Restart (and machine-`stopSession`) behind the separately-tracked "wire the live machine-RPC client into the web" work, exactly as adopt.take/mirror are gated now.

DATA MODEL / where each piece of state lives:
- Session row `status` (plaintext, server-visible): enum `["active","archived","failed","compacted","ended"]` (wire/src/rows.ts:11). `"archived"` is the "Mark done" state and ALREADY exists. Restore must flip it off archived — but the archive route sets `"archived"` flatly and the prior status is LOST, so Restore→"active" is a lossy simplification (a session that was `"ended"` before archiving comes back as `"active"`). Flag: decide whether Restore always returns to `"active"` (simple, slightly dishonest) or whether to persist a pre-archive status to restore to (needs a column or a metadata field). Note status.ts's derived dot re-derives most live state anyway, so `"active"` may be acceptable in practice for a session whose process is gone (derives as offline/idle).
- Title + (proposed) pin live in the ENCRYPTED metadata blob (`{title,path,providerSessionId?,model?}`), never server-readable. Written via `PUT /v1/sessions/:id/metadata` CAS (server/src/app/routes/sessionCas.ts) — the ONE generic optimistic-concurrency writer, fans out `session-update{metadata:{value,version}}`. This is the correct, existing home for Rename and Pin; both are additive fields on the plaintext-shape-frozen-but-content-free metadata JSON, so no wire compat concern (the compat lint only freezes EncryptedBox column SHAPES, not the plaintext inside them).

REUSE, do not reinvent:
- Rename/Pin write = clone cli/src/api/sessionMetadata.ts's CAS-retry loop into a web mutation; crypto bridge already has seal + setSessionKey.
- Archive/Restore/Delete server routes = clone sessionArchive.ts's idempotent-transition-then-fan-out shape (no CAS — "no legitimate concurrent writer for a user-initiated archive"). An unarchive route is a near-copy with the archived-guard inverted.
- Web mutations = clone use-session-lifecycle.ts's optimistic-`['sync']`-cache-patch + rollback pattern (already used by archive/delete); the live `session-update` WS fan-out reconciles.
- Completed Chats screen = reuse groupSessionsByWorkspace + WorkspaceSection + SessionCard over the archived subset; add the inverse filter to Home.
- Restart = add `resumeSession` to the web machineRpc method registry (structural clone of how spawn is listed) once the machine-RPC transport lands.
- Stop (live) = reuse the existing `stop` session RPC via sync/sessionRpc.ts.

WIRE PROTOCOL: no NEW schemas strictly required for Rename/Pin/Archive/Restore if metadata-CAS + a new/generalized status route are used. If Restart is done via machine RPC, `ResumeSessionParamsSchema` already exists — only the web caller registry entry is new. If machine `stopSession` is used for dead sessions, `StopSessionParamsSchema` already exists but needs daemon registration (currently deferred). Everything additive-only; the schemaShape/additiveOnly compat lint (wire/src/__tests__/) must stay green.

KEY ARCHITECTURAL SEAM / BLOCKER: the web currently has NO live machine-RPC + per-machine crypto client (CLAUDE.md: machineClient socket "not yet started from commands.ts"; session-list-screen.tsx hardcodes `actionsDisabled` for adopt). Any action routed through a MACHINE RPC (Restart via resumeSession; Stop-of-dead-session via stopSession) inherits this blocker. Actions routed through the SESSION RPC (Stop-of-live-session) or plain HTTP (archive/unarchive/delete/metadata-CAS) do NOT. This cleanly splits the feature into a "shippable now" set (Stop-live, Rename, Pin, Mark done, Completed Chats, Restore) and a "gated on machine-RPC-transport" set (Restart, Stop-dead).

E2E/SECURITY: title and pin stay inside the encrypted metadata blob → server never learns session titles or which sessions a user pinned (good, preserves design §5.3). Putting pin in a plaintext column would leak "sessions the user cares about" to the server — minor, but avoidable, which is why the metadata-blob home is recommended. archived/status stays plaintext as it already is (the push dispatcher and status derivation need it) — no change.

CONCURRENCY: Rename races the CLI's own metadata updater (which auto-writes model, and may auto-write title). Both use the same CAS PUT with a 409-retry-reconcile loop that re-opens the current box and patches only its own field — as long as the web rename follows the same read-modify-write-on-conflict discipline (patch only `title`, preserve other fields), concurrent CLI model/title writes converge instead of clobbering. This is the single trickiest correctness point.

## Plan (Fable 5)

Adjusted the proposed solution: Core mapping accepted, but three material corrections force a different plan than proposed: (1) The "machine-RPC transport gap" blocker is STALE — the web already has a live per-machine crypto + machine-RPC path (packages/web/src/lib/use-machine-crypto.ts + sync/machineRpc.ts's createMachineRpcClient + apiSocket), used in production by features/git-diff/use-live-git-diff-actions.ts and features/new-session/live-source.ts. Restart is therefore NOT gated on separately-tracked transport work; it ships in this feature by cloning the git-diff live-actions pattern. Only the adopt actions remain mock-disabled, for reasons unrelated to this feature. (2) The proposed "repackage two icon buttons into a context menu" understates what exists: the timeline header ALREADY has the '···' DropdownMenu (packages/web/src/components/timeline/SessionActionsMenu.tsx with Archive / End session / Delete + confirm dialogs + stop-session-state.ts), and Stop-from-web already works there via the session `stop` RPC. The real UI work is converting the Home card's SessionCardActions to that same dropdown and adding Rename/Pin/Restart/Restore to both menus. (3) Machine `stopSession` is dropped from scope entirely (not merely deferred): every live Falcon-managed session — including daemon-spawned detached ones — registers its own session-RPC `stop`; a dead session has no process to stop; Restart covers relaunch. This matches wire rpc.ts:634's own comment. Daemon-side stopSession registration is not needed. (4) NEW critical task the proposal missed: packages/cli/src/api/sessionMetadata.ts's SessionMetadataValueSchema + normalizeMetadata strip unknown fields — after a web `pinned` write, the CLI's next updateModel CAS write would silently erase it. The CLI schema must become loose (zod v4 z.looseObject) and normalizeMetadata must preserve unknown keys, and this must land BEFORE the web metadata-write phase ships. (5) Minor: @falcon/wire exports no ResumeSessionParams/Result type aliases (only schemas) — the web registry entry derives them locally via z.infer, matching the documented adopt.list precedent. (6) Decisions taken on the open questions: Restore always returns status "archived"→"active" only when currently archived (non-archived rows are untouched and the route responds with the honest current status); pin lives in the encrypted metadata blob (account-global, E2E-private); the unarchive route is a dedicated POST /v1/sessions/:id/unarchive inside the existing buildSessionArchiveRoutes plugin (keeping sessionStatus.ts's narrow {failed|ended} route separate); Restart is one action covering both kill-and-relaunch and resume-of-stopped (that is literally what daemon resumeSession.ts does), enabled whenever the session has a machineId and that machine is online; Rename is a small dialog (mirrors the existing delete-confirm Dialog precedent), web-only for this feature (no CLI updateTitle); no wire schema changes at all, so the additive-only compat lint is untouched.

Ship session lifecycle actions (Restart, Stop, Pin, Rename, Mark done + Completed Chats view with Restore) in six phases. Phase 1 adds the one missing server piece (POST /v1/sessions/:id/unarchive inside the existing sessionArchive plugin). Phase 2 hardens the CLI's metadata CAS updater to preserve unknown encrypted-blob fields (prerequisite so web-written pinned/title fields survive CLI model writes). Phase 3 builds the web's first encrypted-metadata write path: a CAS-aware api helper plus a read-modify-write mutation hook that patches only its own fields, retries on 409, and reconciles the ['sync'] cache. Phase 4 converts the Home card's two icon buttons into the same '···' DropdownMenu the timeline header already has, and wires Rename (dialog) + Pin (functional-patch toggle) into both menus, threading a decrypted `pinned` flag through live-source/types/group for pinned-first ordering; card-level Stop reuses the existing session `stop` RPC with lazily-mounted crypto. Phase 5 filters archived sessions out of Home, adds the /completed Completed Chats screen reusing the existing grouping/card components, and wires Restore (new mutation + menu items). Phase 6 adds Restart end-to-end: register resumeSession in the web machine-RPC method table and drive it through the already-live useMachineCrypto/createMachineRpcClient path with a confirm dialog, enabled only when the owning machine is online. No wire-protocol changes anywhere; machine stopSession is explicitly out of scope.

**Risks:** CLI metadata clobbering (highest, and why Phase 2 gates Phases 3-4): cli/src/api/sessionMetadata.ts's normalizeMetadata rebuilds the blob from only {title,path,providerSessionId,model} — without the loose-schema fix, the CLI's next updateModel CAS write silently erases a web-written `pinned` (or any future field). Deployment-order wrinkle: users running an OLD CLI binary will still clobber pins until they upgrade; the web write path must treat a vanished pinned field as 'unpinned' gracefully rather than erroring.; First web-side encrypted-metadata write: the mutation must read the CURRENT box at its tracked version and re-open the 409 conflict body's box on retry, patching only its own keys — any shortcut (sealing a from-scratch object, or reusing a stale decrypted title) clobbers concurrent CLI model writes. The unit test decrypting the final payload for field-level convergence is the guard.; Crypto-worker key races: a bridge worker holds one active session key; the metadata-write hook, stop flow, and restart flow must each own their own worker (or be strictly sequential within one) per live-source.ts's documented constraint — sharing a bridge with useDecryptedTitles/useSessionTitle can decrypt or seal under the wrong session's key, producing garbage ciphertext written back to the server.; Worker-per-card cost: naively instantiating useCryptoBridge in every SessionCard's menu spawns a worker per row; the lazy-mount-on-dialog-open discipline (Phase 4/6) is required, not optional, for lists of dozens of sessions.; Home regression: adding the archived filter without the /completed route shipping in the same phase makes archived sessions unreachable from the UI — Phase 5 deliberately bundles filter + view + restore as one unit.; Restart honesty: daemon resumeSession only re-spawns sessions present in its durable registry (~/.falcon/sessions.json, 14-day expiry) — a terminal-started or expired session will fail with a handler-error; the UI must surface that message verbatim rather than pretend Restart is universal. Also resumeSession has no idempotency key ({sessionId} only) — a double-click double-restarts; disable the confirm button while in flight.; Restore status loss (accepted): archive discards the pre-archive status, so restore of a formerly-'ended' session yields 'active'; deriveSessionStatus re-derives the visible dot from live signals (an active row with a gone process reads idle/offline), so this is a documented simplification, not silent corruption — but the unarchive route must still respond with the honest status for non-archived rows.; Pin semantics are account-global (encrypted metadata blob, all devices see the same pin) — confirmed as intended; there is no per-device state channel to do otherwise without new server work.; Wire compat: this plan changes zero @falcon/wire schemas (unarchive is route-only; pinned lives inside opaque ciphertext; ResumeSession schemas pre-exist) — if the wire compat lint fails at any point, something was implemented off-plan.

### Phase 3: Phase 3 — Web: first encrypted-metadata write path (CAS mutation core for Rename + Pin)

- [x] Add `putSessionMetadataCas(token, sessionId, body: { expectedVersion: number; value: EncryptedBox })` to packages/web/src/lib/api.ts. It cannot reuse the generic request() helper (which throws on non-2xx and discards the body) — use fetch directly like the CLI's updater and return a discriminated union: `{ ok: true; version: number }` on 200, `{ ok: false; current: { value: EncryptedBox | null; version: number } }` on 409, throw a descriptive Error on any other status. Target route: PUT /v1/sessions/:id/metadata (server sessionCas.ts, body shape confirmed against cli/src/api/sessionMetadata.ts).
- [x] Create packages/web/src/lib/use-session-metadata-write.ts exporting `useSessionMetadataPatchMutation(sessionId)`. The mutation accepts a FUNCTIONAL patch `(current: Record<string, unknown>) => Record<string, unknown>` (so Pin can toggle without the caller pre-knowing the current value, and Rename can set title). Flow per attempt: read the session row (dek, metadata.value, metadata.version) from the ['sync'] TanStack cache (useSyncSnapshotQuery / queryClient.getQueryData(syncQueryKey)); use this hook's OWN useCryptoBridge() worker (per live-source.ts's documented one-active-key-per-worker constraint — never share a bridge with other hooks); sequentially: setSessionKey(decodeBase64(dek)) → open(metadata.value) as Record<string, unknown> (a null/unopenable box surfaces an error — do NOT silently start from {} and clobber a title you failed to decrypt) → apply the functional patch (spreading current so foreign fields like model/path/providerSessionId are preserved) → seal → putSessionMetadataCas with expectedVersion = the version the box was read at. On 409: replace current value/version from the conflict body, re-open, re-apply the patch, retry (bounded, e.g. 5 attempts, then reject). On success: patch the ['sync'] cache's session row to `metadata: { value: <the sealed box we sent>, version: <returned version> }` — both useDecryptedTitles (live-source.ts) and useSessionTitle are metadata.version-gated, so this one cache patch makes titles/pins re-decrypt everywhere with no extra invalidation; the WS session-update fan-out reconciles moments later. Toast on terminal failure (sonner, matching use-session-lifecycle.ts). Implementation note: the CAS-retry core is split out as the exported `patchSessionMetadataCas` function (taking an already-constructed `CryptoBridgeClient`) precisely so it can be tested with a REAL loopback-worker-backed bridge instead of a hand-rolled fake — same "core split from its `useX` wrapper" shape as `features/git-diff/live-actions.ts`.
- [x] Unit tests in packages/web/src/lib/use-session-metadata-write.test.ts, mirroring use-session-lifecycle.test.ts's style with a fake bridge + fake api: (a) happy path seals patched plaintext and bumps cache version; (b) 409 path: conflict body carries a concurrently-changed `model` — assert the final sealed plaintext contains BOTH the patch's title and the conflicting model (convergence, no clobber); (c) open() returning null rejects with a visible error and leaves cache untouched; (d) retry bound exhausts → rejects. (Used a real crypto bridge — loopback worker + in-memory key storage, `crypto/__tests__/client.test.ts`'s own recipe — rather than a fake, so the convergence assertion decrypts genuine ciphertext.)

**Acceptance:** pnpm --filter @falcon/web test passes; the 409 test decrypts the final sealed payload via the fake bridge and asserts field-level convergence (patched field + concurrent foreign field both present); pnpm typecheck and pnpm lint green.
